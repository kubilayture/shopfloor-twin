# Runbook

How to start, stop and reset the system and run scenarios. Updated whenever operations change.

## Prerequisites

- Node.js 26 (`nvm use` reads `.nvmrc`)
- pnpm 11 or newer installed globally; it switches itself to the version pinned in `package.json`
- Docker with Compose

## Check the workspace

```bash
pnpm install
pnpm verify
```

`pnpm install` also installs a git pre-commit hook (lefthook) that formats and lints the files you stage. To skip it for one commit in an emergency: `git commit --no-verify`. CI runs the same checks (from #4).

## Run the simulator headless

Runs the plant as fast as possible, with no network servers, and writes an event log and a ground-truth summary (plan section 4).

```bash
pnpm sim:headless --seed 42 --days 7 --out runs/week-42
```

| Option     | Default                     | Meaning                                                                                                                                         |
| ---------- | --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `--seed`   | 1                           | Master seed: the same seed, config and options always give byte-identical output                                                                |
| `--days`   | 7                           | Simulated duration                                                                                                                              |
| `--start`  | `2026-10-12T06:00:00+03:00` | Simulation start, ISO 8601 with an offset or `Z` (a time without an offset is rejected, so the result never depends on the machine's time zone) |
| `--config` | `config/plant`              | Plant configuration directory                                                                                                                   |
| `--out`    | `runs/latest`               | Output directory (`runs/` is git-ignored)                                                                                                       |

Output:

- `events.jsonl`: one JSON object per line. The first line is the run header (`sim-run/1`: seed, start, end, SHA-256 of the configuration); every other line is an event (`sim-event/1`).
- `summary.json`: the ground truth (`sim-summary/2`): time in every state per machine, in total and per shift instance; cycles per result; parts started, finished and scrapped by reason; remaining quantity per lot; and the OEE section (inputs per machine, shift bucket and UTC hour; A, P, Q and OEE per machine, work center and shift bucket).

A week takes about 0.2 s and about 6 MB of events. The files are written under temporary names and renamed at the end, so a failed run never leaves a mix of old and new files. Invalid options exit with status 2, other failures with status 1. The event and summary formats are described in `docs/simulation-model.md`.

## Run the simulator live

Runs the plant paced to wall time × speed and prints every machine state change:

```bash
pnpm sim:live --speed 60
```

Options: `--seed` (default 1), `--speed` (0.5–60, default 60), `--start` (ISO 8601 with an offset), `--config`. Ctrl+C stops it. At 60×, one shift (8 h) takes 8 minutes. For pause, resume, step and speed control, use `pnpm sim:serve` and its control API.

## Serve the plant: OPC UA and the control API

Runs the plant live and exposes the five OPC UA machines (contract: `docs/contracts/opcua-address-space.md`), the WSH-01 washer on Modbus TCP port 5020 (contract: `docs/contracts/modbus-register-map.md`) and the control API (contract: `docs/contracts/simulator-control-api.md`):

```bash
pnpm sim:serve
```

Configuration comes from environment variables, validated at start-up. Examples: `SIM_SPEED=30`, `SIM_SEED=7`, `SIM_AUTOSTART=false`, `OPCUA_PORT_OFFSET=100`, `CONTROL_PORT=4800`. The full list is in the contract.

```bash
SIM_SPEED=30 SIM_AUTOSTART=false pnpm sim:serve
```

Control the run from another terminal:

```bash
curl -s -X POST localhost:4800/api/v1/resume
```

The other commands are `POST /api/v1/pause`, `POST /api/v1/step`, `PUT /api/v1/speed` with a JSON body `{"speed": 10}`, and `GET /api/v1/status`. Plant events stream over a WebSocket at `ws://localhost:4800/api/v1/events`; health is at `/health/live` and `/health/ready`, and metrics at `/metrics`.

- Connect any OPC UA client, for example UaExpert, with security mode None. Read the washer with any Modbus TCP client, unit id 1, holding registers (function 3).
- `curl -s -X POST localhost:4800/api/v1/faults/modbus -H 'content-type: application/json' -d '{"silent": true}'` makes the washer stop answering, to exercise a poller.
- Each server creates its own certificate on first start in `./.pki/<machine>` (git-ignored).
- Logs are JSON lines (pino). `LOG_LEVEL=warn` keeps only warnings and errors.
- Ctrl+C or SIGTERM stops the run, closes the API and shuts the servers down. An invalid environment exits with status 2.
- After changing a route, regenerate the OpenAPI description with `pnpm --filter @shopfloor/simulator openapi`. A test fails while it is out of date.

## Run the edge gateway

The gateway publishes to the broker of the stack (`pnpm stack:up` first). It subscribes to the five OPC UA machines (the simulator of the stack, or `pnpm sim:serve`) and polls the WSH-01 washer over Modbus TCP, and publishes their state, cycles, alarms and telemetry to the UNS.

```bash
MQTT_PASSWORD=<MQTT_GATEWAY_PASSWORD from .env> pnpm --filter @shopfloor/edge-gateway start
```

- Environment: `GATEWAY_ID` (default `gw-01`), `MQTT_URL` (`mqtt://127.0.0.1:1883`), `MQTT_USERNAME` (`gw-01`), `MQTT_PASSWORD` (required), `OPCUA_HOST` (`localhost`), `OPCUA_PORT_OFFSET` (0), `OPCUA_PKI_DIR` (`.pki-gateway`, its own client certificate), `TELEMETRY_SAMPLING_MS` (1000), `MODBUS_HOST` (`127.0.0.1`), `MODBUS_PORT` (5020), `MODBUS_POLL_MS` (250), `BUFFER_PATH` (`.buffer/gateway.db`, the store-and-forward file), `BUFFER_MAX_MESSAGES` (200000), `HTTP_HOST` and `HTTP_PORT` (`127.0.0.1:4900`), `PLANT_CONFIG_DIR`, `LOG_LEVEL`. An invalid environment exits with status 2, and secrets are never echoed.
- `GET /health/live`, `/health/ready` (ready while the broker session is up) and `/metrics` (`gateway_device_connected{machine}`, `gateway_device_facts{machine}`, `gateway_published_messages`, `gateway_buffer_messages`, `gateway_buffer_dropped_messages`).
- While the broker is down, `gateway_buffer_messages` grows; it drains after the broker returns. Deleting `.buffer/` throws away whatever wasn't delivered yet.
- Data-quality incidents (sequence gaps, disconnects) go to `orbis/gebze/_sys/edge-gateway/gw-01/incidents` and to the log at `warn`.
- Try a disconnect: `curl -s -X POST localhost:4800/api/v1/faults/opcua/cnc-01 -H 'content-type: application/json' -d '{"offline": true}'`, then `{"offline": false}`. The washer: `curl -s -X POST localhost:4800/api/v1/faults/modbus -H 'content-type: application/json' -d '{"silent": true}'`.
- Watch the status: `docker compose exec broker mosquitto_sub -u dev -P <MQTT_DEV_PASSWORD> -t 'orbis/gebze/_sys/#' -v`.

The gateway's tests start a real Mosquitto with Testcontainers, so Docker must be running. They also start the simulator as a child process on ports clear of the stack: OPC UA 7941–7945, Modbus 8120, control 7900. Without `DOCKER_HOST` the tests use the active `docker context`, which covers Colima and similar setups.

## Run the MES server

`mes-server` (Phase 4) runs on the stack's TimescaleDB and broker (`pnpm stack:up` first), migrates the database at start-up (ADR-0016) and then subscribes to the UNS (#95):

```bash
DATABASE_URL=postgres://shopfloor:<DB_PASSWORD>@127.0.0.1:5442/shopfloor \
  MQTT_PASSWORD=<MQTT_MES_PASSWORD from .env> pnpm --filter @shopfloor/mes-server start
```

- Environment: `DATABASE_URL` (required, never echoed), `MQTT_URL` (`mqtt://127.0.0.1:1883`, never echoed), `MQTT_USERNAME` (`mes`), `MQTT_PASSWORD` (required: `MQTT_MES_PASSWORD` from `.env`), `MQTT_CLIENT_ID` (`mes-server`), `MQTT_SESSION_EXPIRY_S` (604800, 7 days), `INGEST_GAP_GRACE_MS` (30000), `HTTP_HOST` and `HTTP_PORT` (`127.0.0.1:4700`), `MIGRATIONS_DIR` (`db/migrations`), `LOG_LEVEL`.
- `GET /health/live`, `/health/ready` (database answers, migrations are applied, and the UNS subscription is granted) and `/metrics` (`mes_ingest_messages_total{outcome}` with outcomes `stored`, `duplicate`, `rejected`, `anchor`, `status`, `retained`; `mes_ingest_incidents_total{origin}`; `mes_ingest_store_errors_total`; `mes_ingest_suspensions_total`; `mes_ingest_subscribed`).
- The MES keeps a persistent broker session (client id `mes-server`): while it is stopped, the broker queues up to 100,000 messages for it (about one hour of the plant at 60×), delivered on the next start; the MES stores about 1,000 messages/s, so a full queue drains in about two minutes. Only one MES may use the client id; a second one takes the session over. **Accepted risk until Phase 9:** the plain ACL file can't bind a client id to a user, so any broker user (even `dev`) can connect as `mes-server` and take the session, and with it the queued messages. Phase 9 moves to Mosquitto's dynamic-security plugin. To drop the session (and its queue), start once with another `MQTT_CLIENT_ID` or reset the broker volume (`pnpm stack:reset`).
- What arrived: `SELECT reason, count(*) FROM ingest.rejected_message GROUP BY 1;` lists rejected messages; `SELECT * FROM ingest.data_quality_incident WHERE closed_at IS NULL;` lists open gaps and gateway incidents (contract: `docs/contracts/uns.md`, "Consumer: MES ingest").
- Alarm anchors and snapshots (#141): retained alarm deliveries land in `ingest.alarm_anchor`, the gateway's resync snapshots in `ingest.alarm_snapshot`; both count as `anchor` in `mes_ingest_messages_total`. Rows of an older device epoch than the newest one known for their equipment are kept with `stale = true` and never used, so after a simulator restart the old run's retained alarms never show as active: `SELECT equipment, epoch, code, seq, transition, stale FROM ingest.alarm_anchor ORDER BY 1, 2, 3;` and `SELECT equipment, device_epoch, as_of_seq, active, stale FROM ingest.alarm_snapshot ORDER BY 1, 2;`. To clear the old run's retained alarms from the broker itself, reset its volume (`pnpm stack:reset`).
- Alarm occurrences (#142, ADR-0024): the `alarms` module derives one occurrence per device raise, keyed `{equipment}~{epoch}~{seq}`, from ingest's alarm facts, the retained anchors and the resync snapshots, and stores it in `alarms.alarm_occurrence` with its end (`cleared`; `lost` when a snapshot showed the code inactive after the clear went missing; `superseded` by the next raise of the point; `epoch-ended` by a newer run). A snapshot is applied only once the device stream is settled up to its `asOfSeq` (no open gap below it). At start-up it compares `alarms.occurrence_source` with ingest's alarm fact counts, anchors and snapshots and derives again what differs (log line `alarm occurrences caught up` with the number `derived`). Nothing an operator does is stored there; to derive everything again, stop the MES, `TRUNCATE alarms.alarm_occurrence, alarms.occurrence_source;` and start it (revisions in `alarms.kpi_revision` are kept). Active alarms: `SELECT equipment, code, raised_at FROM alarms.alarm_occurrence WHERE ended_at IS NULL ORDER BY raised_at;`.
- Alarm KPI finality and revisions: a KPI hour of a scope (the plant, a position or an equipment) is final once every equipment of the scope is final through its end plus `fleetingMs` (1 s), or its epoch is closed; a silent machine keeps it provisional, as for OEE. A late fact (a gap filled after it was written off, a snapshot closing a lost clear, the real clear replacing it) raises the revision of every final hour it can change, in every scope of its equipment: `SELECT * FROM alarms.kpi_revision ORDER BY hour;` (log line `late alarm facts: final KPI hours revised`). No row means revision 0.
- A storage failure is logged (`mes_ingest_store_errors_total`). Only a data or integrity error (SQLSTATE classes 22, 23, 54: the database refuses this message for good) is recorded with reason `unstorable` and acknowledged. Any other error (database down, a lock held too long, a migration in progress) is retried for a few seconds; then the MES drops its broker session without acknowledging anything unstored (`mes_ingest_suspensions_total`, readiness 503), waits, reloads its cursors and reconnects, with a growing pause while the failure repeats. The broker queues meanwhile, so an outage shorter than the queue (about an hour) loses nothing (ADR-0017).
- State intervals (#96, ADR-0018): at start-up the `equipment` module compares `equipment.interval_source` with ingest's tables and recomputes what differs (log line `equipment intervals caught up` with the number `rebuilt`), then follows ingest. Every piece lies inside one UTC hour and one shift bucket; the open interval is stored up to the plant watermark and flagged `provisional`. Time per state in a shift: `SELECT equipment, state, sum(end_time - start_time) FROM equipment.equipment_state_interval WHERE shift_key = '2026-10-12/A' GROUP BY 1, 2 ORDER BY 1, 2;` (per epoch after a simulator restart). To recompute everything from ingest's tables, stop the MES, `TRUNCATE equipment.interval_source;` and start it again.
- Hourly aggregates (#118, ADR-0022): `equipment.state_hourly` and `ingest.cycle_hourly` are TimescaleDB continuous aggregates without refresh policies. The MES refreshes them itself, about a second after a change, on two connections of its own (log line `continuous aggregate refreshed` with the window and its duration, at `info`), and once at start-up from the beginning (`catchUp: true`). Rows of the open hour are read from the raw tables. A row written by hand below an aggregate's watermark is not seen until the next MES start (or `CALL refresh_continuous_aggregate('equipment.state_hourly', NULL, '<end>');`). Never add a refresh policy: its window follows the wall clock, not simulation time. The start-up line `cycle counts of final hours checked` lists final hours whose cycle count changed while the MES didn't hear of it (their revision went up).
- API (#97, ADR-0019), on `HTTP_HOST:HTTP_PORT` (`127.0.0.1:4700`), read-only except downtime coding (#121, below), no authentication until Phase 7, no CORS (the web app is served from the same origin, by the `web` container in Compose); errors are problem details (`application/problem+json`). Until the modules have started, `/api/v1/*` answers 503.
  - Environment: `HTTP_ALLOWED_HOSTS` (`localhost,127.0.0.1,[::1]`; `Host` names answered, `*` for any, against DNS rebinding), `HTTP_ALLOWED_ORIGINS` (none; extra origins a WebSocket may connect from, or a write may come from, besides the MES's own host), `MES_WRITES` (`on`), `API_DB_POOL_SIZE` (4; the API's own read pool, so reads never hold up ingest), `API_STATEMENT_TIMEOUT_MS` (5000; a read over it answers 503). A 403 with `host not allowed` or `origin not allowed` means the request came through a name or page not on these lists.
  - `GET /api/v1/equipment` and `/api/v1/equipment/{id}`: master data with hierarchy and current state (`current` is null for equipment that never reported).
  - `GET /api/v1/equipment/{id}/intervals?from&to`: state intervals (stored hour and shift pieces merged back, clipped to the range; at most 7 days; when `truncated`, continue with `from=next`).
  - `GET /api/v1/equipment/{id}/telemetry/metrics`, and `/telemetry?metric&from&to&maxPoints`: metrics with units, and series decimated into at most `maxPoints` time buckets (min, max, avg, count; at most 31 days, 8 metrics, 5,000 buckets).
  - `GET /api/v1/shifts/{date}/{shift}/totals?equipment`: time per state in a shift (for example `/api/v1/shifts/2026-10-12/A/totals`).
  - `GET /api/v1/plant`: site and plant clock (watermark of the newest epoch).
  - OEE (#120, ADR-0021), computed on read by the `oee` module from the hourly aggregates and stop pieces (nothing is stored):
    - `GET /api/v1/oee?scope=equipment|work-center&id&bucket=hour|shift&from&to[&epoch]`: buckets with inputs, A, P, Q and OEE as exact fractions and four-decimal strings, totals, losses, `unplanned`, `anomaly`, `final`, `provisionalMs`, `revision` and `incidents` (hours: at most 7 days; shifts: whole shifts, at most 31 days). Without `epoch`, an equipment's newest epoch with data in the range; a work center uses one epoch for all its machines, the newest any of them has. A work center sums its machines' inputs. A read that overlaps an aggregate refresh is retried once, then reported not final.
    - `GET /api/v1/shifts/2026-10-12/A/oee`: one shift for every machine and work center; `final: true` once nothing that can still arrive changes it (every hour final in equipment, both aggregates refreshed through it, no open stop below the threshold, every member complete). A shift that stays `final: false` after its end usually means a silent machine (see "Reconciliation run", finality) or a refresh that keeps failing (log `continuous aggregate refresh failed`).
    - `GET /api/v1/shifts?from&to` and `/api/v1/shifts/current`: shift instances from the calendar (the current one at the plant clock).
    - `GET /api/v1/reason-codes`, `/api/v1/downtime?equipment&from&to&uncoded=true` (records, UNCODED first; `uncoded=true` only those) and `/api/v1/downtime/pareto?scope&id&from&to` (availability loss by reason, own and external, summed in the database without a row limit, and micro-stops by cause; epochs as for OEE).
    - Quick look: `curl -s 127.0.0.1:4700/api/v1/shifts/2026-10-12/A/oee | jq '.equipment[] | {id, oee: .result.oee.decimal, final}'`.
  - Downtime coding, the MES's first write (#121, ADR-0021 amended, ADR-0023):
    - `PUT /api/v1/downtime/{id}/coding` with `{"segments":[{"from","to","reason","comment"?}],"codedBy","version"}` replaces the codings of one record (`{equipment}~{epoch}~{startMs}`): segments inside the record (an open one: up to the watermark), not overlapping, each with an active reason other than UNCODED; `[]` clears them; two segments are a split. `version` is the record's `version` from `GET /api/v1/downtime` (one per machine and epoch): 409 means someone else coded (or a re-cut clipped codings) meanwhile; read again and retry. 422: a segment outside the record, overlapping, or a reason that is unknown, inactive or UNCODED.
    - `GET /api/v1/downtime/{id}/audit`: the record's history, newest first (`coded`, `cleared`, `orphaned` by `system` after a re-cut), with actor, wall time and request id. `equipment.downtime_audit` is append-only (a trigger refuses UPDATE, DELETE and TRUNCATE). `codedBy` is free text and recorded as unauthenticated.
    - Records in `GET /api/v1/downtime` carry `reason` (in effect over most of the record), `segments`, `codings`, `uncoded` and `version`; the Pareto counts coded time under the coding's reason. OEE never changes with a coding.
    - After a late fact re-cuts a record, codings are clipped to the loss time they still cover within about 100 ms (log line `downtime codings clipped after a re-cut`); the rest is kept as `orphaned` and shows in the audit. At start-up every coding is clipped once.
    - **Write guards** on every non-GET request under `/api/v1` (ADR-0023): allowed `Host`; `MES_WRITES=off` → 405; an `Origin` header, of the MES's own host and port (any scheme) or in `HTTP_ALLOWED_ORIGINS`, else 403; `Sec-Fetch-Site: same-origin` when sent, else 403; `Content-Type: application/json`, else 415; at most 16 KiB (413); 10 writes per second for all clients together, bursts of 20 (429 with `Retry-After`). Every write's answer has `X-Request-Id`, the id in the audit and in the MES log.
    - From the shell: `curl -s -X PUT -H 'Origin: http://127.0.0.1:4700' -H 'Content-Type: application/json' -d '{"segments":[],"codedBy":"me","version":0}' 127.0.0.1:4700/api/v1/downtime/<id>/coding` (through the web: `-H 'Origin: http://localhost:8080'` against `localhost:8080`).
    - `MES_WRITES` (`on`; Compose `MES_WRITES` in `.env`): `off` makes the MES read-only, every write answers 405 (`Allow: GET, HEAD`), reads and push go on. While it is `on`, the MES refuses to start with `HTTP_ALLOWED_HOSTS=*` (any Host would let a rebound name write).
  - Alarms (#142, #143, ADR-0024):
    - `GET /api/v1/alarms?view=active|acknowledged|shelved|history&position&equipment&priority&from&to&limit&cursor`: occurrences newest first (`history` needs a range of at most 7 days; pages of 100, at most 500; continue with `cursor=next`). The views are the operator's lists and partition the occurrences: `active` (default) not acknowledged and not closed (a cleared occurrence stays here until acknowledged), `acknowledged` acknowledged and still active, both with the point not shelved; `shelved` not closed with the point shelved; `history` closed (ended and acknowledged, or ended by a newer epoch). Each occurrence carries `state` (`unacked-active`, `acked-active`, `unacked-cleared`, `closed`), `acknowledged`, `shelved` and `comments`. `GET /api/v1/alarms/{id}` with the definition, its point's shelf and its comments; `GET /api/v1/alarms/{id}/history` with the device raise and end (`seq`, `sourceTime`, `receivedAt`, protocol) and its MES transitions from the audit (acknowledgement, comments, its point's shelf while it was active; actor, wall time, request id), by plant time.
    - `GET /api/v1/alarms/kpi?scope=plant|position|equipment&id&bucket=hour|shift&from&to[&epoch]`: the alarm KPIs computed on read (exact fractions), with `final`, `revision` and `incidents`; hours where something happened and the hour in progress, every shift and `no-shift/{start}` stretch begun. `GET /api/v1/alarms/floods`, `/api/v1/alarms/bad-actors` (top 10 by default) and `/api/v1/alarms/scopes`. `GET /api/v1/alarms/config` (#160): `maxShelveMs`, `minShelveMs`, the KPI thresholds (`floodThreshold`, `windowMs`, `chatterCount`, `chatterWindowMs`, `fleetingMs`, `standingMs`) and the `benchmarks`, as `config/plant/alarms.yaml` has them; the web's shelve presets, flood threshold line, flood banner and rate bands follow it, so after changing the file restart the MES (`docker compose up -d mes`) and reload the page.
    - Quick look: `curl -s '127.0.0.1:4700/api/v1/alarms/kpi?scope=position&id=cell-m1&bucket=shift&from=2026-10-12T03:00:00Z&to=2026-10-12T11:00:00Z' | jq '.buckets[] | {key, raises, peak10, floodWindows, final}'`.
    - Alarm writes (#143, ADR-0023's guards, as for downtime coding; `actor` is free text, recorded as unauthenticated): `POST /api/v1/alarms/{id}/ack` with `{"actor","comment"?}` and `POST /api/v1/alarms/ack` with `{"ids":[…up to 100],"actor","comment"?}` (one transaction, one write for the rate limit; an unknown id is 404 and nothing changes). Acknowledging is monotonic, so there is no version: an occurrence acknowledged already answers `changed: false` and adds no audit entry. `POST /api/v1/alarms/{id}/comments` with `{"actor","text"}` (1–500 characters, append-only).
    - Shelving is per alarm point (equipment, code): `POST /api/v1/alarm-points/{equipment}/{code}/shelve` with `{"actor","reason","durationMs","version"}` and `POST …/unshelve` with `{"actor","version"}`. `version` is `shelf.version` from `GET /api/v1/alarm-points` (0 for a point never shelved); 409 means someone else changed the shelf, or it ended, meanwhile: read again and retry. `durationMs` runs in **plant time**, 1 minute to `maxShelveMs` (`config/plant/alarms.yaml`, 8 hours; longer is 422): `until` = the plant clock at the write + the duration. Once the plant clock passes `until`, the MES unshelves the point itself (`expire`, actor `system`; log `alarm shelf ended by the plant clock`); a newer plant epoch (a simulator restart) ends every shelf of the old one (`epoch-ended`), because plant time starts over. A paused simulator keeps a shelf for as long as it is paused. Shelving changes no KPI: every raise counts, shelved or not.
    - `GET /api/v1/alarms/operator-kpi?scope&id&bucket=hour|shift|range&from&to[&epoch]`: the operator measures (MES only, not reconciled, apart from `/alarms/kpi`): shelved and annunciated raises, time to acknowledge (count, sum, longest in ms of plant time; acknowledgements in a later epoch excluded), unacknowledged at the bucket's end and shelved time per point. Time to acknowledge belongs to the raise's bucket, so a late acknowledgement still changes a bucket with `provisional: false`; unacknowledged at the end counts shelved and cleared-but-unacknowledged occurrences too and is fixed once the bucket is over (#156). An unshelve made after a new epoch began is audited in the shelf's own epoch, at that epoch's last plant time.
    - An acknowledgement that collides with a rebuild of its occurrences (PostgreSQL `deadlock detected`, or a serialization failure) is retried up to 3 times; a 404 after that means the rebuild removed the occurrence.
    - `GET /api/v1/alarm-points?equipment&position&shelved=true`: every defined point (and any other with an active occurrence or a shelf) with its shelf and active occurrence; `GET /api/v1/alarm-points/{equipment}/{code}/audit`: the point's audit, newest first.
    - Tables: `alarms.occurrence_state` (acknowledgements, insert-only by a trigger), `alarms.alarm_shelf` (one row per point ever shelved, with its version) and `alarms.alarm_transition`, the append-only audit (ack, comment, shelve, unshelve, expire, epoch-ended; a trigger refuses UPDATE, DELETE and TRUNCATE). None of them is touched when occurrences are derived again. Shelved now: `SELECT equipment, code, shelved_by, reason, until, plant_epoch FROM alarms.alarm_shelf WHERE shelved;`.
    - From the shell: `curl -s -X POST -H 'Origin: http://127.0.0.1:4700' -H 'Content-Type: application/json' -d '{"actor":"me"}' 127.0.0.1:4700/api/v1/alarms/<id>/ack`.
  - Shifts: instances, the shift report and handover notes (#144, ADR-0025; migration `0014`):
    - The `shifts` module stores one row per (plant epoch, shift key) in `shifts.shift_instance` once the plant clock enters a shift, and at start-up creates the missing ones from the epoch's first stored interval up to the clock (idempotent). `status` is `running`, `ended` (clock past the end, or a newer epoch) or `final` (the report's inputs are final; never goes back). `SELECT epoch, shift_key, status, final_at, inputs_revision, content_revision, content_at_final FROM shifts.shift_instance ORDER BY start_time;`. `content_at_final` (#163, migration `0015`) is `content_revision` at the moment the report became final (null before), served as `revision.contentAtFinal`; the content changed after final `content_revision - content_at_final` times. Reports already final when `0015` ran were backfilled from the note audit (writes dated before `final_at`). The calendar functions are in `@shopfloor/shift-calendar`, shared with `oee`.
    - `GET /api/v1/shifts/{date}/{shift}[?epoch]`: the instance (newest epoch by default; 404 for a shift the plant clock has not reached). `GET …/report[?epoch]`: computed on read; the OEE section is the body of `…/oee`; the downtime Pareto by reason (sums to own plus external availability loss), the ten longest records and the uncoded time; production per machine and finished parts (PCK-01 good); per position and the plant the alarm KPIs of the shift, the top 5 bad actors and the MES-only operator figures (as `/alarms/operator-kpi`; an acknowledgement of a raise in a final shift raises `revision.content`); the notes with their history; `generatedAt` and `asOf` for a printout. `final` once every input is final; `revision.inputs` counts revisions of its OEE and alarm KPI hours after that, `revision.content` note writes and operator recodes inside a final shift (recoding never changes OEE). A report read brings a stored finality or `inputs` that lags behind up to date; a served revision may lag its content, never lead it. A newer epoch closes the handover of older epochs (409).
    - Handover notes: `GET …/notes[?epoch]`; `POST …/notes[?epoch]` with `{"author","text","category"}` (`safety`, `quality`, `equipment`, `material`, `general`; text up to 4,000 characters; at most 200 per shift); `PUT …/notes/{noteId}` with `{"author","text","category","retracted","version"}` (409 when `version` is stale); `GET …/notes/{noteId}/audit` (newest first). No delete: retract a wrong note. Writes are accepted from the shift's start until the end of the following shift (plant time), else 409 `handover closed`. Same write guards as coding; `shifts.handover_audit` is append-only and `shifts.handover_note` refuses DELETE (triggers).
    - From the shell: `curl -s -X POST -H 'Origin: http://127.0.0.1:4700' -H 'Content-Type: application/json' -d '{"author":"me","text":"Coolant topped up","category":"equipment"}' 127.0.0.1:4700/api/v1/shifts/2026-10-12/A/notes`.
    - Push: the `shifts` topic sends `shift` (created, status, revised) and `handover-note` (created, edited) upserts; a report page reads the report again when they move. The live numbers of a running shift come from `oee:<id>` and `alarm-kpi:<scope>`.
    - A report that stays `ended` after its shift: one of its inputs is not final (a silent machine keeps OEE and alarm KPI buckets provisional, see "Reconciliation run"; a provisional downtime record). The module checks ended reports every 10 s and on every change of their inputs.
  - WebSocket `ws://127.0.0.1:4700/api/v1/ws`: subscribe to `states`, `telemetry:<equipment>`, `oee:<equipment or work center>` (current hour and shift, at most one delta a second), `downtime` (records created, closed, recoded), `alarms` (occurrence upserts, also on acknowledge, comment and shelf changes, and point shelf changes) and `alarm-kpi:plant|position:<id>|equipment:<id>` (current hour and shift and open floods, at most one delta a second); protocol in `docs/api/realtime.md`. Metrics `mes_ws_clients`, `mes_push_messages_total{type}`, `mes_push_coalesced_total`, `mes_ws_dropped_total{reason}`.
  - Description: `docs/api/mes.openapi.json` (OpenAPI 3.1) and `docs/api/mes-realtime.schema.json`; after changing a route or message, regenerate them with `pnpm --filter @shopfloor/mes-server openapi` (a test fails on drift; `… openapi --check` only compares).
  - Quick look: `curl -s 127.0.0.1:4700/api/v1/equipment | jq '.equipment[] | {id, state: .current.state}'`.
- Migrations only: `DATABASE_URL=… pnpm --filter @shopfloor/mes-server migrate`.
- A new migration is a new file `db/migrations/NNNN_<module>_<what>.sql`. An applied file is never edited: the server refuses to start if one changed. A statement that can't run in a transaction (`CREATE INDEX CONCURRENTLY`) goes into a file marked `-- migrate:no-transaction`, written so that it can be rerun.
- The golden reconciliations also check the shift reports (#144): one `shift_instance` per scheduled shift (15 in `week-01`, 6 in `alarms-01`, also after a restart), and per shift the report's OEE, production, Pareto and alarm sections against the ground truth; the report is final exactly when its inputs are, with revision 0.
- End-to-end tests (`*.e2e.test.ts`) run apart from the others: `pnpm test:e2e`, one at a time; in CI they have their own job. In `mes-server` these are the golden-scenario reconciliations: `week-01` (about 5 minutes) and `alarms-01` (about 30 s), each replayed from the headless simulator (`--scenario <name>`, injections included) through ingest into TimescaleDB, in order and shuffled with duplicates; intervals, OEE, downtime records and every alarm occurrence and alarm KPI must equal the ground truth. `pnpm test` reconciles a Friday with its night shift.
- The MES tests start their own TimescaleDB and Mosquitto with Testcontainers (the broker harness is shared with the gateway in `@shopfloor/test-kit/broker`).

## Run the web app

`apps/web` (#98, #122, #145, #146) is the MES's browser app: a plant overview, a machine detail, the OEE dashboard (`/oee`), the downtime coding screen (`/downtime`), the alarm list (`/alarms`), the alarm KPIs (`/alarms/kpi`) and the shift reports (`/shifts`). With the MES running (above):

```bash
pnpm --filter @shopfloor/web dev        # http://127.0.0.1:5173, proxies /api to 127.0.0.1:4700
pnpm --filter @shopfloor/web build      # static files in apps/web/dist
```

- `MES_URL` changes the proxy target. The proxy sends the MES's host (so `HTTP_ALLOWED_HOSTS` keeps its default). For the WebSocket it refuses upgrades whose `Host` is not `localhost`, `127.0.0.1` or `[::1]` (Vite's host check skips proxied upgrades, so this keeps the MES's DNS-rebinding protection), and presents a page served under that loopback name as the MES's origin, so `HTTP_ALLOWED_ORIGINS` is not needed; any other origin is passed on and refused by the MES. It does the same for HTTP requests (#121), so writes from `pnpm dev` pass the MES's Origin check. Open the app as `localhost` or `127.0.0.1`.
- The header shows the plant clock (simulation time, Istanbul) and the connection: `Live`, `Connecting…` or `Reconnecting…`. Machine states marked **Stale** are from before a lost connection or from an earlier simulator run (not shown while the page first connects).
- A blank overview with `Could not load the equipment` and `Forbidden: host not allowed` means the request reached the MES under a name not in `HTTP_ALLOWED_HOSTS`; a connection stuck at `Reconnecting…` with 403 upgrades in the MES log means the page's origin is not accepted (`HTTP_ALLOWED_ORIGINS`).
- `/oee` shows the current shift by default (pick an earlier one in **Shift**): OEE, A, P and Q per work center and machine as the MES computed them (four decimals; `n/a` when there was no planned busy time), the hours, the loss waterfall and the downtime Pareto, updated live (about once a second at 60×). **Provisional**, **Revision** and **incidents** say what may still change.
- `/downtime` lists the shift's downtime records, uncoded first. **Code** opens a record: split it at a plant time, pick a reason per segment (or keep the automatic one), add a comment and your name (remembered in this browser), **Save coding**. A message says why a write was refused: 409 means the machine's codings changed since the record was read (it is reloaded; code again), 403 that the page's origin is not accepted (open the app as `localhost` or `127.0.0.1`), 405 writes are off, 429 too many writes. Recoding changes the Pareto and the history, never OEE.
- `/alarms` (#145) lists the alarms live in four tabs: **Active** (not acknowledged, also once cleared: a clear does not acknowledge), **Acknowledged** (still active), **Shelved** (the point is shelved) and **History** (closed, the last 24 hours). Priority shows as colour, a mark and its word. Type your name under **Operator** first (remembered in this browser, shared with **Coded by**). **Acknowledge** one alarm, or tick rows and **Acknowledge selected** (at most 100 at once). **Details** opens the occurrence: definition, acknowledgement with a comment, the point's shelf (shelve with a reason for 15 min, 1 h, 4 h or 8 h of plant time, or unshelve), comments and the full history (device raise and end, and every audited action with its request id). A red **Alarm flood** banner shows per position while more than 10 alarms were raised in the last 10 minutes. A message says why a write was refused: 409 on a shelf means someone else changed it (the panel reloads it; try again), **Reload the shelf** appears when it changed while you were filling in the form, 422 for example a shelf longer than `maxShelveMs`; 403, 405, 415 and 429 as for codings.
- `/alarms/kpi` (#145) shows the shift's alarm KPIs per scope (plant and positions), live: raises by priority, average and peak per 10 minutes against the ISA-18.2 benchmarks, flood windows and episodes, chattering, fleeting, standing, active time, and **Final**, **Provisional** or **Revision**; `n/a` where there is no bucket. **Details for** a scope shows its hours (or the shifts of the last week), the flood episodes, the top 10 bad actors and the MES-only operator measures (time to acknowledge, shelved raises, unacknowledged at the end).
- To see alarms on a disposable stack, inject failures through the simulator's control API, for example `curl -X POST -H 'Content-Type: application/json' -d '{"code":"COOLANT-PRESSURE","repairMs":4000}' http://127.0.0.1:4800/api/v1/faults/failure/cnc-01` (more than 10 within 10 minutes of plant time on Cell M1 make a flood; three of one point within a minute make it chatter). Acknowledgements and the audit are permanent: do this only on a stack you throw away.
- `/shifts` (#146) lists the last week's shifts, current first, with their status (**Running**, **Ended, not final**, **Final**) and revision; a row opens `/shifts/<date>/<shift>` (add `?epoch=<n>` for an earlier simulator run). The report shows status, **Final** or **Provisional**, the revision (inputs, content), `asOf` (plant time) and `generatedAt` (wall clock), then OEE, production, downtime, alarms and the handover notes. While the shift runs, OEE, production and alarm KPIs follow the plant (marked **Live**); the rest is as of `asOf` (**Read again**). The page reads the report again by itself when the shift ends and when the report turns final; a banner says when a final report changed later (late data, notes, recodes, acknowledgements). **Print** opens the browser's print dialog with an A4 layout (no navigation, buttons or forms; charts as still images, every value also in a table); **Download JSON** saves the report as served.
- Handover notes: type your name under **Author** (remembered in this browser, shared with **Coded by** and **Operator**), pick a category, write the note (plain text, up to 4,000 characters) and **Add note**. **Edit** changes the text or category or ticks **Retracted** (a wrong note is retracted, never deleted); **History** shows every version from the audit. If someone else saves the note while you edit, the editor says so and sends nothing; **Reload the note** starts again from their version. Notes can be written from the shift's start until the end of the following shift (plant time); afterwards the MES answers 409 `handover closed`, which the form explains, and 422 after 200 notes. Notes and their audit are permanent: write test notes only on a stack you throw away.
- More (screens, test ids, the nginx container): `apps/web/README.md`. In Compose the app runs as service `web` ("Full stack" below).

## Golden scenarios

A golden scenario is a fixed seed and configuration whose expected output is committed (plan section 9). Each one lives in `apps/simulator/golden/<name>/`:

- `scenario.json`: seed, start, number of days, configuration directory;
- `summary.json`: the expected ground-truth summary, byte for byte;
- `events.sha256`: the SHA-256 and line count of the expected event log. The log itself (about 6 MB per week) is not committed; its hash pins every byte.

| Task                                           | Command                                                       |
| ---------------------------------------------- | ------------------------------------------------------------- |
| Check every scenario against its snapshot      | `pnpm test:golden`                                            |
| Write one scenario's event log and summary     | `pnpm sim:headless --scenario alarms-01 --out runs/alarms-01` |
| Rewrite the snapshots after an intended change | `pnpm test:golden --update`                                   |

Each run also checks the conservation and time-accounting invariants after every simulation step, and fails on the first violation. `pnpm verify` (and the pre-commit hook) does not compare snapshots, to stay fast; CI runs `pnpm test:golden` on every pull request.

**When a snapshot changes:** any change to the plant model, its random draws or the default configuration changes the snapshot. That is the point. Run `--update` only when the change is intended, and explain in the pull request what changed in the simulated behaviour and why (plan section 9). The diff of `summary.json` shows the effect in numbers.

**Smoke writes and a disposable project.** `pnpm stack:smoke` always checks the write refusals (403, 415, nginx's method allowlist), also for the alarm writes, which change nothing. Start order: `db` and `broker` first; `simulator`, then `gateway` (needs broker and simulator); `mes` (needs db and broker); `web` (needs a healthy MES). The gateway does not wait for the MES: the edge must work without it, the MES's broker session is persistent, and the current state of every machine is retained in the UNS, so the overview is complete whenever the MES joins. Only cycles and telemetry published before the MES's very first session (a fresh broker volume) are not stored. The reconciliation needs the stricter order of the Phase 4 plan (database and broker, MES ready, gateway connected, then the simulator resumed at 06:00): `pnpm test:reconcile` starts the simulator with `SIM_AUTOSTART=false` and drives the order itself, in a project of its own (see "Reconciliation run"), so the default stack stays as it is. A consequence: every fresh `docker compose up` records one `sequence-gap` incident per machine (the first numbers of each `device:*` stream, about 30 s after start), because the autostarted simulator publishes before the gateway subscribes. That is expected with `SIM_AUTOSTART=true`.

MES and web notes:

- The overview shows `Live` in its header once the WebSocket through nginx is open. `docker compose logs -f mes` shows ingest and the API; health probes are logged only at `warn`.
- `pnpm stack:down` keeps the database and the broker's queue; on the next start the MES catches up from where it stopped (the broker queued the UNS meanwhile).
- `docker compose up -d --build mes web` rebuilds just these two after a code change (`stack:up` rebuilds everything, from cached layers).
- **403 `host not allowed`** (a blank overview with `Could not load the equipment`, or `curl` answers 403): the browser reached the app under a name not in `MES_ALLOWED_HOSTS`. Use `localhost` or `127.0.0.1`, or add the name to `MES_ALLOWED_HOSTS` in `.env` and run `pnpm stack:up` again.
- **Stuck at `Reconnecting…`, 403 upgrades in the MES log (`origin not allowed`):** the page's origin is not the host nginx forwarded. nginx must send `Host $http_host` (with the port, `apps/web/nginx/default.conf`); a page served from elsewhere needs its origin in `MES_ALLOWED_ORIGINS`.
- **502 from `/api/`:** the MES is down or restarting (`docker compose ps mes`); nginx finds a recreated MES again within 10 s.
- **A write answers 403** (problem details from the MES, `detail` says which guard): `a write needs an Origin header` (a script or `curl` must send `Origin`; browsers always do), `origin not allowed` (the page's origin is not the host and port the request reached: nginx must forward `Host $http_host`; a page served from elsewhere needs its origin in `MES_ALLOWED_ORIGINS`), `Sec-Fetch-Site same-site/cross-site not allowed` (the page is on another origin, for example another port of localhost: open the app through the web container or `pnpm dev`), `host not allowed` (as above). A 403 from nginx itself (HTML, no problem details) means a method other than GET, POST, PUT or DELETE.
- **A write answers 415:** the body was not sent as `Content-Type: application/json`. **405:** writes are off (`MES_WRITES=off` in `.env`; set `on` and `docker compose up -d mes`). **409:** the record's `version` moved on; read `GET /api/v1/downtime` again. Every write refusal and conflict names itself in the problem's `type` (#163, ADR-0023 note): `urn:shopfloor:write-origin`, `…:host-not-allowed`, `…:writes-off`, `…:write-not-json`, `…:write-rate`, `…:coding-stale`, `…:shelf-stale`, `…:note-stale`, `…:handover-closed`, `…:handover-not-open`, `…:note-limit`; `jq .type` on the answer tells which. **429:** more than 10 writes a second in total; wait `Retry-After`. **413:** body over 16 KiB.

Simulator notes:

- The OPC UA servers advertise `localhost` in their endpoint URLs (`SIM_OPCUA_HOST` changes it), so clients on the host, such as UaExpert, connect as with `pnpm sim:serve`. - Certificates persist in the `simulator-pki` volume; `pnpm stack:reset` deletes them. The container's host name is fixed to `simulator`, so the certificate's SAN stays valid when the container is recreated.
- `pnpm stack:smoke` expects the simulator to be running, so it fails with `SIM_AUTOSTART=false`.
- Health probes and metric scrapes are logged only at `warn` and above.
- `docker compose stop simulator` sends SIGTERM; the simulator shuts down in well under a second.
- Gateway, measured the same way: image 398 MB (node-opcua again), about 95 MiB memory and 4% CPU at 60×, under a limit of 384 MB.
- Watch the whole UNS: `docker compose exec broker mosquitto_sub -u dev -P <MQTT_DEV_PASSWORD> -t 'orbis/#' -v`.

  - image 388 MB, mostly `node-opcua` and its nodesets;

### Troubleshooting

- **A port is already in use:** set `DB_PORT`, `MQTT_PORT` or `SIM_CONTROL_PORT` in `.env` (the OPC UA ports 4841–4845 are fixed by the contract) and run `pnpm stack:up` again.
- **`Set DB_PASSWORD in .env`:** `.env` is missing or incomplete; see the first step above.
- **Broker users changed:** the password file is rebuilt from `.env` on every broker start; restart with `docker compose restart broker`.
- **Debugging MQTT connections:** set `connection_messages true` in `config/mosquitto/mosquitto.conf` (off by default because the healthcheck connects every 5 seconds) and restart the broker.
- **Memory:** measured with the full stack at 60× (#99, Colima VM with 2 GiB and 2 CPUs, the web app's detail screen open, `docker stats` every 12 s for 4 minutes, maximum):

  | Service   | Memory  | Limit                         | Image   |
  | --------- | ------- | ----------------------------- | ------- |
  | db        | 61 MiB  | none (tuned for 512 MB)       | 1.45 GB |
  | broker    | 4 MiB   | none                          | 43 MB   |
  | simulator | 190 MiB | 512 MiB                       | 389 MB  |
  | gateway   | 94 MiB  | 384 MiB                       | 398 MB  |
  | mes       | 79 MiB  | 512 MiB                       | 314 MB  |
  | web       | 9 MiB   | 64 MiB                        | 94 MB   |
  | **Total** | 437 MiB | 1.5 GiB + db's tuning (2 GiB) |         |

  The database grows towards its 512 MB tuning as data and queries grow, and `pnpm test` and `pnpm test:e2e` start their own TimescaleDB and Mosquitto containers through Testcontainers beside the stack. The stack fits a 2 GiB VM today, but with little room: give the Docker VM **4 GiB** (Colima: `colima stop && colima start --memory 4 --cpu 2`; Docker Desktop: Settings → Resources). Containers that hit their limit are killed (`docker compose ps` shows the restart, `docker inspect <container> --format '{{.State.OOMKilled}}'`).

## Reconciliation run

One simulated shift through the whole chain, simulator → gateway → broker → MES → web, checked against the simulator's own ground truth (#100; Phase 4 exit criteria 1 and 3; Phase 5 exit criteria 3, 4 and 5 with #120 and #123; Phase 6 exit criteria 3, 4 and 5 with #147). Since #147 the run is the golden scenario `alarms-01`: week-01's seed and start with injected failures, so shift A has a flood, a chattering point and a fleeting alarm to reconcile. It runs as its own CI job (`reconcile`) and locally:

```bash
pnpm playwright:install   # once: Chromium's headless shell for Playwright
pnpm test:reconcile       # about 9 minutes locally: image builds, start-up, 8 minutes of shift
```

It needs Docker (Colima or Docker Desktop; with Colima, export `DOCKER_HOST` from `docker context inspect --format '{{.Endpoints.docker.Host}}'`) and Node.js 26. It does not use `.env`: it writes its own env file with random passwords to a temporary directory and runs Compose as project `shopfloor-reconcile` with `e2e/compose.reconcile.yml` on top of `docker-compose.yml` (ephemeral host ports on `127.0.0.1`, no published database or broker ports, no restarts, fresh volumes). A dev stack on the default ports can keep running beside it; its images are built from the working tree under their own tag (`IMAGE_TAG=reconcile`, so `shopfloor-twin/*:reconcile`; the dev stack's `:dev` images stay as they are). At the end the project is removed with its volumes, also after a failure; Ctrl+C or SIGTERM removes it and the env file before exiting, and after 25 minutes (`RECONCILE_DEADLINE_MS`) the run fails by itself with its report and logs.

What it does, in the Phase 4 plan's order:

1. Builds the images, then starts `db`, `broker` and `mes` and waits until the MES is ready (migrated, subscribed).
2. Starts the simulator idle (`SIM_AUTOSTART=false`, seed and start of the golden week: Monday 2026-10-12 06:00 Istanbul, the start of shift A) and the gateway, and waits until the gateway is ready with all six machines connected and the MES has every machine's start-up state (Off at 06:00, from the gateway's snapshots) for the simulator's epoch. Compose's `depends_on` starts the gateway only once the simulator answers; since the simulator is idle, nothing happens before the MES listens. Then it posts the scenario's 14 shift A injections (`POST /api/v1/faults/failure/{machine}` with `code`, `at` and `repairMs`; control API 1.3) in the scenario's order before the resume, which puts the same events in the queue as the headless run (`docs/contracts/simulator-control-api.md`, "Determinism"): 13 on Cell M1 from 08:00 Istanbul (a flood, with CNC-01 `COOLANT-PRESSURE` chattering) and LKT-01 `FIXTURE-SEAL` with a 500 ms repair (fleeting) at 09:20. The PCK-01 injection of shift B lies after the run and is not posted. `alarms-01`'s event log equals week-01's up to the first injection (the headless test in `apps/simulator/src/headless/alarms-01.test.ts`), so week-01's live evidence of Phases 4 and 5 carries over; the report names that test (`injections.prefixEvidence`).
3. Starts `web`, resumes the simulator at 60× over its control API (`POST /api/v1/resume`) and runs Playwright (`e2e/browser/overview.spec.ts`) beside the shift: Chromium opens the overview, waits for `connection-status` to be `open`, then for 90 s (`OVERVIEW_SAMPLE_MS`) compares each machine's `state-<id>` badge (`data-state`, recorded by the page every 20 ms) with the simulator's current state (`GET /api/v1/ground-truth`, polled every 200 ms). When the truth changes at time t, the page must show that state, or a state the truth took later, by t + 2 s. A change's time is when the paced simulation clock reached the state's start (`pacedTime` of the same answer, at the request's midpoint). The page must also really change: at least half as many transitions as judged changes, and one on every machine whose truth changed, so a frozen page can't pass by showing a state the truth returned to.
   Before both, the same Playwright run (project `live`; files run alphabetically) checks the alarms (`e2e/browser/alarms-live.spec.ts`, #147, Phase 6 exit criterion 3): Chromium opens `/alarms` (Active tab) and `/alarms/kpi` and records every 20 ms which `alarm-row-<id>` rows exist, both positions' `flood-banner-<id>` (`data-episode`) and the KPI cards' `data-raises`, while the test polls `GET /api/v1/ground-truth` every 200 ms until the paced clock is 3 simulated minutes past the last injection (about 200 s of wall time). The truth is complete: `alarms.occurrences` lists every raise to the millisecond and `alarms.scopes.<position>.floods` every episode, each timed as the overview's states are. Rules: every raise appears as a row within 2 s of the paced clock reaching it (each row is resolved to its occurrence with `GET /api/v1/alarms/{id}`, and a row matching no raise fails: the unseen-value floor is 0); the page adds a row for every judged raise (frozen-page ratio 1); all 14 applied injections are among the judged raises; Cell M1's banner shows the episode id within 2 s of the flood's start and goes away within 2 s of its end, Line A1's never shows; each card reaches every count its scope took (or a later one) within 2 s, shows only counts the scope held, agrees with the truth in at least 95 % of the snapshots (one a second, allowing the push's 2 s pacing), and changes at least a quarter as often as the truth (the push sends one delta a second while the flood raises up to 12 alarms a second of wall time).
   The OEE dashboard check comes next (`e2e/browser/oee-live.spec.ts`, #123, Phase 5 exit criterion 5), and the overview's last. It samples for 90 s (`OEE_SAMPLE_MS`): Chromium opens `/oee` (the current shift), the page records `data-oee` of both work-center cards (`oee-card-<id>`) and all six machine rows (`oee-machine-<id>`) every 20 ms, and the test polls `GET /api/v1/shifts/2026-10-12/A/oee` every 100 ms. The API's OEE changes about twice a second, the push at most once a second per topic, so the same rule applies with the four-decimal OEE as the state: by t + 2 s the page shows that value or one the API held later. A value the polls never saw (held between two polls) counts only when the page took it after the change, whatever its age, so the value checks below are what catch a lagging page: at most 5 % of the page's values may be such (real runs: about 1 %). Frozen-page guard: at least half as many page transitions as judged changes (real runs: about 0.7), one on every id; at least 20 judged changes per card and 100 in all. Every 2 s a snapshot of all eight values must equal what the API held within the 2 s before (or 0.5 s after) the snapshot, for at least 95 % of the values and at least once per id.
4. Polls `GET /api/v1/status` every second (lag, progress) until the simulation is 5 minutes past shift end (14:05). From then on it also checks, every second, that the MES has stored a device fact (state change, cycle or alarm) of every machine at least a second (`fleetingMs`, for the alarm KPIs, #142) after the shift end (14:00), and pauses the simulator once it has (#113). A machine that is Down, in Setup or in Maintenance across the shift end sends nothing until that ends (ASM-01, LKT-01 and PCK-01 send no telemetry either), and its shift-A bucket stays provisional until it does. The wait is bounded by `RECONCILE_SILENT_WAIT_MS` (simulated time past 14:05, default 2 hours, two wall minutes); the report records it as `silentWait`, with each machine's first fact after the shift end. In the golden week every machine reports within about 3 simulated minutes, so the run normally pauses at 14:05. The wait also has a wall budget (twice its nominal time plus a minute), and the run fails at once if the simulation clock stops moving for 30 s of wall time, rather than at the 25-minute deadline.
5. Waits until the MES has drained: every machine's current state and start equal the simulator's, the gateway's buffer is empty and the plant watermark is past shift end. The totals are then read once; Phase 4's wait for "totals stable" is gone, since shift A must now be final.
6. Compares, and fails on any difference:
   - time per state, per machine, for shift A (`GET /api/v1/shifts/2026-10-12/A/totals`) equals the simulator's ground truth for that bucket to the millisecond, and the ground truth covers all 8 hours of each machine;
   - shift A is final for every machine: `provisionalMs = 0`, `revision = 0` and `incidents = 0` in the totals (#113, Phase 5 exit criterion 3);
   - the live ground truth equals `alarms-01`'s shift A (`apps/simulator/golden/alarms-01/summary.json`), time per state and OEE: pacing never changes the run;
   - the 14 injections are listed by `GET /api/v1/faults/injections` as `applied` inside shift A (the held ones a little after their `at`);
   - every stored piece (`equipment.equipment_state_interval`, read with `psql` in the `db` container) lies inside one UTC hour and one shift bucket of the shared calendar;
   - no data-quality incident of lost data (`sequence-gap`, `ring-overrun`, `buffer-overflow`) and no rejected UNS message. With this start order there is no start-up gap; one would mean the order is wrong;
   - shift A's OEE (`GET /api/v1/shifts/2026-10-12/A/oee`, #120) becomes `final` for all six machines within 30 s of the drain (the aggregates' refresh debounce), with `provisionalMs = 0`, `revision = 0` and `incidents = 0`, and equals the live ground truth's `oee` exactly for every machine (inputs, fractions, four-decimal strings, totals, losses, `unplanned`) and work center. A difference is printed as `path: truth ≠ MES` lines and kept in `report.json` (`oee`). Both work centers must be final too, the MES and the ground truth must list exactly the plant configuration's six machines and two work centers, and the count of compared buckets (`oee.compared`) must be 8 (#123);
   - shift A's alarm KPIs (`GET /api/v1/alarms/kpi`, #142, #147) for the plant and both operator positions, per shift and per UTC hour, become `final` within 30 s, with `provisional` false, `revision = 0` and `incidents = 0`, and equal the live ground truth's `alarms` section exactly (raises, rates, windows, floods, standing, chattering, fleeting, active time), which in turn equals `alarms-01`'s summary; the hours listed must be the same on both sides. 3 shift buckets and 4 hour buckets are compared (`alarms` in `report.json`), and the run fails unless the plant, Cell M1 and Line A1 raised 14, 13 and 1, Cell M1 has a flood episode and `cnc-01/COOLANT-PRESSURE` chattered, and Line A1 has a fleeting alarm;
   - shift A's report (`GET /api/v1/shifts/2026-10-12/A/report`, #144) is `final` with `revision.inputs = 0` and no incident; its OEE section is `GET …/oee` byte for byte; each scope's alarm KPIs are `GET /alarms/kpi`'s shift bucket byte for byte and the ground truth's; per machine produced, good, scrap and rework equal the OEE inputs and the ground truth's cycles; finished parts are PCK-01's good cycles; the Pareto sums to the own plus external availability loss; the instance has the calendar's start, end and breaks (`shiftReport` in `report.json`).
7. Acts through the UI with the simulator paused and shift A final (Playwright project `final`, files in this order). Around the project it reads the alarm KPIs of every scope (hours and shift) and shift A's OEE, and requires both byte-identical afterwards; then it checks with `psql` that `alarms.alarm_transition` and `shifts.handover_audit` hold rows and refuse UPDATE and DELETE (`coding.auditRefusals`).
   - **Alarm actions** (`e2e/browser/final/alarm-actions.spec.ts`, #147, Phase 6 exit criteria 3 and 5): each of the shift's 14 alarms is `unacked-cleared` (cleared on repair) and final. As `reconcile e2e`, it acknowledges the first one from its row, comments on a CNC-01 `COOLANT-PRESSURE` in its panel, shelves another point for 15 minutes (its alarms move to the Shelved tab) and unshelves it, then acknowledges the rest with **select all** and **Acknowledge selected**. Then every alarm of the shift is `closed` and acknowledged by the operator; each one's `GET /api/v1/alarms/{id}/history` holds the device raise and clear (with `seq`, `receivedAt` and protocol, at the occurrence's times) and its audited transitions (`ack`, plus `comment` for the commented one) with actor, `authenticated: false` and request id, and the panel lists the same entries; the point's audit holds the shelve (version 1, reason, 15 minutes) and the unshelve (version 2). `GET /api/v1/alarms/kpi` stays byte-identical, while `GET /api/v1/alarms/operator-kpi` of each scope counts every raise of the shift as acknowledged (`timeToAck.count` 0 before and the raises after, sum and longest above 0), with raises, shelved raises and unacknowledged at the end unchanged; the KPI page's operator measures show the count. An acknowledgement with a foreign `Origin`, without `Origin` and as a form answers 403, 403 and 415 with the problem types `urn:shopfloor:write-origin`, `…:write-origin` and `…:write-not-json`.
   - **Downtime coding** (`e2e/browser/final/downtime-coding.spec.ts`, #123, Phase 5 exit criterion 4): it takes the longest closed, final record of shift A without codings (the golden week has no UNCODED record), opens `/downtime` for shift A, filters by its machine, splits it on a whole plant second near its middle, picks two leaf reasons other than the automatic one (`reason-picker`), and saves as `reconcile e2e`. Then: one `audit-entry` on screen and one `coded` entry in `GET …/audit` with both segments; the machine's `GET /api/v1/downtime/pareto` for the shift moved exactly by the record (its time left the automatic reason and went to the two coded ones; availability and micro-stops unchanged); the dashboard's Pareto shows the new reason; `GET /api/v1/shifts/2026-10-12/A/oee` is byte-identical before and after, and the cards' `data-oee` on `/oee?shift=2026-10-12/A` are unchanged. Writes with a foreign `Origin`, without `Origin` and with a form content type must answer 403, 403 and 415 (sent with an invalid version, so a broken guard would answer 422, never code anything).
   - **Handover note** (`e2e/browser/final/shift-report.spec.ts`, #147, Phase 6 exit criteria 4 and 5): shift A's report is final with `revision.inputs = 0` and a `contentAtFinal`; the acknowledgements and the recode above have already raised `revision.content`. On `/shifts/2026-10-12/A` it writes an `equipment` note as `reconcile e2e` and edits it; the note's history shows versions 2 (`edited`) and 1 (`created`) on the screen and in `GET …/notes/{id}/audit` (actor, unauthenticated, request id). Afterwards `revision.content` rose by exactly 2, `contentAtFinal` and `inputs` stayed, the OEE and alarm sections are byte-identical to before (the OEE section is `GET …/oee`, each alarm scope `/alarms/kpi`'s bucket), and the page shows the content revision and the **changed after final** banner (`report-revised`). A note with a foreign `Origin`, without `Origin` and as a form answers 403, 403 and 415 with their problem types.

Results go to `e2e/results/` (git-ignored): `report.json` (phase times, wall time and effective speed of the shift, the simulator's lag, the drain, per-machine totals, pieces, incidents, the browser's delays), `overview-latency.json`, `oee-latency.json` (judged changes, delays p50/p95/max, snapshot agreement), `alarms-latency.json` (rows, flood banners and KPI cards: judged changes, delays p50/p95/max, the banner's truth and page values, snapshot agreement), `downtime-coding.json` (the record, reasons, Pareto before and after, OEE identical, refusals), `alarm-actions.json` (the alarms acted on, histories, shelf audit, KPI bytes identical, operator measures before and after, refusals), `shift-report.json` (revisions before and after, sections identical, note history, refusals), and on failure `compose.log` (every service's log; the last 60 lines of each are also printed) and Playwright's trace and screenshot in `playwright/live/` or `playwright/final/` (open a trace with `pnpm --filter @shopfloor/e2e exec playwright show-trace <file>`). A difference is printed as a table of machine, state, truth, MES and delta.

Options: `RECONCILE_SKIP_BUILD=1` uses the images already built, `RECONCILE_BROWSER=0` skips Playwright, `RECONCILE_PROJECT` names the Compose project, `OVERVIEW_SAMPLE_MS` and `OEE_SAMPLE_MS` set how long each live check samples (they run one after the other, after the alarm check's about 205 s; keep their sum below about 200 s, or sampling outlasts the shift: with 90 s each the overview's ends about 410 s into the 480 s shift), `RECONCILE_SILENT_WAIT_MS` how long (simulated) the run may go on for a silent machine's next fact, `RECONCILE_DEADLINE_MS` the overall limit.

Notes:

- Interval finality (#113, ADR-0018): a stored piece is final once it ends at or before its machine's "final through", the latest time of that machine's own device facts with no open sequence gap below them, or once its epoch is closed. So shift A becomes final as soon as each machine has sent a fact after 14:00; the plant watermark alone can't do it, since it is plant-wide and a busy machine moves it past a silent one. If a run fails with `provisionalMs` above 0, look at `silentWait` and the machine's state at 14:00 in the report: a machine silent for longer than `RECONCILE_SILENT_WAIT_MS` fails the run with its name. A `revision` above 0 means a fact arrived for an hour that was already final (a gap reported as an incident and filled late, or a late fact of a closed epoch), and `incidents` above 0 a sequence gap; neither may happen with this start order.
- If the run fails with lag, read `lagMs` in `report.json` (the simulator's `GET /api/v1/status`): at 60× the simulator processes events within a few milliseconds of their time on a laptop. A large lag means the machine (or the CI runner) is short of CPU; the run fails if the shift takes more than twice its nominal wall time, rather than slowing down silently.
- The run uses about 450 MiB in the Docker VM, like the full stack; Chromium runs on the host.
- Duration (#147, measured locally on an M3 MacBook Air with cached images): 523–526 s in all (two passing runs), of which 486 s are the shift at 60× (lag p95 2.4–2.5 ms), about 35 s start-up and about 4.3 s for the `final` project. Cold image builds and the browser's system libraries add several minutes in CI (Phase 5: 10.8 minutes for the whole job), well inside the job's 30-minute limit and the run's own 25-minute deadline.
- If the alarm check fails on `rows`, look at `alarms-latency.json`: `unmatchedRows` are rows of no raise of the truth, and a violation without a latency is a raise never listed. `injected.judged` below `applied` means an injection's raise was applied before sampling began (a browser that started late) or not at all (`GET /api/v1/faults/injections`).
