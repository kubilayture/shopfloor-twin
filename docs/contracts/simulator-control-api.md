# Simulator control API

Version 1.9 (Phase 9; 1.0 in Phase 2, 1.1 adds `GET /api/v1/ground-truth`, #100; 1.2 adds its `oee` section, #117; 1.3 adds failure injection and the `alarms` section, #140; 1.4 adds the production mode, `productionMode` and the `orders` section, #172; 1.5 adds the leak-test drift injection, #196; 1.6 adds the ground truth's `trace` section and `?asOf`, #208; 1.7 adds the console actions and the lot and operator reads, #234; 1.8 adds the ground truth's `lineOee` section, cut by `?asOf` too, #230; 1.9 adds the scenario timelines, #235). The OpenAPI document's `info.version` is `1.9.0`. Source of truth in code: `apps/simulator/src/control/`. The OpenAPI description is generated into `docs/api/simulator-control.openapi.json`; a test fails when it drifts from the routes (`pnpm --filter @shopfloor/simulator openapi` rewrites it). Any change bumps the version here and needs a changelog entry.

The simulation console (Phase 9) is the client. The MES never uses this API: it sees the plant only through OPC UA and MQTT (plan section 5).

## Endpoint

`http://<CONTROL_HOST>:<CONTROL_PORT>`, by default `http://127.0.0.1:4800`. There is no authentication in Phase 2, so the default binds to loopback only. Access control comes with security in Phase 9.

## REST (`/api/v1`)

| Method and path            | Body             | Success                          | Errors                                                      |
| -------------------------- | ---------------- | -------------------------------- | ----------------------------------------------------------- |
| `GET /api/v1/status`       | none             | 200 `Status`                     | none                                                        |
| `GET /api/v1/ground-truth` | `?asOf` (1.6)    | 200 `GroundTruth`, 400           | none                                                        |
| `POST /api/v1/pause`       | none             | 200 `Status`                     | 409 when the run has finished                               |
| `POST /api/v1/resume`      | none             | 200 `Status`; starts an idle run | 409 when the run has finished                               |
| `POST /api/v1/step`        | none             | 200 `{ stepped, status }`        | 409 unless paused or idle                                   |
| `PUT /api/v1/speed`        | `{ "speed": n }` | 200 `Status`                     | 400 when `speed` is missing, not a number or outside 0.5–60 |

- `Status` is `{ state, speed, simTime, lagMs, events }`.
  - `state` is `idle`, `running`, `paused` or `finished`.
  - `simTime` is ISO 8601 UTC.
  - `lagMs` is how far event processing trails the paced clock, in wall milliseconds.
  - `events` is the run-wide sequence number of the last plant event.
- `GroundTruth` is the headless ground truth (`docs/simulation-model.md`, "Ground-truth summary") of the live run so far, as `summary.json` would hold it if the run ended at `simTime`: `machines` (per machine `stateMs`, `byShift` keyed `2026-10-12/A` or `no-shift`, with all ten states, and `cycles`), `production` and `lots`; plus `epoch` (the run's epoch, as the devices publish it), `start`, `simTime` (how far events have been processed; the open state of each machine counts up to here), `pacedTime` (the paced simulation clock at the moment of reading, as `status` reports it; `simTime` trails it by up to about 1 s × speed while running), `currentBucket`, `buckets` (every bucket seen, `complete` once the run has left it; `no-shift` collects every gap between shifts and can be entered again), `current` (each machine's state and when it began) `oee` (1.2: the ground-truth OEE as `summary.json` holds it, see `docs/simulation-model.md`, "Ground-truth OEE": per machine the `oee-core` inputs per shift bucket and UTC hour and the `bucketOee` result per shift bucket, per work center the `workCenterOee` result per shift bucket; fractions as `num/den` strings and four-decimal strings) and `alarms` (1.3: the alarm ground truth as `summary.json` holds it, see `docs/simulation-model.md`, "Ground-truth alarms": every occurrence, and per scope (`plant` and each operator position) the `alarm-core` KPIs per UTC hour and shift bucket, flood episodes and bad actors, with the run's time so far as the horizon, so the hour and shift in progress are `provisional`), `productionMode` (1.4: `schedule` or `orders`, the run's production mode, #172) and `orders` (1.4: the order ground truth as `summary.json` holds it, see `docs/simulation-model.md`, "Ground-truth orders": every accepted job, per order its quantities per operation, scrap, rework passes, WIP, completion and material booked at cycle completion, and the count and hash of every unit's operation records; empty in schedule mode) and `trace` (1.6, #208: the traceability and SPC truth as `trace.json` holds it without its `schema` and `run`, see `docs/simulation-model.md`, "Ground-truth traceability and SPC": the count and `unitsTraceSha256` of every unit's records with lots, operator, leak reading and carton, lots forward in full, cartons, the SPC limit versions, hashed points and every episode, and per drift its first episode and the counterfactual window; provisional while cartons are open, orders incomplete or episodes open). `GET /api/v1/ground-truth?asOf=<ISO 8601>` (1.6) cuts `trace` at that plant time on the server with `trace-core`'s `traceAsOf`: records, cartons, orders, limit versions, points and episodes as they stood then, and the counterfactual readings and drifts of the readings it keeps (a drift ended at or after `asOf` is still active then), as a run that ended at `asOf` would give it (tested against `quality-01`'s shift-A reference run); the response then carries `traceAsOf`, and every other section stays as of `simTime`. So a test can compare shift A at 14:00 even once the run has gone past it. `lineOee` (1.8, #230) is the order and line OEE truth as `line-oee.json` holds it without its `schema` and `run` (see `docs/simulation-model.md`, "Ground-truth order and line OEE"): the bottleneck per product, the planned stops, each order's in-progress time, the line throughput OEE per UTC hour and shift bucket, and per order its order OEE over its job windows (per job too), first-pass yield and line OEE (not additive across orders); a bucket or an order reaching past `simTime` is `provisional`. `?asOf` (1.8) cuts it at the same plant time, as a run that ended at `asOf` gives it (tested against headless runs ended there), and the response carries `lineOeeAsOf` beside `traceAsOf`. An `asOf` that is not ISO 8601 with an offset or `Z`, or is after `simTime`, is 400. Under `scheduledTime: orders` the OEE inputs carry `noOrderIdleMs` where a bucket holds Idle `NO-ORDER` time (1.4). An open Stopped interval appears with `open: true` and its whole length up to `simTime`, so a bucket still in progress can be `provisional` and differ from the MES's; only complete buckets are reconciled (ADR-0021). Cycles are bucketed by their time, but `byShift` and `buckets` follow the shift events: a snapshot taken between a cycle exactly at a shift start and that shift's event (the same simulation millisecond, before the event is processed) can show that shift in `oee` with zero `stateMs` and only the cycle, before `byShift` and `buckets` have it. Reading it never moves the run, and a paused run's buckets don't change. Reconciliation tests compare the MES with it (#100); a client of the plant (the MES) never uses it.
- Pausing a run that is not running, or resuming a running one, changes nothing and returns the status.
- `step` processes exactly one simulation event. `stepped: false` means no event is left before the end.
- Every error, including 404 and malformed JSON, is `{ error, message }`.
- Request bodies are strict: `"5"` or `true` is not a speed, and unknown fields give 400.
- Until every OPC UA server listens, `pause`, `resume`, `step` and `speed` return 503 `the simulator is starting`, so the run cannot move before its events have somewhere to go. `status` always answers.
- Pacing never changes the event stream: a run produces the same events whatever the pauses, steps and speed changes (proven by the pacer's property test, #49).

## Faults (`/api/v1/faults`)

Infrastructure faults for resilience tests (plan section 4), brought forward from Phase 9 for the Phase 3 gateway tests, and failure injection (1.3, #140), brought forward for the Phase 6 alarm tests. Every route exists in every live run.

| Method and path                       | Body                         | Success                                       | Effect                                                                                                                                                                                                       |
| ------------------------------------- | ---------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /api/v1/faults/modbus`          | `{ "silent": true\|false }`  | 200 `{ silent }`                              | WSH-01 accepts connections but stops answering, or answers again. Its registers keep updating meanwhile, so a poller that recovers finds the ring entries it missed, unless more than 64 facts happened      |
| `POST /api/v1/faults/opcua/{machine}` | `{ "offline": true\|false }` | 200 `{ offline }`; 404 for an unknown machine | The machine's OPC UA server drops its connections and refuses new ones, or accepts them again. Its address space keeps following the plant meanwhile, so a reconnecting client sees how far `Sequence` moved |

### Failure injection (1.3)

| Method and path                         | Body                       | Success                     | Errors                                                                                                                                             |
| --------------------------------------- | -------------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/v1/faults/failure/{machine}` | `{ code, at?, repairMs? }` | 200 `{ injection }`         | 404 unknown machine or code; 409 `at` in the past or on a calendar boundary, or the run has finished; 400 invalid `at`, `repairMs` or extra fields |
| `GET /api/v1/faults/injections`         | none                       | 200 `{ injections: [...] }` | none                                                                                                                                               |

- `code` is one of the machine's failure modes (`failures.yaml`). `at` is simulation time, ISO 8601 with an offset or `Z`; without it the injection is due at the simulation's current time, so it applies at the next step. `repairMs` (integer, 1 ms to 365 days) makes the repair take exactly that long once a technician starts it; without it the repair time is drawn from the mode's repair stream, as for a natural failure.
- An injection is a simulation event at `at`. It takes effect only while the machine is `Running`: the cycle halts and the machine goes `Down` with the code as cause, raises the alarm and queues for a technician, as in a natural failure. In any other state it is held and applied where the machine would next enter `Running`, straight to `Down`; several held injections apply in order, one per entry to `Running`. The mode's natural time to failure is not redrawn. See `docs/simulation-model.md`, "Failure injection".
- `at` must not coincide with a calendar boundary (shift start or end, break start or end): the order of the two events would then depend on how they were queued. The same rule refuses such a scenario in `plant-config` (`checkInjections`).
- **Determinism:** posting a scenario's injections in list order before the run starts (`SIM_AUTOSTART=false`, then `POST /api/v1/resume`) puts the same events in the queue as the headless run, which schedules them right after the line starts. The live run then reproduces the headless one, event for event. In production mode `orders` (#172) the jobs come first: dispatch them through OPC UA `LoadOrder` while the run is idle at its start time and wait until each is accepted (its job fact), then post the injections, then resume; the headless run applies a scenario's `dispatches` right after the line starts and before its injections, so both queues hold the same events.
- `injection` is `{ id, machine, code, at, repairMs?, status, heldAt?, appliedAt? }`: `id` counts from 1 in the order accepted; `status` is `scheduled`, `held` (waiting for the machine to enter `Running`) or `applied` (the machine went `Down`). Times are ISO 8601 UTC.
- The event stream carries `injection-held` and `injection-applied` events (`{ machineId, injection, code }`) beside the state change and alarm they cause.

### Leak-test drift injection (1.5)

The plan's "cause sensor drift" (section 4) as a bounded sensor fault (Phase 8 plan, "Leak drift injection and scenario stock", ADR-0033).

| Method and path                       | Body                    | Success                 | Errors                                                                                                                                                                                                                                               |
| ------------------------------------- | ----------------------- | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/v1/faults/drift/{machine}` | `{ shift, at?, until }` | 200 `{ drift }`         | 404 unknown machine; 400 not the leak tester, `shift` not a non-zero whole multiple of the resolution, `until` not after `at`, an invalid time or extra fields; 409 `at` in the past or `at`/`until` on a calendar boundary, or the run has finished |
| `GET /api/v1/faults/drifts`           | none                    | 200 `{ drifts: [...] }` | none                                                                                                                                                                                                                                                 |

- `shift` (Pa/min, the tester's unit) is added to the mean of every LKT-01 reading from `at` (the current time when left out) until `until` or the tester's next calibration, whichever comes first. It must be a non-zero whole multiple of the tester's `resolution` (0.001 Pa/min), at most 1,000,000 steps, positive or negative. `until` is required and after `at`; in a live run without an end it is always checked against the calendar.
- No random draw changes: the reading still draws one normal, and the shift is added in whole resolution steps to the rounded reading, so the reading the same draw gives without the drift is exactly the logged value minus `shift`, and a run is identical to the run without the drift up to `at`. The result decides pass or fail as any reading does.
- `at` and `until` must not coincide with a calendar boundary, as for failure injections (`until` only while it falls inside the run). Posting a scenario's injections in list order before resuming reproduces the headless run; drifts and failure injections share one numbering.
- `drift` is `{ id, machine, shift, at, until, status, appliedAt?, endedAt?, endedBy? }`: `status` is `scheduled`, `active` or `ended`; `endedBy` is `until` or `calibration`. Times are ISO 8601 UTC.
- The event stream carries `leak-drift` events (`{ machineId, injection, transition: applied | ended, shift, endedBy? }`): `applied` when it starts, `ended` at `until` (`endedBy: until`) or at the start of a calibration before it (`endedBy: calibration`). A drift still active at the end of a run has no `ended` event.

## Console actions (1.7)

The physical levers of the simulation console (Phase 9 plan, "Console actions", ADR-0037): block and release a material lot, mark operators absent for a later shift, break a CNC's tool; and the reads the console shows. Every route exists in every live run.

| Method and path                      | Body                   | Success                                     | Errors                                                                                                                                                                                |
| ------------------------------------ | ---------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/lots`                   | none                   | 200 `{ lots: [...] }`                       | none                                                                                                                                                                                  |
| `POST /api/v1/lots/{lot}/block`      | `{ at? }` or none      | 200 `{ action }`                            | 404 unknown lot; 400 invalid `at` or extra fields; 409 `at` in the past or on a calendar boundary, or the run has finished                                                            |
| `POST /api/v1/lots/{lot}/release`    | `{ at? }` or none      | 200 `{ action }`                            | as `block`                                                                                                                                                                            |
| `GET /api/v1/operators`              | none                   | 200 `{ currentShift, operators, absences }` | none                                                                                                                                                                                  |
| `POST /api/v1/operators/absent`      | `{ shift, operators }` | 200 `{ action }`                            | 404 unknown operator or no such shift; 400 a malformed shift key, an empty list, an id listed twice, an operator of another shift; 409 the shift has started, or the run has finished |
| `POST /api/v1/faults/tool/{machine}` | `{ at? }` or none      | 200 `{ action }`                            | 404 unknown machine; 400 not a CNC or invalid `at`; 409 `at` in the past or on a calendar boundary, or the run has finished                                                           |
| `GET /api/v1/actions`                | none                   | 200 `{ actions: [...] }`                    | none                                                                                                                                                                                  |

- **Lots:** each lot is `{ lot, material, remaining, blocked }`, in `stock.yaml` order (or `SIM_STOCK`'s). A block or release is a simulation event at `at` (the current time when left out, so it applies at the next step), as a failure injection is. A blocked lot is skipped as if it were empty: the consuming station starves with cause `MATERIAL:<material>` once no other lot of that material is left; a release wakes every starved station. Blocking a blocked lot, or releasing a free one, changes nothing but is still recorded.
- **Operators:** `currentShift` is the running shift `YYYY-MM-DD/<shift id>` (null between shifts). Each operator is `{ id, shift, skills, speedFactor, status, station, forced }`: `status` is `present`, `absent` or `off-shift` (not rostered on the current shift, or none runs), `station` the station staffed in the current shift, `forced` an absence by a console action. `absences` lists every forced absence, planned or applied.
- **Forced absence:** `shift` is `YYYY-MM-DD/<shift id>` (the date the shift starts on); its start must be after the simulation time, so no running shift's staffing changes. Every listed operator, who must be rostered on that shift, is absent at its start whatever the roster draw says; the draw still happens, one per operator and shift, so every other shift is unchanged. Several requests for one shift add up. Marking both ASM-01-qualified operators of a shift (`op-a1` and `op-a2` for shift A) leaves ASM-01 `Idle` with cause `NO-OPERATOR` at that shift's start.
- **Tool breakage** (CNCs only): at `at` the tool's wear goes to end of life (1.0). A cycle in progress completes normally and draws its defect at wear 1.0 (5 % by default); the tool is changed at the next start (`Setup`, cause `TOOL-CHANGE`, `changeMinutes`), as at a natural end of life. No random draw is added or removed, and there is no `Down` and no new failure code. A breakage that falls due inside the machine's own `TOOL-CHANGE` setup changes nothing: its status is `ignored` and its event carries `ignored: tool-change-in-progress`. An OP10 machine without a tool (one the schedule doesn't list, in schedule mode) is refused with 400 like any machine without one. See `docs/simulation-model.md`, "Tool breakage".
- `action` is one of `{ id, kind: lot-block | lot-release, lot, material, at, status, appliedAt? }`, `{ id, kind: tool-breakage, machine, at, status, appliedAt?, cycles? }` (`status` also `ignored`) (`cycles`: the tool's count when it broke) and `{ id, kind: operators-absent, shift, start, operators, status, appliedAt? }`. `status` is `scheduled` then `applied` (`planned` then `applied` for an absence). Console actions are numbered on their own, from 1, in acceptance order. Times are ISO 8601 UTC.
- **Determinism:** as with injections, posting the actions in a headless run's `actions` order before resuming (after any dispatches and injections) gives the headless run's event log. The calendar-boundary rule is the injections' (`actionIssues` in `plant-config`). Since 1.9 (#235) a lot action, a tool breakage, a failure and a drift are _external_ simulation events: at their time they run before every plant event of that millisecond not yet processed, after the external events accepted before them. So one posted mid-run for a later time lands exactly where the headless run, which accepts everything before it starts, puts it. One posted with `at` equal to the simulation time (or without `at`) runs after the events already processed in that millisecond (all of them after a paced advance or a pause, the ones stepped so far after a step), and before the rest; it equals the headless run of the same action only when none was processed. See `docs/simulation-model.md`, "Scenario timelines".
- The event stream carries `lot` (`{ lotId, material, transition: blocked | released, action }`), `absence` (`{ shiftId, shiftDate, operators }`, at the shift's start, before its `operator` events) and `tool-breakage` (`{ machineId, action, cycles, ignored? }`) events. Only runs with such an action write them.

## Scenario timelines (1.9)

Timelines of `config/scenarios/` (Phase 9 plan, "Scenario playback", ADR-0037; format and semantics in `docs/simulation-model.md`, "Scenario timelines"). The routes exist in every live run.

| Method and path         | Body                         | Success                      | Errors                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ----------------------- | ---------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/scenarios` | none                         | 200 `{ scenarios: [...] }`   | none                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `POST /api/v1/scenario` | `{ name }` or `{ timeline }` | 200 `{ scenario }`           | 404 no committed timeline of that name; 400 a document the schema refuses, a `dispatch` entry, an entry that doesn't fit the configuration or the run (unknown lot, a time outside the run, …), a `stock` key inline, more than 1,000 entries, extra fields; 409 the run is not idle, has a timeline already, has an injection, drift or console action already, an earlier load failed part way, the timeline names another seed, start or production mode, or the run has finished; 413 a body over 512 KiB |
| `GET /api/v1/scenario`  | none                         | 200 `{ scenario }` or `null` | none                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

- **`GET /scenarios`:** `{ name, description }` per committed timeline (`SIM_SCENARIOS_DIR/<name>.yaml`, sorted; `description` null when the file doesn't parse).
- **`POST /scenario`** loads a committed timeline by `name`, or a timeline document given inline as `timeline` (the YAML as JSON, without `stock`), **only while the run is idle** (`SIM_AUTOSTART=false`, before the first resume or step) and has none yet: one timeline per run. It is also refused once an injection, drift or console action has been posted, even while idle: the headless run of the timeline would give those after the timeline's entries, so post them after loading, or put them in the timeline. A timeline has at most 1,000 entries (`MAX_TIMELINE_ENTRIES`), and times finer than a millisecond are refused (the simulation's unit), not truncated. Its `seed`, `start` and `production` must be the run's; `days` and `config` describe the headless run (the live run keeps its own configuration, `SIM_CONFIG_DIR` and `SIM_STOCK`). Every plant entry is accepted at once, at the start time, in the headless order (injections, then console actions, each in timeline order), so their ids are the ones `GET /faults/injections`, `/faults/drifts` and `/actions` list. Nothing is accepted unless everything is checked; should the line still refuse an entry part way (a check missing in the loader), the load answers 409 and every later load is refused too (restart the run), since the entries before it stay accepted. `dispatch` entries are **headless only**: in a live orders run the MES dispatches through `LoadOrder`.
- **Infrastructure entries:** `opcua-offline` (`machine`, optional `until`) and `modbus-silent` (optional `until`) do what `POST /faults/opcua/{machine}` and `/faults/modbus` do, at their simulation time, and undo it at `until`; `speed` sets the speed and `pause` pauses the run at its time (resume with `POST /resume`). Each is applied once the simulation has processed every event at or before its time; none touches the plant model, so the event log is the one a headless run of the same timeline writes, at any speed. The pacer sets its timer for the next cue as for the next event, so a cue fires on time between sparse events (up to the timer's lateness); a speed cue re-anchors where the paced clock is, so it never jumps or goes back; a pause cue leaves the simulation time exactly at its time. A step that reaches a cue's time (the event it processes is at or after it) applies the cue after that event; a pause cue then changes nothing, the run being paused already. Fault windows of one device in a timeline must not overlap (400). A window's `until` sets the device back whatever set it before: it also ends an outage started by hand with `POST /faults/opcua/{machine}` or `/faults/modbus`, and a manual call in the window is undone at `until` or overridden at `at`.
- **`scenario`:** `{ name, description, entries }`; `name` is null for an inline timeline. Each entry is `{ entry, action, at?, status, id? }`: `entry` its place in the document (`timeline[3]`), `at` absent for `operators-absent`, `id` the injection's or console action's id. `status` is the injection's (`scheduled`, `held`, `applied`), the drift's (`scheduled`, `active`, `ended`) or the console action's (`scheduled`, `applied`, `ignored`; `planned` for an absence); an infrastructure entry is `scheduled`, then `applied`, or `active` and `ended` when it has an `until`.

## WebSocket: plant events

`GET /api/v1/events` upgrades to a WebSocket. Every plant event is sent as one text message in exactly the format of a headless event-log line (`schema: sim-event/1`, run-wide `seq`, ISO `at`, sorted keys; see `docs/simulation-model.md`, Event log).

- Events are not replayed: a client receives the events emitted after it connects. A gap in `seq` means the client missed events.
- The stream is read-only. A client that sends a message is closed with code 1003.
- A client whose unsent data exceeds 4 MB is disconnected (terminated, without a close frame, which a stalled client couldn't read) instead of being buffered without bound. It detects the gap through `seq` when it reconnects.

## Configuration (environment)

The simulator validates its environment at start-up. With any invalid value it names each offending variable and exits with status 2. Empty variables count as unset.

| Variable            | Default                              | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SIM_SEED`          | 1                                    | Random seed, decimal digits, 0 to 2³²−1                                                                                                                                                                                                                                                                                                                                                                                     |
| `SIM_SPEED`         | 60                                   | Speed, 0.5–60                                                                                                                                                                                                                                                                                                                                                                                                               |
| `SIM_START`         | `2026-10-12T06:00:00+03:00`          | Simulation start, ISO 8601 with an offset                                                                                                                                                                                                                                                                                                                                                                                   |
| `SIM_CONFIG_DIR`    | `config/plant` in the repository     | Plant configuration directory                                                                                                                                                                                                                                                                                                                                                                                               |
| `SIM_AUTOSTART`     | `true`                               | `false` starts idle; the run begins with `POST /api/v1/resume`                                                                                                                                                                                                                                                                                                                                                              |
| `SIM_PRODUCTION`    | `schedule`                           | `orders` (#172): the CNCs run only the jobs `LoadOrder` gives them                                                                                                                                                                                                                                                                                                                                                          |
| `SIM_STOCK`         | `SIM_CONFIG_DIR/stock.yaml`          | Another stock file (#196), e.g. a golden scenario's own `stock.yaml`                                                                                                                                                                                                                                                                                                                                                        |
| `SIM_TIMELINE`      | none                                 | A timeline loaded before the run starts (#235): a name of `SIM_SCENARIOS_DIR` or a file path; refused as `POST /scenario` refuses, as a start-up error (exit 2)                                                                                                                                                                                                                                                             |
| `SIM_SCENARIOS_DIR` | `config/scenarios` in the repository | The committed timelines (`GET /scenarios`, `POST /scenario` by name)                                                                                                                                                                                                                                                                                                                                                        |

## Shutdown

On SIGTERM or SIGINT the simulator:

1. stops the pacer and flushes and closes the live event log (`SIM_EVENT_LOG`);
2. closes the control API, terminating open WebSockets so that a client which stopped reading can't hold it up, and shuts down the OPC UA servers at the same time;
3. exits with status 0 (SIGTERM) or 130 (SIGINT).

If that takes longer than 10 s, it exits with status 1.
