# Runbook

How to start, stop and reset the system and run scenarios. Updated whenever operations change.

## Prerequisites

- Node.js 26 (`nvm use` reads `.nvmrc`)
- pnpm 11 or newer installed globally; it switches itself to the version pinned in `package.json`
- Docker with Compose

## Check the workspace

```bash
pnpm install
pnpm verify
```

`pnpm install` also installs a git pre-commit hook (lefthook) that formats and lints the files you stage. To skip it for one commit in an emergency: `git commit --no-verify`. CI runs the same checks (from #4).

## Run the simulator headless

Runs the plant as fast as possible, with no network servers, and writes an event log and a ground-truth summary (plan section 4).

```bash
pnpm sim:headless --seed 42 --days 7 --out runs/week-42
```

| Option     | Default                     | Meaning                                                                                                                                         |
| ---------- | --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `--seed`   | 1                           | Master seed: the same seed, config and options always give byte-identical output                                                                |
| `--days`   | 7                           | Simulated duration                                                                                                                              |
| `--start`  | `2026-10-12T06:00:00+03:00` | Simulation start, ISO 8601 with an offset or `Z` (a time without an offset is rejected, so the result never depends on the machine's time zone) |
| `--config` | `config/plant`              | Plant configuration directory                                                                                                                   |
| `--out`    | `runs/latest`               | Output directory (`runs/` is git-ignored)                                                                                                       |

Output:

- `events.jsonl`: one JSON object per line. The first line is the run header (`sim-run/1`: seed, start, end, SHA-256 of the configuration); every other line is an event (`sim-event/1`).
- `summary.json`: the ground truth (`sim-summary/2`): time in every state per machine, in total and per shift instance; cycles per result; parts started, finished and scrapped by reason; remaining quantity per lot; and the OEE section (inputs per machine, shift bucket and UTC hour; A, P, Q and OEE per machine, work center and shift bucket).
- `trace.json` (#208): the traceability and SPC ground truth (`sim-trace/1`): every unit's records with lots, operator, leak reading and carton (hashed), lots forward, cartons, the leak test's control limits, points (hashed) and signal episodes, and per leak-test drift its first episode and the counterfactual readings.
- `line-oee.json` (#230): the order and line OEE ground truth (`sim-line-oee/1`): the bottleneck per product, planned stops, each order's in-progress time, the line throughput OEE per UTC hour and shift bucket, and per order its order OEE over its job windows, first-pass yield and line OEE.

`--scenario NAME` runs a golden scenario instead (its seed, span, configuration, stock and injections); `--end ISO-8601` (#208, with `--scenario` or `--timeline`) stops it earlier, e.g. `pnpm sim:headless --scenario quality-01 --end 2026-10-12T14:00:00+03:00` for the shift-A reference of the live `quality` pass (its event log is a prefix of the full run's). `node apps/simulator/src/headless/drift-search.ts quality-01 --from … --to …` reruns probe P4's search of the drift's start (`docs/simulation-model.md`).

`--timeline NAME` (#235) runs a scenario timeline of `config/scenarios/` (`--timeline FILE` any timeline file, relative to where `pnpm` was started), with its own seed, span and configuration; `--end` works as with `--scenario`. Its infrastructure entries (`opcua-offline`, `modbus-silent`, `speed`, `pause`) are checked and left out, since they don't touch the plant model; a `dispatch` entry needs `production: orders`. Example: `pnpm sim:headless --timeline monday-breakdown-and-recovery`. The format is in `docs/simulation-model.md`, "Scenario timelines".

A week takes about 0.2 s and about 6 MB of events. The files are written under temporary names and renamed at the end, so a failed run never leaves a mix of old and new files. Invalid options exit with status 2, other failures with status 1. The event and summary formats are described in `docs/simulation-model.md`.

## Run the simulator live

Runs the plant paced to wall time × speed and prints every machine state change:

```bash
pnpm sim:live --speed 60
```

Options: `--seed` (default 1), `--speed` (0.5–60, default 60), `--start` (ISO 8601 with an offset), `--config`. Ctrl+C stops it. At 60×, one shift (8 h) takes 8 minutes. For pause, resume, step and speed control, use `pnpm sim:serve` and its control API.

## Serve the plant: OPC UA and the control API

Runs the plant live and exposes the five OPC UA machines (contract: `docs/contracts/opcua-address-space.md`), the WSH-01 washer on Modbus TCP port 5020 (contract: `docs/contracts/modbus-register-map.md`) and the control API (contract: `docs/contracts/simulator-control-api.md`):

```bash
export SIM_CONTROL_TOKEN=$(openssl rand -hex 16)   # required since #237 (control API 1.11)
# OPC UA SignAndEncrypt (#239, ADR-0038): run the pki step once into ./.pki (ignored by Git), then
# give the simulator its folder and the two users' passwords.
PKI_SIMULATOR_DIR=$PWD/.pki/simulator PKI_GATEWAY_DIR=$PWD/.pki/gateway PKI_TOOLS_DIR=$PWD/.pki/tools \
  pnpm --filter @shopfloor/pki pki
export OPCUA_PKI_DIR=$PWD/.pki/simulator
export OPCUA_GATEWAY_PASSWORD=$(openssl rand -hex 16) OPCUA_READER_PASSWORD=$(openssl rand -hex 16)
pnpm sim:serve
```

Without the pki step's certificates the simulator refuses to start (`own/certs/certificate.pem is missing: run the pki step first`). `OPCUA_SECURITY=none` serves the old anonymous None endpoints instead (no certificate, no users, methods open), for a quick local look only; Compose never runs that way.

Configuration comes from environment variables, validated at start-up. Examples: `SIM_SPEED=30`, `SIM_SEED=7`, `SIM_AUTOSTART=false`, `SIM_PRODUCTION=orders` (#172: the CNCs run only the jobs OPC UA `LoadOrder` gives them; `schedule` is the default), `SIM_STOCK=apps/simulator/golden/<scenario>/stock.yaml` (#196: a scenario's own stock in place of `config/plant/stock.yaml`), `SIM_TIMELINE=monday-breakdown-and-recovery` (#235: a timeline of `config/scenarios/` loaded before the run starts; its seed and start must be the run's, so here with `SIM_SEED=20261012`; `POST /api/v1/scenario` loads one into an idle run instead), `SIM_EVENT_LOG=runs/live.jsonl` (#235: the live event log, the headless `events.jsonl` without its header), `OPCUA_PORT_OFFSET=100`, `CONTROL_PORT=4800`. The full list is in the contract.

```bash
SIM_SPEED=30 SIM_AUTOSTART=false pnpm sim:serve
```

Control the run from another terminal. Every route but `/health/*` and `/metrics` needs the token (#237: 401 without it, reads included); pass it on stdin so it stays out of the process list:

```bash
printf 'Authorization: Bearer %s\n' "$SIM_CONTROL_TOKEN" | curl -s -H @- -X POST localhost:4800/api/v1/resume
```

The examples below pass it with `-H` for brevity (it then shows in the process list; the stdin form above doesn't). The other commands are `POST /api/v1/pause`, `POST /api/v1/step`, `PUT /api/v1/speed` with a JSON body `{"speed": 10}`, and `GET /api/v1/status`. Plant events stream over a WebSocket at `ws://localhost:4800/api/v1/events`; health is at `/health/live` and `/health/ready`, and metrics at `/metrics`.

- Connect an OPC UA client with SignAndEncrypt (`Basic256Sha256` or `Aes128_Sha256_RsaOaep`) as `opcua-reader` (`OPCUA_READER_PASSWORD`), presenting a certificate the servers pin: the tools certificate and key in `.pki/tools/own/` (its URI is `urn:orbis-components:shopfloor-twin:tools`), (the pki step owns every `trusted/certs` and removes a certificate added there by hand on its next run). The client must trust the servers' certificates (`.pki/tools/trusted/certs`). `opcua-reader` reads, browses and subscribes; no variable is writable (`BadNotWritable`, address space 1.3), and `LoadOrder` and `LoadProgram` answer it `BadUserAccessDenied` (only `opcua-gateway` may call them, address space 1.3). Read the washer with any Modbus TCP client, unit id 1, holding registers (function 3).
- `curl -s -H "Authorization: Bearer $SIM_CONTROL_TOKEN" -X POST localhost:4800/api/v1/faults/modbus -H 'content-type: application/json' -d '{"silent": true}'` makes the washer stop answering, to exercise a poller.
- Each server uses the certificate the pki step made in `$OPCUA_PKI_DIR/<machine>` and never makes one (with `OPCUA_SECURITY=none`, node-opcua makes one there on first start, as before #239).
- Logs are JSON lines (pino). `LOG_LEVEL=warn` keeps only warnings and errors.
- Ctrl+C or SIGTERM stops the run, closes the API and shuts the servers down. An invalid environment exits with status 2.
- After changing a route, regenerate the OpenAPI description with `pnpm --filter @shopfloor/simulator openapi`. A test fails while it is out of date.

## Run the edge gateway

The gateway publishes to the broker of the stack (`pnpm stack:up` first). It subscribes to the five OPC UA machines (the simulator of the stack, or `pnpm sim:serve`) and polls the WSH-01 washer over Modbus TCP, and publishes their state, cycles, alarms and telemetry to the UNS. From Phase 7 (#173, ADR-0029) it also executes the MES's `cmd/load-order` commands on the CNCs (OPC UA `LoadOrder`) and answers them on `cmd-res/load-order`; it publishes the CNCs' job facts on `events/job` (orders mode).

```bash
MQTT_PASSWORD=<MQTT_GATEWAY_PASSWORD from .env> OPCUA_PKI_DIR=$PWD/.pki/gateway \
  OPCUA_GATEWAY_PASSWORD=<the simulator's OPCUA_GATEWAY_PASSWORD> pnpm --filter @shopfloor/edge-gateway start
```

The gateway connects with SignAndEncrypt as `opcua-gateway` (#239, ADR-0038), presenting the certificate the pki step made in `OPCUA_PKI_DIR` (see "Serve the plant" for the step) and trusting only the server certificates pinned there; without its certificate it refuses to start. `OPCUA_SECURITY=none` connects anonymously over None, to a simulator started the same way.

- Environment: `GATEWAY_ID` (default `gw-01`), `MQTT_URL` (`mqtt://127.0.0.1:1883`), `MQTT_USERNAME` (`gw-01`), `MQTT_CMD_USERNAME` (`gw-01-cmd`, the command connection's user; the broker binds `gw-01` and `gw-01-cmd` to these users, ADR-0039), `MQTT_PASSWORD` (required, both users), `OPCUA_HOST` (`localhost`), `OPCUA_PORT_OFFSET` (0), `OPCUA_PKI_DIR` (`.pki-gateway`, the pki step's gateway folder: its certificate and key and the pinned server certificates), `OPCUA_SECURITY` (`sign-and-encrypt`; `none` for a None simulator), `OPCUA_GATEWAY_PASSWORD` (required with `sign-and-encrypt`), `TELEMETRY_SAMPLING_MS` (1000), `MODBUS_HOST` (`127.0.0.1`), `MODBUS_PORT` (5020), `MODBUS_POLL_MS` (250), `BUFFER_PATH` (`.buffer/gateway.db`, the store-and-forward file), `BUFFER_MAX_MESSAGES` (200000), `GATEWAY_CALL_DEADLINE_MS` (5000, the deadline of each OPC UA request of a command), `GATEWAY_CMD_SESSION_EXPIRY_S` (3600, the command session's expiry at the broker), `HTTP_HOST` and `HTTP_PORT` (`127.0.0.1:4900`; the stack's gateway is not published since #241, `pnpm stack:up:dev` publishes it there), `PLANT_CONFIG_DIR`, `LOG_LEVEL`. An invalid environment exits with status 2, and secrets are never echoed.
- `GET /health/live`, `/health/ready` (ready while both broker sessions are up and the command subscriptions are granted) and `/metrics` (`gateway_device_connected{machine}`, `gateway_device_facts{machine}`, `gateway_cycle_trace_dropped_total{machine}` (OPC UA cycles published without `lots` or `operator` the UNS contract can't carry, #197), `gateway_published_messages`, `gateway_buffer_messages`, `gateway_buffer_dropped_messages`, and for commands `gateway_command_deliveries`, `gateway_command_calls`, `gateway_command_results{result}`, `gateway_command_pending{stage}` with `queued` and `settling`, `gateway_command_call_timeouts` (calls whose deadline passed without an answer, #178), and `gateway_command_settle_acceptances`, which should stay 0: above it, the gateway's and the simulator's clocks disagree).
- Commands: the gateway's second broker connection has client id `gw-01-cmd` and a persistent session, so commands published while it is down wait at the broker for up to `GATEWAY_CMD_SESSION_EXPIRY_S`. Each delivery is recorded in `BUFFER_PATH` (table `command_inbox`) before the broker gets its acknowledgement, and definitive answers are kept in `command_result`: `sqlite3 .buffer/gateway.db 'SELECT command_id, expires_at, json_extract(value, "$.result") FROM command_result'`. A command whose outcome the gateway can't learn is answered `unknown` (log level `warn`) and settled again every 5 s; `gateway_command_pending{stage="settling"}` counts them. A finished simulator run answers every call as "not running", so such a command stays `unknown` until the simulator restarts. Deleting `.buffer/` loses the inbox too: commands acknowledged and not yet answered are then never answered (the MES's `failed` margin reports them).
- While the broker is down, `gateway_buffer_messages` grows; it drains after the broker returns. Deleting `.buffer/` throws away whatever wasn't delivered yet.
- Data-quality incidents (sequence gaps, disconnects) go to `orbis/gebze/_sys/edge-gateway/gw-01/incidents` and to the log at `warn`.
- Try a disconnect: `curl -s -H "Authorization: Bearer $SIM_CONTROL_TOKEN" -X POST localhost:4800/api/v1/faults/opcua/cnc-01 -H 'content-type: application/json' -d '{"offline": true}'`, then `{"offline": false}`. The washer: `curl -s -H "Authorization: Bearer $SIM_CONTROL_TOKEN" -X POST localhost:4800/api/v1/faults/modbus -H 'content-type: application/json' -d '{"silent": true}'`.
- Watch the status: `docker compose exec broker mosquitto_sub -i dev -u dev -P <MQTT_DEV_PASSWORD> -t 'orbis/gebze/_sys/#' -v`.

The gateway's tests start a real Mosquitto with Testcontainers, so Docker must be running. They also start the simulator (and, end to end, the gateway) as child processes on ports chosen at runtime, so several runs, worktrees or agents can share the machine (#212): Modbus, control API, gateway HTTP and proxy ports are OS-assigned, and the OPC UA servers and their TCP proxies each take a block of five consecutive ports at a random offset (`OPCUA_PORT_OFFSET` 1000–9990, ports about 5841–14835) whose every port is checked free before use; a process that exits before it is ready (a port taken in the meantime) is started again (on new ports, unless it is a restart where its clients left it), and every child still running is killed when the test process exits. Without `DOCKER_HOST` the tests use the active `docker context`, which covers Colima and similar setups.

## Run the MES server

**Upgrade order for UNS contract 1.4 (#197):** deploy the MES (migrations `0028`, `0029`; ingest accepting `lots` and `operator` on cycles) before the edge gateway. An older MES refuses every 1.4 cycle that carries the fields (`invalid-payload`), which leaves gaps in the device sequences; a 1.4 MES with an older gateway just stores cycles without them. Compose starts both from the same tag, so this matters only for a partial upgrade.

`mes-server` (Phase 4) runs on the stack's TimescaleDB and broker and subscribes to the UNS (#95). Start the stack with `pnpm stack:up:dev` first: since #241 (ADR-0039) `pnpm stack:up` no longer publishes the database (5442 below), only the dev override `compose.dev-ports.yml` does (stop the stack's own `mes` with `docker compose stop mes` while yours runs, or give yours another `HTTP_PORT` and `MQTT_CLIENT_ID`). Since #169 it no longer migrates itself (ADR-0016 amended, ADR-0027): the `migrate` step does, as the bootstrap superuser, and the MES connects as `mes_app` and waits (not ready, a warning every 30 s) until the database's migration history equals its own. Outside Compose, migrate first, then start:

```bash
DATABASE_URL=postgres://shopfloor:<DB_PASSWORD>@127.0.0.1:5442/shopfloor \
  DB_APP_PASSWORD=<DB_APP_PASSWORD from .env> pnpm --filter @shopfloor/mes-server migrate
DATABASE_URL=postgres://mes_app:<DB_APP_PASSWORD>@127.0.0.1:5442/shopfloor \
  MQTT_PASSWORD=<MQTT_MES_PASSWORD from .env> pnpm --filter @shopfloor/mes-server start
```

(`pnpm stack:up` runs the `migrate` service already; the first command matters only against a database no stack has migrated.)

- Environment: `DATABASE_URL` (required, never echoed), `MQTT_URL` (`mqtt://127.0.0.1:1883`, never echoed), `MQTT_USERNAME` (`mes`), `MQTT_CMD_USERNAME` (`mes-cmd`, the command connection's user), `MQTT_PASSWORD` (required: `MQTT_MES_PASSWORD` from `.env`, both users), `MQTT_CLIENT_ID` (`mes-server`; the broker accepts only this id for `mes` and `{MQTT_CLIENT_ID}-cmd` for `mes-cmd`, ADR-0039), `MQTT_SESSION_EXPIRY_S` (604800, 7 days), `INGEST_GAP_GRACE_MS` (30000), `HTTP_HOST` and `HTTP_PORT` (`127.0.0.1:4700`), `MIGRATIONS_DIR` (`db/migrations`), `LOG_LEVEL`.
- `GET /health/live`, `/health/ready` (database answers, migrations are applied, and the UNS subscription is granted) and `/metrics` (`mes_ingest_messages_total{outcome}` with outcomes `stored`, `duplicate`, `rejected`, `anchor`, `status`, `retained`; `mes_ingest_incidents_total{origin}`; `mes_ingest_cycle_trace_dropped_total{equipment}` (cycles stored without refused trace fields, recorded as `trace-dropped` in `ingest.rejected_message`, #197); `mes_ingest_store_errors_total`; `mes_ingest_suspensions_total`; `mes_ingest_subscribed`; from #245 (ADR-0040) `mes_ingest_lag_seconds{class}` (gateway `receivedAt` to the commit, observed after the commit and only for live device facts (`state`, `cycle`, `alarm`, `job`, `telemetry`) stored for the first time over the session, never for `deliver()`'s replays; buckets 5 ms to 60 s with edges at 0.25, 1 and 5 s), `mes_ingest_lag_excluded_total{reason}` (`retained`, `anchor` (a retained state or alarm delivery), `snapshot`, `duplicate`), `mes_ingest_lag_max_seconds` (the largest lag of the last 5 to 10 s: a histogram has no max), `mes_ingest_oldest_pending_age_seconds` (now minus the `receivedAt` of the delivery the MES is handling, 0 when none: behind a backlog, the backlog head's age) and, as a diagnostic, `mes_ingest_pending_messages` (PUBLISH packets read from the session's socket and not yet committed; at most the receive maximum of 100, so a backlog beyond it waits in the broker, which reports no per-client queue)).
- The MES keeps a persistent broker session (client id `mes-server`): while it is stopped, the broker queues up to 100,000 messages for it (about one hour of the plant at 60×), delivered on the next start; the MES stores about 1,000 messages/s, so a full queue drains in about two minutes. Only one MES may use the client id; a second one takes the session over. Since #240 (ADR-0039) the broker binds `mes-server` to the user `mes` (and `mes-server-cmd` to `mes-cmd`) and refuses any other client id for them, so the MES must keep `MQTT_CLIENT_ID=mes-server`, and no other broker user can take the session: every user is bound to its own client id. To drop the session (and its queue), stop the MES and connect once with a clean start under its id: `docker compose stop mes`, then `docker compose exec broker mosquitto_sub -u mes -P <MQTT_MES_PASSWORD> -i mes-server -t orbis/none -E`; or reset the broker volume (`pnpm stack:reset`).
- What arrived: `SELECT reason, count(*) FROM ingest.rejected_message GROUP BY 1;` lists rejected messages; `SELECT * FROM ingest.data_quality_incident WHERE closed_at IS NULL;` lists open gaps and gateway incidents (contract: `docs/contracts/uns.md`, "Consumer: MES ingest").
- Alarm anchors and snapshots (#141): retained alarm deliveries land in `ingest.alarm_anchor`, the gateway's resync snapshots in `ingest.alarm_snapshot`; both count as `anchor` in `mes_ingest_messages_total`. Rows of an older device epoch than the newest one known for their equipment are kept with `stale = true` and never used, so after a simulator restart the old run's retained alarms never show as active: `SELECT equipment, epoch, code, seq, transition, stale FROM ingest.alarm_anchor ORDER BY 1, 2, 3;` and `SELECT equipment, device_epoch, as_of_seq, active, stale FROM ingest.alarm_snapshot ORDER BY 1, 2;`. To clear the old run's retained alarms from the broker itself, reset its volume (`pnpm stack:reset`).
- Alarm occurrences (#142, ADR-0024): the `alarms` module derives one occurrence per device raise, keyed `{equipment}~{epoch}~{seq}`, from ingest's alarm facts, the retained anchors and the resync snapshots, and stores it in `alarms.alarm_occurrence` with its end (`cleared`; `lost` when a snapshot showed the code inactive after the clear went missing; `superseded` by the next raise of the point; `epoch-ended` by a newer run). A snapshot is applied only once the device stream is settled up to its `asOfSeq` (no open gap below it). At start-up it compares `alarms.occurrence_source` with ingest's alarm fact counts, anchors and snapshots and derives again what differs (log line `alarm occurrences caught up` with the number `derived`). Nothing an operator does is stored there; to derive everything again, stop the MES, `TRUNCATE alarms.alarm_occurrence, alarms.occurrence_source;` and start it (revisions in `alarms.kpi_revision` are kept). Active alarms: `SELECT equipment, code, raised_at FROM alarms.alarm_occurrence WHERE ended_at IS NULL ORDER BY raised_at;`.
- Alarm KPI finality and revisions: a KPI hour of a scope (the plant, a position or an equipment) is final once every equipment of the scope is final through its end plus `fleetingMs` (1 s), or its epoch is closed; a silent machine keeps it provisional, as for OEE. A late fact (a gap filled after it was written off, a snapshot closing a lost clear, the real clear replacing it) raises the revision of every final hour it can change, in every scope of its equipment: `SELECT * FROM alarms.kpi_revision ORDER BY hour;` (log line `late alarm facts: final KPI hours revised`). No row means revision 0.
- A storage failure is logged (`mes_ingest_store_errors_total`). Only a data or integrity error (SQLSTATE classes 22, 23, 54: the database refuses this message for good) is recorded with reason `unstorable` and acknowledged. Any other error (database down, a lock held too long, a migration in progress) is retried for a few seconds; then the MES drops its broker session without acknowledging anything unstored (`mes_ingest_suspensions_total`, readiness 503), waits, reloads its cursors and reconnects, with a growing pause while the failure repeats. The broker queues meanwhile, so an outage shorter than the queue (about an hour) loses nothing (ADR-0017).
- State intervals (#96, ADR-0018): at start-up the `equipment` module compares `equipment.interval_source` with ingest's tables and recomputes what differs (log line `equipment intervals caught up` with the number `rebuilt`), then follows ingest. Every piece lies inside one UTC hour and one shift bucket; the open interval is stored up to the plant watermark and flagged `provisional`. Time per state in a shift: `SELECT equipment, state, sum(end_time - start_time) FROM equipment.equipment_state_interval WHERE shift_key = '2026-10-12/A' GROUP BY 1, 2 ORDER BY 1, 2;` (per epoch after a simulator restart). To recompute everything from ingest's tables, stop the MES, `TRUNCATE equipment.interval_source;` and start it again.
- Hourly aggregates (#118, ADR-0022): `equipment.state_hourly` and `ingest.cycle_hourly` are TimescaleDB continuous aggregates without refresh policies. The MES refreshes them itself, about a second after a change, on two connections of its own (log line `continuous aggregate refreshed` with the window and its duration, at `info`), and once at start-up from the beginning (`catchUp: true`). Rows of the open hour are read from the raw tables. A row written by hand below an aggregate's watermark is not seen until the next MES start (or `CALL refresh_continuous_aggregate('equipment.state_hourly', NULL, '<end>');`). Never add a refresh policy: its window follows the wall clock, not simulation time. The start-up line `cycle counts of final hours checked` lists final hours whose cycle count changed while the MES didn't hear of it (their revision went up).
- API (#97, ADR-0019), on `HTTP_HOST:HTTP_PORT` (`127.0.0.1:4700`; in Compose the MES's port is not published since #241: use the web front, `https://localhost:8443/api/v1/…` with `curl --cacert dev-ca.pem` ("HTTPS and the dev CA" below), or `pnpm stack:up:dev`, which publishes the MES on `127.0.0.1:4700` again; the `127.0.0.1:4700` examples below are for that or an MES started by hand), read-only except downtime coding (#121, below), a session on every route but the login (`MES_AUTH`, on by default since #170; "Identity" below), no CORS (the web app is served from the same origin, by the `web` container in Compose); errors are problem details (`application/problem+json`). Until the modules have started, `/api/v1/*` answers 503. The `curl` examples below need a session cookie: log in first and add `-b jar` ("Identity", below).
  - Environment: `HTTP_ALLOWED_HOSTS` (`localhost,127.0.0.1,[::1]`; `Host` names answered, `*` for any, against DNS rebinding), `HTTP_ALLOWED_ORIGINS` (none; extra origins a WebSocket may connect from, or a write may come from, besides the MES's own host), `MES_WRITES` (`on`), `API_DB_POOL_SIZE` (4; the API's own read pool, so reads never hold up ingest), `API_STATEMENT_TIMEOUT_MS` (5000; a read over it answers 503). A 403 with `host not allowed` or `origin not allowed` means the request came through a name or page not on these lists.
  - `GET /api/v1/equipment` and `/api/v1/equipment/{id}`: master data with hierarchy and current state (`current` is null for equipment that never reported).
  - `GET /api/v1/equipment/{id}/intervals?from&to`: state intervals (stored hour and shift pieces merged back, clipped to the range; at most 7 days; when `truncated`, continue with `from=next`).
  - `GET /api/v1/equipment/{id}/telemetry/metrics`, and `/telemetry?metric&from&to&maxPoints`: metrics with units, and series decimated into at most `maxPoints` time buckets (min, max, avg, count; at most 31 days, 8 metrics, 5,000 buckets).
  - `GET /api/v1/shifts/{date}/{shift}/totals?equipment`: time per state in a shift (for example `/api/v1/shifts/2026-10-12/A/totals`).
  - `GET /api/v1/plant`: site and plant clock (watermark of the newest epoch).
  - OEE (#120, ADR-0021), computed on read by the `oee` module from the hourly aggregates and stop pieces (nothing is stored):
    - `GET /api/v1/oee?scope=equipment|work-center&id&bucket=hour|shift&from&to[&epoch]`: buckets with inputs, A, P, Q and OEE as exact fractions and four-decimal strings, totals, losses, `unplanned`, `anomaly`, `final`, `provisionalMs`, `revision` and `incidents` (hours: at most 7 days; shifts: whole shifts, at most 31 days). Without `epoch`, an equipment's newest epoch with data in the range; a work center uses one epoch for all its machines, the newest any of them has. A work center sums its machines' inputs.   - Downtime coding, the MES's first write (#121, ADR-0021 amended, ADR-0023):
    - `PUT /api/v1/downtime/{id}/coding` with `{"segments":[{"from","to","reason","comment"?}],"version"}` replaces the codings of one record (`{equipment}~{epoch}~{startMs}`): segments inside the record (an open one: up to the watermark), not overlapping, each with an active reason other than UNCODED; `[]` clears them; two segments are a split. `version` is the record's `version` from `GET /api/v1/downtime` (one per machine and epoch): 409 means someone else coded (or a re-cut clipped codings) meanwhile; read again and retry. 422: a segment outside the record, overlapping, or a reason that is unknown, inactive or UNCODED.

    - **Write guards** on every non-GET request under `/api/v1` (ADR-0023): allowed `Host`; `MES_WRITES=off` → 405; an `Origin` header, of the MES's own host and port (any scheme) or in `HTTP_ALLOWED_ORIGINS`, else 403; `Sec-Fetch-Site: same-origin` when sent, else 403; `Content-Type: application/json`, else 415; at most 16 KiB (413); 10 writes per second for all clients together, bursts of 20 (429 with `Retry-After`). Every write's answer has `X-Request-Id`, the id in the audit and in the MES log.

  - Alarms (#142, #143, ADR-0024):

The views are the operator's lists and partition the occurrences: `active` (default) not acknowledged and not closed (a cleared occurrence stays here until acknowledged), `acknowledged` acknowledged and still active, both with the point not shelved; `shelved` not closed with the point shelved; `history` closed (ended and acknowledged, or ended by a newer epoch). Acknowledging is monotonic, so there is no version: an occurrence acknowledged already answers `changed: false` and adds no audit entry. `POST /api/v1/alarms/{id}/comments` with `{"text"}` (1–500 characters, append-only).
    - Shelving is per alarm point (equipment, code): `POST /api/v1/alarm-points/{equipment}/{code}/shelve` with `{"reason","durationMs","version"}` and `POST …/unshelve` with `{"version"}`. `version` is `shelf.version` from `GET /api/v1/alarm-points` (0 for a point never shelved); 409 means someone else changed the shelf, or it ended, meanwhile: read again and retry. `durationMs` runs in **plant time**, 1 minute to `maxShelveMs` (`config/plant/alarms.yaml`, 8 hours; longer is 422): `until` = the plant clock at the write + the duration. Once the plant clock passes `until`, the MES unshelves the point itself (`expire`, actor `system`; log `alarm shelf ended by the plant clock`); a newer plant epoch (a simulator restart) ends every shelf of the old one (`epoch-ended`), because plant time starts over. A paused simulator keeps a shelf for as long as it is paused. Shelving changes no KPI: every raise counts, shelved or not.
    - `GET /api/v1/alarms/operator-kpi?scope&id&bucket=hour|shift|range&from&to[&epoch]`: the operator measures (MES only, not reconciled, apart from `/alarms/kpi`): shelved and annunciated raises, time to acknowledge (count, sum, longest in ms of plant time; acknowledgements in a later epoch excluded), unacknowledged at the bucket's end and shelved time per point. Time to acknowledge belongs to the raise's bucket, so a late acknowledgement still changes a bucket with `provisional: false`; unacknowledged at the end counts shelved and cleared-but-unacknowledged occurrences too and is fixed once the bucket is over (#156). An unshelve made after a new epoch began is audited in the shelf's own epoch, at that epoch's last plant time.

    - `GET /api/v1/alarm-points?equipment&position&shelved=true`: every defined point (and any other with an active occurrence or a shelf) with its shelf and active occurrence; `GET /api/v1/alarm-points/{equipment}/{code}/audit`: the point's audit, newest first.
    - Tables: `alarms.occurrence_state` (acknowledgements, insert-only by a trigger), `alarms.alarm_shelf` (one row per point ever shelved, with its version) and `alarms.alarm_transition`, the append-only audit (ack, comment, shelve, unshelve, expire, epoch-ended; a trigger refuses UPDATE, DELETE and TRUNCATE). - Identity (#168, #170, ADR-0026; migration `0016`, schema `identity`):
  - Environment: `MES_AUTH` (`on`: a session on every `/api/v1` route but the login, and on the WebSocket; `off` is for one-off diagnosis only: reads and the WebSocket are then served without a session, while every write, and the session and password routes, still need a session and its permission, 401/403), `MES_COOKIE_SECURE` (`on` since #241, ADR-0039: the `Secure` cookie `__Host-sft_session`, as the browser reaches the MES through the HTTPS front; `off`, the plain `sft_session`, only for a browser on plain HTTP straight to the MES, such as the Vite dev server, and the MES logs a warning), `MES_BOOTSTRAP_ADMIN_PASSWORD` (optional, 12–128 characters, never echoed). Compose passes all three (`MES_AUTH` and `MES_COOKIE_SECURE` default to `on` there too). With `MES_AUTH=off` the MES logs a warning at start.
  - First admin: set `MES_BOOTSTRAP_ADMIN_PASSWORD` in `.env` and restart the MES; it creates the user `admin` (only when no enabled admin exists), which must change its password at first login. Or, without it: `printf '%s' "$PASSWORD" | DATABASE_URL=… pnpm --filter @shopfloor/mes-server user:create --username alice --role admin` (roles repeat: `--role supervisor --role quality`; `--must-change` makes the password temporary). In the stack: `docker compose exec -T mes node apps/mes-server/src/user-cli.ts --username alice --role admin < password.txt`. The password is read from stdin only (a terminal echoes it: pipe it).
  - **An existing dev stack after #170** (`MES_AUTH` was `off`, nobody has logged in yet): set `MES_BOOTSTRAP_ADMIN_PASSWORD` in `.env` (or create an admin with `user:create --role admin` as above), run `pnpm stack:up` again (the MES restarts with `MES_AUTH=on`), open <https://localhost:8443/login> (since #241; trust the dev CA first, "HTTPS and the dev CA"), log in as `admin` with that password and choose a new one, then create the users in **Users** (`/admin/users`). A leftover `MES_AUTH=off` in `.env` keeps the diagnosis mode: remove it. Until an admin exists, nobody can log in.
  - Log in from the shell, through the web front (#241; `dev-ca.pem` from `pnpm stack:ca`): `curl -s --cacert dev-ca.pem -c jar -H 'Origin: https://localhost:8443' -H 'Content-Type: application/json' -d '{"username":"alice","password":"…"}' https://localhost:8443/api/v1/session`, then `curl -s --cacert dev-ca.pem -b jar https://localhost:8443/api/v1/session` (user, roles, permissions, expiry). Log out: `curl -s --cacert dev-ca.pem -b jar -X DELETE -H 'Origin: https://localhost:8443' -H 'Content-Type: application/json' -d '{}' https://localhost:8443/api/v1/session`. Straight at an MES on `127.0.0.1:4700` (`pnpm stack:up:dev`), use `http://127.0.0.1:4700` and `-H 'Origin: http://127.0.0.1:4700'` instead (curl may keep a `Secure` cookie from its jar off plain HTTP: then pass it by hand, `-b "__Host-sft_session=<value>"`). Own password: `POST /api/v1/account/password` with `{"currentPassword","newPassword"}` (ends the user's other sessions). Users (`user:admin`): `GET /api/v1/users`, `POST /api/v1/users` (`{"username","roles","password"}`, temporary), `PUT /api/v1/users/{username}` (`{"roles"?,"enabled"?}`; disabling ends the user's sessions and sockets; the last enabled admin stays one), `POST /api/v1/users/{username}/password` (`{"password"}`, temporary; clears a lock).
  - Sessions: idle 60 min (`desk`) or 15 min (`terminal`), at most 12 h. Who logged in or failed (with the client address of each failure and lock): `SELECT at, username, action, after FROM identity.audit_log ORDER BY id DESC LIMIT 20;`.
  - **Login throttling** (#242, ADR-0039 "Login throttling"; checklist S5). Every failure is the same 401, whatever failed.
    - **Per (user, address):** five failed logins in a row from one client address lock the user **for that address** for 15 minutes; the right password from there is refused too, while the same user logs in from any other address. The address is the one nginx saw (`X-Real-IP`, believed only from nginx over the `edge` network); a request straight to the MES (`pnpm stack:up:dev`, 4700) is keyed by its own connection. **On a developer machine every host client reaches nginx from one address** (Colima's port forwarding), so the browser and anything else on the host share one pair. A normal user is reported `locked` (Users screen, `GET /api/v1/users`) while any of its addresses is locked.
    - **Per user, from all addresses together:** once a user has 10 or more failed logins in the last 15 minutes (n), an attempt within `min(2^(n − 10) s, 30 s)` of the last failure is answered **429** `urn:shopfloor:login-rate`, "too many failed logins for this user; try again later", with `Retry-After` (the remaining wait in whole seconds, rounded up), without checking the password, **except from an address that logged in as that user within those 15 minutes** (a browser that logged in recently keeps working). A 429 doesn't count as a failure. No counter locks the account as a whole, but **a sustained attacker on several addresses keeps the account at one judged attempt per 30 s for every address without a recent login**: a user coming from a new address then meets 429s and may wait several times 30 s. Remedy: an admin's password reset (below), which clears every failure. Through Colima every host client is one address, so on a developer machine an attacker on the host shares the browser's pair and exemption.
    - **Admins** are never locked, also not per address: from the fifth failure on, an attempt within the delay (1 s, doubling, at most 5 min; `next_attempt_at`) is answered **429** with `Retry-After`, without checking the password; the global delay above applies too.
    - **Login buckets** (in memory, per MES process): 5 per second, bursts of 10, per client address; 1 per second, bursts of 5, per (user name, client address); 10 per second, bursts of 20, for all logins together (about what the password hashes can do), not asked for an address that logged in as that user within 15 minutes. One address can't spend another's buckets, but **two attacker addresses at their 5/s caps fill the shared ceiling**: an honest login from a fresh address then gets through about 37 % of the time with 2 attacker addresses, 15 % with 4 and 27 % with 8 (each refusal a quick 429). Ways back in: log in from a browser that logged in within the last 15 minutes (it skips the ceiling); have an admin reset the password (Users, or `POST /api/v1/users/{username}/password`; the user CLI has only create and disable), which clears every failure; with no enabled admin left, restart the MES with `MES_BOOTSTRAP_ADMIN_PASSWORD` set: the bootstrap admin's upsert at start clears its failures (it runs only while no enabled admin exists). At most 10 logins wait for a password hash at once (3 per address); beyond that a login is answered 429 at once rather than queued (#264 re-review). Attempts inside a known wait are answered from memory without the database, and logins use a database pool of their own (two connections), so a flood of logins doesn't slow the rest of the API (`mes_db_pool_waiting{pool="login"}`).
    - **What an owner does:** a 429 needs no action: wait the `Retry-After` seconds (at most 30) and log in. For a lock: wait 15 minutes, log in from another address, or have an admin reset the password (**Users**, or `POST /api/v1/users/{username}/password`, a temporary password the user changes at the next login), which clears every lock and failure of that user. Without a working admin, as the superuser in the stack: `docker compose exec -T db psql -U "$DB_USER" -d "$DB_NAME" -c "DELETE FROM identity.login_address WHERE user_id = (SELECT id FROM identity.user_account WHERE username = 'alice'); DELETE FROM identity.login_failure WHERE user_id = (SELECT id FROM identity.user_account WHERE username = 'alice');"` (the MES role can do the same; nothing else needs a restart). What is locked: `SELECT u.username, a.address, a.failed_logins, a.locked_until FROM identity.login_address a JOIN identity.user_account u ON u.id = a.user_id WHERE a.locked_until > now();`; n per user: `SELECT u.username, count(*) FROM identity.login_failure f JOIN identity.user_account u ON u.id = f.user_id WHERE f.at > now() - interval '15 minutes' GROUP BY 1;`.
  - **Cookie scope on localhost:** browsers scope cookies by host, not port. A session set through `https://localhost:8443` (since #241: `__Host-sft_session`, `Secure`, host-only) is also sent to other `localhost` ports the browser treats as secure (Chromium counts `http://localhost` as such: a Vite dev server, the simulator's 4800, and with `pnpm stack:up:dev` the MES's 4700 and the gateway's 4900), and not to `https://127.0.0.1:8443`, a different host. **Open the app as `localhost`**, not `127.0.0.1`, and stay on one name. Firefox and WebKit were not probed (Chromium was).
  - Answers: 401 `urn:shopfloor:unauthenticated` (no or ended session, failed login), 403 `urn:shopfloor:forbidden` (the role lacks the permission; the matrix is `ROLE_PERMISSIONS` in `packages/contracts/src/identity.ts`), 403 `urn:shopfloor:password-change-required`, 422 `urn:shopfloor:password-rejected`, 409 `urn:shopfloor:user-exists`, 429 `urn:shopfloor:write-rate` (also per user: 5 per second, bursts of 10). 429 `urn:shopfloor:login-rate` (the login buckets and the user's delays above). The WebSocket closes with 4401 (no session) or 4403 (password to change). With `MES_WRITES=off` the login, logout and password change stay open.
- Database roles (#169, ADR-0027; migrations `0017`–`0019`):
  - `migrate` (`pnpm --filter @shopfloor/mes-server migrate`, or the Compose service `migrate`) connects as the bootstrap superuser (`DATABASE_URL` as `DB_USER`, its password in `PGPASSWORD`), creates or updates the roles `mes_owner` (no login: owns every schema, table, view and function), `mes_cagg` (no login: owns `equipment.state_hourly` and `ingest.cycle_hourly`) and `mes_app` (login, password `DB_APP_PASSWORD` when given, kept otherwise; a member of `mes_cagg` WITH INHERIT FALSE, SET TRUE), and runs the pending migrations under `SET ROLE mes_owner`. It never logs the password, and the `ALTER ROLE` runs with statement logging off.

The aggregate refresher runs `SET ROLE mes_cagg`, `CALL refresh_continuous_aggregate(…)`, `RESET ROLE` on its own connection (ADR-0022 amended). The grants per role and object: `DECLARED_GRANTS` in `apps/mes-server/src/db/grants.ts` and the "Roles and grants" table in `docs/data-model.md`.
  - Check: `docker compose exec db psql -U shopfloor -d shopfloor -c "SELECT usename, count(*) FROM pg_stat_activity WHERE datname = current_database() GROUP BY 1"` shows the MES's connections as `mes_app`; `\dp identity.*` its grants.
  - **A database from before #169** (everything owned by `DB_USER`) needs no manual step beyond `DB_APP_PASSWORD` in `.env` (below): the next `migrate` runs `0017`, which moves every schema, table, view, sequence and function to `mes_owner` and the two aggregates to `mes_cagg` object by object (`REASSIGN OWNED` can't: 2BP01), then `0018` copies every row of the three module audits into `identity.audit_log` (`legacy`, counts checked) and freezes two of them. If anything goes wrong there, `pnpm stack:reset` starts from an empty database.
  - One audit log (#169): every downtime coding, alarm acknowledgement, comment, shelve and unshelve and handover note write is a row of `identity.audit_log`, in the write's transaction, with the session's user and roles and `authenticated: true`; every write needs a session, also with `MES_AUTH=off`. Since #170 the requests have no `codedBy`, `actor` or `author` (sending one is 400); rows with a typed name and `authenticated: false` are from before #170. `SELECT at, username, roles, authenticated, action, entity_type, entity_id FROM identity.audit_log WHERE NOT legacy ORDER BY id DESC LIMIT 20;`. The history endpoints (`/downtime/{id}/audit`, a note's history) read it, legacy rows included; the alarm module keeps `alarms.alarm_transition` as its transition log (system expiry and epoch ends included).
  - `shifts.crew_assignment` (who is signed on at a work center during a shift) exists from `0019`; the terminal writes it from #177. Who is signed on now: `SELECT username, work_center, from_plant_at FROM shifts.crew_assignment WHERE to_at IS NULL;`. Operators' open activity on order operations: `SELECT order_id, operation, username, kind, reason FROM orders.operation_activity WHERE to_at IS NULL;`. An order that won't close (409 `sign-off-missing`): `SELECT operation, work_center, signed_off_by FROM orders.order_operation WHERE order_id = '…';` names the operations still to be signed off at their terminals.
  - **An aggregate that may have been edited** (anyone who could `SET ROLE mes_cagg`, the MES included, can change the materialised rows, and an incremental refresh leaves ranges the raw table never invalidated as they are; ADR-0027): rebuild it from the raw rows as the superuser, `docker compose exec db psql -U shopfloor -d shopfloor -c "CALL refresh_continuous_aggregate('equipment.state_hourly', NULL, NULL, force => true)"` (and the same for `ingest.cycle_hourly`), then restart the MES so its refresher reads the watermark again. If the aggregate itself was altered or dropped, `pnpm stack:reset` is the simple way back; by hand, recreate it from `0006` and repeat `0017`'s `ALTER MATERIALIZED VIEW … OWNER TO mes_cagg` and its `GRANT SELECT … TO mes_app` as `mes_cagg`.
- Migrations only: `DATABASE_URL=… DB_APP_PASSWORD=… pnpm --filter @shopfloor/mes-server migrate`. Status without changing anything: the MES's readiness (`/health/ready` 503 while it differs) and its log line `waiting for the database to be migrated` with the pending, unknown or changed files.
- A new migration is a new file `db/migrations/NNNN_<module>_<what>.sql`; it runs as `mes_owner` and grants `mes_app` what its objects need (`GRANT … TO mes_app` at its end, and `DECLARED_GRANTS` in the same change: a test compares them with the database). An applied file is never edited: `migrate` refuses to run and the MES stays not ready if one changed. A statement that can't run in a transaction (`CREATE INDEX CONCURRENTLY`) goes into a file marked `-- migrate:no-transaction`, written so that it can be rerun.
- The golden reconciliations also check the shift reports (#144): one `shift_instance` per scheduled shift (15 in `week-01`, 6 in `alarms-01`, also after a restart), and per shift the report's OEE, production, Pareto and alarm sections against the ground truth; the report is final exactly when its inputs are, with revision 0.
- End-to-end tests (`*.e2e.test.ts`) run apart from the others: `pnpm test:e2e`, one at a time; in CI they have their own job. In `mes-server` these are the golden-scenario reconciliations: `week-01` (about 6 minutes since #199), `alarms-01` (about 30 s), `orders-01` (about 2 minutes) and `quality-01` (about 5 minutes; the genealogy of `week-01`, `orders-01` and `quality-01` against `trace.json`, #199), each replayed from the headless simulator (`--scenario <name>`, injections included) through ingest into TimescaleDB, in order and shuffled with duplicates; intervals, OEE, downtime records and every alarm occurrence and alarm KPI must equal the ground truth. `pnpm test` reconciles a Friday with its night shift.
- The MES tests start their own TimescaleDB and Mosquitto with Testcontainers (the broker harness is shared with the gateway in `@shopfloor/test-kit/broker`).
- **Genealogy (#199, ADR-0034):** the MES imports the ERP's lot list (`GET /api/v1/lots`) at start and every `ERP_POLL_MS`; a lot no longer listed is kept `retired`. Incidents: `GET /api/v1/genealogy-incidents?open=true` (`unknown-lot`: a cycle names a lot the ERP doesn't list, closed by the next import that lists it; `serial-reused`: serials repeat across simulator runs, expected after a simulator restart on a dev stack; `material-mismatch`: a lot the BOM doesn't list for that operation and pass, judged once the unit's order is final). Trace answers say `final: false` with `notFinal` while a machine hasn't reported past the answer's latest record; cartons are placed only on PCK-01's final data, so a silent PCK-01 keeps an order's last carton open.
- **Orders (#174):** the MES pulls the ERP's feed from `ERP_URL` with `ERP_API_TOKEN` every `ERP_POLL_MS` (without `ERP_URL` it imports nothing and its ERP outbox waits); commands go out on its own MQTT connection (client id `{MQTT_CLIENT_ID}-cmd`, user `MQTT_CMD_USERNAME`, default `mes-cmd`, bound to `mes-server-cmd`) with the timings `COMMAND_TTL_MS`, `COMMAND_RESEND_MS`, `COMMAND_ATTEMPTS` (published deliveries; one written but never acknowledged by the broker is resent with a backoff from `COMMAND_RESEND_MS` up to 8 × it and doesn't count, so the command recovers once the cause is fixed; a broker refusal such as 0x87 is a `command-publish-refused` incident: check the ACL of the MES's user) and `COMMAND_FAIL_MARGIN_MS`. Incidents: `GET /api/v1/order-incidents?open=true`.
- **Line OEE (#232):** `MES_PRODUCTION_MODE` (`schedule`, the default, or `orders`) is the plant's production mode; in `orders` mode line OEE plans only the time an order is in progress (ADR-0036). Compose sets it from `SIM_PRODUCTION`, so the MES and the simulator agree; a MES started by hand against an orders-mode simulator needs `MES_PRODUCTION_MODE=orders`.
  - **An ERP cancellation after release is refused:** a new revision (also one with ERP status `cancelled`) replaces only an order still `imported` or `rejected`; for a released or dispatched order it is logged `revision-refused` and `rejected-revision` is posted to the ERP. To stop such an order, a supervisor cancels it in the MES while it is not dispatched yet (`POST /orders/{id}/cancel`); a dispatched order runs on (no cancel on the machine in Phase 7).
  - **A command that never settles** blocks its CNC's later commands (one in flight per CNC). It settles by the gateway's answer, by the CNC's facts through `seqAfterExpiry`, or when its device run ends (a simulator restart). Once the run has ended, a supervisor may write it off explicitly: `POST /orders/{id}/abandon-command` with `{ "version", "commandId" }` (permission `order:abandon`, audited); its whole quantity then counts as dispatched, so the order can end short, never over. A `command-conflict` answer (the device holds another job under the id) keeps the command unsettled with an incident until its run ends, and its quantity counts too.
- **Execution and confirmations (#175, ADR-0031):** units and their records follow the cycle facts (`GET /api/v1/execution/units?orderId=…`); `GET /api/v1/orders/{id}/execution` shows an order's quantities, backflushed material, WIP and when each operation was complete. An operation is confirmed to the ERP once no unit can come back to it; a fact that arrives after its gap was written off sends a correction with the deltas (`GET /orders/{id}` → `confirmations`). Routing violations: `GET /api/v1/execution-incidents?open=true` (a suspect becomes one only once the expected machine is final through it).
  - **An order stays `in-progress` after a simulator restart:** a job lost with its run keeps OP10 open, so the order is not completed on the blanks the old run made. Re-dispatch the remainder (`POST /orders/{id}/redispatch`), or, when nothing remains, write the lost command off (`abandon-command`); the order then completes on its units (short).
  - **Scrap coding:** `PUT /api/v1/scrap-records/{id}/coding` with `{ "version", "reason", "comment"? }` (permission `scrap:code`: operator, quality, supervisor); the reason is the record's machine reason or one below it in `config/plant/scrap.yaml` (`GET /api/v1/scrap-reasons`). It never changes a quantity or a confirmation.

## Run the ERP mock

The ERP mock (#171, ADR-0028) serves production orders with their routing and BOM as a change feed, the lots, and takes the MES's confirmations, status messages and (Phase 8) quality notifications, idempotently. It needs no other service.

```bash
ERP_API_TOKEN=<ERP_API_TOKEN from .env> pnpm --filter @shopfloor/erp-mock start
```

- Environment: `ERP_API_TOKEN` (required, no whitespace, never echoed), `ERP_DATASET` (`config/erp/orders.yaml`; a scenario's `orders.json` works too), `PLANT_CONFIG_DIR` (`config/plant`: routings, BOMs and the default lots), `ERP_STORE_PATH` (`.store/erp.db`, the messages received and the orders added), `ERP_ADMIN` (`off`; `on` enables the dev-only `POST /api/v1/orders`), `HTTP_HOST` and `HTTP_PORT` (`127.0.0.1:4600`), `LOG_LEVEL`. An invalid environment exits with status 2, an invalid dataset with status 1 and the entry named. A token shorter than 16 characters or `change-me` starts with a warning.
- The token (#242, checklist S7): one shared bearer token for the MES (its only client) on every `/api/v1` route, checked before routing (an unknown path or method without it is 401 too, counted in `erp_unauthorized_requests_total`); `/health/*` and `/metrics` stay open on loopback. The comparison hashes both sides with SHA-256 and compares the digests with `timingSafeEqual`, so neither where a guess differs nor its length shows in the time. **Rotate it** by putting a new value in `.env` (`ERP_API_TOKEN=$(openssl rand -hex 24)`) and restarting both ends together: `docker compose up -d erp mes` (Compose recreates both, as their environment changed). Until both run with the new value the MES's polls answer 401 and it retries; nothing is lost (its outbox waits). One shared token stays an accepted risk on loopback (`docs/security-review.md`, S7).
- API (`Authorization: Bearer <token>` on every `/api/v1` route, else 401): `GET /api/v1/orders?after=<cursor>&limit=<n>` (the change feed; pass the answer's `cursor` as the next `after`, and keep its `feedId`: another `feedId`, or a 409 `erp-cursor-ahead`, means the feed was replaced and the cursor starts again at 0), `GET /api/v1/orders/<orderNumber>` (the ERP's view: latest revision, status from the MES, confirmed totals per operation), `GET /api/v1/lots` (with the feed's `feedId`, which also changes when only the lots change), `GET /api/v1/lots/<id>` (the ERP's view of a lot: the holds on it from the quality notifications, `blocked` while one is open or rejected), `GET|POST /api/v1/confirmations`, `GET|POST /api/v1/order-status` and `GET|POST /api/v1/quality-notifications` (`GET` takes `?holdId=`; posts need the `Idempotency-Key` built from the body, `confirmationKey`, `statusKey` or `qualityNotificationKey` of contracts, e.g. `ORD-1001~OP10~conf~1`, `ORD-1001~r1~status~accepted` and `17~opened~1`, else 422: 201 the first time, 200 with the same receipt for the same body, 409 `urn:shopfloor:erp-idempotency-conflict` for another body; a notification on a lot or order the ERP doesn't hold is 422 `erp-unknown-subject`, a release or rejection before the hold's opening 422 `erp-hold-sequence`, a second decision 409 `erp-hold-decided`). Schemas: `@shopfloor/contracts/erp-api`.
- `GET /health/live`, `/health/ready` and `/metrics` (`erp_feed_entries`, `erp_messages_stored{kind}`, `erp_message_posts_total{kind,outcome}`, `erp_unauthorized_requests_total`), without a token.
- Quick look: `printf 'Authorization: Bearer %s\n' "$ERP_API_TOKEN" | curl -s -H @- '127.0.0.1:4600/api/v1/orders?limit=2' | jq '.entries[].order | {orderNumber, revision, product, quantity}'` (the token goes on stdin, not on the command line).
- Add an order for a demo (`ERP_ADMIN=on`): `POST /api/v1/orders` with `{"orderNumber":"ORD-2001","revision":1,"product":"VB-200","quantity":10,"plannedStart":"2026-10-14T06:00:00+03:00","dueDate":"2026-10-14T14:00:00+03:00"}`; it goes to the end of the feed and is kept in the store. If you then change the dataset, delete the store: the mock refuses to start when the added orders' feed numbers no longer follow the dataset.
- Deleting `.store/` forgets every message received; the MES would post its outbox again and get 201s.

## Run the web app

`apps/web` (#98, #122, #145, #146) is the MES's browser app: a plant overview, a machine detail, the OEE dashboard (`/oee`), the downtime coding screen (`/downtime`), the alarm list (`/alarms`), the alarm KPIs (`/alarms/kpi`) and the shift reports (`/shifts`). With the MES running (above):

```bash
pnpm --filter @shopfloor/web dev        # http://127.0.0.1:5173, proxies /api to 127.0.0.1:4700 (pnpm stack:up:dev)
pnpm --filter @shopfloor/web build      # static files in apps/web/dist
```

- The MES on `127.0.0.1:4700` is the dev stack's with `pnpm stack:up:dev` (#241: `pnpm stack:up` doesn't publish it) or one started by hand. The page is plain HTTP, so the MES's `Secure` cookie (`MES_COOKIE_SECURE=on`, the default) is kept only by a browser that treats `http://127.0.0.1` as secure (Chromium does); if the login doesn't stick (back at `/login` right after signing in), run the dev stack with `MES_COOKIE_SECURE=off` while you use the dev server (`MES_COOKIE_SECURE=off pnpm stack:up:dev`, or in `.env`), and remove it afterwards.
- `MES_URL` changes the proxy target. The proxy sends the MES's host (so `HTTP_ALLOWED_HOSTS` keeps its default). For the WebSocket it refuses upgrades whose `Host` is not `localhost`, `127.0.0.1` or `[::1]` (Vite's host check skips proxied upgrades, so this keeps the MES's DNS-rebinding protection), and presents a page served under that loopback name as the MES's origin, so `HTTP_ALLOWED_ORIGINS` is not needed; any other origin is passed on and refused by the MES. It does the same for HTTP requests (#121), so writes from `pnpm dev` pass the MES's Origin check. Open the app as `localhost` (the session cookie is per host name; "Cookie scope on localhost" above).
- The simulation console (#237) is not served by `pnpm dev`: `/console` needs nginx's `/sim/` proxy (its allowlist, the permission check and the control token), so use the web container ("Full stack" below).
- Login (#170): every screen needs a session; without one the app opens `/login` and returns to the page after the login. A temporary password (a new user, a reset, the bootstrap `admin`) must be changed there first. The header shows the user (a link to `/account`: roles, permissions, session times, password change) and **Log out**. **Users** (`/admin/users`, admins only) creates users with a generated 16-character temporary password, shown once to hand over, changes roles, disables and enables them and resets passwords (a new temporary one; the user's sessions end). Screens hide the actions the user's roles lack (`ROLE_PERMISSIONS`); nobody types a name any more, the MES takes it from the session.
- Idle timeout (#170, ADR-0026): a person's input (pointer, key, wheel, touch) in any of this browser's tabs counts as use; pushed messages and background refreshes don't. Two minutes before the idle limit (60 min desk, 15 min terminal) a banner offers **Stay logged in**; then the app logs out by itself and `/login` says so. The deadline is the earliest of the idle limit after the last input, the MES's own idle expiry and the 12-hour limit, read on the browser's clock through the offset of the API answers' `Date` header (only answers back within 1 s count). Behind a proxy that sets its own `Date` header, the offset reflects the proxy's clock, not the MES's: nginx, which serves the web in Compose, sends its own `Date` (it never passes the upstream's), which is fine there because the containers share the host's clock; behind another proxy keep its clock in sync with the MES's. While someone types, in this tab or another, the app reads the session at most every 30 s, and once when the warning opens, which keeps it alive at the MES. Screens that refresh on a timer keep the MES's session alive too, so on a shared terminal it is the app's timer that logs the last person out. The 12-hour limit is announced too and can't be extended. When a session ends while a form holds unsaved input, the page stays under a login dialog for the same user, who carries on after logging in; **Log in as someone else** discards the input.
- Operator terminal (#177): open `/terminal` (or the **Terminal** link) once per tablet and pick the work center; the tablet then stays on `/terminal/<work center>`. Operators sign on there with their own user name and password (a 15-minute terminal session; a running shift is needed) and sign off with **Sign off**, which ends their session; the next operator starts from an empty screen. Signing on at a tablet where someone else is logged in ends that person's session. Start, pause and resume record the operator's time only: machines run their queues regardless. An operation can be signed off once the MES has it complete; a supervisor can close an order only when every operation (at both work centers) is signed off.
- The header shows the plant clock (simulation time, Istanbul) and the connection: `Live`, `Connecting…` or `Reconnecting…`. Machine states marked **Stale** are from before a lost connection or from an earlier simulator run (not shown while the page first connects).
- A blank overview with `Could not load the equipment` and `Forbidden: host not allowed` means the request reached the MES under a name not in `HTTP_ALLOWED_HOSTS`; a connection stuck at `Reconnecting…` with 403 upgrades in the MES log means the page's origin is not accepted (`HTTP_ALLOWED_ORIGINS`).
- `/oee` shows the current shift by default (pick an earlier one in **Shift**): OEE, A, P and Q per work center and machine as the MES computed them (four decimals; `n/a` when there was no planned busy time), the hours, the loss waterfall and the downtime Pareto, updated live (about once a second at 60×). **Provisional**, **Revision** and **incidents** say what may still change.
- `/downtime` lists the shift's downtime records, uncoded first. **Code** opens a record: split it at a plant time, pick a reason per segment (or keep the automatic one), add a comment, **Save coding** (the coding is recorded under the logged-in user). A message says why a write was refused: 409 means the machine's codings changed since the record was read (it is reloaded; code again), 403 that the page's origin is not accepted (open the app as `localhost`) or that the role may not code, 405 writes are off, 429 too many writes. Recoding changes the Pareto and the history, never OEE.
- `/alarms` (#145) lists the alarms live in four tabs: **Active** (not acknowledged, also once cleared: a clear does not acknowledge), **Acknowledged** (still active), **Shelved** (the point is shelved) and **History** (closed, the last 24 hours). Priority shows as colour, a mark and its word. Actions are recorded under the logged-in user. **Acknowledge** one alarm, or tick rows and **Acknowledge selected** (at most 100 at once). **Details** opens the occurrence: definition, acknowledgement with a comment, the point's shelf (shelve with a reason for 15 min, 1 h, 4 h or 8 h of plant time, or unshelve), comments and the full history (device raise and end, and every audited action with its request id). A red **Alarm flood** banner shows per position while more than 10 alarms were raised in the last 10 minutes. A message says why a write was refused: 409 on a shelf means someone else changed it (the panel reloads it; try again), **Reload the shelf** appears when it changed while you were filling in the form, 422 for example a shelf longer than `maxShelveMs`; 403, 405, 415 and 429 as for codings.
- `/alarms/kpi` (#145) shows the shift's alarm KPIs per scope (plant and positions), live: raises by priority, average and peak per 10 minutes against the ISA-18.2 benchmarks, flood windows and episodes, chattering, fleeting, standing, active time, and **Final**, **Provisional** or **Revision**; `n/a` where there is no bucket. **Details for** a scope shows its hours (or the shifts of the last week), the flood episodes, the top 10 bad actors and the MES-only operator measures (time to acknowledge, shelved raises, unacknowledged at the end).
- To see alarms on a disposable stack, inject failures through the simulator's control API, for example `curl -H "Authorization: Bearer $SIM_CONTROL_TOKEN" -X POST -H 'Content-Type: application/json' -d '{"code":"COOLANT-PRESSURE","repairMs":4000}' http://127.0.0.1:4800/api/v1/faults/failure/cnc-01` (more than 10 within 10 minutes of plant time on Cell M1 make a flood; three of one point within a minute make it chatter). Acknowledgements and the audit are permanent: do this only on a stack you throw away.
- `/shifts` (#146) lists the last week's shifts, current first, with their status (**Running**, **Ended, not final**, **Final**) and revision; a row opens `/shifts/<date>/<shift>` (add `?epoch=<n>` for an earlier simulator run). The report shows status, **Final** or **Provisional**, the revision (inputs, content), `asOf` (plant time) and `generatedAt` (wall clock), then OEE, production, downtime, alarms and the handover notes. While the shift runs, OEE, production and alarm KPIs follow the plant (marked **Live**); the rest is as of `asOf` (**Read again**). The page reads the report again by itself when the shift ends and when the report turns final; a banner says when a final report changed later (late data, notes, recodes, acknowledgements). **Print** opens the browser's print dialog with an A4 layout (no navigation, buttons or forms; charts as still images, every value also in a table); **Download JSON** saves the report as served.
- Handover notes (written under the logged-in user): pick a category, write the note (plain text, up to 4,000 characters) and **Add note**. **Edit** changes the text or category or ticks **Retracted** (a wrong note is retracted, never deleted); **History** shows every version from the audit. If someone else saves the note while you edit, the editor says so and sends nothing; **Reload the note** starts again from their version. Notes can be written from the shift's start until the end of the following shift (plant time); afterwards the MES answers 409 `handover closed`, which the form explains, and 422 after 200 notes. Notes and their audit are permanent: write test notes only on a stack you throw away.
- `/console` (#237, the **Console** link; admins only, permission `sim:control`) is the simulation console: the run (state, simulation time, speed, events; **Pause**, **Start**/**Resume**, **Step one event**, the speed 0.5–60×), a committed scenario timeline (**Load**, only while the run is idle and has no action yet; then its progress per entry), failure injection (machine, failure code, optional simulation time and repair minutes), the leak tester's sensor drift, OPC UA offline per machine and the washer's Modbus silence (the page shows what it last set; the control API has no read of these switches), lots (**Block**, **Release**: an action applies at the next simulation step, so a paused run still shows the lot as it was), operators (mark several absent for a later shift by date and shift id), tool breakage per CNC, the console action list and the last 30 plant events. Every action goes through nginx's `/sim/` proxy to the simulator's control API; the browser never holds the control token. A refusal is shown as the simulator or nginx gave it: 401 your session ended, 403 not an admin (or a request from another page), 409 for example a timeline load after the run started. Only an action counts as use of the session: an open console nobody touches times out like any page. The levers change the simulated plant, never the MES: the MES sees their effects through the machines.
- More (screens, test ids, the nginx container): `apps/web/README.md`. In Compose the app runs as service `web` ("Full stack" below).

## Golden scenarios

A golden scenario is a fixed seed and configuration whose expected output is committed (plan section 9). Each one lives in `apps/simulator/golden/<name>/`:

- `scenario.json`: seed, start, number of days, configuration directory;
- `summary.json`: the expected ground-truth summary, byte for byte;
- `events.sha256`: the SHA-256 and line count of the expected event log. The log itself (about 6 MB per week) is not committed; its hash pins every byte.

| Task                                           | Command                                                       |
| ---------------------------------------------- | ------------------------------------------------------------- |
| Check every scenario against its snapshot      | `pnpm test:golden`                                            |
| Write one scenario's event log and summary     | `pnpm sim:headless --scenario alarms-01 --out runs/alarms-01` |
| Rewrite the snapshots after an intended change | `pnpm test:golden --update`                                   |

Each run also checks the conservation and time-accounting invariants after every simulation step, and fails on the first violation. `pnpm verify` (and the pre-commit hook) does not compare snapshots, to stay fast; CI runs `pnpm test:golden` on every pull request.

**When a snapshot changes:** any change to the plant model, its random draws or the default configuration changes the snapshot. That is the point. Run `--update` only when the change is intended, and explain in the pull request what changed in the simulated behaviour and why (plan section 9). The diff of `summary.json` shows the effect in numbers.

## Continuous integration

`.github/workflows/ci.yml` runs on every pull request and every push to `main`:

| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `verify`      | `pnpm install --frozen-lockfile`, then `pnpm verify` (format check, lint, typecheck, tests), then `pnpm test:golden`                                                                                                                                                                                                                                        |
| `end to end`  | `pnpm test:e2e`: the whole-system Vitest suites (`*.e2e.test.ts`), one at a time                                                                                                                                                                                                                                                                            |
| `reconcile`   | `pnpm test:reconcile`: shift A of `alarms-01` (with injected failures) through the whole Compose stack, reconciled with the simulator's ground truth, and Playwright on the live alarms, OEE dashboard and overview, then alarm actions, a downtime coding and a handover note through the UI (see "Reconciliation run"); uploads `e2e/results/` on failure |

The jobs run in parallel. A pull request is merged only when every job is green on its latest commit (ADR-0011). GitHub Actions has not run since PR #149 (spending limit): until it does, the merge gate below replaces it. If CI fails but `pnpm verify` passes locally, check the Node.js and pnpm versions first: CI uses exactly `.nvmrc` and `packageManager`. A lockfile change that was not committed fails `--frozen-lockfile`.

## Merge gate

`pnpm gate` (#178, `scripts/gate.ts`) runs the local equivalent of every CI job on the checked-out commit, in this order and one at a time (each job is heavy): `pnpm verify --concurrency=1`, `pnpm test:golden`, `pnpm test:e2e`, the stack smoke with `SMOKE_WRITES=1` on a disposable Compose project (`GATE_PROJECT`, default `shopfloor-gate`) and `pnpm test:reconcile` (all three passes since #204: `alarms`, `orders`, `quality`) with the smoke's images; `pnpm test:trace-perf` (exit criterion 6, "Trace performance") is run on its own, not by the gate. The smoke's env file is made from `.env.example` in a temporary directory (mode 600) with a random value for every `*_PASSWORD` and `*_TOKEN` key, the required secrets appended if `.env.example` lacks one, `COMPOSE_PROJECT_NAME` and `IMAGE_TAG` (`GATE_TAG`, default `gate`); the repository's `.env` is neither read nor changed (`SMOKE_ENV_FILE` makes `stack-smoke.sh` read that file and pass it to every `docker compose` call). The smoke's host ports are ephemeral (`SMOKE_EPHEMERAL_PORTS=1`, #228), as the reconciliation's are, so a dev stack on the default ports can stay up during the gate. A failed job stops the gate (the later ones are `skipped`); Ctrl+C, SIGTERM or SIGHUP is passed to the running job's process group (never to the cleanup), the gate waits for the job, cleans up the same way and exits 130, 143 or 129, and a second signal kills the job's group (a killed reconciliation cannot remove its own `reconcile` Compose projects and env files: remove those by hand with `docker compose -p <project> down --volumes`); it refuses `GATE_PROJECT=shopfloor-twin` (the dev stack's) and `GATE_TAG=dev`. In every case the project is removed with its volumes, the images of the tag are removed (`GATE_KEEP_IMAGES=1` keeps them) and the env file is deleted.

It ends with one record for the pull request's "Gate" section, also written to `e2e/results/gate.json`: the commit (and whether the tree had uncommitted changes), each job with its duration and result, Node, Docker and Compose versions, the free disk space at the start and the image digests the smoke and the reconciliation ran.

**One heavy suite at a time (#228, Phase 9 plan "Local gate").** Every heavy command takes a host-wide lock first: `pnpm gate`, `pnpm verify` (its Testcontainers suites), `pnpm test`, `pnpm test:e2e`, `pnpm test:reconcile`, `pnpm test:trace-perf`, `pnpm test:console`, `pnpm test:resilience` (#243) and Playwright (its global setup), and from its issue on `pnpm test:perf`. The commands go through `scripts/heavy.ts` (the gate and Playwright call the same code, `@shopfloor/test-kit/heavy-lock`).

- The lock is the directory `~/.cache/shopfloor-twin/heavy.lock` (a fixed path for every worktree, agent and sandbox session: the account's home directory from the user database, not `$HOME`; never the temporary directory) with `holder.json`: the holder's PID, command and checkout, start time, a token, the machine's boot time and the holder process's start time; and a `group-<pgid>` file (holding the group leader's start time) for each process group the holder started (`scripts/heavy.ts`'s command, each gate job). `cat ~/.cache/shopfloor-twin/heavy.lock/holder.json` shows who holds it.
- A command that finds it taken prints the holder (`heavy lock: waiting for …`) and waits up to `HEAVY_LOCK_TIMEOUT_MS` (default 3 hours, `10800000`), then fails with exit 1 naming the holder.
- The lock is alive while the holder's PID exists (`kill(pid, 0)` succeeds, or fails with `EPERM`: a process of another user) **or** any recorded process group does (`kill(-pgid, 0)`), so killing `scripts/heavy.ts` or the gate with SIGKILL doesn't free the lock while the suite it started still runs. It is stale when neither exists (`ESRCH`), or when the holder's PID now belongs to a process started at another time (a reused PID). Start times are read with `ps -o lstart=` in a fixed locale and time zone (`LC_ALL=C`, `TZ=UTC`, so a Turkish-locale terminal and an agent's shell read the same) and compared as instants; a live PID with the recorded start time is conclusive, and when the times can't be compared the PID counts as alive unless the boot time differs by more than 5 minutes (an earlier boot; a clock step or a second of jitter is not one). A recorded group counts as gone when a process with its PGID's number exists with another start time than the leader recorded (a reused PGID). The next command removes a stale lock and says so, once. A lock directory without a valid `holder.json` is waited for (with a message) and counted stale after 60 s.
- A holder's children inherit it through `SHOPFLOOR_HEAVY_LOCK` (the gate's `verify`, the reconciliation's Playwright): they run at once instead of waiting on their own parent.
- Holding the lock (not when inherited), a command refuses to start below **25 GiB free on the host** (the repository's file system) or **15 GiB free in Docker's data root** (inside the VM; measured with `df` in a throw-away container of the broker's image), exit 2, saying which. Free space with `docker system df` and `df -h /`; reclaim with `docker image prune`, `docker volume ls` (remove only volumes you know) and `docker builder prune`.
- **A wedged lock** (a waiter keeps printing a holder you know is gone, say after a crash the rules above can't see): check first, then remove it by hand.

  ```bash
  cat ~/.cache/shopfloor-twin/heavy.lock/holder.json   # pid, command, checkout, start
  ls ~/.cache/shopfloor-twin/heavy.lock                 # group-<pgid> files
  ps -p <pid> -o pid,lstart,command                     # is the holder still running?
  ps -g <pgid> -o pid,command                           # is any of its groups? (per group)
  rm -r ~/.cache/shopfloor-twin/heavy.lock              # only when nothing above runs
  ```

  Never remove it while its holder or one of its groups runs: two heavy suites would then share the machine. A leftover `heavy.lock.break` (a breaker killed in the middle) is removed by the next waiter when its writer is gone or the guard is older than a minute (its writer's PID may have been reused).

- **Docker must run:** `pnpm verify`, `pnpm test` and every other heavy command measure Docker's free space before they start (the disk check above), so they now refuse to start, saying "Docker is not running", while Docker is down; start it (`colima start`) first. The probe never pulls its image (`docker run --pull never`): if the broker's image isn't on the machine, the message says to `docker pull` it once.
- Signals: `scripts/heavy.ts` runs the command in its own process group and passes SIGINT, SIGTERM and SIGHUP on (a second signal kills the group); the lock is released when the command ends. Harnesses stop what they started by PID or process group, never by name (no unscoped `pkill`).

**Cleanup per run (#228).** The gate removes its smoke project with its volumes and the images of its `GATE_TAG` (also on failure); `pnpm test:reconcile` and `pnpm test:trace-perf` remove their projects with their volumes and, when they built them, their images (`RECONCILE_KEEP_IMAGES=1`, `TRACE_PERF_KEEP_IMAGES=1` keep them; the gate passes `RECONCILE_KEEP_IMAGES=1` and removes them itself after recording the digests). After each build the BuildKit cache is pruned to 10 GiB (`docker builder prune --force --all --keep-storage 10GB`; the gate also at its end). The prune is **machine-wide**: it trims every project's build cache on the Docker host (other worktrees' and other repositories' too), keeping the most recently used 10 GiB. `--all` is what makes the cap hold: without it only dangling records may go, so the cache could stay above 10 GiB.

**The manual smoke takes no lock.** `pnpm stack:smoke` (and `sh scripts/stack-smoke.sh`) is not a heavy command on its own: it checks a stack you already run. Run it beside a heavy suite only on a stack of your own; the gate's smoke runs under the gate's lock.

## Full stack (Compose)

Database, broker, simulator, edge gateway, MES server, ERP mock and web app (`docker-compose.yml`).

First time only: create your local secrets file. It is git-ignored; never commit it.

**Upgrading an existing stack (#241, ADR-0039): HTTPS on 8443, internal ports unpublished.** Nothing to add to `.env` (no new secret); in order:

1. `pnpm stack:up`: the `pki` step makes the stack's dev CA and nginx's certificate (new volumes `pki-ca` and `web-tls`), and the web comes up on **<https://localhost:8443>** (HTTPS only; `http://localhost:8080` no longer answers, and plain HTTP to 8443 is answered 400). A `WEB_PORT` line in `.env` is no longer read: use `WEB_HTTPS_PORT` (default 8443) if the port is taken.
2. `pnpm stack:ca`: writes the dev CA's certificate to `dev-ca.pem` and prints its SHA-256 fingerprint; trust it in your browser or keychain ("HTTPS and the dev CA" below), then open <https://localhost:8443> and log in again (the session cookie is now `__Host-sft_session`, `Secure`; the old `sft_session` is ignored).
3. The MES (4700), the gateway (4900) and the database (5442) are no longer published by `pnpm stack:up`. Need them (psql, the Vite dev server, your own scripts)? Use `pnpm stack:up:dev`, which adds `compose.dev-ports.yml`, or `docker compose exec`. New optional variables: `WEB_HTTPS_PORT` (8443) and `MES_COOKIE_SECURE` (`on`; `off` only for a browser on plain HTTP straight to the MES).

**Upgrading an existing `.env` (#237):** it must gain `SIM_CONTROL_TOKEN`, or `pnpm stack:up` stops with `Set SIM_CONTROL_TOKEN in .env`: `printf 'SIM_CONTROL_TOKEN=%s\n' "$(openssl rand -hex 16)" >> .env`.

**Upgrading an existing `.env` (#239):** it must gain the two OPC UA users' passwords, or `pnpm stack:up` stops with `Set OPCUA_GATEWAY_PASSWORD in .env` (or `OPCUA_READER_PASSWORD`): `printf 'OPCUA_GATEWAY_PASSWORD=%s\nOPCUA_READER_PASSWORD=%s\n' "$(openssl rand -hex 16)" "$(openssl rand -hex 16)" >> .env`. The first `pnpm stack:up` after #239 runs the new `pki` step, which replaces the certificates node-opcua made in `simulator-pki` (they carry both extended key usages) and makes the gateway's in the new `gateway-pki` volume; the old client certificate in `gateway-data` is no longer used. It also removes every certificate node-opcua pinned by itself in `simulator-pki` before #239 (it accepted every client then) and empties the CRL and issuer folders; the pki log lists each removal.

**Upgrading to dynamic security (#240, ADR-0039):** no new secret: the gateway's and the MES's second broker users (`gw-01-cmd`, `mes-cmd`) take `MQTT_GATEWAY_PASSWORD` and `MQTT_MES_PASSWORD`, so an existing `.env` keeps working once the passwords are random and without spaces (`change-me` still starts, but replace it). Rebuild the gateway and MES images with the broker (`pnpm stack:up` does): an old image logs its command connection in as `gw-01` or `mes`, which the broker now refuses under `gw-01-cmd` or `mes-server-cmd`. The broker volume is kept: on its first start the broker removes the old password file and generates its dynamic-security configuration; the MES's persistent session and the retained messages survive. Every broker user is bound to one client id, `dev` and `healthcheck` included: manual `mosquitto_sub` and `mosquitto_pub` commands need `-i dev` (one `dev` session at a time), and Compose's `MQTT_USERS` adds `smoke-reader` (the smoke's second reader) with `MQTT_DEV_PASSWORD`. Sessions left under client ids the broker now refuses (an old `MQTT_CLIENT_ID`, a manual `mosquitto_sub -c` from before) can't be resumed or cleared by their user; the broker removes any persistent session not resumed for 14 days (`persistent_client_expiration 14d`), or `pnpm stack:reset` drops them at once.

**Smoke writes and a disposable project.** `pnpm stack:smoke` always checks the write refusals (403, 415, nginx's method allowlist, 401 without a session, 403 for a permission the role lacks), also for the alarm writes, which change nothing. Since #170 it logs in as an operator `smoke-<hex>` it creates for the run with `user:create` in the `mes` container (password generated with `openssl`, passed on stdin, never written to a file); on every exit (pass, fail, a `set -e` stop or Ctrl-C, through an `EXIT` trap) it disables that user again (`node apps/mes-server/src/user-cli.ts --disable --username …`, also `pnpm --filter @shopfloor/mes-server user:disable`); the user row and its audit entries stay in the database (users are never deleted). With `SMOKE_WRITES=1` it also codes one closed, final, uncoded downtime record through the web and clears it again, and acknowledges the newest unacknowledged alarm occurrence of the last 7 days of plant time (twice: the second answer must be `changed: false`; skipped when the plant has raised none yet), both audited as the smoke user; with `MES_BOOTSTRAP_ADMIN_PASSWORD` set it also checks that the bootstrap admin must change its password first (403 `password-change-required`, WebSocket 4403; the smoke never changes it). CI sets it on a throw-away stack. Those audit rows and the acknowledgement are **permanent** (append-only and insert-only), so never set it against a database you keep. To run it locally on a disposable stack of its own, beside your dev stack (#228: `SMOKE_EPHEMERAL_PORTS=1` publishes every port on an ephemeral host port, `e2e/compose.ephemeral-ports.yml`):

```bash
COMPOSE_PROJECT_NAME=shopfloor-smoke IMAGE_TAG=smoke SMOKE_EPHEMERAL_PORTS=1 SMOKE_WRITES=1 pnpm stack:smoke
docker compose -p shopfloor-smoke down --volumes
docker image rm shopfloor-twin/simulator:smoke shopfloor-twin/edge-gateway:smoke shopfloor-twin/mes-server:smoke shopfloor-twin/erp-mock:smoke shopfloor-twin/web:smoke
```

`COMPOSE_PROJECT_NAME` overrides the file's `name:`, so the smoke gets its own containers and volumes and your `shopfloor-twin` data is untouched; `IMAGE_TAG` keeps its images apart from your `dev` ones. The smoke reads every host address back with `docker compose port` (also on the default ports), so it never assumes a fixed port; with `SMOKE_EPHEMERAL_PORTS=1` it also asserts that no default port is published and that the broker, OPC UA and Modbus ports are not published at all. Either way (#241) it asserts the hardened set: the MES, the gateway and the database published on no host port (it reaches them with `docker compose exec`), the web on no HTTP port, and every published container port one of checklist S8's on `127.0.0.1`. It reads the dev CA's and nginx's certificates from the web container and trusts that CA alone (`curl --cacert`, `NODE_EXTRA_CA_CERTS`); it checks that the certificate is untrusted without it, that the handshake presents the `pki` step's certificate over TLS 1.3 as `localhost` and `127.0.0.1` (TLS 1.2 and another name refused), that plain HTTP to the port is answered 400 without a redirect, that no `Strict-Transport-Security` is sent, that the login sets `__Host-sft_session` with `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/` and no `Domain`, that `/sim/` refuses a write from the `http://` origin of the same host and port, and that `pki-ca` is mounted by no running service and `web-tls` by the web alone, read-only.

Since #178 the smoke also checks, before `up`, that Compose refuses a configuration without each required secret (`DB_PASSWORD`, `DB_APP_PASSWORD`, `ERP_API_TOKEN`, `SIM_CONTROL_TOKEN` since #237, the four MQTT passwords) and accepts one without `MES_BOOTSTRAP_ADMIN_PASSWORD` (`docker compose config` in a clean environment); and through the web, as the operator, the order-path refusals that change nothing: release, dispatch and close of an imported order are 403 `forbidden`, a terminal write without a crew row is 409 `not-signed-on`, a sign-on with a desk session is 409 `terminal-session-required`. With `SMOKE_WRITES=1` it creates a second user, a supervisor `smoke-sup-<hex>` (disabled again by the exit trap), which releases and dispatches that order (the schedule-mode simulator refuses the job, so no job is made) and is refused an abandon of the command while its run goes on (409 `order-state`). Without an order still `imported` the order checks are skipped, except with `SMOKE_WRITES=1` (a disposable stack must have one), where that fails. `SMOKE_ENV_FILE` names another env file than `./.env` (the merge gate's throw-away one). Since #237 it also checks the control token (the control API answers 401 to reads, writes and unknown routes without it or with another, its health check stays open), the console's `/sim/` proxy (401 anonymous; 404 for the ground truth, the recorded run, health and metrics; 403 for a cross-origin write) and the edge trust: through nginx every proxied request reached the MES trusted (`mes_http_proxy_requests_total{trusted="true"}` above 0, `trusted="false"` at 0), the MES logged its learned `edge` network, the network has no gateway (IPAM or endpoints), and a client's `X-Original-Method: POST` on a GET through `/api/` doesn't count as session use (the token never reaching the browser is the console run's check). Since #242 (checklist S5, S7, S8) it also runs four probe containers (`smoke-login-<hex>-a` to `-d`, the MES image's `node` with `scripts/stack-smoke-login.mjs`, removed by the exit trap) on the Compose network as four client addresses: five failures from probe a lock its pair while probe b logs in; probe c sending a forged `X-Real-IP` straight to `mes:4700` is keyed by its own address (and counted untrusted); then, for a second user, n is driven to 15 from a, b and c (waiting out each 429), the 30 s wait is let run out, and 20 concurrent attempts from d give exactly one judged (401) and 19 × 429 with `Retry-After` the remaining wait (n = 16 afterwards). It then searches the containers' logs, the images' metadata and history and the repository for every password and token of the run (none may appear; the gate searches its own output of the smoke for its generated secrets too), and checks that no service's main process runs as root. The login part adds about 70 s.

Start order: `db` and `broker` first; `simulator`, then `gateway` (needs broker and simulator); `mes` (needs db and broker); `web` (needs a healthy MES and the `pki` step, #241). The gateway does not wait for the MES: the edge must work without it, the MES's broker session is persistent, and the current state of every machine is retained in the UNS, so the overview is complete whenever the MES joins. Only cycles and telemetry published before the MES's very first session (a fresh broker volume) are not stored. The reconciliation needs the stricter order of the Phase 4 plan (database and broker, MES ready, gateway connected, then the simulator resumed at 06:00): `pnpm test:reconcile` starts the simulator with `SIM_AUTOSTART=false` and drives the order itself, in a project of its own (see "Reconciliation run"), so the default stack stays as it is. A consequence: every fresh `docker compose up` records one `sequence-gap` incident per machine (the first numbers of each `device:*` stream, about 30 s after start), because the autostarted simulator publishes before the gateway subscribes. That is expected with `SIM_AUTOSTART=true`.

MES and web notes:

- The overview shows `Live` in its header once the WebSocket through nginx is open. `docker compose logs -f mes` shows ingest and the API; health probes are logged only at `warn`.
- `pnpm stack:down` keeps the database and the broker's queue; on the next start the MES catches up from where it stopped (the broker queued the UNS meanwhile).
- `docker compose up -d --build mes web` rebuilds just these two after a code change (`stack:up` rebuilds everything, from cached layers).
- **403 `host not allowed`** (a blank overview with `Could not load the equipment`, or `curl` answers 403): the browser reached the app under a name not in `MES_ALLOWED_HOSTS`. Use `localhost` or `127.0.0.1`, or add the name to `MES_ALLOWED_HOSTS` in `.env` and run `pnpm stack:up` again.
- **Stuck at `Reconnecting…`, 403 upgrades in the MES log (`origin not allowed`):** the page's origin is not the host nginx forwarded. nginx must send `Host $http_host` (with the port, `apps/web/nginx/default.conf.template`); a page served from elsewhere needs its origin in `MES_ALLOWED_ORIGINS`.
- **The simulation console (#237).** nginx proxies `/sim/api/v1/…` to the simulator's control API for an allowlist of exact routes and methods only (`apps/web/nginx/default.conf.template`, ADR-0037 amendment): the ground truth, the recorded run, `/health/*` and `/metrics` are 404 there. Each request passes nginx's `Origin` check (a write or WebSocket upgrade from another origin: 403), then `auth_request` to the MES (`GET /api/v1/session/permission/sim:control`: 401 without a session, 403 without the admin role), then goes to `http://simulator:4800` with nginx's `Authorization: Bearer $SIM_CONTROL_TOKEN`. **401 or 403 on `/console`:** log in again, as an admin. **500:** the MES couldn't answer the permission check (starting, or down). **502:** the simulator is down. **The `web` container exits at once** with `SIM_CONTROL_TOKEN must be set`: the token is missing from `.env` or has characters outside `A-Z a-z 0-9 . _ ~ + / = -`. **Your own tools** talk to the control API on `127.0.0.1:${SIM_CONTROL_PORT}` with the same token (`Authorization: Bearer …`); the recorded run (`GET /api/v1/scenario/recorded`) is only there.
- **Edge network (#237, ADR-0026 amendment).** nginx reaches the MES as `mes-edge` on the internal network `edge` (only `web` and `mes` on it), and the MES believes proxy headers (`X-Original-Method`; `X-Real-IP` from P9-15) only from that network's subnet, which it learns at start (`docker compose logs mes | grep 'edge network'`). **The MES exits at once with `MES_EDGE_ALIAS mes-edge does not resolve to a local interface`:** the `mes` service is not on `edge` with the alias `mes-edge` (an edited Compose file or override); restore `networks: edge: aliases: [mes-edge]`. `docker compose exec mes wget -qO- http://127.0.0.1:4700/metrics | grep mes_http_proxy_requests_total` (or `curl -s 127.0.0.1:4700/metrics` with `pnpm stack:up:dev`) shows the proxied requests: every one should be `trusted="true"`; a growing `trusted="false"` means something proxies to the MES from outside `edge` (nginx must use `mes-edge`, never `mes`).
- **502 from `/api/`:** the MES is down or restarting (`docker compose ps mes`); nginx finds a recreated MES again within 10 s.
- **A write answers 403** (problem details from the MES, `detail` says which guard): `a write needs an Origin header` (a script or `curl` must send `Origin`; browsers always do), `origin not allowed` (the page's origin is not the host and port the request reached: nginx must forward `Host $http_host`; a page served from elsewhere needs its origin in `MES_ALLOWED_ORIGINS`), `Sec-Fetch-Site same-site/cross-site not allowed` (the page is on another origin, for example another port of localhost: open the app through the web container or `pnpm dev`), `host not allowed` (as above). A 403 from nginx itself (HTML, no problem details) means a method other than GET, POST, PUT or DELETE.
- **A write answers 415:** the body was not sent as `Content-Type: application/json`. **405:** writes are off (`MES_WRITES=off` in `.env`; set `on` and `docker compose up -d mes`). **409:** the record's `version` moved on; read `GET /api/v1/downtime` again. Every write refusal and conflict names itself in the problem's `type` (#163, ADR-0023 note): `urn:shopfloor:write-origin`, `…:host-not-allowed`, `…:writes-off`, `…:write-not-json`, `…:write-rate`, `…:coding-stale`, `…:shelf-stale`, `…:note-stale`, `…:handover-closed`, `…:handover-not-open`, `…:note-limit`; `jq .type` on the answer tells which. **429:** more than 10 writes a second in total; wait `Retry-After`. **413:** body over 16 KiB.

### OPC UA certificates (#239, ADR-0038)

The one-shot `pki` service runs on every `docker compose up` (and `pnpm stack:up`) before the simulator and the gateway, so certificates within 30 days of their end are renewed there automatically. It makes a key and a self-signed certificate (RSA 2048, valid 365 days) for each machine server, the gateway and the tools client, keeps existing ones that are valid for more than 30 days, pins the peers (each server: the gateway's and the tools certificates; the gateway and the tools client: the five servers'), makes each `trusted/certs` exactly those pins (any other file there is removed) and empties `trusted/crl`, `issuers/certs` and `issuers/crl`, prints one line per certificate and exits 0. The simulator and the gateway start only after it succeeded, and refuse to start without their certificate. No CA is involved: trust is the pinned certificates in each component's `trusted/certs`.

- **See the expiry dates:** `docker compose run --rm pki` (or `docker compose logs pki` after an `up`) prints each certificate's `until` date and SHA-1 thumbprint, and whether it was kept or made.
- **Renew:** rerun the step: `docker compose run --rm pki` replaces every certificate within 30 days of its end (and any that doesn't say what the step would write), removes the superseded certificate from every `trusted/certs` and pins the new one. `PKI_RENEW=edge-gateway,tools docker compose run --rm pki` renews named ones now (`cnc-01` … `pck-01`, `edge-gateway`, `tools`; a key thought compromised); an unknown name stops the step with exit 2 and changes nothing. **Whenever the step renewed a certificate or changed a trust folder it prints `pki: !!! RENEWED … RESTART THE SIMULATOR AND THE GATEWAY … !!!`:** run `docker compose restart simulator gateway`, since node-opcua reads its certificate and pins only when it starts. This also holds after an automatic renewal at `pnpm stack:up` (check `docker compose logs pki`): `up` reruns the step but doesn't recreate an unchanged simulator or gateway.
- **Rerunning the step on a running stack** (every `pnpm stack:up` or `docker compose up` does; #265): when nothing is renewed it leaves every pin alone (its summary says `20 pins (0 written)`) and prints no restart line, so the running simulator and gateway keep trusting each other; no restart is needed. A renewal or a removed trust file still needs `docker compose restart simulator gateway`, as above. **After any renewal (automatic, or `PKI_RENEW`, e.g. for a key thought compromised) always restart:** until they restart, the running simulator and gateway may keep trusting the **old** certificate (and may miss the new pin); the renewal is guaranteed only after the restart. The step stages what it writes in `.staging` inside each component's PKI folder (outside the folders node-opcua watches) and removes it before it exits.
- **Reset all PKI volumes:** `docker compose stop simulator gateway`, `docker compose rm -f simulator gateway pki`, `docker volume rm shopfloor-twin_simulator-pki shopfloor-twin_gateway-pki shopfloor-twin_opcua-tools-pki` (the prefix is the Compose project), then `pnpm stack:up`. `pnpm stack:reset` deletes them with everything else.
- **A tool of your own (UaExpert):** use the tools certificate, which every server pins, and the user `opcua-reader`: `docker compose run --rm --no-deps opcua-tools cat /var/lib/pki/tools/own/certs/certificate.pem > tools-cert.pem` and the same for `own/private/private_key.pem` (keep the key private, delete it after use), and trust the servers' certificates in `/var/lib/pki/tools/trusted/certs`. `docker compose run --rm opcua-tools` runs the security checks of checklist S1 against the stack.
- **The gateway logs `BadSecurityChecksFailed`, or the simulator `BadCertificateUntrusted`:** a pin is missing or stale (a volume reset on one side only); rerun the step and restart the simulator and the gateway. **`own/certs/certificate.pem is missing: run the pki step first`** (exit 2): the step didn't run or failed (`docker compose logs pki`). **`BadUserAccessDenied` when a session opens:** a wrong `OPCUA_GATEWAY_PASSWORD` or `OPCUA_READER_PASSWORD` (the simulator and the gateway read the same `.env`; recreate both after changing it).

### HTTPS and the dev CA (#241, ADR-0039)

The web front is HTTPS only, on `https://localhost:8443` (`WEB_HTTPS_PORT`): no HTTP listener (plain HTTP to the port gets nginx's 400 "The plain HTTP request was sent to HTTPS port", never a redirect), TLS 1.3 only, no HSTS. Its certificate (RSA 2048, 365 days, SAN `localhost` and `127.0.0.1`, `serverAuth`) is issued by the stack's own **dev CA**, which the same one-shot `pki` step makes (RSA 2048, one year, renewed by the step with the web certificate). The CA's key stays in the `pki-ca` volume, which only the `pki` step mounts; nginx reads its certificate and key from `web-tls`, read-only. The CA carries name constraints for TLS server names (`localhost`, every `*.localhost`, and `127.0.0.1`) and the extended key usage `serverAuth` only: browsers and Node refuse a TLS server certificate it signs for another name, so trusting it for SSL doesn't let it vouch for any real web site. **Trust it for SSL only:** name constraints don't cover other purposes (code signing, S/MIME, client certificates), and a CA trusted for everything would vouch for those too on macOS.

**Accepted risk (ADR-0039):** while you trust it, anyone who can read its key (anyone with access to Docker on this machine can read the `pki-ca` volume) can impersonate any HTTPS service of yours under `localhost`, a `*.localhost` name or `127.0.0.1`, on any port (your other local development services included). Remove the trust when you aren't using the project, and trust the new CA after a reset or renewal. It is separate from OPC UA trust (pinned leaves, above).

- **Trust the dev CA once per stack:** `pnpm stack:ca` (the dev stack; `COMPOSE_PROJECT_NAME=… pnpm stack:ca` for another) reads the CA certificate from the web container, checks that it issued the certificate nginx serves, writes it to `dev-ca.pem` (ignored by Git; `pnpm stack:ca <file>` for another path) and prints its SHA-256 fingerprint (the `pki` step logs the same: `docker compose logs pki | grep 'dev CA sha256'`). Then:
  - macOS (Safari, Chrome, Edge): `security add-trusted-cert -r trustRoot -p ssl -k ~/Library/Keychains/login.keychain-db dev-ca.pem` (asks for your password; `-p ssl` trusts it for TLS servers only), or Keychain Access → File → Import, then in the certificate's Trust section set **only "Secure Sockets Layer (SSL)"** to "Always Trust" and leave "When using this certificate" at "Use System Defaults". Check the fingerprint against the one printed. Remove it when you don't need it: `security delete-certificate -c 'shopfloor-twin dev CA' ~/Library/Keychains/login.keychain-db`.
  - Firefox (its own store): Settings → Privacy & Security → Certificates → View Certificates → Authorities → Import, tick "Trust this CA to identify websites".
  - Node.js tools: `NODE_EXTRA_CA_CERTS=$PWD/dev-ca.pem node …`; curl: `curl --cacert dev-ca.pem https://localhost:8443/healthz`.
  - Open the app as `localhost` (the certificate covers `127.0.0.1` too, but the cookie is per host name).
- **The browser says `NET::ERR_CERT_AUTHORITY_INVALID` / "Your connection is not private":** the dev CA isn't trusted yet, or this stack has a new one (after `pnpm stack:reset`, which deletes `pki-ca`, or `PKI_RENEW=dev-ca`). Run `pnpm stack:ca` and trust it again; remove the old "shopfloor-twin dev CA" from the keychain (`security delete-certificate -c 'shopfloor-twin dev CA' ~/Library/Keychains/login.keychain-db` removes one by name).
- **See the expiry dates:** `docker compose run --rm pki` (or `docker compose logs pki`) prints `dev-ca` and `web` with their `until` dates beside the OPC UA certificates, the CA's SHA-256 fingerprint and the web certificate's SPKI hash.
- **Renew:** the step renews what expires within 30 days on every `up`. `PKI_RENEW=web docker compose run --rm pki` renews nginx's certificate now; `PKI_RENEW=dev-ca …` makes a new CA and a new web certificate (then trust the new CA). **When it prints `pki: !!! RENEWED the web certificate: RESTART THE WEB !!!`:** `docker compose restart web` (nginx reads its certificate when it starts; `up` doesn't recreate an unchanged web container).
- **`docker compose ps` lists `8080/tcp` on the web:** cosmetic, the base image (`nginx-unprivileged`) declares `EXPOSE 8080`; nothing listens or is published there.
- **Reset only the HTTPS material:** `docker compose stop web`, `docker compose rm -f web pki`, `docker volume rm shopfloor-twin_pki-ca shopfloor-twin_web-tls`, then `pnpm stack:up` and trust the new CA.
- **The `web` container exits at once with `/etc/nginx/tls/server.pem is missing or unreadable`:** the `pki` step didn't run or failed (`docker compose logs pki`); `docker compose up -d` runs it. **The web stays unhealthy:** its health check fetches `https://localhost:8443/healthz` against the dev CA; a certificate from another CA (a hand-edited volume) fails it: rerun the step with `PKI_RENEW=web`.
- **`http://localhost:8080` no longer answers:** the web moved to `https://localhost:8443` in #241; update bookmarks and scripts. **400 "plain HTTP request was sent to HTTPS port":** use `https://`.
- **Scripts and tools that used the MES on 4700, the gateway on 4900 or the database on 5442:** run the stack with `pnpm stack:up:dev` (the same stack, those three ports published on `127.0.0.1` again), go through the web front (`https://localhost:8443/api/v1/…` with the dev CA and a session), or use `docker compose exec` (`docker compose exec db psql -U shopfloor -d shopfloor`, `docker compose exec mes wget -qO- http://127.0.0.1:4700/metrics`).
- **The harnesses** trust only the stack they start: they read `ca.pem` and `server.pem` from the web container, check that the handshake presents exactly that certificate, trust the CA in their own process and through `NODE_EXTRA_CA_CERTS` in their children, and launch Playwright's Chromium with `--ignore-certificate-errors-spki-list=<SPKI hash of that certificate>` (never `ignoreHTTPSErrors`), so the browser accepts that one key and refuses any other certificate (`e2e/browser/tls/tls.spec.ts`).

### Observability profile (#244, P9-17, ADR-0012 amendment)

Prometheus and Grafana beside the stack, opt-in (`compose.observability.yml`). `pnpm stack:up` never starts them and needs nothing new. The file has two profiles: `observability` is Prometheus, `grafana` is Grafana on top of it. `pnpm stack:up:observability` starts both; the performance suite (P9-18) starts Prometheus only. Prometheus scrapes every component's `/metrics` every 5 s inside the Compose network (the MES on `mes:4700`, the gateway on `gateway:4900`, the simulator on `simulator:4800`, the ERP mock on `erp:4600`, and itself), so the MES and the gateway stay unpublished. Grafana has the Prometheus datasource and **no dashboards** (on the Phase 9 cut line, cut): use its Explore view or Prometheus's own UI with the queries below.

First time: add the Grafana admin's password to `.env` (Grafana's profile refuses to start without it; no default):

```bash
printf 'GRAFANA_ADMIN_PASSWORD=%s\n' "$(openssl rand -hex 16)" >> .env
pnpm stack:up:observability      # the stack, Prometheus and Grafana; add `--file compose.dev-ports.yml` by hand if you need both
pnpm stack:down:observability    # stops all of it; plain `pnpm stack:down` leaves Prometheus and Grafana running
pnpm stack:reset:observability   # the same with every volume, Prometheus's data included
```

| What       | URL (127.0.0.1 only)                        | Login                              |
| ---------- | ------------------------------------------- | ---------------------------------- |
| Prometheus | <http://localhost:9090> (`PROMETHEUS_PORT`) | none (as the `/metrics` it reads)  |
| Grafana    | <http://localhost:3000> (`GRAFANA_PORT`)    | `admin` / `GRAFANA_ADMIN_PASSWORD` |

- **Grafana keeps its state in memory** (a tmpfs on `/var/lib/grafana`): the password is `.env`'s on every start and restart (change it there and `pnpm stack:up:observability`), and a restart ends every session and API token and drops anything saved in its UI.
- **What Grafana can't do:** anonymous access, sign-up, plugin installs (also from the UI), plugin signature-key downloads, usage reports, update checks, news, external snapshots, public dashboards, alerting and its own `/metrics` are off; its data source proxy is allowed `prometheus:9090` only.
- **What it still can, an accepted risk (ADR-0012 amendment):** its `observability` network can't be `internal` (an internal network can't publish a port), so the container has a route to the Docker host (with Colima, everything the Mac publishes on `127.0.0.1`: the plant's ports, other projects' databases) and to the internet. The only user is `admin` with a random password on `127.0.0.1`; don't share it, and stop the profile when you don't use it.
- **Prometheus sends no CORS header**, so a web page on another origin can't read the metrics from your browser. It has no Host check, so a DNS-rebinding page still could: read-only metrics, no secrets (accepted, ADR-0012 amendment).
- **Prometheus keeps 3 days or 1 GB**, whichever comes first (`PROMETHEUS_RETENTION_TIME`, `PROMETHEUS_RETENTION_SIZE`), in the volume `prometheus-data`. Prometheus reads "GB" as GiB, and its write-ahead log can take it a little over the size limit. `pnpm stack:reset:observability` removes it with the stack's volumes; a `down --volumes` without `--file compose.observability.yml` leaves it behind.
- **Limits:** 0.5 CPU each; Prometheus 256 MiB, Grafana 512 MiB. Measured with the stack at 60× (#244, Colima VM 4 GiB / 4 CPUs, a few minutes after start): Prometheus 33 MiB anonymous memory (1,385 series, 180 KB on disk), Grafana 231 MiB anonymous plus page cache (`docker stats` shows 340–470 MiB, peak 502 MiB); no OOM kill. That peak is why the performance suite leaves Grafana out (T5: every container's peak below 80 % of its limit). Images: Prometheus 357 MB, Grafana 1.8 GB unpacked.
- **Ports:** `PROMETHEUS_PORT=0` or `GRAFANA_PORT=0` lets Docker choose a free port; read it back with `docker compose --file docker-compose.yml --file compose.observability.yml --profile observability --profile grafana port grafana 3000`.
- **Check it:** `pnpm stack:smoke:observability` starts the stack and both profiles (as `stack:up:observability`, from `.env` or `SMOKE_ENV_FILE`) and checks every target up, one metric of each component, no CORS header, Grafana's health, the refusal of anonymous and `admin:admin` logins, the datasource reaching Prometheus, Grafana's hardening (no `/metrics`, no plugin admin, state on a tmpfs) and both networks; it prints both containers' memory.
- **Not in Prometheus:** the broker and the database (no exporter), nginx, and container CPU and memory (no cAdvisor: it needs the Docker socket). The simulator's, gateway's and MES's `process_*` metrics are there; the ERP mock has none.

### Troubleshooting

- **A port is already in use:** set `WEB_HTTPS_PORT`, `MQTT_PORT`, `SIM_CONTROL_PORT` or `ERP_HTTP_PORT` in `.env` (and with `pnpm stack:up:dev` `DB_PORT`, `MES_HTTP_PORT` or `GATEWAY_HTTP_PORT`; the OPC UA ports 4841–4845 are fixed by the contract) and run the same start again.
- **`Set DB_PASSWORD in .env`:** `.env` is missing or incomplete; see the first step above. **`Set DB_APP_PASSWORD in .env`:** an `.env` from before #169; add the line as shown above.
- **The MES stays unhealthy, logging `waiting for the database to be migrated`:** the `migrate` service failed or hasn't run (`docker compose logs migrate`); `docker compose up migrate` runs it again. **`password authentication failed for user "mes_app"`:** `DB_APP_PASSWORD` changed while `migrate` didn't run since; `docker compose up -d` runs it, which sets the password again.
- **Broker users changed:** the dynamic-security configuration (`/mosquitto/data/dynamic-security.json`, password hashes, `0600`) is rebuilt from `config/mosquitto/dynamic-security.json` and `.env` on every broker start; restart with `docker compose restart broker`. The broker logs `entrypoint: …` and exits when `MQTT_USERS` names a user the template doesn't have or a template user gets no password. There is no admin user: users and roles change only in the template.
- **`Connection Refused: not authorised` (CONNACK 0x87) for the gateway or the MES** (ADR-0039): the broker binds client ids to users: `gw-01` and `gw-01-cmd` (`MQTT_GATEWAY_PASSWORD`), `mes` with client id `mes-server` and `mes-cmd` with `mes-server-cmd` (`MQTT_MES_PASSWORD`). Another `GATEWAY_ID` or `MQTT_CLIENT_ID`, or an old image that logs its command connection in as `gw-01` or `mes`, is refused. Every other user is bound to its own name too (`healthcheck`, `dev`, `smoke-reader`), so every manual command needs `-i` (`mosquitto_sub -i dev …`) and `dev` has one session at a time: a second `-i dev` takes the first one's session over. Never connect as `mes` while the MES runs: a clean connection under `mes-server` ends its persistent session and its queue.
- **Debugging MQTT connections:** set `connection_messages true` in `config/mosquitto/mosquitto.conf` (off by default because the healthcheck connects every 5 seconds) and restart the broker.
- **Memory:** measured with the full stack at 60× (#99, Colima VM with 2 GiB and 2 CPUs, the web app's detail screen open, `docker stats` every 12 s for 4 minutes, maximum):

  | Service   | Memory  | Limit                   | Image   |
  | --------- | ------- | ----------------------- | ------- |
  | db        | 61 MiB  | 1 GiB, 1.5 CPUs (#228)  | 1.45 GB |
  | broker    | 4 MiB   | 128 MiB, 0.5 CPU (#228) | 43 MB   |
  | simulator | 190 MiB | 512 MiB                 | 389 MB  |
  | gateway   | 94 MiB  | 384 MiB                 | 398 MB  |
  | mes       | 79 MiB  | 512 MiB                 | 314 MB  |
  | web       | 9 MiB   | 64 MiB                  | 94 MB   |
  | **Total** | 437 MiB | 2.6 GiB                 |         |

  Every service has a limit since #228 (security review S8): the database's 1 GiB leaves room above its 512 MB tuning (`DB_TUNE_MEMORY`) for connections and maintenance, and the broker's 128 MiB is about 30 times its use; the ERP mock (128 MiB, 0.5 CPU) and the one-shot `migrate` step (256 MiB, 0.5 CPU) are not in the table above. The database grows towards its 512 MB tuning as data and queries grow, and `pnpm test` and `pnpm test:e2e` start their own TimescaleDB and Mosquitto containers through Testcontainers beside the stack. The stack fits a 2 GiB VM today, but with little room: give the Docker VM **4 GiB** (Colima: `colima stop && colima start --memory 4 --cpu 2`; Docker Desktop: Settings → Resources). Containers that hit their limit are killed (`docker compose ps` shows the restart, `docker inspect <container> --format '{{.State.OOMKilled}}'`).

## Reconciliation run

One simulated shift through the whole chain, simulator → gateway → broker → MES → web, checked against the simulator's own ground truth (#100; Phase 4 exit criteria 1 and 3; Phase 5 exit criteria 3, 4 and 5 with #120 and #123; Phase 6 exit criteria 3, 4 and 5 with #147). Since #147 the run is the golden scenario `alarms-01`: week-01's seed and start with injected failures, so shift A has a flood, a chattering point and a fleeting alarm to reconcile. It runs as its own CI job (`reconcile`) and locally:

```bash
pnpm playwright:install   # once: Chromium's headless shell for Playwright
pnpm test:reconcile       # about 9 minutes locally: image builds, start-up, 8 minutes of shift
```

It needs Docker (Colima or Docker Desktop; with Colima, export `DOCKER_HOST` from `docker context inspect --format '{{.Endpoints.docker.Host}}'`) and Node.js 26. It does not use `.env`: it writes its own env file with random passwords (`MES_BOOTSTRAP_ADMIN_PASSWORD` included, #170) to a temporary directory and runs Compose as project `shopfloor-reconcile-alarms` (and `shopfloor-reconcile-orders` for the orders pass, below) with `e2e/compose.reconcile.yml` on top of `docker-compose.yml` (ephemeral host ports on `127.0.0.1`, no published database or broker ports, no restarts, fresh volumes). A dev stack on the default ports can keep running beside it; its images are built from the working tree under their own tag (`IMAGE_TAG=reconcile`, so `shopfloor-twin/*:reconcile`; the dev stack's `:dev` images stay as they are). At the end the project is removed with its volumes, also after a failure; Ctrl+C or SIGTERM removes it and the env file before exiting, and after 25 minutes (`RECONCILE_DEADLINE_MS`) the run fails by itself with its report and logs.

What it does, in the Phase 4 plan's order:

1. Builds the images, then starts `db`, `broker` and `mes` (after the one-shot `migrate`) and waits until the MES is ready (migrated, subscribed). The bootstrap admin logs in, changes its temporary password and creates the run's `reconcile-supervisor` through the API (#170, `provisionUsers` in `e2e/src/clients.ts`); the run's API reads use its session and the Playwright checks log in as it through `/login` (`e2e/browser/login.ts`).
2. Starts the simulator idle (`SIM_AUTOSTART=false`, seed and start of the golden week: Monday 2026-10-12 06:00 Istanbul, the start of shift A) and the gateway, and waits until the gateway is ready with all six machines connected and the MES has every machine's start-up state (Off at 06:00, from the gateway's snapshots) for the simulator's epoch. Compose's `depends_on` starts the gateway only once the simulator answers; since the simulator is idle, nothing happens before the MES listens. Then it posts the scenario's 14 shift A injections (`POST /api/v1/faults/failure/{machine}` with `code`, `at` and `repairMs`; control API 1.3) in the scenario's order before the resume, which puts the same events in the queue as the headless run (`docs/contracts/simulator-control-api.md`, "Determinism"): 13 on Cell M1 from 08:00 Istanbul (a flood, with CNC-01 `COOLANT-PRESSURE` chattering) and LKT-01 `FIXTURE-SEAL` with a 500 ms repair (fleeting) at 09:20. The PCK-01 injection of shift B lies after the run and is not posted. `alarms-01`'s event log equals week-01's up to the first injection (the headless test in `apps/simulator/src/headless/alarms-01.test.ts`), so week-01's live evidence of Phases 4 and 5 carries over; the report names that test (`injections.prefixEvidence`).
3. Starts `web` (HTTPS since #241: the run reads the dev CA's and nginx's certificates from the web container, checks that the handshake on the published port presents that certificate, trusts the CA in its own process and through `NODE_EXTRA_CA_CERTS` in Playwright's, and launches Chromium pinned to that certificate's key with `--ignore-certificate-errors-spki-list`; "HTTPS and the dev CA"), resumes the simulator at 60× over its control API (`POST /api/v1/resume`) and runs Playwright beside the shift (project `live`; its files run in name order: `1-oee-live`, `2-alarms-live`, `3-overview`). The overview check (`e2e/browser/3-overview.spec.ts`) runs last: Chromium opens the overview, waits for `connection-status` to be `open`, then for 90 s (`OVERVIEW_SAMPLE_MS`) compares each machine's `state-<id>` badge (`data-state`, recorded by the page every 20 ms) with the simulator's current state (`GET /api/v1/ground-truth`, polled every 200 ms). When the truth changes at time t, the page must show that state, or a state the truth took later, by t + 2 s. A change's time is when the paced simulation clock reached the state's start (`pacedTime` of the same answer, at the request's midpoint). The page must also really change: at least half as many transitions as judged changes, and one on every machine whose truth changed, so a frozen page can't pass by showing a state the truth returned to.
   Before it, the alarm check (`e2e/browser/2-alarms-live.spec.ts`, #147, Phase 6 exit criterion 3) starts after the OEE check and before the first injection (it fails at once if the paced clock is already past it): Chromium opens `/alarms` (Active tab) and `/alarms/kpi` and records every 20 ms which `alarm-row-<id>` rows exist, both positions' `flood-banner-<id>` (`data-episode`) and the KPI cards' `data-raises`, while the test polls `GET /api/v1/ground-truth` every 200 ms until the paced clock is 3 simulated minutes past the last injection (about 200 s of wall time). The truth is complete: `alarms.occurrences` lists every raise to the millisecond and `alarms.scopes.<position>.floods` every episode, each timed as the overview's states are. Rules: every raise appears as a row within 2 s of the paced clock reaching it (each row is resolved to its occurrence with `GET /api/v1/alarms/{id}`, and a row matching no raise fails: the unseen-value floor is 0); the page adds a row for every judged raise (frozen-page ratio 1); all 14 applied injections are among the judged raises; Cell M1's banner shows the episode id within 2 s of the flood's start and goes away within 2 s of its end, Line A1's never shows; each card reaches every count its scope took (or a later one) within 2 s, shows only counts the scope held, agrees with the truth in at least 95 % of the snapshots (one a second, allowing the push's 2 s pacing), and changes at least a quarter as often as the truth (the push sends one delta a second while the flood raises up to 12 alarms a second of wall time).
   The OEE dashboard check runs first (`e2e/browser/1-oee-live.spec.ts`, #123, Phase 5 exit criterion 5), from the shift's start as in Phase 5. It samples for at most 90 s (`OEE_SAMPLE_MS`), and stops when the paced clock reaches 15 simulated minutes (15 s at 60×) before the first injection, so the alarm check starts in time in a slower environment: Chromium opens `/oee` (the current shift), the page records `data-oee` of both work-center cards (`oee-card-<id>`) and all six machine rows (`oee-machine-<id>`) every 20 ms, and the test polls `GET /api/v1/shifts/2026-10-12/A/oee` every 100 ms. The API's OEE changes about twice a second, the push at most once a second per topic, so the same rule applies with the four-decimal OEE as the state: by t + 2 s the page shows that value or one the API held later. A value the polls did not see within 5 s of the page showing it (held between two polls) counts only when the page took it after the change, so the value checks below are what catch a page lagging more than that: at most 5 % of the page's values may be values the polls never saw in the whole run (real runs: about 1 %). Since #147 "seen" means seen within those 5 s, not anywhere in the run: four-decimal OEE values repeat (later in the shift about half of them repeat an earlier one), and a transient value whose four decimals the polls had seen at another moment was taken for a stale one, which made a change wait for the next push and failed runs. A page lagging 2 to 5 s still has its stale values judged as stale, and one lagging more fails the snapshot agreement (unit tests in `e2e/src/latency.test.ts`). Frozen-page guard: at least half as many page transitions as judged changes (real runs: about 0.7), one on every id; at least 20 judged changes per card and 100 in all. Every 2 s a snapshot of all eight values must equal what the API held within the 2 s before (or 0.5 s after) the snapshot, for at least 95 % of the values and at least once per id.
4. Polls `GET /api/v1/status` every second (lag, progress) until the simulation is 5 minutes past shift end (14:05). From then on it also checks, every second, that the MES has stored a device fact (state change, cycle or alarm) of every machine at least a second (`fleetingMs`, for the alarm KPIs, #142) after the shift end (14:00), and pauses the simulator once it has (#113). A machine that is Down, in Setup or in Maintenance across the shift end sends nothing until that ends (ASM-01, LKT-01 and PCK-01 send no telemetry either), and its shift-A bucket stays provisional until it does. The wait is bounded by `RECONCILE_SILENT_WAIT_MS` (simulated time past 14:05, default 2 hours, two wall minutes); the report records it as `silentWait`, with each machine's first fact after the shift end. In the golden week every machine reports within about 3 simulated minutes, so the run normally pauses at 14:05. The wait also has a wall budget (twice its nominal time plus a minute), and the run fails at once if the simulation clock stops moving for 30 s of wall time, rather than at the 25-minute deadline.
5. Waits until the MES has drained: every machine's current state and start equal the simulator's, the gateway's buffer is empty and the plant watermark is past shift end. The totals are then read once; Phase 4's wait for "totals stable" is gone, since shift A must now be final.
6. Compares, and fails on any difference:
   - time per state, per machine, for shift A (`GET /api/v1/shifts/2026-10-12/A/totals`) equals the simulator's ground truth for that bucket to the millisecond, and the ground truth covers all 8 hours of each machine;
   - shift A is final for every machine: `provisionalMs = 0`, `revision = 0` and `incidents = 0` in the totals (#113, Phase 5 exit criterion 3);
   - the live ground truth equals `alarms-01`'s shift A (`apps/simulator/golden/alarms-01/summary.json`), time per state and OEE: pacing never changes the run;
   - the 14 injections are listed by `GET /api/v1/faults/injections` as `applied` inside shift A (the held ones a little after their `at`);
   - every stored piece (`equipment.equipment_state_interval`, read with `psql` in the `db` container) lies inside one UTC hour and one shift bucket of the shared calendar;
   - no data-quality incident of lost data (`sequence-gap`, `ring-overrun`, `buffer-overflow`) and no rejected UNS message. With this start order there is no start-up gap; one would mean the order is wrong;
   - shift A's OEE (`GET /api/v1/shifts/2026-10-12/A/oee`, #120) becomes `final` for all six machines within 30 s of the drain (the aggregates' refresh debounce), with `provisionalMs = 0`, `revision = 0` and `incidents = 0`, and equals the live ground truth's `oee` exactly for every machine (inputs, fractions, four-decimal strings, totals, losses, `unplanned`) and work center. A difference is printed as `path: truth ≠ MES` lines and kept in `report.json` (`oee`). Both work centers must be final too, the MES and the ground truth must list exactly the plant configuration's six machines and two work centers, and the count of compared buckets (`oee.compared`) must be 8 (#123);
   - shift A's alarm KPIs (`GET /api/v1/alarms/kpi`, #142, #147) for the plant and both operator positions, per shift and per UTC hour, become `final` within 30 s, with `provisional` false, `revision = 0` and `incidents = 0`, and equal the live ground truth's `alarms` section exactly (raises, rates, windows, floods, standing, chattering, fleeting, active time), which in turn equals `alarms-01`'s summary; the hours listed must be the same on both sides. 3 shift buckets and 4 hour buckets are compared (`alarms` in `report.json`), and the run fails unless the plant, Cell M1 and Line A1 raised 14, 13 and 1, Cell M1 has a flood episode and `cnc-01/COOLANT-PRESSURE` chattered, and Line A1 has a fleeting alarm;
   - shift A's report (`GET /api/v1/shifts/2026-10-12/A/report`, #144) is `final` with `revision.inputs = 0` and no incident; its OEE section is `GET …/oee` byte for byte; each scope's alarm KPIs are `GET /alarms/kpi`'s shift bucket byte for byte and the ground truth's; per machine produced, good, scrap and rework equal the OEE inputs and the ground truth's cycles; finished parts are PCK-01's good cycles; the Pareto sums to the own plus external availability loss; the instance has the calendar's start, end and breaks (`shiftReport` in `report.json`).
7. Acts through the UI with the simulator paused and shift A final (Playwright project `final`, files in this order). Around the project it reads the alarm KPIs of every scope (hours and shift) and shift A's OEE, and requires both byte-identical afterwards; then it checks with `psql` that `alarms.alarm_transition` and `shifts.handover_audit` hold rows and refuse UPDATE and DELETE (`coding.auditRefusals`): each statement runs inside `BEGIN; …; ROLLBACK`, and only the trigger's own error (`append-only (UPDATE refused)`, `append-only (DELETE refused)`) counts as a refusal; success or any other error fails the run.
   - **Alarm actions** (`e2e/browser/final/alarm-actions.spec.ts`, #147, Phase 6 exit criteria 3 and 5): each of the shift's 14 alarms is `unacked-cleared` (cleared on repair) and final. As `reconcile-supervisor`, it acknowledges the first one from its row, comments on a CNC-01 `COOLANT-PRESSURE` in its panel, shelves another point for 15 minutes (its alarms move to the Shelved tab) and unshelves it, then acknowledges the rest with **select all** and **Acknowledge selected**. Then every alarm of the shift is `closed` and acknowledged by the operator; each one's `GET /api/v1/alarms/{id}/history` holds the device raise and clear (with `seq`, `receivedAt` and protocol, at the occurrence's times) and its audited transitions (`ack`, plus `comment` for the commented one) with actor, `authenticated: true` and request id, and the panel lists the same entries; the point's audit holds the shelve (version 1, reason, 15 minutes) and the unshelve (version 2). `GET /api/v1/alarms/kpi` stays byte-identical, while `GET /api/v1/alarms/operator-kpi` of each scope counts every raise of the shift as acknowledged (`timeToAck.count` 0 before and the raises after, sum and longest above 0), with raises, shelved raises and unacknowledged at the end unchanged; the KPI page's operator measures show the count. An acknowledgement with a foreign `Origin`, without `Origin`, as a form and without a session answers 403, 403, 415 and 401 with the problem types `urn:shopfloor:write-origin`, `…:write-origin`, `…:write-not-json` and `…:unauthenticated`.
   - **Downtime coding** (`e2e/browser/final/downtime-coding.spec.ts`, #123, Phase 5 exit criterion 4): it takes the longest closed, final record of shift A without codings (the golden week has no UNCODED record), opens `/downtime` for shift A, filters by its machine, splits it on a whole plant second near its middle, picks two leaf reasons other than the automatic one (`reason-picker`), and saves (as `reconcile-supervisor`, from the session). Then: one `audit-entry` on screen and one `coded` entry in `GET …/audit` with both segments; the machine's `GET /api/v1/downtime/pareto` for the shift moved exactly by the record (its time left the automatic reason and went to the two coded ones; availability and micro-stops unchanged); the dashboard's Pareto shows the new reason; `GET /api/v1/shifts/2026-10-12/A/oee` is byte-identical before and after, and the cards' `data-oee` on `/oee?shift=2026-10-12/A` are unchanged. Writes with a foreign `Origin`, without `Origin`, with a form content type and without a session must answer 403, 403, 415 and 401 (sent with an invalid version, so a broken guard would answer 422, never code anything).
   - **Handover note** (`e2e/browser/final/shift-report.spec.ts`, #147, Phase 6 exit criteria 4 and 5): shift A's report is final with `revision.inputs = 0` and a `contentAtFinal`; the acknowledgements and the recode above have already raised `revision.content`. Notes:

- Interval finality (#113, ADR-0018): a stored piece is final once it ends at or before its machine's "final through", the latest time of that machine's own device facts with no open sequence gap below them, or once its epoch is closed. So shift A becomes final as soon as each machine has sent a fact after 14:00; the plant watermark alone can't do it, since it is plant-wide and a busy machine moves it past a silent one. If a run fails with `provisionalMs` above 0, look at `silentWait` and the machine's state at 14:00 in the report: a machine silent for longer than `RECONCILE_SILENT_WAIT_MS` fails the run with its name. A `revision` above 0 means a fact arrived for an hour that was already final (a gap reported as an incident and filled late, or a late fact of a closed epoch), and `incidents` above 0 a sequence gap; neither may happen with this start order.
- If the run fails with lag, read `lagMs` in `report.json` (the simulator's `GET /api/v1/status`): at 60× the simulator processes events within a few milliseconds of their time on a laptop. A large lag means the machine (or the CI runner) is short of CPU; the run fails if the shift takes more than twice its nominal wall time, rather than slowing down silently.
- The run uses about 450 MiB in the Docker VM, like the full stack; Chromium runs on the host.
- Duration (#147, measured locally on an M3 MacBook Air with cached images): 523–526 s in all (two passing runs), of which 486 s are the shift at 60× (lag p95 2.4–2.5 ms), about 35 s start-up and about 4.3 s for the `final` project. Cold image builds and the browser's system libraries add several minutes in CI (Phase 5: 10.8 minutes for the whole job), well inside the job's 30-minute limit and the run's own 25-minute deadline.
- If the alarm check fails on `rows`, look at `alarms-latency.json`: `unmatchedRows` are rows of no raise of the truth, and a violation without a latency is a raise never listed. `injected.judged` below `applied` means an injection's raise was applied before sampling began (a browser that started late) or not at all (`GET /api/v1/faults/injections`).

- **After each fault:** readiness within 30 s of wall time; the MES caught up (the same conditions through the fault's end); the metrics show the outage (broker: `gateway_buffer_messages` > 0 or `gateway_mqtt_connected` 0; database: the MES not ready, `mes_ingest_suspensions_total` or `mes_ingest_store_errors_total` up; ERP, MES, gateway: the service gone; OPC UA and Modbus: `gateway_device_connected` 0); then a mark for Playwright (`e2e/browser/resilience`, project `resilience`), which keeps the overview open through the run: the WebSocket open again within 30 s of readiness (the client's backoff is capped at 15 s), every badge current within 2 s of the later of that and the MES having caught up, and every state change after it shown within 2 s for at least 15 s.
- **No loss (R1, R2):** after the drain, shift A's time per state, OEE per machine and work center, alarm KPIs and report (`e2e/src/shift-checks.ts`, the reconciliation's own), order and line OEE, units, quantities and confirmations (`e2e/src/orders-pass.ts`), and the trace at 14:00 (`e2e/src/quality-pass.ts`, no drift) equal the live truth and are final; every fact the simulator raised is stored exactly once; no `sequence-gap`, `ring-overrun` or `buffer-overflow` incident, no rejected message; every MES message to the ERP sent and held by the ERP exactly once (the same idempotency keys); WSH-01 raised fewer facts in its silence than its 64-entry ring.
- **Detected loss (R3):** per machine the numbers in the MES's `sequence-gap` incidents equal (raised − stored); each lost fact lies in [outage start − ε, resync] in simulated time with its number at most the resync's `asOfSeq` (ε = 2 simulated minutes; the start read from the control API when the fault was taken; `asOfSeq` from the gateway's first alarm snapshot after the session returned, and its time from the simulator's event log, not from the system under test), the largest lead recorded; gap numbers compared as a multiset (a number in two incidents fails); no `ring-overrun`, `buffer-overflow` or rejected message; the state resynced within 10 s (a new state anchor equal to the simulator's state); every machine's shift A OEE final; and, once the stack is gone, `apps/mes-server/src/resilience-replay.e2e.test.ts` feeds the facts and anchors the MES stored into the golden harness's modules on a Testcontainers database, sweeps the holes and must answer shift A's OEE and totals exactly as the live MES did. **R3's schedule is moved from the plan's** (coordinator's decision on #243, ADR-0009 amendment): the plan's CNC-01 outage 07:00–07:30 loses nothing (an OPC UA server offline keeps the gateway's session and subscription, which republish every queued event on the reconnect), and its gateway kill 10:00–10:05 lies in shift A's break (10:00–10:30), when no machine raises a fact. The default kills the gateway at 10:45 while the line runs and must lose at least one fact (`exercised: true`), or the run fails. `RESILIENCE_R3_SCHEDULE=plan` runs the plan's first schedule as a non-loss variant (reported `exercised: false`, not a pass of exit criterion 5).
- **Environment:** `RESILIENCE_RUNS` (default `r1,r2,r3`), `RESILIENCE_TAG` (images, default `resilience`), `RESILIENCE_SKIP_BUILD=1`, `RESILIENCE_KEEP_IMAGES=1` (removed by default), `RESILIENCE_DEADLINE_MS` (per run, default 35 minutes), `RESILIENCE_R3_SCHEDULE` (`default`, or `plan` for the non-loss variant). About 10 minutes per run after a build; each project is removed with its volumes, also on failure, and the images at the end.
- **Results:** `e2e/results/resilience/results.json`: the commit, the VM (CPUs, memory, kernel, Docker, Docker's free disk, `colima list`), the host (CPUs, memory, free disk, load average at the start and the end), the image ids, and per run and fault the scheduled and actual simulated times, spacing, the settled check's wait and ingest figure, readiness and catch-up times, exit codes, the outage signals, the resyncs, the facts raised, stored and lost, the ε lead and the replay; per run `report.json`, `recovery.json`, Playwright traces and, on failure, `compose.log`.
