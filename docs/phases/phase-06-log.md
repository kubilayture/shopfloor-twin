# Phase 06 – Alarms and shifts: log

Dated entries, one per merged pull request: what merged, what was learned, deviations from the plan.

## 2026-10-16

- Phase 6 planned: issues #138–#148, milestone "Phase 06 – Alarms and shifts".
- Merged #149 (#138): Phase 6 plan, revised twice after review (failure injection only in `Running` and held otherwise, revisions over every hour a late fact can change, old-epoch anchors and snapshots, lost clears closed by resync snapshots).
- #139: `@shopfloor/alarm-core` and the alarm definitions (ADR-0024; ADR-0005 amended).
  - The KPIs per bucket and scope as the plan defines them, in integers and `oee-core`'s BigInt fractions; `exactnessRules` now covers `alarm-core`. A bucket is any range on whole UTC hours, so a shift or a `no-shift` stretch is computed directly or composed from its hours; a property test checks that both agree for every field.
  - `docs/alarm-kpi-reference-cases.md` has 22 cases covering every case in exit criterion 1, recomputed by an independent brute-force Python script (it counts the window at every candidate instant, without the sweep the code uses) before the TypeScript ran; both agreed on the first run. The tests parse the six tables (occurrences, horizons, buckets, episodes, bad actors, revised hours); changing one digit fails a test.
  - The purity rule now lets a pure package import another pure package by its exact name; `alarm-core` imports `oee-core`. A subpath, `plant-config`, `contracts`, an app or a Node.js built-in is still refused (tested).
  - `config/plant/alarms.yaml` is loaded by `plant-config` outside `SIMULATION_FILES`. The simulator's hash test changes thresholds, definitions and positions and still gets the golden summary's `configSha256`; `pnpm test:golden` is byte-identical.
  - `alarmVocabulary` in `@shopfloor/contracts` lists what the plant can raise; the simulator now imports its calibration alarm constants from there.
  - Deviation (strengthening): the plan's revision rule for a late raise is [t, t + max(window)] plus its active span. `revisionSpans` also covers an earlier open occurrence of the same point that the late raise now supersedes, and every flood episode in flood during [t, t + window] to its end, because a late raise can join two episodes and change the id and peak of every later hour of the joined one (reference case 20). For a late clear the span runs from the raise to the later of the two ends, so the hours after the clear that showed the occurrence active are revised too (case 19), not only the raise→clear span.
  - Deviation: a flood episode's id is `{startAt}~{equipment}~{code}`, not the plan's (start, seq): `seq` is per device, and an id without it lets the ground truth and the MES agree by construction. Raises in one millisecond are ordered by equipment, then `seq` (within a device), then code.
  - Decisions the plan left open, recorded in ADR-0024: at one instant the raises that leave the window go before the raises that arrive, and the flood state is the count after both, so an episode goes on when its last counted raise leaves as another arrives; a superseded or epoch-ended occurrence is never fleeting; an open raise is undecided while raise + `fleetingMs` − 1 > `asOf`; in a closed epoch a running flood ends at the close.
  - Review (PR #150), adopted: a raise arriving at the instant a flood ends was counted as one of its raises (now [start, end), reference case 21); raise order and flood ids no longer compare sequence numbers across devices (case 22); `clearKind: 'lost'` is never fleeting; a bucket after `asOf` lists no open episode; the reviewer's revision-completeness fuzz is a property test; the OPC UA servers take their alarm codes from `alarmVocabulary`; ADR-0024 notes that floods are scope-wide, so a late fact revises position and plant hours.
  - `analysisConfigSha256` belongs to #140 (`sim-summary/3`), not here.
- #141: ingest, gateway and master data for alarms (ADR-0017 amended; UNS contract 1.2; register map 2).
  - Gateway: the alarm snapshot is published with every state snapshot. OPC UA reads `Epoch`, `Sequence` and the `Active` variables in one Read call; the codes come from `plantAlarms` (the machine's slice of the vocabulary). A Read with any value not Good publishes nothing; the next resync tries again. `sourceTime` is the `Sequence` value's source timestamp, the time of fact `asOfSeq`, so a lost clear closed at the snapshot's time is never later than the snapshot proves.
  - Contract change, additive: the WSH-01 map had only a heater-fault status bit (register 8), which is refreshed at read time and covers one code. Register 17 `activeAlarms` holds a bit per alarm table entry and is written in the same step as the ring entry and `eventCounter`, so one read of registers 0–17 is atomic. Map version 2; a version 1 reader of 0–16 is unaffected. The only simulator change is that register (`washer-server.ts`), apart from #140's files.
  - Topic: `_snapshot` is the one non-kebab topic name, allowed only under `alarms`, so it can never collide with an alarm code's topic.
  - Ingest: a retained alarm or a snapshot counts as `anchor` in the metrics. The newest epoch of an equipment is the greatest of its device stream's cursor, its state anchors' device epochs, its alarm anchors and its snapshots; staleness is stored, not computed on read, so every reader sees the same rule. A test starts ingest after a simulator restart with the old run's alarms and snapshot retained, in both arrival orders, and none is listed as active.
  - Deviation: the brief named the table `master_data.alarm_point`; the plan's `alarm_definition` is kept, with `alarm_position` and `alarm_position_work_center` for the positions. `alarmFacts` takes `fromSeq`/`toSeq` (inclusive), like `stateFacts`, for the plan's `from`/`to`.
  - Added beyond the plan: `alarmFactCounts()` for the alarms module's catch-up, and `alarmBaseline()` with the pure `resolveAlarmBaseline`, so the snapshot-versus-anchor rule is tested here, before #142 uses it.
