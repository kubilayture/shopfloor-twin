## Scope

The plant runs from orders, and every MES write has a known user:

- **`identity` module:** users, roles, login, server-side sessions in a cookie, scrypt password hashes, a permission matrix, one append-only `identity.audit_log` that replaces the three module-local audits; every existing write (downtime coding, alarm lifecycle, handover notes) takes its actor from the session. Reads and the WebSocket need a session too.
- **Database roles:** migrations run as an owner role in a separate step; the MES connects as an application role that owns no table, so it can no longer disable an audit trigger (the ADR-0023 promise); the continuous aggregates belong to a role of their own that the MES assumes only to refresh them.
- **`erp-mock` app:** a small REST service holding orders (with their routing and BOM), lots and the confirmations it received; the MES pulls orders from it and posts confirmations and status messages back, idempotently.
- **Order-driven simulator:** a production mode `orders` in which the CNCs run only the jobs dispatched to them; a new idempotent OPC UA method `LoadOrder`; job facts in the device sequence; ground truth per order and per part.
- **Command path:** MES → UNS `cmd/load-order` → gateway → OPC UA `LoadOrder` → `cmd-res`, at-least-once with idempotent execution, proven exactly-once by device facts; broker ACLs so only the MES can command.
- **`orders` module:** import, release, dispatch to a CNC, command tracking, order status, confirmations and status messages to the ERP through a transactional outbox.
- **`execution` module:** every part tracked through OP10–OP50 from cycle facts, rework passes, WIP, quantities per order operation, backflushed material.
- **Operator terminal:** a tablet screen per work center: sign on and off, current order, start, pause and resume, scrap reason coding, operation sign-off.
- **OEE:** the scheduled-time rule switches to `orders` (an `Idle` with no startable order is excluded from planned busy time).
- **Web:** login, user administration, orders list and detail (release, dispatch), the terminal; every existing write screen loses its free-text name field.

Out of scope here:

- lot genealogy, serial and carton trees, `material_lot` in the MES, lot-level consumption facts on the UNS, operators per serial and the traceability screen (Phase 8). Phase 7 keeps parts, not genealogy;
- quality holds, SPC and measurements as records (Phase 8); manual physical scrap of a part the machines didn't scrap (needs a control-API action; Phase 9 console);
- commands other than `load-order` (no hold, cancel or short-close on the machine), Modbus writes to WSH-01 (the washer's register map is read-only), automatic make-up jobs for scrap;
- per-order OEE and a throughput-based line OEE (section 7 "per order"): deferred to Phase 8 with the order data in place;
- alarm positions that follow crews (ADR-0024 "revisit"): positions stay configured work centers;
- OPC UA and simulator control-API authentication, MQTT dynamic security (client-id binding), TLS and `Secure` cookies by default (Phase 9);
- partial (per-shift) confirmations; only final and correction confirmations;
- retention and compression, `prom-client`'s successor, the O(hours × occurrences) alarm KPI read (carried).

## Decisions made in this plan

### What the code does today

- **The simulator decides its own production.** `config/plant/schedule.yaml` gives each CNC a list of campaigns (product, quantity); `ProductionLine.#nextBlank` takes the first campaign with `remaining > 0`, changes over when the product differs, and goes `Idle` with `SCHEDULE-COMPLETE` when none is left. Stock comes from `config/plant/stock.yaml`.
- **`LoadProgram(Product, Quantity)`** (Phase 2, #52) `unshift`s a campaign to the _front_ of a CNC's queue, returns `Position = 1`, has no order or command id and is not idempotent: a retried call makes a second campaign. Its `program-loaded` event goes to the event log only, not to OPC UA or the UNS.
- **Parts:** `partId` is a counter per simulator run, shared by both CNCs; the serial `VB-100-000123` is set at the end of OP10 (also for a part scrapped there) and every later `cycle-complete` carries it and the `partId`, except WSH-01's, which carries `partId` and an empty serial (a legacy washer reads no DMC; register map). `material-consumed` (part, material, lot) exists in the event log (#27) but is not published. A leak-test failure sends the part back to ASM-01 once (`result: rework`); a second failure scraps it.
- **Gateway:** publish-only. No `cmd` subscription, no method call; `gw-01` has no `cmd` / `cmd-res` rights (`config/mosquitto/acl`); `mes` may already write `…/cmd/#`. The UNS contract lists `cmd/…`, `cmd-res/…` as "Phase 7".
- **MES:** no users; actors are free text (`codedBy`, `actor`, `author`) audited with `authenticated: false` in three module audits (`equipment.downtime_audit`, `alarms.alarm_transition`, `shifts.handover_audit`). The MES connects as `DB_USER`, the image's bootstrap **superuser**, and migrates at start-up (ADR-0016), so it owns every table and could disable every trigger. `master_data` has products but no routings or BOMs. Reads are unauthenticated (ADR-0019).
- **CI:** GitHub Actions has not run since PR #149 (spending limit). The workflow's jobs (`verify`, `end to end`, `stack smoke`, `reconcile`) are configured and will be extended in this phase, but they don't run; every exit criterion below is proven by local gates (see "Local gate").

### Phase size and waves

- **One phase, two waves,** not a renumbering. Wave A (identity, database roles, web login, ERP mock) has no dependency on the order path and can merge first; wave B (simulator, gateway, orders, execution, terminal, screens, end to end) builds on it. Wave A ends with a checkpoint entry in the phase log: exit criterion 1 (identity and roles) demonstrated except its Playwright part.
- **Why not split the row into two phases:** the exit criterion "role permissions tested" only means something once the order writes exist, and every order write would otherwise be built unauthenticated and then reworked. If the owner prefers a split (7 = identity and ERP mock, 7b = orders and execution), the issue order below already is that split; only the milestone and the master plan's row change.
- **Cut line** if the phase grows: the terminal's pause and resume, the user-administration screen (the CLI stays) and the order-detail command history are the first to move to Phase 8, in that order, each recorded as a deviation.

### Identity (ADR-0026)

- **Phase 7, not 9.** Master plan row 7 lists `identity`; the Phase 5 plan already corrected the Phase 4 plan's "Phase 9 security". Phase 9 keeps the hardening: TLS, `Secure` cookies by default, OPC UA SignAndEncrypt, MQTT dynamic security, simulator control-API access.
- **Roles:** the master plan's five (section 7): `operator`, `supervisor`, `maintenance`, `quality`, `admin`. A user has one or more. There is no `engineer` role; plant configuration is files, not a screen.
- **Permissions,** defined once in `@shopfloor/contracts` (`PERMISSIONS`, `ROLE_PERMISSIONS`) so the MES enforces and the web hides with the same table:

  | Permission                                                                           | operator | maintenance | quality | supervisor | admin |
  | ------------------------------------------------------------------------------------ | -------- | ----------- | ------- | ---------- | ----- |
  | read (every GET, WS)                                                                 | ✓        | ✓           | ✓       | ✓          | ✓     |
  | `downtime:code`                                                                      | ✓        | ✓           |         | ✓          |       |
  | `alarm:ack`, `alarm:comment`                                                         | ✓        | ✓           | ✓       | ✓          |       |
  | `alarm:shelve`                                                                       |          | ✓           |         | ✓          |       |
  | `note:write`                                                                         | ✓        | ✓           | ✓       | ✓          |       |
  | `terminal:operate` (sign on, start, pause, sign-off)                                 | ✓        |             |         | ✓          |       |
  | `scrap:code`                                                                         | ✓        |             | ✓       | ✓          |       |
  | `order:release`, `order:dispatch`, `order:cancel`, `order:redispatch`, `order:close` |          |             |         | ✓          |       |
  | `user:admin`                                                                         |          |             |         |            | ✓     |

  Admin administers users and nothing else (separation of duties); a person who needs both gets both roles.

- **Sessions, not tokens.** `POST /api/v1/session` (username, password) sets an opaque 256-bit random token in a cookie `sft_session` (`HttpOnly`, `SameSite=Strict`, `Path=/`, `Secure` when `MES_COOKIE_SECURE=on`, off by default because the stack is plain HTTP on loopback). The MES stores only its SHA-256 in `identity.session` with the user, kind (`desk` or `terminal`), creation, last use and expiry. Idle timeout 60 min (terminal 15 min), absolute 12 h; a new token on every login; `DELETE /api/v1/session` ends it; a password change ends the user's other sessions; disabling a user ends all of them and closes their sockets. JWTs were rejected: revocation needs a server table anyway, and a token readable by script is worse than an `HttpOnly` cookie.
- **Cookie scope on localhost** (review probe `cookie/`, Chromium): cookies are scoped by host, not by port, so `sft_session` set through `http://localhost:8080` is also sent to every other `localhost` port (the MES on 4700, the simulator's control API on 4800, the gateway on 4900, a Vite dev server), and not to `http://127.0.0.1:8080`, a different host. None of those services reads it, and `SameSite=Strict` doesn't change it. A `__Host-` name would bind the cookie to the host without a `Domain`, but browsers accept that prefix only with `Secure`, which plain HTTP can't carry, so the name stays `sft_session` and the scope is documented in the runbook ("open the app as `localhost`, not `127.0.0.1`"). With `MES_COOKIE_SECURE=on` behind TLS (Phase 9) the name becomes `__Host-sft_session`. Firefox and WebKit were not probed; the login Playwright check of #178 runs on Chromium, and the other two are a known gap.
- **CSRF:** the ADR-0023 guards stay as they are and are the CSRF defence (`Origin` required and same-origin, `Sec-Fetch-Site`, JSON only, no CORS), with `SameSite=Strict` as a second layer. No CSRF token: it would guard against nothing these don't. Login itself passes the guards (login CSRF). The guards move one place: after `Host` and `MES_WRITES`, authentication (401) and permission (403) come after the origin checks, so a cross-site request never learns whether a session exists.
- **Enforcement switch, so every merge stays green:** `MES_AUTH=off|on`. #168 builds identity with enforcement behind `MES_AUTH=off` (the default in that PR): sessions, login and the permission checks exist and are tested with `on`, while the rest of the stack, the web, the smoke and the reconciliation keep working without a session. #170 turns the default to `on` in the same PR that adds the login screen and moves e2e, smoke and reconcile to log in. `on` is then the only supported setting; `off` stays for one-off diagnosis and makes the MES log a warning at start.
- **Every `/api/v1` route needs a session** (with `MES_AUTH=on`) except `POST /session`; `/health/*` and `/metrics` stay open on loopback. Anonymous is 401 `urn:shopfloor:unauthenticated`, missing permission 403 `urn:shopfloor:forbidden` (new `PROBLEM_TYPES`). The WebSocket upgrade needs the cookie; a session that ends closes the socket with code 4401, and the web goes to `/login`. ADR-0019's "unauthenticated until Phase 9" is amended.
- **Passwords:** `node:crypto` scrypt, N = 2^15, r = 8, p = 3 (32 MiB, an OWASP-listed setting), 16-byte salt, stored as `scrypt$N$r$p$salt$hash` so the cost can rise later with rehash on login. Every call passes `maxmem: 64 MiB` explicitly: Node's default `maxmem` is 32 MiB, which these parameters just exceed, so without it the call fails (review probe `scrypt/`). No dependency. At most two hashes at a time (a semaphore) so login bursts stay inside the 512 MiB container. Length 12–128, no composition rules (NIST SP 800-63B). An unknown username costs one dummy hash; the 401 text is the same in every case.
- **Lockout, an accepted risk:** five consecutive failures lock a normal account for 15 minutes. The lock is per account (behind nginx there is no client address), so anyone who can reach the login page can keep a known user locked out: a denial of service accepted on a loopback plant network until Phase 9. The `admin` account is not hard-locked, so that this attack can't lock out the one account able to unlock the others: its failures add an exponential delay instead (1 s doubling, at most 5 min between attempts). Every failure and lock is audited. Passwords and tokens never reach a log (a test captures pino's output during login, failure and lockout).
- **Actors:** the MES takes the user from the session. The request fields `codedBy`, `actor` and `author` are removed in two steps so no merge breaks a client: #169 makes them optional and uses them only when `MES_AUTH=off` (with `on`, the session's user wins and the field is ignored); #170 removes them from the request schemas (strict zod then refuses them), together with the web forms that send them. Responses keep the actor's username and `authenticated`. The web's name fields and their `localStorage` keys go.
- **One audit log:** `identity.audit_log` (append-only by trigger and by grants, below): wall time, plant time, user id, username and roles at that moment (or `system`), `authenticated`, action (`downtime.code`, `alarm.ack`, `order.release`, `session.login-failed`, `user.create`, …), entity type and id, before, after, request id. Modules write through `Identity.audit(trx, entry)` inside their own transaction. A migration copies the existing rows of the three module audits into it (`authenticated: false`, `legacy: true`, counts asserted); `equipment.downtime_audit` and `shifts.handover_audit` are then frozen (the app role loses `INSERT`) and every history endpoint reads `identity.audit_log`. `alarms.alarm_transition` stays: it is the alarm module's transition log (system expiry, epoch ends), not only an audit, and a user transition writes both.
- **Bootstrap:** `MES_BOOTSTRAP_ADMIN_PASSWORD` (optional, in `.env`) creates the user `admin` with `mustChangePassword` only when no enabled admin exists. Without it the MES starts normally, logs a warning, and has no admin until the variable is set and the MES restarted, or `pnpm --filter @shopfloor/mes-server user:create --role admin` (password from stdin) creates one. Compose does not require it: it is not a `:?` variable.
- **Secrets:** no password or token is in the repository. "No secret value" is defined: every secret key in `.env.example` (`*_PASSWORD`, `*_TOKEN`) holds only a placeholder (empty, or `change-me`), and a test parses `.env.example` and fails on any other value. The required ones (`DB_PASSWORD`, `DB_APP_PASSWORD`, `ERP_API_TOKEN`, the MQTT passwords) stay `:?` in Compose. Tests generate random passwords per run and never write them to the repository; the stack smoke and the reconciliation do the same in their disposable `.env`.
- **Crews:** signing on at a terminal writes `shifts.crew_assignment` (user, work center, shift instance, from, to); signing off, a session's end or the shift's end closes it. The shift report gets a crew section.
- **Rate limits:** the global write bucket stays (ADR-0023) and a per-user bucket (5 per second, bursts of 10) is added, now that a user is known.

### Database roles (ADR-0027)

- **Four roles:** the image's bootstrap superuser (`DB_USER`) only creates the others and runs the `migrate` step; `mes_owner` (`NOLOGIN`) owns every schema, table, function and trigger; `mes_cagg` (`NOLOGIN`) owns only the two continuous aggregates (below); `mes_app` (`LOGIN`, `DB_APP_PASSWORD`) is what the MES connects as.
- **`mes_app`'s grants:** `USAGE` on the module schemas; `SELECT, INSERT, UPDATE, DELETE` on ordinary tables, except `shifts.handover_note`, which gets no `DELETE` (notes are retracted, never deleted, ADR-0025); `SELECT, INSERT` only on the append-only tables (`identity.audit_log`, `alarms.alarm_transition`, `alarms.occurrence_state`); `SELECT` only on the two frozen audits; `SELECT` on both aggregates (without it a read is 42501, review probe `tsdb/p2`). It owns no table, so `ALTER TABLE … DISABLE TRIGGER`, `TRUNCATE` and DDL on them are refused (42501), and the append-only triggers still fire for it (`tsdb/p4`).
- **Continuous aggregates (B1).** The probes showed that only an aggregate's owner may refresh it (`must be owner of continuous aggregate`, `tsdb/p2`), and that the refresh can't be wrapped: `refresh_continuous_aggregate()` refuses to run inside a function, a `SECURITY DEFINER` procedure or a transaction block (SQLSTATE 25001, `tsdb/p3` and `tsdb/p4`). So:
  - `mes_cagg` owns `equipment.state_hourly` and `ingest.cycle_hourly` and has `SELECT` on their sources (`equipment.equipment_state_interval`, `ingest.equipment_event`); without that `SELECT` the refresh fails on the source (`tsdb/p6`). It has `USAGE` but no `CREATE` on any module schema, so it can't create anything there itself.
  - **How the migration gets there** (`review180/tsdb2`): the migration runs as the superuser; it creates each aggregate under `SET ROLE mes_owner`, then `RESET ROLE` and `ALTER MATERIALIZED VIEW … OWNER TO mes_cagg` (as superuser; the aggregate's materialisation hypertable and internal views follow), then issues `GRANT SELECT ON … TO mes_app` under `SET ROLE mes_cagg`, because after the transfer only the new owner (or the superuser) can grant on it and `mes_owner` can't. Creating the aggregate directly as `mes_cagg` is not possible without `CREATE` on the schema, which it deliberately doesn't get.
  - `mes_app` is a member of `mes_cagg` with `INHERIT FALSE` (PostgreSQL 16+), so it has none of `mes_cagg`'s rights until it asks: the aggregate refresher (ADR-0022) runs `SET ROLE mes_cagg`, the `CALL`, then `RESET ROLE`, on its own two connections, outside any transaction. The reviewer's probe verified this variant (`review180/tsdb2`, `app.sql`): the refresh succeeds after `SET ROLE mes_cagg` and is refused without it.
  - `cagg_watermark()`: `mes_app` reads it with `SELECT` on the aggregate (`tsdb/p4`), which the refresher (ADR-0022) needs at start-up; a test reads it as `mes_app` and asserts that it moves with a refresh made under `SET ROLE mes_cagg`.
  - **Accepted cost:** as a member, `mes_app` can `SET ROLE mes_cagg` and then drop or alter the two aggregates (the probe dropped one inside a rolled-back transaction, `tsdb/p6`). They are derived data that a refresh rebuilds from the raw tables, which `mes_app` still can't alter. The audit tables are owned by `mes_owner`, of which `mes_app` is not a member, so they stay protected. A test asserts both: `DROP` succeeds after `SET ROLE mes_cagg` inside a rolled-back transaction, and `ALTER TABLE identity.audit_log DISABLE TRIGGER …` fails with or without it.
  - No TimescaleDB refresh policies: the MES refreshes explicitly, as ADR-0022 decided; a policy would need a `LOGIN` owner and a background worker (`tsdb/p5`, case 7).
- **Hypertables as a non-owner work:** `mes_app` inserted rows that created new chunks and read them (`tsdb/p2`); chunks inherit the hypertable's grants.
- **Migrations become a step:** a one-shot Compose service `migrate` (the MES image, command `migrate`) connects as `DB_USER`, creates or updates the roles, and runs the migrations under `SET ROLE mes_owner` (aggregates under `SET ROLE mes_cagg`). The MES starts after it (`depends_on: condition: service_completed_successfully`), connects as `mes_app`, and is not ready while the database's migration history differs from its own (ADR-0016 amended: the MES no longer migrates itself). Each migration grants what its objects need.
- **Existing databases (M1):** a database migrated up to `0015` has every object owned by the bootstrap user. `REASSIGN OWNED BY` can't move them (`cannot reassign ownership of objects owned by role postgres because they are required by the database system`, `tsdb/p5`), so `migrate` runs a one-time ownership step before the new migrations: per object `ALTER SCHEMA … OWNER TO`, `ALTER TABLE … OWNER TO` (hypertables carry their chunks with them), `ALTER SEQUENCE`, `ALTER FUNCTION`, and `ALTER MATERIALIZED VIEW … OWNER TO mes_cagg` for the aggregates (their materialised hypertable and internal views follow, `tsdb/p5`). It is idempotent and recorded in `schema_migrations` like a migration. `pnpm stack:reset` remains the fallback in the runbook.
- **`DECLARED_GRANTS`** lists every grant per role and object, the aggregates included, like `DECLARED_COLUMNS`; a test compares it with `information_schema.role_table_grants` and the aggregates' ACLs, excluding `_timescaledb_internal` (chunks and materialisation tables inherit, and their names aren't stable).
- **Audit backfill proven on old data:** a test migrates a database to `0015`, writes rows into the three module audits through the Phase 5 and 6 code paths, then runs `migrate` (ownership step and the new migrations) and asserts that `identity.audit_log` holds every old row with its fields, `legacy: true`, `authenticated: false`, and that the counts match.
- **Test harness:** `test-kit`'s database helper creates the same roles, migrates as owner and hands the module code an `mes_app` connection, so a missing grant fails a test, not the stack.

### ERP mock (ADR-0028)

- **What it holds:** orders (ERP order number, revision, product, quantity, planned start, due date, priority, status), each with its routing (OP10–OP50 with work center) and BOM (blank and OP30 components, rework components) built from `config/plant/products.yaml`, with each operation's work center taken from `config/plant/plant.yaml` (the equipment's work center for that operation); lots (id, material, quantity) from `config/plant/stock.yaml`; and everything the MES sent back (confirmations, status messages). Ideal cycle times stay MES master data.
- **Interface: REST, pulled by the MES.** `GET /api/v1/orders?after={cursor}` is a change feed: every order version has a feed number, the MES keeps its cursor (`orders.erp_cursor`), committed in the same transaction as the orders it imported (a crash never skips or half-imports a feed page), and asks every `ERP_POLL_MS` (default 10 s wall). `GET /api/v1/lots`. `POST /api/v1/confirmations` and `POST /api/v1/order-status`. A shared bearer token (`ERP_API_TOKEN`, `.env`) authenticates the MES. A file drop was rejected: it adds a shared volume and a poller for nothing a REST feed doesn't give.
- **Idempotency:** imports are keyed (ERP order number, revision); the same revision again changes nothing. A new revision updates an order the MES has only imported; after release it is refused and logged (`erp_message_log`, `revision-after-release`) and the MES posts a `rejected-revision` status. Every message the MES posts carries `Idempotency-Key` (`{order}~{operation}~conf~{n}`, `{order}~status~{status}`): the first post answers 201, a repeat with the same body 200 with the stored answer, the same key with another body 409. The MES records a 409 as an `erp-conflict` incident on the message and does not retry it: it means the MES itself built two different messages under one key, a defect for a person to look at.
- **Order status feedback:** the MES posts `accepted` (imported and valid), `rejected` (invalid: unknown product, routing or BOM that differs from MES master data), `released`, `in-progress` (first OP10 cycle), `completed` (all parts accounted for, with `short: true` when good < quantity), `closed` (operator and supervisor sign-off, like a technical completion) and `cancelled`. The ERP mock derives and serves its view per order: status, confirmed yield, scrap and material per operation.
- **Storage:** `node:sqlite` (as the gateway's outbox, ADR-0014; no dependency) for received messages, so a restart keeps them; orders and lots are loaded from a dataset file at start (`ERP_DATASET`, default `config/erp/orders.yaml`; a golden scenario has its own `orders.json`). A dev-only `POST /api/v1/orders` (`ERP_ADMIN=on`) adds orders for demos.
- **Deterministic:** the dataset fixes order numbers, revisions and feed order; nothing depends on wall time except `receivedAt`. Its API schemas live in `@shopfloor/contracts/erp-api`, so the MES and the e2e tests validate against the same schemas and the golden harness can serve a scenario's dataset without importing the app.
- **Lots:** the simulator can't call a business system (section 5: it knows nothing above the gateway). "The simulator takes lots from the ERP mock" becomes: the ERP mock serves the lot master data and the simulator stocks the same lots physically, both from the same file. The MES does not import lots in Phase 7 (`material_lot` is Phase 8's genealogy).

### Order-driven simulator (ADR-0030)

- **Production mode:** `production: schedule | orders` in the scenario (`scenario.json`, recorded in the run header only when `orders`, so `week-01`'s and `alarms-01`'s headers and `events.sha256` stay byte-identical) and `SIM_PRODUCTION` in live mode. The default stays `schedule`, also in Compose, so the stack smoke and the existing reconcile pass (`alarms-01`) keep producing exactly as today; the `orders-01` reconcile pass starts its simulator with `SIM_PRODUCTION=orders`. In `orders` mode:
  - each CNC station gets `campaigns: []`, not `undefined` (the line tells a CNC from other stations by `station.campaigns`), and the schedule file is not read;
  - `plant-servers` skips its use of `schedule.machines[…][0]` (the initial `Program`), so `Program` starts empty;
  - nothing is loaded at the start (`loadedProduct` undefined), so every CNC's first job begins with the changeover `CHANGEOVER none→<product>` (25 min, the existing path, #126), which the dispatch rule counts;
  - `LoadProgram` is refused (`BadInvalidState`).
- **`LoadOrder` method** on CNC-01 and CNC-02 (`…ShopFloor.LoadOrder`): in `CommandId`, `OrderId`, `Product`, `Quantity` (blanks to machine), `NotBefore` (UtcTime, plant time; the job doesn't start earlier), `DeviceEpoch` (the run the command was meant for) and `ExpiresAt` (UtcTime, wall time); out `Position` (1-based place in the queue), `Duplicate`, and `AcceptedSeq` and `AcceptedAt` (the device sequence number and plant time of the job's `accepted` event; for a duplicate, the original's).
  - **Order of the checks, dedup first:** the device looks the `CommandId` up in its dedup table (the current epoch's accepted commands) **before** any other check. A hit with the same job returns `Duplicate = true` with the original `AcceptedSeq` and `AcceptedAt`, even when `ExpiresAt` has passed: a late call for a job that was already accepted always learns that it was. Only on a miss come the other checks.
  - **Stale commands are refused by the device itself:** on a miss, a `DeviceEpoch` other than the current run's is `BadInvalidState` (`epoch-mismatch`), and an `ExpiresAt` in the past (the simulator's wall clock) is `BadInvalidState` (`expired`). So a command not accepted before its expiry can never be accepted later, whatever the gateway does, and an `expired` answer from the device proves that it was never accepted.
  - **FIFO:** the job is _appended_; the CNC runs its queue in order and the head job waits for its `NotBefore`. At most 50 queued jobs.
  - **Idempotent by `CommandId`** within the device epoch: the same id with the same job (`OrderId`, `Product`, `Quantity`, `NotBefore`) returns the first answer with `Duplicate = true` and adds nothing, whatever its `ExpiresAt` (a resend carries a new one); the same id with another job is `BadInvalidArgument` (`command-conflict`). The device's own table makes the command safe even if the gateway forgets it. The review's probe (`opcua/p1.js`) showed why it must be on the device: a call that times out on the client after the server acted, then retried, made two jobs without dedup and one with it.
- **Job facts in the device sequence:** a new OPC UA event type `ShopFloorJobEventType` (ADR-0009: events with `Sequence`) and `PlantEvent` `job` with `transition: accepted | started | completed`, `commandId`, `orderId`, `product`, `quantity`. `started` is the first blank taken (after a changeover), `completed` the end of the last OP10 cycle of the job, whatever its result. The event-log line format stays `sim-event/1` (`EVENT_SCHEMA`): `job` is a new event type that only orders-mode runs write, as `inject-failure` events appear only in runs with injections. Variables `ShopFloor.ActiveOrder` and `ShopFloor.QueuedJobs` show the queue.
- **New cause `NO-ORDER`:** an `Idle` CNC whose queue has no startable job (empty, or the head waits for `NotBefore`; a wake-up event is scheduled at `NotBefore`). The wake-up only calls the normal start path: a wake-up that falls in a break, a planned stop or outside a shift (`PlannedStop`, `Off`) starts nothing, and the job starts when the machine next leaves that state, as any start does. A test puts `NotBefore` inside the 10:00–10:30 break and at the instant the break starts and ends, and asserts no zero-length interval and no start inside the break. Added to `CAUSES` and `causeVocabulary`, and to `reasons.yaml`'s rules (planned, `No order`).
- **Quantity semantics:** a job's quantity is blanks started. OP10 scrap uses up a slot, and the MES dispatches the order quantity without allowance, so scrap makes an order short (`completed`, `short: true`). Make-up jobs are out of scope.
- **Scenario dispatches (B3):** `scenario.json` may carry `dispatches: [{ commandId, machine, orderId, product, quantity, notBefore }]`. Headless applies them **after `line.start` and before the injections**, in list order, at the start time; that is exactly the live order: the simulator is attached and idle at the start time (`SIM_AUTOSTART=false`; the line has started, the pacer has not), the test dispatches, waits until every command is confirmed by its device fact, then posts the injections, then resumes. So both runs put the same events in the queue with the same tie-breaking sequence, and the live run equals the headless run. If a CNC with an empty queue enters `Idle NO-ORDER` at the start time, the dispatch moves it to `Setup` at the same instant; both runs see that identical pair of events, and the issue's test asserts how the zero-length `Idle` is handled (dropped as a zero-length interval by both the ground truth and the MES, ADR-0018). The MES's dispatch of the scenario's orders must produce exactly this list (tested in the golden reconciliation), so the headless run never depends on MES code.
- **Ground truth per order and per part** (`sim-summary/4`, control API 1.4 `GET /ground-truth` gains `orders`):
  - per job: command id, order, machine, product, quantity, accepted, started and completed times;
  - per order: parts started, OP10 scrap, OP40 scrap, rework passes, packed good, WIP at the end (per buffer and station), the time the last part reached a terminal state, and quantities per operation (in, good, scrap, rework);
  - **material, at the point the MES can see it (H2):** consumption is booked when the consuming cycle completes (a blank with the unit's OP10 cycle, components with its OP30 cycle of that pass), because the MES knows a cycle only from its completion fact. What the simulator has taken for a cycle still running at the run's end (`material-consumed` before a `cycle-complete`) is reported separately as `materialInProcess` per order and is not reconciled;
  - per part: its operation records (operation, equipment, pass, completion time, result), hashed as `unitsSha256` with the count, the full list derived in the tests from the event log;
  - OEE and alarms computed as before, with `oee.yaml`'s rule.
- **Golden scenario `orders-01`:** the week-01 seed and start, two days, `production: orders`, the 14 shift A injections of `alarms-01` (so the Phase 5 and 6 live checks keep their flood, chattering and fleeting alarm), an ERP dataset `orders.json` and its `dispatches`. Required by construction and asserted in its test (exact orders fixed in the issue):
  - at least three orders that complete inside shift A (small VB-100 and VB-200 orders on both CNCs, with a changeover);
  - an order that ends short through scrap;
  - an order with a planned start on Tuesday 11:17 local (outside the 10:00–10:30 break), after both CNCs ran dry, so `Idle NO-ORDER` time exists inside shifts;
  - an order still in WIP at the run's end; an ERP revision before release; an order never released;
  - stock that covers every dispatched job.
- **No change for the other scenarios (M6):** the simulation inputs `config/plant/products.yaml` and `stock.yaml` must not change in this phase (the ERP mock and the routing read them as they are), `EVENT_SCHEMA` stays `sim-event/1`, and `week-01` and `alarms-01` keep `events.sha256` byte-identical; their `summary.json` is regenerated for `sim-summary/4` (schema line, an empty `orders` section, `analysisConfigSha256` because `oee.yaml` changes) with every KPI value byte-identical, asserted by a test that compares every other field. The written reason goes into `apps/simulator/golden/README.md`; the owner's approval is deferred as in Phase 6.

### Command path (ADR-0029)

- **Topics:** `…/{equipment}/cmd/load-order` (schema `uns.cmd.load-order/1`) and `…/{equipment}/cmd-res/load-order` (`uns.cmd-res/1`), QoS 1, not retained. UNS contract 1.3.
- **Command envelope,** not the fact envelope (a command is not a measurement): `schema`, `source` (`mes-server`), `epoch` (MES process start), `seq` (per topic), `issuedAt` and `expiresAt` (wall time, default 60 s), `value: { commandId, orderId, operation: 'OP10', product, quantity, notBefore, deviceEpoch }`. `deviceEpoch` is the simulator run the MES targets (from facts, anchors or snapshots). `expiresAt` and `deviceEpoch` go to the device as `ExpiresAt` and `DeviceEpoch`, which refuses a stale command itself (above).
- **Command identity:** `commandId = {orderId}~OP10~{n}`, `n` the dispatch number of that order (1, then 2 after a re-dispatch). Deterministic, so the golden scenario's device facts carry the ids the MES generates. Resends reuse the id and the job; only `expiresAt` changes.
- **MES side, transactional outbox** (`orders.dispatch_command`): a dispatch writes the command row in the same transaction as the order change; a publisher loop sends pending commands. Per CNC strictly one command in flight: the next is published only after the previous has a final result (below), so a resend can never swap two jobs in the queue. No result within 15 s (wall) → resend the same command with a new `expiresAt`, up to 5 attempts. Sending pauses while the gateway's `_sys` status is `offline`.
- **Gateway:**
  - **Subscription (M2):** commands arrive on a second MQTT connection of the gateway with its own client id `gw-01-cmd` (same broker user `gw-01`), so it never takes over the publishing connection's session. It is persistent: `clean: false`, a session expiry interval (`GATEWAY_CMD_SESSION_EXPIRY_S`, default 1 h, longer than any command's life), subscriptions `orbis/gebze/{area}/+/+/cmd/#` per area, QoS 1. A command's PUBACK is sent only after the command is recorded in the gateway's SQLite database (MQTT.js `customHandleAcks`-style gating, as the MES does for facts, ADR-0017), so a gateway crash before recording gets the command redelivered.
  - **Calls (B2):** one command at a time per equipment. The gateway calls only when the OPC UA session to that machine is ready (connected, subscription and resync done); otherwise the command waits. Each call has an application-level deadline (`GATEWAY_CALL_DEADLINE_MS`, default 5 s), independent of node-opcua's transaction timeout (the review's probes `opcua/p1.js`, `p2.js` and `p4.js`: a slow handler, a TCP cut mid-call and a server killed mid-call). Before any retry the gateway re-reads `ShopFloor.Epoch`; if it differs from the command's `deviceEpoch` it answers `rejected` (`epoch-mismatch`) without calling. It retries until `expiresAt`, then stops calling with that `expiresAt`. A command that arrives already expired, for an id the gateway has never called, is answered `expired` without a call.
  - **Settling an unknown outcome:** a call whose outcome the gateway doesn't know (its deadline passed, the transport failed, the session dropped) is settled after `expiresAt`, never guessed: once the session is ready again and the wall clock is past `expiresAt`, the gateway reads `ShopFloor.Sequence` (`seqAfterExpiry`, a device sequence number read after the expiry) and then makes **one more call** with the same arguments. Because the device checks its dedup table first, `Duplicate` means the job was accepted (result `duplicate`, with `AcceptedSeq`); the device's `expired` means it was never accepted (result `expired`); `epoch-mismatch` means the run ended (result `rejected`, and the MES's epoch rule applies). If that call fails too, or the session never becomes ready, the gateway reports `unknown` (with `seqAfterExpiry` when it could read it) and keeps trying to settle while the command's device epoch lasts. It never reports `expired` or `failed` for an outcome it doesn't know.
  - **Result table (by definitive answer only):** `accepted`, `duplicate` and `rejected` are stored by `commandId`, and a redelivered or resent command with that id is answered from there without calling. An `expired` result is stored by (`commandId`, `expiresAt`), so a resend with a new `expiresAt` is called again (and the device's dedup makes that safe). `unknown` is not stored as an answer; it is settled again. `cmd-res` goes through the store-and-forward outbox, so a result is not lost to a broker outage.
- **Results and what they mean:**

  | Result      | Meaning                                                                                                                                                                 | Final for the MES?                                                      |
  | ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
  | `accepted`  | The device accepted the job now (`position`, `AcceptedSeq`, `AcceptedAt`)                                                                                               | Yes: the job exists                                                     |
  | `duplicate` | The device had already accepted this command id (original `AcceptedSeq`, `AcceptedAt`)                                                                                  | Yes: the job exists                                                     |
  | `rejected`  | The device refused the job (`code`: invalid product or quantity, `command-conflict`, `epoch-mismatch`; OPC UA status)                                                   | Yes: no job                                                             |
  | `expired`   | The device answered `expired` on a dedup miss, or the gateway refused a command whose id it had never called: never accepted                                            | Yes: no job, for that `expiresAt`; a resend may still be sent           |
  | `unknown`   | The gateway couldn't learn the outcome, even after the settle call; carries `seqAfterExpiry` when read                                                                  | No                                                                      |
  | `failed`    | Not a gateway result: the MES's own state of a command with no final result after its last attempt's `expiresAt` plus a margin (`COMMAND_FAIL_MARGIN_MS`, default 30 s) | No: an incident and the order flag `dispatch-failed` for the supervisor |

  An `accepted` or `duplicate` result carries the device's acceptance: its plant time and its `seq` (M4), from `LoadOrder`'s `AcceptedSeq` and `AcceptedAt` outputs.

- **A re-dispatch can never make a second job (B2).** Enforced in the `orders` module and tested:
  - a re-dispatch (new `n`) is allowed only when every earlier command of the order is settled: an `accepted` fact or `accepted`/`duplicate` result (its quantity counts as accepted), `rejected`, `expired` for its last `expiresAt`, of a device epoch that has ended, **or**, for a command that is `unknown` or `failed`, once the CNC's final-through has passed the `seqAfterExpiry` that the gateway read into the settle result with no `accepted` fact for that command id below it (any acceptance happened before the expiry, so its fact lies below that sequence number, and final-through past it means every such fact has arrived). Without a settled answer and without a `seqAfterExpiry`, there is no re-dispatch until the epoch ends;
  - its quantity is at most the order quantity minus the quantities of the order's jobs the device accepted, so the sum of job quantities accepted for an order can never exceed the order quantity.
- **Truth is the device fact.** The MES marks a command `confirmed` only by the job `accepted` fact with its id in the device sequence; `cmd-res` is the fast path. A `cmd-res accepted` without its fact once the device's final-through has passed the `cmd-res`'s acceptance `seq` and plant time (M4: both in the device's own clock and sequence, never wall time) is a `command-unconfirmed` incident; a job fact with an unknown command id is an `unknown-job` incident.
- **Exactly-once, restated per order (B2):** for every order, the sum of the quantities of the jobs the device accepted is at most the order quantity, and for every command id there is exactly one `accepted` job fact, however many deliveries, resends and results there were.
- **ACL (M2):** the broker user `gw-01` (both its connections, client ids `gw-01` and `gw-01-cmd`) gets `read …/cmd/#` and `write …/cmd-res/#` per area (areas listed one by one, as today); the command connection only subscribes to `cmd` and the publishing connection publishes `cmd-res` through the outbox. The plain ACL file grants per user, not per client id; tying the two ids to their uses waits for dynamic security (Phase 9). `mes` keeps `write …/cmd/#` and cannot write `cmd-res` (it still reads results through `read orbis/#`); `dev` stays read-only. Tests publish to `cmd` as `gw-01` and `dev` and to `cmd-res` as `mes`, each refused with PUBACK 0x87. Client-id takeover stays an accepted risk until Phase 9 (UNS contract).
- **Simulator restart:** a new device epoch empties the CNC queue. The old epoch's jobs not `completed` become `lost`, their parts in WIP `lost`, the order `dispatch-lost`; a supervisor re-dispatches the not-started remainder (`order:redispatch`, new `n`, the rules above). No automatic re-dispatch.

### Orders (`orders` module)

- **Ownership (ADR-0016):** schema `orders`: `production_order`, `order_operation`, `dispatch_command`, `erp_message_log` (inbound feed entries and outbound messages with key, payload, status, attempts, last error), `confirmation`, `erp_cursor`. `master_data` gains `routing`, `routing_operation`, `bom_item`, seeded from `products.yaml`.
- **Import:** each feed entry is validated against master data (product, routing operations and work centers, BOM). Valid → `imported` and `accepted` posted; invalid → stored as `rejected` with the reason and `rejected` posted.
- **Lifecycle:** `imported → released → dispatched → in-progress → completed → closed`, plus `cancelled` (before dispatch) and the flags `short`, `dispatch-failed`, `dispatch-lost`. Release, dispatch, cancel, re-dispatch and close are supervisor writes with a `version` per order (409 `urn:shopfloor:order-stale`), audited.
- **Dispatch rule** (deterministic, from master data and the MES's own queue only): the whole order goes to the CNC whose queue finishes first by an ideal-time estimate, ties to the lower id. The estimate walks the CNC's queue in order: a job starts at the later of its `notBefore` and the previous job's estimated end (so `NotBefore` waits count), plus a changeover when its product differs from the one before it (also the first job of a run, `none→…`), plus quantity × ideal OP10 cycle; breaks and shift ends are ignored, which is enough for a deterministic choice; `notBefore` is the order's planned start, and a CNC's queue is kept in planned-start order. The supervisor may name the CNC. No automatic split. Dispatching all of `orders-01`'s released orders at t0 reproduces its `dispatches` exactly.
- **Completion (H1):** an order operation is complete only when no unit of the order can still come back to it: every unit started for the order has passed the operation for good or been scrapped, and, because a leak-test failure sends a unit back to OP30 once, OP30 and OP40 are complete only after every unit has passed OP40 for good or been scrapped (a unit with one failure is still open for both). OP10 is complete when the order's jobs are `completed`; OP20 when every unit passed it or was scrapped at OP10; OP50 when every unit is packed or scrapped. All of it at or below the equipment's final-through (ADR-0018). The order is `completed` when OP50 is; `short` when packed good < quantity.
- **Confirmations to the ERP** from final data only: one final confirmation per order operation (yield, scrap by reason, rework passes, backflushed material at OP10 and OP30), sent through the `erp_message_log` outbox with backoff. A late fact that changes a confirmed operation (a gap filled after its incident) sends a `correction` with the delta (`n + 1`), judged against what was confirmed before the change (the Phase 6 rule). Status messages likewise.
- **API:** `GET /orders?status&from&to`, `GET /orders/{id}` (operations, jobs, commands with every result, confirmations, ERP messages, history), `POST /orders/{id}/release|dispatch|cancel|redispatch|close`. Push `orders`: order and command upserts (the client reads first and applies upserts by id; reset on subscribe and release, Phase 6 lesson).

### Routing execution per part (`execution` module, ADR-0031)

- **Units, not serials yet:** a unit is keyed (device epoch, `partId`), with its serial once OP10 gives one. `partId` restarts with the simulator, so serials are unique only within an epoch; Phase 8's genealogy owns real serial identity (`serial_unit`) and builds on these rows. WSH-01 is followed by `partId` because it reads no serial.
- **Attribution:** an OP10 cycle belongs to the job whose `started` fact is the latest one below it in the CNC's device sequence (one part at a time on a CNC, so this is exact and survives reordering). The job gives the order; every later cycle of the same unit inherits it.
- **Operation records** (`execution.operation_record`): one per (unit, operation, pass): equipment, completion time (the cycle fact's `sourceTime`; cycle facts carry no start, so none is invented), result and reason. Rework: LKT-01 `rework` opens pass 2 at OP30 and OP40; a second LKT-01 failure scraps. Derived and rebuilt from facts like occurrences (Phase 6); a reordered fact rebuilds the unit.
- **Routing order:** facts are facts and are never refused; a unit seen at an operation without its predecessor is flagged `routing-violation` (incident), never silently fixed.
- **WIP:** a unit's position (at a station, or in the buffer after its last good operation) and per order the units in WIP; at a run's end it must equal the ground truth's.
- **Quantities and material:** per order operation in, good, scrap by reason, rework passes; material is backflushed from the BOM per completed cycle (a blank with each OP10 cycle, components with each first-pass OP30 cycle, rework components with each later pass), which equals the ground truth's consumption booked at cycle completion (H2). Material taken for a cycle still running is not visible to the MES and not reconciled. Lots stay out (Phase 8).
- **Scrap records:** every machine scrap (OP10 `DIMENSIONAL`, OP40 second `LEAK`) is a scrap record; an operator or quality user codes it with a detailed reason from a new `scrap` tree in `reasons.yaml` (version per record, 409, audited). Coding never changes quantities.

### Operator terminal

- **Screen** `/terminal` (pick a work center) and `/terminal/$workCenter`, for a tablet (375–1024 px, large touch targets). Sign-on with username and password creates a `terminal` session (15 min idle); several operators may be signed on to one work center; sign-off ends the session and the crew row.
- **Shows:** per machine its state and the current job or order; for Line A1 the orders whose units are at its stations; per order at this work center in, good, scrap, rework and WIP; the queue of released and dispatched orders; uncoded scrap records; who is signed on.
- **Actions** (`terminal:operate`, audited): **start**, **pause** (with a reason) and **resume** the operator's work on an order operation, kept as activity intervals on the operation (they don't stop a machine: the CNC runs its queue, and a pause records the operator's time, not the machine's); **scrap coding**; **sign-off** of an order operation, allowed only once the MES has it complete, which is what lets a supervisor close the order (`closed` posted to the ERP).
- **Shared device, lessons of Phase 6:** everything the screen holds is keyed by (user, work center, order operation); sign-off and session end clear the query cache, the live subscriptions and every draft, so the next operator never sees or sends the previous one's input.

## Exit criteria (plan section 11)

Row 7: "An order runs end to end: ERP → MES → machine program → production → confirmation in ERP, quantities reconciled; role permissions tested". Every criterion is proven by local runs on the final commits (see "Local gate"); the CI jobs exist but don't run.

1. **Role permissions and identity:**
   - a matrix test sends every write route the declared answer for each of the five roles and for anonymous (allowed, 403 `urn:shopfloor:forbidden`, 401 `urn:shopfloor:unauthenticated`); every read route and the WebSocket refuse anonymous (401, 4401); the route list is compared with the OpenAPI document, so no route escapes the matrix (counts asserted);
   - login, wrong password, lockout after five failures (and the exponential delay, not a lock, for `admin`), idle and absolute expiry, logout, password change ending the other sessions, and a disabled user's session and socket ending are tested; stored hashes are scrypt with their parameters; no password or token appears in the captured logs;
   - every write's audit row in `identity.audit_log` has the user, roles, `authenticated: true` and the request id; the backfilled legacy rows equal the three module audits' counts;
   - as `mes_app`, `ALTER TABLE … DISABLE TRIGGER`, `TRUNCATE`, `UPDATE` and `DELETE` on the append-only tables, and `CREATE` in a module schema are refused (42501), also after `SET ROLE mes_cagg`, in the tests and on the stack; a refresh under `SET ROLE mes_cagg` succeeds and moves `cagg_watermark()`; the grants equal `DECLARED_GRANTS` (aggregates included, `_timescaledb_internal` excluded); a database migrated to `0015` with old audit rows migrates to the new roles with every row backfilled;
   - Compose refuses to start without the required secrets (`DB_PASSWORD`, `DB_APP_PASSWORD`, `ERP_API_TOKEN`, the MQTT passwords) but not without `MES_BOOTSTRAP_ADMIN_PASSWORD`: without it the MES starts and has no admin until one is set; with it the bootstrap admin must change its password; every secret key in `.env.example` holds only a placeholder (tested);
   - Playwright on the live stack: an operator sees no release or dispatch control and the API answers 403; a supervisor releases and dispatches; an admin manages users and gets 403 on a production write.
2. **Golden `orders-01`,** in order and shuffled with 10 % duplicates: the MES's dispatch equals `dispatches`; every command confirmed by exactly one device fact, no command or job incident; every unit's operation records, WIP at the end, and per order and operation the quantities, scrap by reason, rework passes, backflushed material (booked at cycle completion; material in process not compared) and completion time equal the ground truth; the confirmations equal those computed from the ground truth; OEE (`orders` rule), alarm KPIs and shift reports equal the ground truth. `orders-01` holds at least three orders completed in shift A, a short order, `Idle NO-ORDER` time inside a shift, an order in WIP at the end, a revision and an unreleased order (asserted). Comparison counts are asserted.
3. **Commands exactly once,** per order and per command (B2): in integration tests with real Mosquitto, gateway and simulator, each case ends with, for every order, the sum of the job quantities the device accepted at most the order quantity, and for every command id exactly one `accepted` job fact. Cases: a duplicated delivery; a resend after a lost `cmd-res`; a gateway restart between the call and its result, and between receiving a command and recording it; a call that times out on the client after the device acted; a TCP cut and a simulator restart mid-call (the retry re-reads the epoch and is refused); the MES restarted between the outbox commit and the publish; an expired command (refused by the gateway without a call, and by the device when called late); a wrong device epoch (refused); an invalid product (rejected, order flagged); a broker outage while a result is pending (delivered from the outbox); a command declared `failed` followed by a re-dispatch (no second job, and a re-dispatch refused while an earlier command is not final); and **a call that times out on the gateway but executes on the device, with the device's `accepted` fact and its `cmd-res` held in the gateway's outbox (broker down) past the MES's failure margin**: the command is `failed`, the supervisor's re-dispatch is refused until either the settle call answers `duplicate` or the CNC's final-through passes `seqAfterExpiry`, after which the held fact counts the job as accepted and no second job is created. The ACL refusals (0x87) for `gw-01` and `dev` on `cmd` and `mes` on `cmd-res` pass.
4. **An order end to end, live** (`pnpm test:reconcile`, its `orders-01` pass, shift A at 60× in orders mode; the `alarms-01` pass keeps its Phase 6 checks): the ERP mock holds the orders; the MES imports them (`accepted` in the ERP); a supervisor releases and dispatches through the UI; every command has exactly one `accepted` job fact, every order's accepted job quantities sum to at most its quantity, and the CNC queues equal `orders-01`'s; shift A's states, OEE and alarm KPIs are final and equal the live ground truth, which equals `orders-01`'s shift A; at least three orders complete in shift A, and for each the ERP mock holds one final confirmation per operation and the status `completed`, with quantities and material equal to the MES's and the ground truth's; posting the MES's outbox again (MES restarted) leaves the ERP's totals unchanged.
5. **Operator terminal, live:** an operator signs on to Line A1's terminal through the UI (crew row written), sees the current order and its counts change within 2 s of the cycles (Playwright latency judge with its value floors), starts, pauses and resumes the operation, codes a scrap record, and signs off a completed operation, after which a supervisor closes the order and the ERP mock shows `closed`; every action is in `identity.audit_log` with the operator; a sign-off and a second operator's sign-on show none of the first one's drafts.
6. **No regression:** `week-01` and `alarms-01` keep `events.sha256` byte-identical (`EVENT_SCHEMA` still `sim-event/1`, `products.yaml` and `stock.yaml` unchanged); their summaries differ only in the schema line, the empty `orders` section and `analysisConfigSha256` (asserted field by field); their golden reconciliations pass unchanged.

## Deviations from the master plan

Master plan rev. 7, in the same pull request as this plan, takes over the command path (`load-order`), the production modes, the lot file, the `NO-ORDER` rule, identity and database roles, and the XL size into sections 4, 5, 7, 11 and 12, so the plan and this list don't disagree. The others are recorded here and in the phase's ADRs.

- **Section 5, data path 3:** `cmd/load-order` and a new method `LoadOrder` instead of `cmd/load-program` and `LoadProgram`. `LoadProgram` puts a campaign at the front, has no order or command id and is not idempotent, so a retried command would double a job. `LoadProgram` stays for schedule mode.
- **Section 5, commands:** a command envelope (`issuedAt`, `expiresAt`, `deviceEpoch`) beside the fact envelope; device-confirmed jobs (`events/job`) as the proof of execution; WSH-01 gets no commands (its Modbus map is read-only).
- **Section 4, materials:** "issued by the mock ERP" becomes one lot file served by the ERP mock and stocked by the simulator; the simulator never calls the ERP, and the MES doesn't import lots before Phase 8.
- **Section 4, production schedule:** kept as a mode (`schedule`) and still the default, also in Compose, so the stack smoke and the `alarms-01` reconcile pass are unchanged; `orders` mode runs in `orders-01` (golden and its own reconcile pass) and wherever `SIM_PRODUCTION=orders` is set.
- **Section 7, scheduled time:** "Idle without a dispatched order is excluded" is expressed as `Idle` with cause `NO-ORDER`; downstream `Starved` stays a loss; `SCHEDULE-COMPLETE` keeps its Phases 1–6 meaning.
- **Section 7, `identity`:** reads become authenticated in Phase 7, not Phase 9 (ADR-0019 amended); `audit_log` replaces two module audits and sits beside `alarms.alarm_transition`; `crew_assignment` comes from terminal sign-on.
- **Section 7, `execution` and `genealogy`:** Phase 7 tracks units keyed (epoch, `partId`); `serial_unit`, lots and genealogy links are Phase 8's. WSH-01 is followed by `partId`.
- **Section 7, `oee` "per order":** per-order and throughput line OEE move to Phase 8.
- **Section 7, `orders`:** confirmations are final and correction only, not partial per shift.
- **Section 8 / ADR-0016:** migrations run as a separate step as an owner role; the MES no longer migrates itself. The continuous aggregates are owned by a role of their own (`mes_cagg`) that the MES assumes for refreshes, an accepted weakening for derived data only.
- **Section 1 roles:** the five roles of section 7; no `engineer` role.
- **Section 9 and 11, CI:** the end-to-end and reconcile jobs are configured but don't run (Actions spending limit); every exit criterion is proven by local gates, recorded per PR.
- **Size:** XL rather than L, in two waves (see "Phase size and waves").
- **Alarm positions** stay configured work centers (ADR-0024's "revisit when operators log in" is deferred): the KPI reconciliation depends on positions the ground truth knows.
