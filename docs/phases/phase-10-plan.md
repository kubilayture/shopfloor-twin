## Goal

A stranger can clone the repository and start the whole system with one documented command line, watch a recorded walkthrough of what it does, read an architecture document that matches the code, and find in one final report how each of the six v1 success criteria was proved on the release commit. `v1.0.0` is tagged by the owner once he has signed off the phases Claude closed for him.

## Scope

- **Fresh-clone start (success criterion 1):** a dependency-free init step that writes a throwaway `.env` from `.env.example`, the one start command, and a harness that runs both on a fresh clone in a disposable directory and Compose project.
- **Recorded property seeds** (inherited from Phase 9): every `pnpm verify` prints the fast-check seed it used, and a seed can be pinned to reproduce a run.
- **Documentation pass:** README, runbook, API references, glossary and a documentation index made current against the code; master plan corrections.
- **Architecture views:** `docs/architecture.md` rewritten with C4-style views in Mermaid (context, containers, components, runtime, deployment), checked against the code by a script.
- **Demo scenario:** a live-playable timeline and a scripted walkthrough of the console, OEE, alarms, SPC, holds and traceability that also asserts what each scene shows.
- **Demo recording:** a headless video of that walkthrough, its screenshots and captions, committed under a size limit.
- **Final report** (`docs/final-report.md`): each success criterion with its proof on the release commit; the Sparkplug B decision (ADR-0041); known limits of v1.0; the consolidated register of decisions awaiting the owner.
- **Release mechanics:** `CHANGELOG.md` 1.0.0, the product version, the runbook's release procedure.
- **Phase 10 close** and the owner's sign-off that gates the tag.

Out of scope here:

- new plant, MES or UI capabilities; the month-scale follow-ups of #245 (`OrderOee.lineOrders` bounded, `GET /oee/line/orders` paginated, `#finals` evicted): v1.0 is proven at shift and week scale, which T4 and T5 measure; after v1.0;
- the resilience suite's pending stand-in moved to `mes_ingest_oldest_pending_age_seconds` (Phase 9 known issue): the stand-in is a settle precondition between faults, not a pass criterion, and the suite passed twice on `1cecd17` with it; changing a proven judge in the release phase costs two resilience runs for no new evidence; after v1.0, recorded as a known limit;
- the carry-overs from Phase 8 and earlier (retention and compression policies, the O(hours × occurrences) alarm KPI read, one transaction per ingested message, broker persistence up to the last autosave, Vite's 500 KB chunk warning, scrap at paced speed, `mes_app` able to drop the continuous aggregates after `SET ROLE mes_cagg`, serials repeating across simulator runs): listed as known limits in the final report, none fixed in v1.0;
- Sparkplug B itself (proposed here: not in v1.x; decided by ADR-0041), SSO, cloud deployment (master plan non-goals);
- GitHub Actions billing, the Renovate app and the owner's own dev `.env` and dev CA trust: owner items, carried; no success criterion depends on them (below).

### Success criterion 1: what "one command" means

- **Decided:** on a machine with Docker and Compose v2, git and a POSIX shell (no Node.js, no pnpm), a fresh clone starts the whole system with **one command line**:

  ```sh
  sh scripts/stack-init.sh && docker compose up -d --wait
  ```

  `scripts/stack-init.sh` is a one-time init: it writes `.env` from `.env.example` with a new random value for every `*_PASSWORD` and `*_TOKEN` key (the rule `scripts/gate.ts` already uses, so the two can't disagree; a test asserts that both produce the same key set), created under `umask 077` with `set -C` (noclobber), so it is mode 600 and never replaces a file that appeared meanwhile. Then `docker compose up -d --wait` is the master plan's own verification command unchanged, and Compose's `pki` and `migrate` steps run inside it.

- **Why not literally `docker compose up` alone:** the stack can't start without per-stack secrets (ADR-0026, ADR-0038, ADR-0039; checklist S7 forbids committing them), and Compose can't generate a value it **interpolates** (`${VAR:?}` is resolved before any service runs). A one-shot step writing the secrets into a volume, with every service reading `*_FILE` as the `pki` step does for certificates (ADR-0038), could make `docker compose up` alone enough; it is rejected for v1.0 and deferred until after it (option (d) under "Open decisions"). A committed default secret would make every clone share it. So the honest reading is "one command line, of which the first part runs once": it is written so in the README and the final report, and recorded as a deviation from the letter of section 1 ("`docker compose up` on a fresh clone") for the owner's review.
- **Init rules:** POSIX `sh` only, with `openssl rand -hex 16` and a fallback to `od` on `/dev/urandom` (a test runs it without `openssl` on `PATH` and gets the same key set). It acts on **its working directory** (or the directory given as `$1`), never on a path derived from its own location; its tests copy it into a temporary directory and never run it in the checkout. It **never overwrites** an existing `.env`: if `.env` exists and every required key has a value other than `change-me`, it says "already initialised" and exits 0 (so the line can be rerun); a required key that is missing **or empty** is reported as missing, and one set to `change-me` as a weak secret, by name only (never a value), exit 1. The required keys are **one list shared with `scripts/gate.ts`** (`REQUIRED_SECRETS`), asserted equal by a test; the optional `GRAFANA_ADMIN_PASSWORD` (observability profile only) is generated but never reported as missing. It prints the bootstrap admin's password once **only when its output is a terminal** (that password must be changed at the first login, ADR-0026); otherwise it prints where the password is (`.env`, `MES_BOOTSTRAP_ADMIN_PASSWORD`), so no harness log ever holds it. `pnpm stack:init` is an alias for developers.
- **What "starts" covers and what it doesn't:** "starts" is `up --wait` returning 0 with every service healthy and the one-shot steps exited 0. Using the web in a browser additionally needs the stack's dev CA trusted, or the browser's warning accepted once; the README says so and gives a way to export the CA without Node (`docker compose exec -T web cat /etc/nginx/tls/ca.pem > dev-ca.pem`) beside `pnpm stack:ca`. The Docker VM needs 4 GiB (README).
- **Host ports become variables:** `docker-compose.yml` gains `SIM_OPCUA_HOST_PORTS` (default `4841-4845`) and `SIM_MODBUS_HOST_PORT` (default `5020`), so every published port of the default stack is set in `.env`. Defaults unchanged, so the owner's stack and S8's port list don't change; the gate's overrides already `!override` the simulator's ports.

**The fresh-clone test (`pnpm test:fresh-clone`, `e2e/src/fresh-clone.ts`, under the heavy lock):**

1. `git clone --no-local` of the repository **at the commit under test** (the committed tree, never the working tree; the result records the commit and refuses a dirty tree unless `FRESH_CLONE_ALLOW_DIRTY=1`, which then marks the record "not of record"; **for the closing run the commit must be contained in `origin/main`**) into a new directory under the OS temporary directory, outside the repository. It asserts that the clone has no `.env` before the init (nothing leaked from a working tree).
2. It reads the README's quick-start block (fenced, between `<!-- quick-start -->` markers) and runs **those lines verbatim** in the clone, the `git clone` and `cd` lines excepted. **Isolation is by process environment, never by editing a file:** `docker-compose.yml` has `name: shopfloor-twin` and its images default to `:dev`, so a slip would reach the owner's dev project and its data. The shell that runs the README line gets `COMPOSE_PROJECT_NAME=fresh-<hex>`, `IMAGE_TAG=fresh-<hex>` and a free host port in every port variable, chosen by the harness (for `SIM_OPCUA_HOST_PORTS`, five contiguous free ports, each checked). The process environment takes precedence over `.env` in Compose's interpolation, and `COMPOSE_PROJECT_NAME` over the file's `name:`, so the clone's `.env` stays exactly as the init wrote it and nothing else differs from what a user types.
3. **The shell is Node-free:** its `PATH` is a fresh directory of links to exactly `sh`, `git`, `docker`, `openssl`, the POSIX utilities the init uses (listed in the script's header) and any `docker-credential-*` helper the Docker configuration names; no system or Homebrew directory is on it, since Node and pnpm often share one with Docker. `command -v node` and `command -v pnpm` must fail in that shell before the line runs. Docker CLI plugins (`compose`, `buildx`) are found through `~/.docker/cli-plugins` or `cliPluginsExtraDirs`, not `PATH`, so the shell keeps `HOME`, `DOCKER_CONFIG`, `DOCKER_HOST` and the current Docker context.
4. **Resolution checked before the README line, before any build, `up` or `down`:** the clone has no `.env` yet, so the check can't read the init's output, and the README line is run verbatim, so nothing can be inserted between its init and its `up`. Instead the harness writes `<tmp>/placeholder.env` **outside the clone**: every key of the clone's `.env.example`, with each `*_PASSWORD` and `*_TOKEN` and every other required key set to the literal `placeholder`. With the isolation environment it runs `docker compose --env-file <tmp>/placeholder.env config --format json` and requires `.name == "fresh-<hex>"` and every built image to end in `:fresh-<hex>`. The standing rule forbids interpolated `config` output because it prints secrets; it is allowed here only because **(1) the harness has first asserted that the clone has no `.env`, (2) every secret value is a placeholder, and (3) the output is parsed in memory and never printed or logged**. If the check fails, nothing is built, started or removed. After `up`, the project is asserted again from the containers' `com.docker.compose.project` labels (`docker compose ls`, `docker ps --filter label=…`), and before the smoke, with the isolation environment: the placeholder-env check repeated (`--env-file <tmp>/placeholder.env`, so the clone's `.env` is not read; Compose doesn't load `.env` when `--env-file` is given), and `docker compose ps --all --format json` must list only containers whose `com.docker.compose.project` label is `fresh-<hex>`, with none of project `shopfloor-twin` created or recreated since the run began (`docker ps -a --filter label=com.docker.compose.project=shopfloor-twin`, compared before and after). Interpolated `config` is never run against a file holding real secrets.
5. `FRESH_CLONE_NO_CACHE=1` (the closing gate uses it) runs `docker compose --env-file <tmp>/placeholder.env build --no-cache --pull` with the isolation environment, **before the README line**; no build takes a secret (the build sections have no args), and the README line's `up` then builds over that fresh cache. The placeholder values go only to this command and the check in step 4, never to the README line. `--pull` re-pulls only the build bases; the `db` and broker images are used as they are on the machine, and their digests are recorded and said so. A truly clean Docker host isn't simulated: images of other projects stay on the machine, which is recorded.
6. **Assertions:** both commands exit 0; every long-running service healthy, `pki` and `migrate` exited 0, `opcua-tools` not started (profile); the set of **published container ports** equals checklist S8's set (8443, 1883, 4800, 4841–4845, 5020, 4600), each bound to `127.0.0.1` on the host port the harness chose, with 4700, 4900 and 5442 unpublished; the clone's own `scripts/stack-smoke.sh` passes, run in the clone with `SMOKE_ENV_FILE` = the clone's `.env`, without `SMOKE_WRITES`, and with exactly the isolation environment of step 2 (`COMPOSE_PROJECT_NAME`, `IMAGE_TAG`, the port variables). **Every Compose call made after the README line, whether by the harness, the smoke or cleanup, gets that environment**; the step 4 check is repeated before the smoke; the bootstrap admin logs in over HTTPS trusting only the clone's dev CA and is told to change the password (403 `password-change-required`); the harness then changes that password **in the throwaway stack**, and with that session the plant overview's API lists all six machines with a state; no generated secret appears in the harness's output (S7, the gate's check reused).
7. **Cleanup, also on failure:** `docker compose -p fresh-<hex> down --volumes` with the project named explicitly, the `fresh-<hex>` images removed, the clone deleted; every cleanup refuses to run if the project name is `shopfloor-twin` or the tag is `dev`. In the checkout the harness **writes only `e2e/results/fresh-clone/`, never runs Compose there and never touches `.env`**; it reads the checkout only through `git clone`.
8. **Record:** `e2e/results/fresh-clone/result.json`: the commit, durations of init, build and `up`, Docker, Compose and VM figures, image digests (the built images and the `db` and broker images).

### Sparkplug B (ADR-0041)

- **Proposed here (not in v1.x), decided by ADR-0041.** The UNS stays the ISA-95 topic tree with JSON envelopes (section 5).
- **Why:** Sparkplug B prescribes its own topic namespace (`spBv1.0/<group>/<message type>/<edge node>[/<device>]`), which would replace or duplicate the ISA-95 tree the MES subscribes to; its payloads are Protobuf with metric aliases, so the versioned JSON Schemas and their contract tests (`docs/contracts/uns/`) would need a second definition; what Sparkplug's birth, death and `seq` provide, the project already has with stronger guarantees: per-source sequence numbers and device epochs with dedup and gap incidents (ADR-0015, ADR-0009), retained state and anchors, the gateway's last will. Sparkplug's `seq` wraps at 256 and wouldn't carry ADR-0015's exactly-once accounting. No consumer in the project needs it (no SCADA or historian speaks only Sparkplug).
- **If one is ever needed:** an optional egress bridge that publishes a Sparkplug B view of the UNS for a named consumer, beside the UNS, never replacing it; it would be its own ADR and phase.
- Recorded as ADR-0041 (status accepted, deciders Claude, **awaiting the owner's review**), and the master plan's open decision points to it.
