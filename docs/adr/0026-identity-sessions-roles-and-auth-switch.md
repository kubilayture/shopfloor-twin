# ADR-0026: Identity: local users with roles, cookie sessions, scrypt and an enforcement switch

- Status: accepted
- Date: 2026-10-16
- Deciders: Claude (#168), within the Phase 7 plan ("Identity"); recorded for the owner under the standing instruction of 2026-10-15

## Context and problem statement

Until Phase 7 the MES has no users: reads are open on loopback (ADR-0019) and writes are guarded by origin checks and audited under a name the operator types (ADR-0023). Phase 7 adds order writes that only a supervisor may make, and the master plan's exit criterion "role permissions tested". The Phase 7 plan decides the shape of identity; implementing it (#168) left these questions:

- How does a browser prove who it is: tokens or sessions, and where are they kept?
- How are passwords stored without a new dependency, and how does a burst of logins stay inside the MES container's 512 MiB?
- What happens on repeated failures, when nginx hides every client address?
- Where are roles and permissions defined so the MES and the web can't disagree?
- How does the first admin come to exist without a password in the repository?
- How can identity merge without breaking the web, the e2e tests, the stack smoke and the reconciliation, none of which can log in yet (#170)?

## Considered options

Credentials: (a) JWTs in `localStorage` or a header; (b) an opaque random token in an `HttpOnly` cookie, its hash stored server-side.

Password hashing: (a) bcrypt or argon2 from npm; (b) `node:crypto` scrypt.

Repeated failures: (a) no limit; (b) lock every account after N failures; (c) lock normal accounts, delay admins.

Rollout: (a) enforce authentication in the same PR; (b) build it behind a switch, `MES_AUTH=off` by default, and turn it on with the login screen (#170).

## Decision outcome

Credentials (b), hashing (b), failures (c), rollout (b).

**Roles and permissions.** The five roles of master plan section 7 (`operator`, `maintenance`, `quality`, `supervisor`, `admin`) and fourteen permissions (`read` and one per kind of write) are defined once in `@shopfloor/contracts/identity` as `ROLES`, `PERMISSIONS` and `ROLE_PERMISSIONS`, the plan's matrix cell by cell (a test compares them). A user has one or more roles. `admin` holds only `read` and `user:admin`: separation of duties, and a person who needs both gets both roles. The roles are also rows of `identity.role` (seeded by migration `0016`, checked against contracts at start-up); permissions are code, not data.

**Sessions.** `POST /api/v1/session` (user name, password, `kind` `desk` or `terminal`) sets the cookie `sft_session` to 32 random bytes in base64url, `HttpOnly; SameSite=Strict; Path=/; Max-Age=43200`, with `Secure` and the name `__Host-sft_session` when `MES_COOKIE_SECURE=on` (behind TLS, Phase 9). Only the token's SHA-256 is stored (`identity.session`), so a read of the table can't be replayed. A session ends when idle (60 min desk, 15 min terminal; the last use is written at most once a minute and moves the idle expiry), 12 h after login whatever the use, on logout (`DELETE /api/v1/session`, body `{}` because every write is JSON; it needs no live session and clears the cookie also for an ended or invalid one), when the user changes the password (the other sessions), when an admin resets it or disables the user (all of them), and when a login presents it (a login always gets a new token). JWTs were rejected: revocation needs a server table anyway, and a token a script can read is worse than an `HttpOnly` cookie. The cookie's scope on `localhost` (every port, not `127.0.0.1`) is in the runbook.

**Passwords.** `scrypt` from `node:crypto` with N = 2^15, r = 8, p = 3 (32 MiB, an OWASP-listed setting), a 16-byte salt and a 32-byte key, stored as `scrypt$N$r$p$salt$hash` so the cost can rise later; a login with a hash of other parameters rehashes it. Every call passes `maxmem: 64 MiB`: Node's default of 32 MiB is just below what these parameters need and the call would fail (a test shows both). At most two hashes run at a time (a semaphore), so 512 MiB hold a burst of logins. A password has 12–128 characters (code points) and no composition rule (NIST SP 800-63B). An unknown user name costs one hash of a dummy (made at start) and the same lookup transaction as a known one, which finds no row; a known one costs one real hash: the answer and, as far as practical, its time don't tell them apart. A failed login of an unknown or malformed name is logged and audited as `(unknown)`, never as typed (it may be a mistyped password). Every failure (unknown or disabled user, wrong password, a lock, an admin's delay) is the same 401 `urn:shopfloor:unauthenticated` with the same text.

**Failures.** Every attempt is **reserved before its hash** (review of PR #182): one transaction locks the user's row (`SELECT … FOR UPDATE`), refuses a disabled, locked or delayed user, and otherwise counts the attempt as a failure in advance, setting the lock or the next delay the moment the count reaches five; a success then clears the count. So however many attempts run at once, at most five of a normal account's are evaluated before it locks, and one per delay for an admin (tested with twelve parallel attempts). A wrong current password in a password change is reserved and counted the same way. Five consecutive failures lock a normal account for 15 minutes; the right password is refused while it is locked, and a failure after the lock ran out starts the count anew. Users with the `admin` role are never locked, so that an attacker can't lock out the one account that can unlock the others: from the fifth failure on, the next attempt is refused for 1 s, doubling with each failure, at most 5 min. The lock is per account, because behind nginx there is no client address: anyone who can reach the login page can keep a known user locked out. That denial of service is accepted on a loopback plant network until Phase 9; part of it is that with more than five concurrent logins on one account, the attempts after the fifth are refused, even one with the right password. Every failure, lock, login, logout and user change is a row of the append-only `identity.audit_log` (a trigger refuses UPDATE, DELETE and TRUNCATE); #169 moves the module audits into it.

**Bootstrap.** `MES_BOOTSTRAP_ADMIN_PASSWORD` (optional, 12–128 characters, never echoed) creates the user `admin` with the admin role and a password it must change, only when no enabled admin exists; an existing `admin` account is restored that way. Without it the MES starts, logs a warning and has no admin until the variable is set and the MES restarted, or `pnpm --filter @shopfloor/mes-server user:create --username <name> --role admin` creates one (password from stdin, so it is in no process list or shell history). The last enabled admin can't be disabled or lose the role (409). A user with a temporary password (bootstrap, an admin's create or reset) gets 403 `urn:shopfloor:password-change-required` on every route but the session and password routes until it changes it.

**Enforcement.** Each route declares its access: a permission, `session` (the session and password routes) or `public` (the login). With `MES_AUTH=on` the `/api/v1` hook checks, in this order (for every request, also one carrying an `Upgrade` header that is not a real WebSocket upgrade of the push route): `Host` (403), `MES_WRITES` (405), `Origin` and `Sec-Fetch-Site` (403), JSON (415), as ADR-0023, then the session (401 `urn:shopfloor:unauthenticated`), the temporary password and the permission (403 `urn:shopfloor:password-change-required`, `urn:shopfloor:forbidden`), and last the rate limits (429): a cross-site request never learns whether a session exists, and an anonymous one never spends a token. Unknown routes need a session too, so they don't reveal which exist. `/health/*` and `/metrics` stay open. The WebSocket upgrade passes the Host and Origin checks first; its session is checked in the same hook, and a socket without one is accepted and closed at once with code 4401 (`WS_CLOSE_UNAUTHENTICATED`), because a browser can't read the status of a refused upgrade; a session that must change its password, or whose roles lack `read`, gets 4403 (`WS_CLOSE_FORBIDDEN`). Only a real upgrade (`@fastify/websocket`'s `request.ws`, from `Connection: upgrade`) of `GET /api/v1/ws` takes that branch. A socket's session is closed with 4401 as soon as the session ends (logout, password change, disabled user) and, for expiry, within the next check (every 15 s). Pushed messages don't count as use; a screen that only listens ends after the idle timeout. Session lookups use a pool of their own (two connections), never one that ingest's acknowledgement path waits for.

**Rate limits.** The global write bucket of ADR-0023 stays; each user gets a bucket of its own (5 per second, bursts of 10), checked first, both answering 429 `urn:shopfloor:write-rate`. Logins never spend them (otherwise anyone reaching the login page could starve plant writes): they have buckets of their own, one per user name (1 per second, bursts of 5) and one for all logins together (5 per second, bursts of 10), answering 429 `urn:shopfloor:login-rate` with `Retry-After`. Logout spends none.

**`MES_WRITES=off`.** The login, logout and the password change stay open (their Origin and JSON guards still apply): with `MES_AUTH=on`, a read-only MES would otherwise lock everyone out.

**Rollout.** `MES_AUTH` defaults to `off` in #168: the session routes need a session, and everything else behaves exactly as before (no session, no permission, the old actor fields), so the web, the end-to-end tests, the stack smoke and the reconciliation stay green. The tests run both settings. #170 changes the default to `on` together with the login screen and the tests' logins; after that, `off` is only for diagnosis and the MES logs a warning at start (it does already).

### Consequences

- Good: one permission table for the MES and the web; a route without a declared access can't exist (the type requires it for writes, reads default to `read`), and a test compares every route of the OpenAPI document with the matrix for anonymous and each role.
- Good: no new dependency; tokens and passwords never reach a log (a test captures Fastify's and the module's log lines through logins, failures and a lockout).
- Good: every merge stays green while identity grows (H4 in the plan).
- Bad: per-account lockout is a denial of service for anyone who can reach the login page (accepted until Phase 9); an admin under attack waits up to 5 minutes between attempts.
- Bad: until #170 the switch is off in Compose: identity exists but protects nothing on the stack.
- Bad: a session's last use is written at most once a minute, so the idle expiry is exact to a minute; an expired socket closes up to 15 s late.
- Bad: plain HTTP means no `Secure` cookie and the cookie goes to every `localhost` port; TLS is Phase 9.

## Notes (#170)

- **Default on.** `MES_AUTH` defaults to `on` in the environment and in Compose, together with the web's login and the tests' logins (the stack smoke creates an operator per run with `user:create`; the reconciliation generates `MES_BOOTSTRAP_ADMIN_PASSWORD`, and that admin creates the run's supervisor through the API). The consequence above of a switch that is off in Compose no longer holds.
- **What `off` means now.** `MES_AUTH=off` is a diagnosis switch only: reads (access `read`) and the WebSocket are served without a session, while every write, and the session and password routes, still need a session and its permission (401, 403); the MES logs a warning at start. Writes stay behind a session so that every write has a known user: the typed `codedBy`, `actor` and `author` are gone from the request schemas (strict, so a client still sending one gets 400), and with them #169's unauthenticated path. Answers still carry the actor's user name and `authenticated` (false only in rows written before #170).
- **Shared limits.** `SESSION_IDLE_MS` (desk 60 min, terminal 15 min) and `SESSION_ABSOLUTE_MS` (12 h) moved to `@shopfloor/contracts/identity`, so the web times out on the MES's limits.
- **Idle timeout in the web.** The MES counts requests as use, never pushed messages. The web counts a person's input (pointer, key, wheel, touch) in any of the browser's tabs (shared through `localStorage`), and neither pushed messages nor background refreshes. Its deadline is the earliest of: the idle limit after the last input, the MES's own `idleExpiresAt` as last read, and the absolute `expiresAt`, the MES's times moved onto the browser's clock by the offset of the answers' `Date` headers (review of PR #186, M3), so the web never shows a session longer than the MES keeps it. Two minutes before the deadline a warning offers **Stay logged in** and reads the session once (the MES's expiry may have moved with requests the tab doesn't see); at the deadline the web ends the session itself (`DELETE /session`) and its login says why. So that the MES doesn't end the session of someone typing a long draft without sending it, the web reads the session (`GET /session`, which counts as use) at most every 30 s while there is input, in this tab or another. The absolute limit is warned too and can't be extended.
- **Polling screens keep the MES session alive.** Several screens refresh REST reads on a timer (machine detail, OEE dashboard, the shift picker), and the MES counts every request as use, so an unattended desk on such a screen never reaches the MES's idle expiry. On a shared terminal the protection against the next person therefore depends on the web's own timer above, which only a person's input moves; a page whose JavaScript is stopped (a frozen tab) keeps the session until the 12 h limit. Accepted until Phase 9; the terminal screens of #177 have no polling of their own beyond what they show.
- **Drafts.** A session lost while a form holds unsaved input doesn't unmount the page: it stays, inert and covered, under a login for the same user, who carries on and sends it. Logging in as someone else discards the input, so a shared screen never sends one user's input as another's.
- **4401 and 4403.** A 401 from REST, or a WebSocket close 4401, takes the web to its login and back to the page afterwards; a 403 `urn:shopfloor:password-change-required`, or a close 4403, to the forced password change. The live client doesn't reconnect after 4401 or 4403 (another attempt would only be closed again) and starts after the next login.

## Notes (#177): the operator terminal

- **Sign-on is a login plus a crew row.** At `/terminal/$workCenter` an operator logs in with `kind: terminal` (15 min idle), then `POST /api/v1/terminal/{workCenter}/sign-on` opens the crew row (`shifts.crew_assignment`, ADR-0027) for that session in the shift instance the plant clock is in. A desk session can't sign on (409 `urn:shopfloor:terminal-session-required`), nor can anyone while no shift runs (409 `urn:shopfloor:no-shift`). Every operation write (start, pause, resume, sign-off) needs `terminal:operate` and an open crew row of the user at the operation's work center held by the very session that writes (409 `urn:shopfloor:not-signed-on`), so a desk session or another tablet's session never acts at a terminal it didn't sign on to.
- **Crew rows end with the session.** A session that ends (logout, password change or reset, a disabled user, a new login presenting the cookie) ends its crew rows through `onSessionsEnded`; one that expires (idle, absolute) is found by the shifts module's tick (`Identity.live`, every 5 s); the shift's end closes rows at the shift end; a sign-on of the same user at the same work center from another session ends the first row (`replaced`). An ended crew row closes the user's open activity intervals at that work center.
- **One tablet, several operators over time.** One browser holds one cookie: a second operator signing on at the same tablet replaces the first one's session (and so their crew row). Several operators at one work center use several tablets. The terminal screen keeps nothing of one operator for the next: its reads are keyed by (user, work center), its components by (user, work center), and a sign-off or an ended session empties the terminal's queries, every mutation's input and the pushed view, and stops the live client.
