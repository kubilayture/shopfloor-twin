# MES WebSocket push

`mes-server` pushes equipment states, telemetry, OEE, downtime records, alarm occurrences and alarm KPIs to subscribed screens (#97, #120, #142, ADR-0019). OpenAPI can't describe a WebSocket, so this page does; the JSON Schema of every message is generated from the zod schemas (`packages/contracts/src/mes-api.ts`, shared with `web`, ADR-0020) into [`mes-realtime.schema.json`](mes-realtime.schema.json) (`pnpm --filter @shopfloor/mes-server openapi`), and a test fails when it drifts. The REST API is in [`mes.openapi.json`](mes.openapi.json).

## Connection

- URL: `ws://<host>:4700/api/v1/ws` (the MES binds to `127.0.0.1` by default; in Compose the web container proxies it as `ws://localhost:8080/api/v1/ws`, #99). Read-only. With `MES_AUTH=on` (#168, ADR-0026; the default since #170) the upgrade needs the session cookie `sft_session` (`POST /api/v1/session`): a socket without a live session is closed at once with code **4401**, and an open socket is closed with 4401 when its session ends (logout, password change, the user disabled) or expires (checked every 15 s; pushed messages don't count as use). A session that must change its password first, or whose roles lack `read`, is closed with **4403**. A client goes to its login on 4401, to the password change on 4403. With `MES_AUTH=off` (diagnosis only, #170) the socket needs no session.
- Every message is one JSON text frame. A client message may be at most 4 KiB.
- The server pings every 15 s; a client that misses a pong is disconnected (browsers answer pings on their own).
- At most 64 clients; one more is closed with code 1013 (try again later).
- An upgrade with an `Origin` header is accepted only from the MES's own host or an origin in `HTTP_ALLOWED_ORIGINS`, and the `Host` header must be in `HTTP_ALLOWED_HOSTS` (DNS rebinding); otherwise the answer is 403 (ADR-0019). Clients that send no `Origin` (not a browser page) are accepted.
- Client messages are limited to 10 per second on average, in bursts of up to 20; above that, `rate-limited` errors.

## Client messages

| Message                                                                              | Meaning                                                                           |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| `{ "type": "subscribe", "topic": "states" }`                                         | Current state of every equipment, then each change                                |
| `{ "type": "subscribe", "topic": "telemetry:wsh-01" }`                               | Every metric of one equipment: latest values, then each                           |
| `{ "type": "subscribe", "topic": "telemetry:wsh-01", "metric": "bath-temperature" }` | One metric (repeat for more)                                                      |
| `{ "type": "unsubscribe", "topic": "telemetry:wsh-01" }`                             | Stops the topic (with `metric`: only that metric)                                 |
| `{ "type": "subscribe", "topic": "oee:cell-m1" }`                                    | OEE of an equipment or work center: current hour and shift, then each change      |
| `{ "type": "subscribe", "topic": "oee:order:PO-2610-001" }`                          | An order's OEE, jobs and first-pass yield (#231): now, then each change           |
| `{ "type": "subscribe", "topic": "oee:line" }`                                       | Line throughput OEE of the current hour and shift, with the bottleneck (#232)     |
| `{ "type": "subscribe", "topic": "downtime" }`                                       | Downtime records as they are created, closed or recoded                           |
| `{ "type": "subscribe", "topic": "alarms" }`                                         | Alarm occurrences as they are raised, cleared or change, and shelves (#142, #143) |
| `{ "type": "subscribe", "topic": "alarm-kpi:position:cell-m1" }`                     | Alarm KPIs of a scope: current hour and shift and open floods, then changes       |
| `{ "type": "subscribe", "topic": "shifts" }`                                         | Shift instances (created, status, revision) and handover notes (#144)             |
| `{ "type": "subscribe", "topic": "orders" }`                                         | Production orders and their dispatch commands as they change (#174)               |
| `{ "type": "subscribe", "topic": "quality" }`                                        | SPC signal episodes and characteristic changes (#200)                             |
| `{ "type": "subscribe", "topic": "terminal:line-a1" }`                               | A work center's operator terminal view (#177)                                     |

`metric` applies to telemetry topics only. A client may hold up to 16 OEE topics, 16 order OEE topics (`oee:order:…`, a budget of their own since #232) and 16 alarm KPI topics (`too-many-subscriptions`) and up to 64 telemetry subscriptions, counted per metric (a whole equipment counts one), and read up to 4 snapshots at a time (`busy`). Subscribing again sends a fresh snapshot. A client subscribed to every metric of an equipment can't unsubscribe one of them: unsubscribe the topic and subscribe the metrics wanted.

## Server messages

| `type`                                    | Fields                                                                                                                                      | When                                                                                                 |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `subscribed`, `unsubscribed`              | `topic`, `metric` (or null)                                                                                                                 | Answer to a request                                                                                  |
| `snapshot` (topic `states`)               | `clock` (`epoch`, `watermark`, or null), `states`: `[{ equipment, current }]`                                                               | Right after `subscribed`: every equipment that has reported                                          |
| `snapshot` (topic `telemetry:…`)          | `samples`: `[{ equipment, metric, unit, t, value }]`                                                                                        | Right after `subscribed`: the latest stored sample per metric                                        |
| `snapshot` (topic `oee:…`)                | `hour`, `shift`: OEE buckets (as in `GET /api/v1/oee`), each null without data                                                              | Right after `subscribed`: the hour and shift the plant clock is in                                   |
| `snapshot` (topic `alarm-kpi:…`)          | `hour`, `shift`: alarm KPI buckets (as in `GET /api/v1/alarms/kpi`), each null without a clock; `floods`: episodes still in flood           | Right after `subscribed`: the hour and shift the plant clock is in                                   |
| `state`                                   | `equipment`, `current` (as in `GET /api/v1/equipment/{id}`)                                                                                 | The equipment's state, cause, start or epoch changed                                                 |
| `oee`                                     | `topic`, `hour`, `shift` (as in the snapshot)                                                                                               | Inputs of a member machine changed: at most once a second per topic                                  |
| `snapshot` / `oee-order` (`oee:order:…`)  | `topic`, `order` (as `GET /api/v1/oee/orders/{id}`, null for an unknown order)                                                              | On subscribe, then when its inputs changed and the body differs: at most once a second per topic     |
| `snapshot` / `oee-line` (`oee:line`)      | `topic`, `productionMode`, `bottlenecks`, `hour`, `shift` (line buckets as in `GET /api/v1/oee/line`; `shift` null outside a shift)         | On subscribe, then when its inputs changed and the body differs: at most once a second               |
| `downtime`                                | `event` (`created`, `closed`, `recoded`, `updated`, `removed`), `record` (as in `GET /api/v1/downtime`)                                     | A record changed (within about 250 ms of its write)                                                  |
| `alarm`                                   | `event` (`raised`, `cleared`, `updated`, `acknowledged`, `commented`, `shelf`), `occurrence` (as in `GET /api/v1/alarms`)                   | An occurrence was stored or changed, or an operator acted (its commit)                               |
| `alarm-point`                             | `event` (`shelved`, `unshelved`, `expire`, `epoch-ended`), `point` (as in `GET /api/v1/alarm-points`)                                       | A point's shelf changed (#143)                                                                       |
| `alarm-kpi`                               | `topic`, `hour`, `shift`, `floods` (as in the snapshot)                                                                                     | Its alarms or the plant clock changed: at most once a second per topic                               |
| `shift`                                   | `event` (`created`, `status`, `revised`), `shift` (as in `GET /api/v1/shifts/{date}/{shift}`)                                               | The plant clock entered the shift, its status moved, or its report's revision rose                   |
| `handover-note`                           | `event` (`created`, `edited`), `note` (as in `GET /api/v1/shifts/{date}/{shift}/notes`)                                                     | A note was written (its commit)                                                                      |
| `order`                                   | `event` (`imported`, `updated`), `order` (as in `GET /api/v1/orders`)                                                                       | An order was imported or changed (status, flags, revision, quantities; its commit)                   |
| `command`                                 | `event` (`created`, `updated`), `command` (as in `GET /api/v1/orders/{id}`, without attempts and results)                                   | A dispatch created a command, or its reading changed (published, answered, a fact)                   |
| `spc-signal`                              | `event` (`opened`, `updated`, `final`, `withdrawn`, `removed`, `acknowledged`), `signal` (as in `GET /api/v1/quality/signals`)              | An episode was stored, changed or removed: extent, finality, withdrawal, acknowledgement             |
| `spc-characteristic`                      | `event` (`readings`, `limits`, `notice`), `characteristic` (as in `GET /api/v1/quality/characteristics`)                                    | Its readings changed (read its chart again), a limit version, or a notice                            |
| `quality-hold`                            | `event` (`opened`, `commented`, `released`, `rejected`, `scope`), `hold` (as in `GET /api/v1/quality/holds`)                                | A hold was opened, commented or decided, or its scope or held-material-consumed count changed (#201) |
| `snapshot` / `terminal` (`terminal:<id>`) | `topic`, `view` (as `GET /api/v1/terminal/{workCenter}`)                                                                                    | The whole terminal view of a work center: on subscribe, then whenever it changed (#177)              |
| `telemetry`                               | `equipment`, `metric`, `unit`, `t`, `value`                                                                                                 | A sample was stored                                                                                  |
| `clock`                                   | `epoch`, `watermark`                                                                                                                        | The plant clock moved (at most once a second, to `states` subscribers)                               |
| `error`                                   | `code` (`invalid-message`, `unknown-equipment`, `too-many-subscriptions`, `unknown-topic`, `busy`, `rate-limited`, `unavailable`), `detail` | A request was refused; the connection stays open                                                     |

`current` is `{ epoch, state, cause, since, seq, provisionalUntil, ageMs }`: `since` is when the state began (simulation time), `ageMs` the time in it up to the epoch's watermark. All times are ISO 8601 UTC with milliseconds, simulation time.

### OEE and downtime topics (#120)

- `oee:<id>` names an equipment or a work center (`cell-m1`, `line-a1`); another id gets `unknown-equipment`. The epoch is the plant clock's, for all machines of a work center alike. The buckets are those the plant clock (the newest epoch's watermark) is in, read just before it: at 07:00:00.000 the current hour is 06:00. Each is the full bucket of `GET /api/v1/oee` (inputs, exact fractions, losses, `final`, `provisionalMs`, `revision`, `incidents`), so a client replaces what it holds.
- The topic is computed off ingest's path: a change to a member's pieces or cycles marks it dirty, and a timer computes dirty topics at most once a second (`oee` delta only when the result differs). The snapshot of a new subscriber comes from the next computation, never from a stale one; a pending delta of that topic is dropped for it.
- `oee:order:<order number>` (#231, ADR-0036 P9-04 amendment) is the body of `GET /api/v1/oee/orders/{id}`: the order OEE over its job windows, every job (head time, window, OEE, `final`), the first-pass yield and the CNC cut-offs. A CNC's pieces or a command to it mark dirty the topics of the orders with a job on that CNC (other orders on a CNC decide head times; a topic not computed yet too), an order or execution change that order's; while an order's body is not final in every part (the order OEE, `firstPassYield.final` or `line.final`, #233 review), any machine's pieces (ASM-01's decide `line.final`, PCK-01's packs and every station's units the yield) and the plant clock moving (an open `line` runs to it) mark its topic dirty too; it is computed like `oee:<id>`, at most once a second, an `oee-order` delta only when the body differs, and counts against its own budget of 16 order OEE topics (#232: an order list subscribing per order can't starve the dashboard's `oee:<id>` topics on a shared socket). A final order (`final` and `firstPassYield.final`) with no `incidents` never changes again; one with `incidents` lies over a written-off gap (ADR-0018), carries `mayRevise: true` and may still be revised: its `revision` (the highest revision of the final hours under it) rises when it is, so a consumer tells a revised final from an unchanged one. The body also carries the order's own line OEE (`line`, #232).
- `oee:line` (#232, ADR-0036 P9-05 amendment) is the line throughput OEE of the hour and the shift bucket the plant clock is in (read just before the newest watermark, as `oee:<id>`), each as a bucket of `GET /api/v1/oee/line` (`plannedBusyMs`, `good`, `idealMs`, `oee`, `aboveOne`, `through`, `final`, `incidents`, `mayRevise`, `revision`), with the designed bottleneck per product and the production mode. It turns dirty only for the changes it reads: the pieces of a contributing machine (schedule mode: the packing and bottleneck machines; orders mode: every line machine) or a packing cycle in or after the hours it last covered (a late fact of an earlier hour leaves it alone), and in orders mode any order OEE change (commands, orders, execution); it is computed at most once a second, an `oee-line` delta only when the body differs, and counts against a budget of its own.
- `downtime` has no snapshot (read `GET /api/v1/downtime` first). Every record change follows a change of its pieces or of its operator codings (#121); the MES reads the records of the changed hours about 250 ms later and compares them with those it knows. A record that is created and closed between two reads arrives once, as `created` with its end. Deltas are keyed per record, so a slow client may get only the latest event of a record: treat every `downtime` message as an upsert by `record.id` (`removed`: delete).
- `recoded` (#121): the record's reasons changed: its auto reason (new rules at start-up), or its codings (a `PUT /api/v1/downtime/{id}/coding`, or a clip after a re-cut). The record carries `reason`, `segments`, `codings`, `uncoded` and the coding set's `version`; it is read after the write, so it equals the version the `PUT` answered. That version also moves with writes to other records of the same machine and epoch: each of those records the MES knows (the last two days) then goes out as `updated` with the new version (#122), so a client holding the pushed records writes with the current version; a write still answers 409 when the version moved meanwhile. No OEE topic changes with a coding: reasons never change OEE (ADR-0021).
- The WebSocket carries no writes: its client messages are subscriptions only (ADR-0023).

### Alarm topics (#142)

- `alarms` has no snapshot: read `GET /api/v1/alarms` (active, or the history of a range) first, then apply every `alarm` message as an upsert by `occurrence.id` (`{equipment}~{epoch}~{seq}`). `raised`: a new occurrence (a raise fact or a retained delivery); `cleared`: it ended (any `endReason`: the device's clear, a resync snapshot's `lost`, `superseded` by the next raise, `epoch-ended`); `updated`: anything else (an anchor replaced by its fact, a late clear replacing a `lost` end, a priority after a configuration change). Deltas are keyed per occurrence, so a slow client may get only the latest state of each. Operator actions (#143) push the occurrence again with its `state`, `acknowledged`, `shelved` and `comments`: `acknowledged`, `commented`, and `shelf` for every occurrence of a point that is not closed when the point's shelf changes; the shelf itself comes as an `alarm-point` message (keyed per point), also when the plant clock ends it (`expire`, `epoch-ended`). Device upserts carry the operator's state as well, read after their commit in the module's order, so a later message is never older. Operator actions never mark an `alarm-kpi` topic dirty: they change no KPI.
- `alarm-kpi:<scope>` names the plant (`alarm-kpi:plant`), an operator position (`alarm-kpi:position:cell-m1`) or an equipment (`alarm-kpi:equipment:cnc-01`); another gets `unknown-equipment`. The buckets are those the plant clock is in, read just before it, in the newest epoch: the UTC hour, and the shift (whole) or the `no-shift/{start}` stretch up to the end of the current hour, each the full bucket of `GET /api/v1/alarms/kpi` with `final`, `revision` and `incidents`. `floods` lists the episodes still in flood (the banner of a position, #145).
- The topic is computed off ingest's path, like OEE: an occurrence change or a finality move of a member, or the plant clock moving (active time grows while an alarm is active), marks it dirty; a timer computes dirty topics at most once a second, and an `alarm-kpi` delta goes out only when the content differs.

### Shifts topic (#144, ADR-0025)

- `shifts` has no snapshot: read `GET /api/v1/shifts/{date}/{shift}/report` (or the instance, or its notes) first, then apply `shift` messages as upserts by (`shift.epoch`, `shift.key`) and `handover-note` messages as upserts by `note.id`. Deltas are keyed that way, so a slow client may get only the latest of each.
- `created`: the plant clock entered the shift; `status`: `running` → `ended` → `final`; `revised`: `revision.inputs` (an input of a final report was revised) or `revision.content` (a note was written, or a recode inside a final shift) rose. A client showing a report reads it again when its instance's `status` or `revision` moves. `revision.contentAtFinal` (#163) is `content` at the moment the report became final, stored with it (null before): it is set by the `status` event that makes the instance final and never moves after, so it plays no part in ordering; `content - contentAtFinal` is how often the content changed after final.
- There is no paced `shift-report:<key>` topic: while a shift runs, its live numbers come from `oee:<id>` and `alarm-kpi:<scope>`, already paced at one delta a second; recomputing a whole report every second would repeat them.

### Orders topic (#174)

- `orders` has no snapshot: read `GET /api/v1/orders` (and `GET /api/v1/orders/{id}` for an order shown in detail) first, then apply `order` messages as upserts by `order.id` and `command` messages as upserts by `command.commandId`; reset what you hold on every (re)subscribe and read again. Deltas are keyed that way, so a slow client may get only the latest of each.
- A command's `state` is read from every delivery published, every `cmd-res` the gateway answered and the device's job facts (ADR-0029); `confirmed` turns true when its `accepted` fact arrived. A write (release, dispatch, cancel, re-dispatch, close) pushes the order after its commit, and a dispatch its new command (`created`).

### Quality topic (#200, ADR-0032)

- `quality` has no snapshot: read `GET /api/v1/quality/characteristics` and the chart shown (`GET /api/v1/quality/characteristics/{id}/chart`) first, then apply `spc-signal` messages as upserts by `signal.id` and `spc-characteristic` messages as upserts by `characteristic.id`; reset what you hold on every (re)subscribe and read again. Deltas are keyed that way, so a slow client may get only the latest of each (an `opened` episode may arrive already as `final`).
- `spc-signal`: `opened` (new, `provisional` or already `final`), `updated` (its extent grew or shrank, `extentFinal` turned true, or it came back after a withdrawal), `final` (the leak tester is final through its triggering point), `withdrawn` (re-derived away and kept, with `withdrawnReason`: a final one, or an acknowledged provisional one, whose acknowledgement is then orphaned), `removed` (an unacknowledged provisional one re-derived away and deleted: drop it), `acknowledged`.
- `quality-hold` (#201): upserts by `hold.id`, read `GET /api/v1/quality/holds` first; `scope` when the scope derived from the genealogy grew or changed or a `held-material-consumed` incident was raised (read the hold's detail again for its units).
- `spc-characteristic`: `readings` when its measurements changed (read the chart again, at most as often as you need, with `If-None-Match`: an unchanged derivation answers 304), `limits` when a version was created (version 1 automatically) or ended, `notice` when a late reading changed version 1's baseline window.

Telemetry deltas of an equipment that arrive while its snapshot is being read are sent after it (state deltas are not held); a snapshot is not sent if the client unsubscribed meanwhile; a delta may repeat a value the snapshot already holds, so clients keep the newest by time.

### Terminal topics (#177)

- `terminal:<workCenter>` (any work center of master data; another is an `unknown-equipment` error) answers a `snapshot` with the whole `view`, the body of `GET /api/v1/terminal/{workCenter}`: machines and their states and jobs, the active orders with their operations at this work center (counts, completion, sign-off, open activities, version), the WIP, the queue, the uncoded scrap records of its operations, the crew, and since #203 a read-only `quality` part (the open holds touching its orders, the SPC episodes of its machines that are open or not yet acknowledged, each machine's last cycle's lots). Then a `terminal` message carries the whole view again whenever it changed (an order, command or operation change, execution's units and scrap records, a crew row of this work center, one of its machines' states; since #203 a signal episode, a hold, or a genealogy round that rebuilt units), computed at most every `terminalMs` (500 ms) and sent only when it differs. A client replaces what it holds; there is nothing to merge.
- Terminal topics count like the OEE and alarm KPI ones, 16 per client.

## Delivery and slow clients

- Deltas leave the MES within milliseconds of the commit (the test pushes the 60× rate, about 25 messages/s, and checks the 2 s budget of exit criterion 3; measured about 30 ms at most locally).
- They are queued per client by key: one state per equipment, one sample per metric, one clock, one OEE pair per topic, one event per downtime record, one upsert per alarm occurrence, one alarm KPI delta per topic. While a client's socket buffers more than 256 KiB, its queue waits and a newer delta replaces the older one of the same key, so a slow client skips intermediate values and catches up with the latest. Above 4 MiB it is disconnected.
- At 60× even a fast client may see a short stop only as two quick deltas; history comes from REST (`/intervals`, `/telemetry`).
- Pushing never delays ingest's acknowledgements: the listeners only queue, and sending happens on a later turn of the event loop.
- Metrics: `mes_ws_clients`, `mes_push_messages_total{type}`, `mes_push_coalesced_total`, `mes_ws_dropped_total{reason}`.
