# ADR-0039: MQTT dynamic security, an HTTPS-only web front and login throttling

- Status: accepted (HTTPS: #241, P9-14; MQTT: #240, P9-13; login throttling: #242, P9-15)
- Date: 2026-10-19
- Deciders: Claude, within the Phase 9 plan ("Dev CA, HTTPS and ports", "MQTT dynamic security", "Login throttling"; review decisions round 1 findings 3, 10 and 25, round 2 finding 12, round 3 and the final check); recorded for the owner under the standing instruction of 2026-10-15

The Phase 9 plan gives this ADR three parts, each written by its own issue in its own section: **HTTPS** (the dev CA, the HTTPS-only front, `Secure` cookies, the harnesses' trust and the published ports; #241), **MQTT** (dynamic security; #240) and **login throttling** (P9-15). ## MQTT (#240, P9-13)

### Context and problem statement

Since Phase 3 the broker has authenticated users from a plain password file and authorized topics from a plain ACL file (`config/mosquitto/acl`, ADRs 0015 and 0029). An ACL file grants per user and can't tie a client id to a user, so any user with a valid password could connect with the gateway's client id `gw-01` (disconnecting the real gateway, whose will then says `offline`), with `gw-01-cmd` (the gateway's persistent command session, ADR-0029), or with `mes-server` (the MES's persistent session, its subscriptions and up to 100,000 queued messages). The UNS contract and the runbook carried that as an accepted risk "until Phase 9". Security review item S2 asks: client-id takeover of `gw-01`, `gw-01-cmd` and `mes-server` refused, every ACL refusal kept (PUBACK 0x87), passwords random per stack.

Constraints: `config/mosquitto` is mounted read-only (`:ro`), so anything the broker writes lives in the `broker-data` volume (`/mosquitto/data`); the passwords are this stack's random values from `.env`; the test brokers (testcontainers) must use the same generation as Compose.

### Considered options

1. **Keep the ACL file** and record the takeover as a permanent accepted risk.
2. **`use_username_as_clientid true`**: Mosquitto replaces every client id with the username. No plugin, but each user then has exactly one session: the gateway's two connections (`gw-01` publishing, `gw-01-cmd` subscribing) would take each other's session, so it needs a second gateway user and a second MES user and a change to ADR-0029's ACL; `dev` and `healthcheck` would kick their own concurrent tools (`mosquitto_sub`, overlapping healthchecks).
3. **Mosquitto's dynamic-security plugin** with a client id bound to every user (the plan bound only the gateway's and the MES's; see "Every user bound").

### Decision outcome

Chosen option: 3, the dynamic-security plugin (`/usr/lib/mosquitto_dynamic_security.so`, part of the `eclipse-mosquitto:2.1.2-alpine` image already used), because it closes the session takeover with the image we have and keeps the rights exactly as they were.

- **Generated configuration.** `config/mosquitto/dynamic-security.json` is a template without secrets: the users, their bound client ids, the roles and their ACLs, and the default access (`publishClientSend` and `publishClientReceive` denied, `subscribe` and `unsubscribe` allowed; see "ACL parity"). `config/mosquitto/entrypoint.sh` copies it into `/mosquitto/data/dynamic-security.json` **on every start** and sets each user's password from `MQTT_USERS` with `mosquitto_ctrl -f <file> dynsec setClientPassword` (Mosquitto 2.1 edits the file without a running broker; the hash is PBKDF2-SHA512). It refuses to start when `MQTT_USERS` names a user the template doesn't have or when a template user gets no password. The file is `0600`, owned by `mosquitto`; the Phase 8 password file is removed. Every start, not only the first, so a password changed in `.env` takes effect on the next start and nothing written at run time survives: there is **no admin user**, so nobody can change users or roles over `$CONTROL/dynamic-security` (publishing there is denied by default). **Hardening after the security review of PR #261:** user names in `MQTT_USERS` must be a-z, 0-9 and `-` and match a template user exactly (`grep -F`; a name such as `d.v` matched `dev` as a pattern before, and `mosquitto_ctrl` exits 0 even for a client it doesn't find, so its output is checked for `Error`); globbing is off while the entries are split (`set -f`); an empty password is refused; and `MQTT_USERS` is unset before `exec mosquitto`, so the broker's environment holds no password (`MQTT_HEALTHCHECK_PASSWORD` stays for the Compose healthcheck). **Known exposure:** each password is on `mosquitto_ctrl`'s command line (argv) while it is hashed, a moment per user at start, visible only to processes inside the broker container (as `mosquitto_passwd -b` was before).
- **Users and client ids.** A dynamic-security client binds a user to one client id, so each bound connection needs its own user:

  | User           | Client id                | Role          | Password (`.env`)           |
  | -------------- | ------------------------ | ------------- | --------------------------- |
  | `gw-01`        | `gw-01` (bound)          | `gateway`     | `MQTT_GATEWAY_PASSWORD`     |
  | `gw-01-cmd`    | `gw-01-cmd` (bound)      | `gateway`     | `MQTT_GATEWAY_PASSWORD`     |
  | `mes`          | `mes-server` (bound)     | `mes`         | `MQTT_MES_PASSWORD`         |
  | `mes-cmd`      | `mes-server-cmd` (bound) | `mes`         | `MQTT_MES_PASSWORD`         |
  | `dev`          | `dev` (bound)            | `dev`         | `MQTT_DEV_PASSWORD`         |
  | `smoke-reader` | `smoke-reader` (bound)   | `dev`         | `MQTT_DEV_PASSWORD`         |
  | `healthcheck`  | `healthcheck` (bound)    | `healthcheck` | `MQTT_HEALTHCHECK_PASSWORD` |

  The second user of each component shares its component's password and role (no new secret; both connections run in the same container with the same environment). `smoke-reader` is the stack smoke's second reader: it reads with `dev`'s role and password while `dev` publishes in an ACL check, since one user now has one session. The gateway and the MES connect their command connection as `MQTT_CMD_USERNAME` (defaults `gw-01-cmd`, `mes-cmd`). A user connecting with another id is refused (CONNACK 0x87), and so is a generated id.

- **ACL parity.** The roles are the Phase 8 ACL translated line by line: `topic read X` became `publishClientReceive X`, `topic write X` became `publishClientSend X`, `readwrite` both. Measured on the Phase 8 broker, Mosquitto 2.1's ACL file grants every subscription (any filter, `#` and `$SYS/#` included, for every user) and checks each message on delivery; so the template grants subscriptions by default and filters delivery per role. Refusing subscriptions outside a role's reads would be stricter, and is left as a possible follow-up (a behaviour change, not parity). Each component's two users carry the same role, so each has exactly the old user's rights. A test runs the Phase 8 broker (its ACL, password-file entrypoint and configuration frozen in `packages/test-kit/fixtures/legacy-mosquitto`) next to the new one and checks every (user, topic, action) of a table of 23 publish topics, 18 subscription filters, the deliveries and unsubscribe on both.
- **What `dev` reads:** the `dev` role (and so `smoke-reader`) reads all of `orbis/#`, commands (`cmd`) and their answers (`cmd-res`) included, as the Phase 8 ACL allowed; it publishes nothing.
- **Session expiry for orphans:** `persistent_client_expiration 14d` removes persistent sessions not resumed for 14 days. A session left under a client id the broker now refuses (an old `MQTT_CLIENT_ID`, a tool's generated id from before the binding) could otherwise never be resumed or cleared by its user and would queue messages for ever. 14 days is longer than the MES's 7-day session expiry, so it never ends a session the MES could still resume.
- **Anonymous** clients stay refused (`allow_anonymous false`, and no anonymous group).
- **Every user bound, `dev` and `healthcheck` included (round-1 decision reversed).** Review finding 20 of round 1 left `dev` and `healthcheck` unbound, because `mosquitto_sub` and the test-kit's readiness probe make their own ids and both users are read-only. That decision assumed a binding also reserves the id. Implementing it showed otherwise: Mosquitto checks no username when a new connection takes over a session (`src/handle_connect.c`, 2.1.2), and dynamic security binds a user to an id, not an id to a user. So an unbound user could connect as `gw-01`, `gw-01-cmd`, `mes-server` or `mes-server-cmd` and take that session; with a clean start under `mes-server` it would end the MES's persistent session and its queue (verified on 2.1.2 before the reversal). Since a client id is safe only when no user may use any id but its own, the round-1 decision was reversed in #240 (2026-10-19): security outweighs the convenience, and every user is bound (`healthcheck` → `healthcheck`, `dev` → `dev`, `smoke-reader` → `smoke-reader`). A test pins it: every user with every other user's id is refused while all sessions stay connected.

### Consequences

- Good: no broker user can take over another user's session: the gateway's users can't use `mes-server` or `mes-server-cmd`, the MES's users can't use `gw-01` or `gw-01-cmd`, `dev` and `healthcheck` can't use any of them, and no user can open a second session under another id. S2 needs no accepted risk for the takeover. Tested in `apps/edge-gateway/src/broker-security.test.ts` and in the stack smoke.
- Good: rights are unchanged (the parity test), and are reviewed in one JSON file as the ACL was; the gateway test that keeps the areas in step with `plant.yaml` now reads that file.
- Good: no new secret; nothing to back up (the configuration is derived on each start).
- Bad, **the cost of binding `dev` and `healthcheck`:** one `dev` session at a time (a second connection under `-i dev` takes the first one's session over: same user, so Mosquitto allows it), and `-i dev` on every manual command (`mosquitto_sub -i dev -u dev …`; runbook). The Compose healthcheck connects with `-i healthcheck`, and its probes run one at a time (5 s interval, 3 s wait). A tool that reads while `dev` publishes needs a second user: `smoke-reader`.
- Bad: the gateway and the MES each log in under two users; tests that impersonate a component must use its bound id (`brokerLogin()` in `@shopfloor/test-kit/broker`), so a test can't run two connections of the same bound user at once, and a test that resumes the persistent session must end it explicitly between tests. The runbook's "start once with another `MQTT_CLIENT_ID` to drop the MES's session" no longer works (that id is refused); resetting the broker volume does.
- Bad: the smoke's rights checks publish as `gw-01` under its bound id, taking the gateway's publishing session over for a moment (it reconnects; its outbox resends). The smoke never connects as `mes`, whose session is persistent.
- Bad, **accepted risk: a leaked component password allows a denial of service of that component.** Whoever holds `MQTT_MES_PASSWORD` can connect as `mes` under `mes-server` (the binding admits the right user) and take the MES's session; a clean start ends that persistent session and loses its queue (up to 100,000 messages, seen by the MES as sequence gaps). Likewise `MQTT_GATEWAY_PASSWORD` lets one kick the gateway's connections, and their rights let one publish forged machine data or commands. The binding stops one user taking another user's session; it can't tell a component from someone holding its password. Accepted: the passwords live only in `.env` and the component's own container, random per stack, on a loopback-only port.
- **MQTT TLS: cut** (Phase 9 cut line, recorded as a deviation in the phase log). The listener stays plaintext on `127.0.0.1:1883` and the Compose network; passwords cross loopback and the Docker bridge unencrypted. Accepted risk for S2's named sub-finding "plaintext MQTT on loopback if TLS is cut": the port is published on loopback only, and anyone who can read loopback or the bridge on the host can already read `.env`. Re-adding it later: a broker certificate from the dev CA (HTTPS section), a `listener 8883` with `certfile`/`keyfile`, `mqtts://` URLs and the CA for the clients.

## HTTPS (#241, P9-14)

### Context and problem statement

Until #241 nginx served the web app and the API on plain HTTP at `127.0.0.1:8080`, and the session cookie was `sft_session` without `Secure` (ADR-0026: "plain HTTP means no `Secure` cookie … TLS is Phase 9"). Compose also published the MES (4700), the gateway's health and metrics (4900) and the database (5442) on the host, so a process on the machine could reach the MES without nginx, and with it the proxy-header path P9-15 builds on. The master plan's security row and the Phase 9 plan ask for an HTTPS-only front with `Secure` cookies and fewer published ports (checklist S4 and S8). The questions:

- Who issues the web's certificate, and how do a browser, Node harnesses and Playwright trust it without trusting anything else?
- HTTPS only, or HTTPS beside an HTTP listener that redirects? HSTS?
- How does development keep the MES, the gateway and the database reachable once the default stack stops publishing them?

### Considered options

1. **Issuer:** (a) a self-signed certificate for nginx alone; (b) a dev CA per stack, made by the `pki` step, issuing nginx's certificate; (c) a locally trusted tool such as mkcert on the host.
2. **Listener:** (a) HTTPS plus an HTTP listener redirecting to it; (b) HTTPS only.
3. **HSTS:** (a) sent; (b) not sent.
4. **Chromium's trust in the harnesses:** (a) `ignoreHTTPSErrors`; (b) the dev CA in an NSS database of the test profile; (c) `--ignore-certificate-errors-spki-list` with the SPKI hash of this stack's nginx certificate.
5. **Ports:** (a) keep publishing everything on 127.0.0.1; (b) unpublish the MES, the gateway and the database in the default Compose and publish them for development through an override.

### Decision outcome

Chosen: 1b, 2b, 3b, 4c and 5b.

- **The dev CA** (`@shopfloor/pki`, `ensureWebTls`, run by the same `pki` step as the OPC UA material after it): one per stack, RSA 2048, valid one year (#241 review; renewed by the step like everything else, the web certificate with it), `CA:true` with path length 0, `keyCertSign` and `cRLSign`, extended key usage `serverAuth` only (#241 review: OpenSSL and Node then refuse its chain for any other purpose), and **critical name constraints** for TLS server names: only the DNS name `localhost` (and its subdomains) and the address `127.0.0.1`. A browser or Node that trusts the CA still refuses a TLS server certificate it signs for another name (OpenSSL: "permitted subtree violation", tested), so its key, if it leaked, could not impersonate another web site. Name constraints say nothing about other purposes: the security review minted code-signing, S/MIME and `clientAuth` certificates with the key and macOS accepted them from a CA trusted for everything, so the owner trusts it **for SSL only** (`security add-trusted-cert … -p ssl`; in Keychain Access only "Secure Sockets Layer (SSL)" set to Always Trust). Its key lives only in the `pki-ca` volume (`private/ca-key.pem`, 600, in a 700 folder), which no long-running service mounts.
- **nginx's certificate:** RSA 2048, valid 365 days (below Apple's 825-day limit for TLS server certificates), issued by the dev CA: SAN DNS `localhost` and IP `127.0.0.1` (every harness and the browser use one of them: the web is published on 127.0.0.1 only, so `[::1]` can't reach it; a container on the Compose network connects to `web` with `localhost` as the server name), key usage `digitalSignature`, `keyEncipherment`, extended key usage `serverAuth` only, no URI. It goes into the `web-tls` volume with the CA certificate (public) beside it; nginx mounts that volume read-only at `/etc/nginx/tls`. The key is 0640 with nginx's group (101 in the web image), which the `pki` step joins for that (`group_add`, `PKI_WEB_KEY_GID`), so nginx reads it as another user than the step's.
- **Renewal** as for the OPC UA material: kept while valid for more than 30 days and still what the step would write (the CA: a CA, its key, the same name constraints; the web certificate: issued by the current CA, the SAN, the EKU, its key), else replaced; a new CA always brings a new web certificate, and `ca.pem` beside nginx is always the current CA's. `PKI_RENEW` takes `dev-ca` and `web` beside the OPC UA identities. The step prints the CA's SHA-256 fingerprint and the web certificate's SPKI hash on every run, and `!!! RENEWED the web certificate: RESTART THE WEB !!!` (nginx reads it when it starts) or `!!! RENEWED the dev CA: trust the new one !!!`.
- **Separate from OPC UA trust:** the OPC UA material stays pinned leaf certificates (ADR-0038). Neither the CA nor nginx's certificate is in any OPC UA trust folder (the step keeps `issuers/*` and `trusted/crl` empty and `trusted/certs` exactly the pins), so a certificate the dev CA issues opens no OPC UA session.
- **HTTPS only (2b):** `listen 8443 ssl` is nginx's only listener; there is no HTTP listener, so no redirect can point at a wrong port when a gate project publishes 8443 on an ephemeral host port. A plain HTTP request to the port is answered 400 by nginx itself ("The plain HTTP request was sent to HTTPS port"), never redirected. Compose publishes it as `127.0.0.1:${WEB_HTTPS_PORT:-8443}:8443`; `WEB_PORT` and 8080 are gone. The container's health check is `curl --cacert /etc/nginx/tls/ca.pem https://localhost:8443/healthz`, so a missing, foreign or misnamed certificate makes it unhealthy, and an entrypoint check stops the container with a message when the certificate or key is missing.
- **TLS settings:** Mozilla's "modern" profile: TLS 1.3 only (its suites are all AEAD with forward secrecy), the client's preference, `X25519:prime256v1:secp384r1`, a 2 MB shared session cache, no session tickets (their key would outlive a session). HTTP/1.1 as before (nginx has no extended CONNECT for WebSockets over HTTP/2).
- **No HSTS (3b):** on `localhost` it would hold every port of the name to HTTPS in the browser, other local apps included; the front has no HTTP to upgrade from anyway. Tested: no `Strict-Transport-Security` in any nginx file, and none in the answers.
- **`Secure` cookies by default:** `MES_COOKIE_SECURE` defaults to `on` in the MES's environment and in Compose, so the session cookie is `__Host-sft_session; Path=/; HttpOnly; SameSite=Strict; Secure`, host-only (no `Domain`), as ADR-0026 planned for TLS. `off` is for a browser on plain HTTP straight to the MES only (the Vite dev server against `pnpm stack:up:dev`), set explicitly; the MES logs a warning with it. Node clients that talk to the MES directly over HTTP (the reconciliation's API clients) need nothing: they send the cookie they were given, whatever its name.
- **The `/sim/` Origin check** compares `Origin` with `$scheme://$http_host`, and `$scheme` is now `https` on the only listener: the console's writes pass, and an `http://` origin of the same host and port is refused like any other (the smoke tests it). ADR-0037's note on a TLS terminator in front of nginx holds: P9-14 terminates TLS in nginx itself.
- **Published ports (5b, checklist S8):** `docker compose up` and `pnpm stack:up` stay the hardened default and publish, on 127.0.0.1 only, the web's HTTPS 8443, the broker 1883, the control API 4800 (token), the OPC UA servers 4841–4845 (SignAndEncrypt), Modbus 5020 and the ERP mock 4600 (token). **Not published:** the MES 4700, the gateway 4900, the database 5432 (5442 on the host before). Nothing but nginx reaches the MES from outside the Compose network. `compose.dev-ports.yml` publishes those three again on their old host ports (`MES_HTTP_PORT`, `GATEWAY_HTTP_PORT`, `DB_PORT`), and `pnpm stack:up:dev` starts the stack with it. Harnesses don't use it: each publishes what its own clients need on ephemeral ports in its own project (`e2e/compose.reconcile.yml`: the MES and the gateway; `e2e/compose.trace-perf.yml`: the database), while the gate's smoke keeps the hardened set (`e2e/compose.ephemeral-ports.yml` moves the published ports to ephemeral ones and publishes nothing more) and reaches the MES and the gateway with `docker compose exec`.
- **The owner's trust:** `pnpm stack:ca` reads the CA certificate from the web container, checks that it issued the served certificate, writes `dev-ca.pem` (git-ignored) and prints its SHA-256 fingerprint and how to trust it (macOS keychain for SSL only, Firefox, `NODE_EXTRA_CA_CERTS`, `curl --cacert`). The name constraints, the `serverAuth` EKU and the SSL-only trust setting make trusting it a bounded decision, within the accepted risks below.

### Harness trust (4c)

- **The material comes from the stack, the handshake must match it.** Every harness reads `ca.pem` and `server.pem` from the web container (the `pki` step's volume), never from the handshake (which would trust whatever answers), checks that the CA issued the certificate, and then that a TLS 1.3 handshake with the published port, verified against that CA alone, presents exactly that certificate (`@shopfloor/test-kit/tls`, `establishWebTrust`; `Stack.webTrust()` in `e2e/src/stack.ts`; the smoke in shell and `scripts/stack-smoke-web.mjs`).
- **Node clients** trust the dev CA through `NODE_EXTRA_CA_CERTS` (the smoke's web checks, the Playwright test runner and its API contexts). Node reads that variable only when a process starts, and the reconciliation, the console run and the trace-performance run learn the CA after they started the stack, so in their own process they add it to the default store with `tls.setDefaultCACertificates` (the same store, the same effect for `fetch`, WebSocket and `https`), and pass `NODE_EXTRA_CA_CERTS` to their children. curl uses `--cacert`.
- **Chromium** reads neither, and `ignoreHTTPSErrors` would accept any certificate, which would make checklist S4's "the browser refuses another certificate" untestable. So the harness passes the SPKI SHA-256 of this stack's nginx certificate (`RECONCILE_WEB_SPKI`), and `playwright.config.ts` launches Chromium with `--ignore-certificate-errors-spki-list=<that hash>`: it accepts a chain containing that key and no other. `e2e/browser/tls/tls.spec.ts` proves it in the same browser: the stack's page loads over TLS 1.3 with the dev CA's certificate, and a certificate valid for the same names (`localhost`, `127.0.0.1`) but of another key and CA is refused with `ERR_CERT_AUTHORITY_INVALID`. A Vitest check (`e2e/src/compose.test.ts`) keeps `ignoreHTTPSErrors` and the blanket `--ignore-certificate-errors` out of the Playwright configuration and specs.
- **Where it runs:** the TLS spec runs in the reconciliation's `orders-dispatch` project (the gate's reconcile step, while the simulator waits idle) and in `pnpm test:console`.

### Consequences

- Good: the browser talks to the stack over TLS 1.3 only, the session cookie is `__Host-` and `Secure`, and nothing outside the Compose network reaches the MES but through nginx (S4, S8). The evidence: the `pki` step's tests (`packages/pki/src/tls.test.ts`: the CA's constraints refusing another name, renewal, the key's access), the trust helper's tests, the static Compose and nginx checks, the stack smoke (HTTPS with the dev CA only, untrusted without it, plain HTTP 400 without a redirect, no HSTS, TLS 1.2 and another name refused, the handshake's certificate equal to the step's, the `__Host-` cookie's attributes, every published port within the S8 list and none of 4700, 4900, 5432 or 8080) and the Playwright TLS spec.
- Good: a harness trusts exactly the stack it started: another certificate, also one of the same CA with another key, fails its handshake check.
- Good: `pnpm test:trace-perf` measures through the HTTPS front; the connection is kept, so the series carry no handshake (Phase 8's 100 ms p95 still holds, figures in the phase log).
- Bad: the owner trusts a new CA per stack: after `pnpm stack:reset` (the `pki-ca` volume goes) or `PKI_RENEW=dev-ca`, and once a year when the step renews it; until then the browser shows a certificate warning (runbook, "HTTPS and the dev CA").
- Bad: the old URL `http://localhost:8080` no longer answers; scripts that used the MES on 4700, the gateway on 4900 or the database on 5442 need `pnpm stack:up:dev` or `docker compose exec`.
- Bad: the Vite dev server against the dev stack is plain HTTP: a browser that refuses `Secure` cookies on a plain `http://localhost` origin needs `MES_COOKIE_SECURE=off` while it is used.
- Bad: a renewed web certificate is served after `docker compose restart web`; `up` reruns the step but doesn't recreate an unchanged web container.
- **Origin scheme (#241 review):** the MES's own `Origin` guard (ADR-0023) compares host and port; for a request it trusts from the `edge` network (nginx) it now also requires the Origin's scheme to equal `X-Forwarded-Proto` (always `https` from the front), on writes, on reads that carry an Origin and on WebSocket upgrades (403 otherwise; tested in `identity.test.ts`). Requests from elsewhere (an MES on 4700 with `pnpm stack:up:dev`) keep the host-and-port rule.
- **Accepted risk: what the CA can vouch for (#241 review).** The `localhost` name constraint permits every `*.localhost` name, on any port: while the owner trusts this CA, whoever reads its key (anyone with access to the Docker host can read the `pki-ca` volume) can impersonate any local HTTPS service under a `localhost` name or `127.0.0.1`, the owner's other development services included. Bounded by the one-year validity, the name constraints, the `serverAuth` EKU and the SSL-only trust; the runbook advises removing the trust when the project isn't in use.
- **Accepted risk: the `__Host-` cookie on localhost (#241 review).** Cookies are scoped by host name, not port, so `__Host-sft_session` set by `https://localhost:8443` is also sent to other `localhost` ports a browser treats as secure (Chromium counts `http://localhost`), among them another local service of the owner's or the MES on 4700 with `pnpm stack:up:dev`; `SameSite=Strict` keeps it off cross-site requests (schemeful same-site), and a service there could read it only from requests the browser sends to it. A dedicated host name for the app was not adopted now (it needs a resolver entry on every machine); runbook, "Cookie scope on localhost". **Note (#244):** with the observability profile up, Grafana on 3000 and Prometheus on 9090 are two more such `localhost` ports. Both are plain HTTP on `127.0.0.1`, so the browser sends them the cookie (Chromium treats `http://localhost` as secure). Neither reads it: Prometheus has no login and Grafana its own session cookie. The risk is the same as for any other local service, and it ends with `pnpm stack:down:observability`.
- Cosmetic: the web container still lists `8080/tcp` in `docker compose ps`: the base image (`nginx-unprivileged`) declares `EXPOSE 8080`; nothing listens there and nothing publishes it.

## Login throttling (#242, P9-15)

### Context and problem statement

ADR-0026 locks a normal account after five consecutive failed logins, for 15 minutes, and delays an admin instead. The lock is per account because, until Phase 9, the MES saw no client address behind nginx: anyone who could reach the login page could keep a known user locked out, a denial of service ADR-0026 accepted "until Phase 9". Since #237 (P9-10) the MES knows which requests come from nginx over the internal `edge` network (`apps/mes-server/src/edge.ts`, `EdgeTrust`), and nginx overwrites `X-Real-IP` with `$remote_addr` on every request it proxies. Checklist S5 asks that a lock from one address leave the account open from another, that a burst of concurrent guesses be held to one judged attempt per wait, and that the account never be locked as a whole.

### Considered options

- **Address source:** (a) `X-Real-IP` from any source; (b) `X-Real-IP` only from the `edge` network (P9-10's trust), the socket address otherwise; (c) a shared-secret header from nginx. (a) lets any container on the default network pick a pair by sending its own header straight to `mes:4700`; (c) was rejected in P9-10 for the trust as a whole.
- **Global brake:** (a) none, the pair lock alone; (b) a global per-account lock; (c) a global per-account delay that refuses without hashing, decided under the user's row lock; (d) a delay before judging (sleep, then hash). (b) brings back ADR-0026's denial of service; (d) lets parallel guesses through, each sleeping on its own.
- **Where the login buckets sit** (ADR-0026's in-memory buckets, 5 per second for all logins and 1 per second per name, #168 review M2): (a) before the identity module, as before; (b) inside the reservation, after the global delay.

### Decision outcome

Chosen: address (b), brake (c), buckets (b).

- **The client address** is `X-Real-IP` when the request came from nginx over `edge` (`EdgeTrust.trusts`, the IPv4-mapped form normalised) and the header is an IP address; otherwise the connection's own address. A spoofed header from anywhere else is ignored and counted in `mes_http_proxy_requests_total{trusted="false"}`; the smoke asserts both. A request without an address (module tests, the CLI) is keyed `unknown`.
- **Per (account, address)** (`identity.login_address`, migration 0033): five consecutive failures from one address lock that pair for 15 minutes; the right password from that address is refused (the same 401) while it is locked; a success from that address deletes its pair; a lock that has run out starts its count anew. The account-wide `locked_until` is dropped. `GET /users` reports a user `locked` while any of its pairs is.
- **Per account, from all addresses together** (`identity.login_failure`): n is the number of the account's **judged** failures (wrong passwords, counted when reserved) in the last 15 minutes. Once n ≥ 10, an attempt made less than `min(2^(n − 10) s, 30 s)` after the account's last failure is refused with **429**, problem type `urn:shopfloor:login-rate`, detail "too many failed logins for this user; try again later", and `Retry-After` = the remaining wait in whole seconds, rounded up (at least 1). It is decided before any hash and is neither audited nor counted: a 429 never raises n. A success deletes the account's failures (n = 0); otherwise n falls as failures leave the window; the sweep deletes them after 15 minutes. **The account is never locked:** the right password is judged as soon as the wait is over, from any address whose pair isn't locked.
- **Under the row lock:** the decision is taken in ADR-0026's reserve-before-hash transaction, after `SELECT … FOR UPDATE` on the user's row, in this order: the global delay (429); the login buckets (429, `admit`); a disabled user, a locked pair or an admin within its delay (the same 401, one dummy hash); otherwise the attempt is counted in advance (a `login_failure` row, the pair's count, the account's count for an admin's delay) and hashed outside the transaction. Concurrent attempts on one account are therefore decided one after another: past the threshold, the first after the wait is judged and writes a new failure, and every other attempt of the burst finds the new wait and gets 429. A password change (`POST /account/password`) runs the same reservation with its request's address.
- **The login buckets** are now asked inside the reservation, after the global delay, so an attempt the delay refuses spends no token and answers its own `Retry-After`; an unknown or malformed user name (no row) asks them before its dummy hash, as before. Without this, a burst of 20 on one name would meet the per-name bucket (5) first and get the bucket's 1 s `Retry-After` instead of the remaining wait.
- **Admins** keep ADR-0026's account-wide doubling delay (1 s from the fifth failure, at most 5 minutes) and have no pair lock; the global delay applies to them too, and answers first inside its wait.
- **OPC UA logins** stay as ADR-0038 decided: 250 ms per refused password, not serialised per user name. Serialising them would let anyone holding a pinned certificate delay the gateway's own reconnect indefinitely; the passwords are 32 random hex characters behind a pinned client certificate. Recorded as an accepted risk in `docs/security-review.md` (S1, S5).

### Consequences

- Good: an attacker on one address no longer locks a user out on the others: ADR-0026's accepted denial of service is **reduced**, not removed. Through Colima's port forwarding every host client reaches nginx from one address, so on a developer machine the browser and an attacker on the host share a pair; the global delay is then the only brake, and it never locks.
- Good: a burst of concurrent guesses is held to one judged attempt per wait from any number of addresses, without hashing the others: at n = 15, 20 concurrent attempts from a fresh address give exactly one 401 and 19 × 429 with `Retry-After: 30` (`identity.test.ts`, deterministic on the test's clock; the stack smoke, from four probe containers on the Compose network through nginx).
- Good: the address comes only from nginx over `edge`; a container on the default network that sends `X-Real-IP` straight to the MES is keyed by its own address (tested in `identity.test.ts` and in the smoke).
- Bad: a 429 tells the caller that the name is a user with recent failures (an unknown name always gets 401). Accepted: the plan asks for 429 with `Retry-After`, and the names are not secret (the audit and the user list name them).
- Bad: every login now opens the reservation transaction before the in-memory buckets refuse it (one indexed select under the row lock for a known name); an unknown name still costs no transaction beyond the lookup.
- Bad: `identity.login_failure` holds the client addresses of the last 15 minutes' failures and `identity.login_address` those of unlocked pairs for a day; the audit log names the address of every failure and lock (`after.address`). The audit keeps them as it keeps everything else.
- Neutral: an owner unlocks a pair by resetting the user's password (`POST /api/v1/users/{username}/password`, a temporary password, which also clears the account's failures) or waits 15 minutes; the global delay needs no unlocking (at most 30 s). Runbook, "Login throttling".
