## Scope

Every packed part can be traced back to what it is made of and how it was tested, every lot forward to where it went, and the leak test is under statistical control:

- **Device facts for traceability:** the cycle facts carry the lots the machine consumed for that part (CNC: the blank lot; ASM-01: the component lots of that pass) and, at ASM-01, the operator at the station. Both are fields on the existing cycle event, so no new event enters the device sequence and no event log changes.
- **`spc-core` and `trace-core`:** pure packages, the same definitions for the simulator's ground truth and the MES (as `oee-core` and `alarm-core`): I-MR and X̄-R charts, control-limit estimation, Nelson run rules, with hand-calculated reference cases; the carton rule and the trace tree.
- **Simulator:** an injectable, time-bounded leak-test drift (scenario and control API), a scenario-local stock file, and a traceability ground truth (`trace.json`, `sim-trace/1`, with the counterfactual readings the drift replaced) beside each golden summary, which stays byte-identical.
- **Golden scenario `quality-01`:** orders mode with small lots that change mid-order and mid-carton, a rework with a second seal-kit lot, a leak scrap, and an injected drift in shift A after the SPC baseline.
- **`genealogy` module:** lots imported from the ERP, `serial_unit` over Phase 7's units, lot links per operation and pass, cartons by a packing rule, backward and forward trace queries that say whether their answer is final.
- **`quality` module:** characteristics, measurements from the leak-test facts, control limits (versioned), SPC points and signals on final data, signal acknowledgement; quality holds on a lot, serial, carton or order whose scope follows the genealogy, release or rejection by the `quality` role, and quality notifications to the ERP mock.
- **ERP mock:** idempotent quality notifications with a per-lot view; a scenario's lots come from its dataset's `lots` (already supported).
- **Web:** a traceability screen (serial back, lot and carton forward), SPC charts with signals, a holds list and detail; the terminal shows the holds and signals that touch its work center and the component lots in use.
- **End to end:** a third live reconcile pass running `quality-01`'s shift A; the Phase 7 passes unchanged.

Out of scope here:

- per-order OEE and throughput-based line OEE (deferred from Phase 7): moved to Phase 9 (see "Decisions" and "Deviations"). Phase 8 has no new OEE input;
- a hold that stops a machine or blocks a lot physically: the MES never commands the simulator for quality, and `blockLot` stays a console action (Phase 9). A hold is a record with consequences in the MES and the ERP only;
- physical scrap or rework of a held part decided by quality (`rejected` records the decision and notifies the ERP; quantities change only from machine facts, as in Phase 7);
- inspections other than the leak test (no OP10 dimension measurement: adding one changes every event log), attribute charts (p, np, c, u), capability indices other than Cpu and Cpk (one-sided specification; shown, not reconciled), automatic holds from SPC signals, reaction plans;
- cartons on pallets, shipping documents, delivery notes, cartons sent to the ERP (handling units);
- an inbound ERP lot block (ERP → MES hold); lot master data changes after import beyond quantity and status;
- serials unique across simulator runs (see "Serial identity"); OPC UA and control-API security, TLS (Phase 9);
- retention and compression, `prom-client`'s successor, the O(hours × occurrences) alarm KPI read (carried).

## Decisions made in this plan

### What the code does today

- **Serials:** a part gets `<product>-<six digits>` at the end of its OP10 cycle (also when scrapped there); the counter is `partId`, shared by both CNCs and restarting with every simulator run, so serials repeat across runs (ADR-0030, ADR-0031). WSH-01's cycle carries `partId` and an empty serial.
- **Lots:** `material-consumed` (machine, `partId`, material, lot) is in every mode's event log: a blank when a CNC cycle starts, the components when an ASM-01 cycle starts, the rework components on a rework pass, first in first out per material in file order. The OPC UA machine server ignores it (`machine-server.ts`, `record()`), so it never reaches the UNS or the MES. `stock.yaml` has one lot per material except BLANK-100 (two lots of 900); in a two-day scenario no lot changes. The ERP mock's dataset already accepts an optional `lots` list (`erpDatasetSchema`), defaulting to `stock.yaml`.
- **Operators:** ASM-01's operator is an OPC UA variable (`ShopFloor.Operator`) and an `operator` event in the log; neither reaches the UNS. The MES knows its own users' crew rows (`shifts.crew_assignment`, Phase 7 terminal sign-on).
- **Leak test:** every LKT-01 cycle carries a `measurement` (`leak-rate`, value at 0.001 Pa/min, unit, `upperLimit` 3.2) on the event log, the OPC UA event (`measurementValue`) and the UNS (`uns.events.cycle-complete/1`). The reading is normal(2.0 + drift, 0.45) with drift 0.04 Pa/min per day since calibration (every 7 days, `Maintenance CALIBRATION`). There is no drift injection: only failure injections exist (`inject-failure`, ADR in Phase 6). The MES stores the payload in `ingest.equipment_event` (jsonb) and makes no measurement record.
- **Cartons:** not modelled. PCK-01 is a 30 s cycle with a result; there is no carton, label or carton event anywhere.
- **MES:** `execution.unit` (epoch, `part_id`, serial, product, order, status, position) exists in both production modes (order null in schedule mode), with `operation_record` per cycle fact and pass and `scrap_record` with coding from `config/plant/scrap.yaml`. No `genealogy` or `quality` schema. Quality's role holds `read`, alarm ack and comment, `note:write`, `scrap:code`.
- **Ground truth:** `sim-summary/4` with `lots` (remaining per lot) and `orders` (units hashed as `unitsSha256`); no per-unit lots, operators or readings, no SPC.
- **Gate:** `pnpm gate` (verify, golden, e2e, smoke, reconcile with two passes; about 24 minutes at the Phase 7 close). **`pnpm verify` is not deterministic:** the Phase 6 `alarm-core` property test "revision completeness" fails for some random seeds (open bug from the Phase 7 closing gate, `revisionSpans`).
- **CI:** GitHub Actions still stopped by the spending limit; every criterion below is proven by local gates.

### Device facts for traceability (ADR-0033)

- **Fields, not events.** The OPC UA cycle event (`CycleCompleteEventType`) gains `LotMaterials` and `LotIds` (two `String[]` of equal length, in consumption order) and `Operator` (`String`, the station's operator when the cycle started, empty where a machine has none). The rule is one pure function, `attachConsumption(events)` in `trace-core` (a fold over the event stream: the `material-consumed` events of a part on a machine, which come before that part's `cycle-complete` there, attach to that cycle; the operator is the one at the cycle's start, the instant of the part's first `material-consumed` at ASM-01), used by both the machine server and the MES's golden harness, so the two can't differ. Nothing new enters the device sequence, so every sequence number, every event log and every summary stays as it is. A test runs a scripted shift and compares (machine, `seq`, event type) of every OPC UA event with a digest recorded from `main`.
- **What a cycle carries:** a CNC's OP10 cycle the blank lot; ASM-01's OP30 cycle the component lots of that pass (pass 1 the `components`, a rework pass the `reworkComponents`); every other cycle an empty list. Material taken for a cycle still running at a run's end is reported by no fact (as `materialInProcess` in Phase 7, H2).
- **UNS contract 1.4:** `uns.events.cycle-complete/1` gains optional `lots: [{ material, lot }]` and `operator: string | null`. Optional, so the schema name keeps `/1` and older payloads stay valid (as `deviceEpoch` in contract 1.1). WSH-01 (Modbus) sends neither. The gateway maps the new fields; the MES's ingest validates and stores them in the payload it already keeps, with a new expression index on the lot ids (`ingest.equipment_event`, `event_type = 'cycle'`) for forward queries during catch-up.
- **Address space 1.2** documents the fields; a generic OPC UA client sees them (integration test).
- **Probe P1 (done, review of PR #207):** node-opcua 2.187.3 delivered 3,000 cycle events with `String[]` fields through an event filter, all intact and in order, non-ASCII lot ids included; an empty array arrives as an empty `String` array and a field the event type lacks as `Null`, so "no lots" and "no field" are told apart. Arrays are kept; the encoded-string fallback is dropped.

### Leak drift injection and scenario stock (ADR-0033)

- **`leak-drift` injection:** a scenario entry `{ at, until, machine: 'lkt-01', kind: 'leak-drift', shift }` and the control API `POST /api/v1/faults/drift/{machine}` (1.5) add `shift` (Pa/min) to the reading's mean from `at` until `until` or the next calibration, whichever comes first, as a sensor fault bounded in time. `until` may be at or after the run's end (the drift then lasts to the end). `shift` must be a whole multiple of the tester's `resolution` (0.001 Pa/min; refused otherwise), so the counterfactual reading is exact in integer steps from the log (`steps − shift/resolution`). No random draw changes (the reading still draws one normal), so the run before `at` is identical to the run without it (tested as Phase 6 tested failure injections). **The drift is its own variant of the event union**, not `injection-applied` (whose variant carries a failure code): `PlantEvent` `{ type: 'leak-drift', at, machineId, injection, transition: 'applied' | 'ended', shift, endedBy?: 'until' | 'calibration' }`. A drift ended by calibration before `until` writes `leak-drift` `ended` with `endedBy: 'calibration'` at the calibration's start; one ended at `until` writes `endedBy: 'until'`; one still active at the run's end writes no `ended` line. Only runs with the injection write the variant, and the run header lists the injection only then (a header entry without `kind` stays a failure injection, so existing headers are unchanged). Same calendar-boundary rule as failure injections, for `at` and for an `until` inside the run.
- **Scenario-local stock:** `scenario.json` may name `stock` (a file in the scenario's folder); live mode reads `SIM_STOCK` (default `config/plant/stock.yaml`). The ERP mock needs nothing new: the scenario's ERP dataset carries `lots` (already supported by `erpDatasetSchema`), asserted equal to its `stock`. The run's `configSha256` hashes the stock it used, so only `quality-01`'s header differs. `config/plant/stock.yaml`, `products.yaml` and `reasons.yaml` do not change in this phase.
- **Why not change `stock.yaml`:** it is a simulation input of `week-01`, `alarms-01` and `orders-01`; any change regenerates their event logs. Small lots are a property of the one scenario that needs lot changes inside two days.

### Ground truth for traceability and SPC (ADR-0033)

- **A sidecar, not a new summary version:** `trace.json` (`sim-trace/1`) is written next to `summary.json` for every golden scenario and served live by `GET /ground-truth` 1.5 under `trace` (provisional for the bucket in progress, as OEE). `summary.json` stays `sim-summary/4` and byte-identical for `week-01`, `alarms-01` and `orders-01`: no golden regeneration, so no owner approval is needed for existing snapshots. Adding a new file to a golden folder is not a regeneration; it is recorded in `apps/simulator/golden/README.md`. Once committed, every change to a `trace.json` (also `quality-01`'s) is a golden regeneration: written reason, and the owner's approval, deferred to the owner (master plan section 12).
- **Contents:** `traceConfigSha256` (`packing.yaml`, `quality.yaml`); per unit, hashed as `unitsTraceSha256` with the count (the full list derived in the tests from the event log, as Phase 7's `unitsSha256`): serial, `partId`, product, order, status, per record (operation, pass, machine, completion time, result) its lots, the operator at ASM-01, the leak reading at LKT-01, and its carton; per lot in full: material, quantity consumed, units, orders, cartons; cartons in full: id, order, product, capacity, members' count and hash, closing time; SPC in full: per characteristic the limit versions, points hashed, signals (rule, chart, triggering point, time); the injected drift's first signal and its latency in readings; and **the counterfactual readings**: for every first-pass reading from the injection's start to 20 readings after it, the value the same draw gives without the shift (the logged steps minus `shift/resolution`, exact), so the tests can show that the drift, not chance, made the signal; readings before the start are their own counterfactual.
- **Same definitions:** cartons from `trace-core`, SPC from `spc-core`, both with the MES's configuration files, so a difference points to lost or distorted facts, not to two definitions (the master plan's ground-truth rule).
- **Live reference and the time cut:** a headless run of `quality-01` with `end` set to the end of Monday's shift A (14:00 Istanbul) is the reference of the live `quality` pass; a test asserts that its event log is a prefix of the full run's (every line after the header). Comparisons at a time cut use one pure function, **`traceAsOf(trace, T)` in `trace-core`**: it keeps the records completed before T with their lots, operators and readings; cartons in their state as of T (members placed and open or closed by then); the SPC points before T; and the episodes as they stand from the points before T (an episode still open at T stays open). Exit criterion 5 compares three projections at T = 14:00: the reference truth, the live truth and the MES's answers (read through the API and mapped to the trace shape), each through `traceAsOf`.

### Golden scenario `quality-01`

The week-01 seed and start, two days, `production: orders`, its own ERP dataset (`orders.json`, with `lots` equal to its `stock.yaml`, asserted) and `dispatches` (reproduced by the MES's dispatch rule, as in `orders-01`), its own `stock.yaml` with small lots, and one bounded `leak-drift` injection of +0.6 Pa/min (about 1.3 σ) on LKT-01 in shift A after the SPC baseline is complete; probe P4 tunes the dispatches (so that enough first-pass readings fall in shift A), the injection's start and its end. No failure injections (the alarm checks stay with `orders-01`). Required by construction and asserted in its test (exact values fixed in #208):

- a blank lot that runs out inside an order, so one order uses two blank lots, and a carton holds units of both;
- a component lot (SK-1 or SK-2) that runs out inside an order, and one lot used by two orders;
- a reworked unit whose rework pass consumed a seal kit from a different lot than its first pass;
- a leak scrap (second failure), and at least one OP10 `DIMENSIONAL` scrap if the seed gives one (else asserted absent and recorded);
- the SPC baseline (20 subgroups of 5, the first 100 first-pass readings) complete before the drift; **the counterfactual window is 60 readings**: the 40 first-pass readings before the injection's start and the 20 after it; the 40 before may overlap the baseline, whose points are judged retroactively against the version 1 limits. So shift A needs at least 140 first-pass readings (100 baseline, then 40 after the start, the start right after the baseline at the earliest); `orders-01`'s Monday shift A has only 127, so `quality-01`'s dispatches are tuned for it. **Fallback:** if P4's search finds no start whose 60-reading counterfactual window opens no episode inside shift A, the window becomes 20 before and 20 after (N = 20), and the plan's criterion uses N = 20; the choice is recorded in #208 and the golden README. The test asserts the counts it relies on: first-pass readings in shift A, the baseline, the readings before and after the start inside shift A, and N; the drift's first episode within 20 first-pass readings of the start; and no episode on the counterfactual readings in the window (exit criterion 3);
- at least two orders completed in shift A with all cartons closed, one short order with a partial last carton, a unit in WIP at the end;
- stock that covers every dispatched job (no `MATERIAL:` starvation unless planted and asserted).

### Serial identity (ADR-0034)

- **Options:** (a) serial text unique in the MES, a repeat refused or held; (b) units keyed (epoch, `partId`) as in Phase 7, `serial_unit` maps a serial to its units, a repeat across runs is a data-quality incident; (c) make the simulator's serials unique across runs (a run prefix), which changes every event log and `unitsSha256`.
- **Chosen (b):** `genealogy.serial_unit` has one row per unit (epoch, `partId`) with its serial, product, order and carton, and `serial` is indexed, not unique. A serial seen in a second epoch raises `serial-reused` (an incident, not a hold; one incident per pair of epochs, however many serials repeat); a lookup by serial returns every unit with it, newest first, and the screens ask which. A real line never reuses a DMC; the simulator does because its counter restarts per run, so this is a recorded simulator limit, invisible in the goldens and the reconcile passes (one run each on a fresh database). (a) would hold or refuse every part after any `stack:up` of a dev stack; (c) breaks the byte-identical rule for nothing a test needs.
- **WSH-01** is followed by `partId` within the epoch (ADR-0031); a serial is known from the unit's OP10 cycle.

### Genealogy (`genealogy` module, ADR-0034)

- **Ownership (ADR-0016):** schema `genealogy`: `material_lot` (id, material, quantity received, status, imported at, ERP feed), `serial_unit`, `genealogy_link` (typed edges: `lot → unit` with operation, pass, equipment, the fact's (equipment, epoch, seq) and time; `unit → carton`), `carton` (id, order, product, capacity, status `open | closed`, closed at, member count), `genealogy_incident`.
- **Lots from the ERP:** the MES imports `GET /api/v1/lots` on the ERP poll (ADR-0028), upserting by lot id inside one transaction; a lot no longer listed is kept (`status: retired`). A cycle fact naming a lot the MES has not imported is stored and raises `unknown-lot`, closed when the import catches up.
- **Links from facts:** built and rebuilt from cycle facts per unit, like execution's records (a reordered or late fact rebuilds the unit's links, never patches). A lot of a material that the order's BOM doesn't list for that operation and pass (the product's BOM from master data when the unit has no order, as in schedule mode) is a `material-mismatch` incident (none expected in any scenario; tested with a crafted fact). Execution keeps the unit's order and status; genealogy reads them through `Execution`'s interface and never its tables.
- **Operators:** the device operator per OP30 pass, taken at the cycle's start (the part's first `material-consumed` at ASM-01, from the fact, reconciled), and the MES crew signed on to the work center at that same instant (from `shifts.crew_assignment`, shown, not reconciled: there is no ground truth for MES users; checked live).
- **Cartons (MES packing rule, `trace-core`):** cartons per order and product; capacity per product in `config/plant/packing.yaml` (new, not a simulation input: VB-100 20, VB-200 12, assumptions); an order's PCK-01 good cycles fill its cartons in plant-time order (ties by device sequence); a carton closes when full, and the order's last carton closes when the order's OP50 is complete (ADR-0031), so a short order has a partial carton. Carton id `{orderId}-C{nn}`: the carton's number with at least two digits, growing past 99 (`-C07`, `-C100`). Membership is decided only on final data: a PCK-01 cycle is placed only once PCK-01 is final through it (ADR-0018), because a late earlier cycle would shift every later unit by one place. Schedule-mode units have no order and no carton.
- **Options for cartons:** (a) the simulator models cartons and emits carton facts; (b) the MES forms cartons by a rule, the simulator's ground truth applies the same rule. **Chosen (b):** in a real line the MES usually creates the handling unit and prints its label; (a) needs a new event kind that only a new mode could emit, and its reconciliation would test a fact path, not genealogy. The packing rule lives in `trace-core` so the truth and the MES can't disagree.
- **"Shipped":** the plant has no shipping step. A serial counts as shipped once it is in a closed carton (packing and labelling done); the exit criterion's "any shipped serial" means every unit in a closed carton.
- **Trace queries:** `GET /trace/serials/{serial}` (backward: per unit its operations and passes with machine, time, result, lots, device operator and crew, leak readings, scrap or rework records, order, carton, holds), `GET /trace/lots/{lot}` (forward: units, orders, cartons, open holds; and for a component lot the blank lots of the same units, one level of "where used with"), `GET /trace/cartons/{id}`, `GET /trace/search?q=` (serial, lot, carton or order). Plain SQL over the edge table (a recursive CTE is not needed for a two-level tree; kept as a function in the module, one query per answer). Every answer carries `final: boolean` and the machines whose final-through is below the answer's latest record, so a forward trace taken while facts are still arriving says so.
- **Performance target:** backward trace of a serial and forward trace of the largest lot answer in under 100 ms at p95 **through HTTP on the stack**. Load: the MES's golden harness ingests `week-01` (in order, as in the golden reconciliation) into the database of a disposable Compose project (migrated by its `migrate` step, reached on the project's own published port), then that project's MES and web start on it. The event-log → fact converter stays in `mes-server`'s test support while only `mes-server` uses it; if #204's tooling outside `mes-server` needs it, it moves to `test-kit` in #204. Measurement: `e2e/src/trace-perf.ts` (`pnpm test:trace-perf`, Node's built-in `fetch` and `performance.now()`, no new dependency) sends 200 backward traces of random serials and 200 forward traces of the largest lot from the host through nginx (`web`) to `/api/v1/trace/…` with a supervisor's session, one at a time, and records p50, p95, max, the database size and the response payload sizes. Probe P2 measured the queries themselves at 0.02 ms and 3.6 ms.

### SPC (`quality` module, `spc-core`, ADR-0032)

- **One characteristic in this phase:** `leak-rate` at LKT-01, from `config/plant/quality.yaml` (new, not a simulation input): characteristic id, equipment, operation, unit, the specification limit taken from `process.yaml`'s `upperLimit` (not duplicated), subgroup size 5, baseline 20 subgroups, enabled run rules. Seeded into `quality.characteristic`.
- **Measurements:** every LKT-01 cycle fact with a `measurement` becomes `quality.measurement` (fact key, unit, pass, value, unit, limit, result, time), rebuilt like records. **SPC uses first-pass readings only:** a retest after rework belongs to another population (a reworked part), and mixing them inflates the variation; retests are shown on the chart as separate marks.
- **Charts:** I-MR on individual readings (centre X̄, limits X̄ ± 2.66·M̄R, MR chart UCL 3.267·M̄R) and X̄-R on consecutive subgroups of 5 first-pass readings in plant-time order (A2 = 0.577, D3 = 0, D4 = 2.114, d2 = 2.326). Constants and formulas in `spc-core`, with hand-calculated cases in `docs/spc-reference-cases.md` driving its unit tests (as `docs/oee-reference-cases.md`). Coverage 95 % lines, 90 % branches, as the other pure packages.
- **Control limits, versioned:** version 1 is estimated automatically (user `system`, audited) from the first 20 complete subgroups of final first-pass readings, and **never re-derived**: a late fact inside its baseline window (from a written-off gap) raises a `baseline-changed` notice on the characteristic, and a `quality` user decides whether to create version 2. A `quality` user can estimate a new version from a chosen window or end a version (`spc:limits`, audited, 409 on a stale version). Limits never move by themselves, so a drift can't hide in its own limits. `quality.control_limit` is append-only.
- **Run rules:** Nelson rules 1–8 implemented, enabled per chart and characteristic. **Defaults: rules 1 (beyond 3σ), 2 (nine on one side) and 5 (two of three beyond 2σ) on the I and X̄ charts, and rule 1 on the MR and R charts**; the others are off. Rule 3 ("six in a row rising or falling") means six points with five successive differences all strictly positive or all strictly negative; an equal pair ends the run; the reference cases pin this, ties included. Probe P4b measured the in-control rate with rules 1, 2, 5 on I and X̄ at 16.5 signalling readings per 1,000 (37.4 for the draft's defaults); ADR-0032 records the false-alarm run length of the final defaults (average in-control readings to a new episode), measured in #195.
- **Signals are episodes:** an episode opens at the first point that triggers a rule on a chart, stays open while consecutive points keep triggering the same rule on the same chart, and closes at the first point that doesn't. It is keyed (characteristic, limit version, chart, rule, first triggering fact), pushed and acknowledged once per episode, not per point. A late point can split or join episodes; that is a rebuild like any other (below).
- **Finality and late facts (the Phase 5–7 defect class):** a point is placed by plant time; a late reading inserts a point and moves every later moving range, subgroup and run. So points, subgroups and signals are derived and rebuilt from the readings, and a signal is **final** only once LKT-01 is final through its triggering point (and, for a subgroup, through its last reading). Provisional signals are shown and pushed (marked provisional); a final signal is never revised except by a fact from a written-off gap, which re-derives it and records `withdrawn` with the reason, like a correction. An acknowledgement stays on its episode by its key and is shown as orphaned if the episode is withdrawn. Probe P3 (rebuild cost, including the database rewrite of the episodes) stays open and is measured in #200: under 20 ms per reading on a week of readings, or the module re-derives from the earliest changed point only.
- **Epochs:** points are ordered by plant time within LKT-01's device epoch; a new epoch starts a new segment on the chart (runs don't span it), with the same limit version.
- **Signals and people:** an episode is pushed on `quality` and shown on the SPC screen and the Line A1 terminal; `spc:ack` (quality, supervisor) acknowledges with a comment (audited). **No automatic hold:** the quality user decides, with a suggested scope (units tested since the last in-control point). Cpu and Cpk (equal to Cpu, the specification being one-sided) are shown against the limit-version window, not reconciled.

### Quality holds (`quality` module, ADR-0035)

- **Subjects:** a lot, a serial (a unit), a carton or an order. The scope is derived, never listed by hand: the units the subject covers through the genealogy (a lot: every unit that consumed it at any operation and pass; a carton: its members; an order: its units), with their cartons and orders. **The scope grows with facts:** a unit that consumes a held lot after the hold, or whose fact arrives late, joins it. Each hold stores `opened_plant_at`, the plant time of the epoch clock when it opened (scripted golden holds set it explicitly); a consumption after `opened_plant_at` raises `held-material-consumed` (the line kept using a held lot, which the MES can see but not stop).
- **Lifecycle:** `open → released | rejected`, with a reason (from a short `quality.yaml` list) and comments; `version` per hold (409 `urn:shopfloor:hold-stale`). `released` means use as is; `rejected` records that quality wants the units scrapped or reworked outside the MES: quantities and confirmations don't change (they change only from machine facts, Phase 7), the cartons stay blocked, and the ERP is told. `quality.hold` (current state) and `quality.hold_transition` (append-only); `quality.hold_unit` derived and rebuilt.
- **Consequences in the MES:** a carton is `held` while any member is in an open or rejected hold; `Orders.close` is refused (409 `urn:shopfloor:quality-hold`) while any unit of the order is in an open hold. **The close guard first requires genealogy's processed watermark to cover every fact of the order's units** (for each machine and epoch the order's units have records on, genealogy's processed-through sequence at or above the highest record's `seq`; otherwise a retryable 409 `urn:shopfloor:genealogy-pending`, because a link not yet written could put a held lot in the order). **Then it derives the scope at check time** from the open holds' subjects and the genealogy links, never from the derived `quality.hold_unit` (which a rebuild may not have caught up; the review reproduced an order closed beside an open hold that way, probe P2). **Opening a hold and closing an order serialize on one transaction-level advisory lock** (`pg_advisory_xact_lock` on a fixed key for holds and closes), taken first in both transactions (`Orders.close` takes it inside `#write`'s transaction, before `#lock` reads and locks the order row; a hold transaction takes it before anything else): row locks on `production_order` would need the hold's affected orders before its scope is derived, and both writes are rare human actions. Under READ COMMITTED the guard's query, run after the lock, sees every hold committed before it. The check is a `CloseGuard` injected into the orders module at composition (the pattern of Phase 7's `BlankCounter`), so `orders` imports nothing of `quality`; `Orders.close` takes the lock through it. `Orders.enqueueErpMessage(trx, …)` never takes the orders module's in-process `#serial` queue and touches no `production_order` row, so a hold transaction holding the advisory lock never waits on a close that holds `#serial` and waits on the advisory lock. #201 adds a two-connection test (a hold opening while a close is between its check and its commit, both orders of arrival), a same-process test with a timeout (a hold and a close at once in one MES process must both finish), and a `genealogy-pending` test (a close while an order's last facts are not yet processed by genealogy). Sign-off at the terminal is not blocked (it states the operation is done, not that the goods are good).
- **Permissions:** `quality:hold` (open, comment; quality and supervisor: a supervisor must be able to stop shipment at night), `quality:release` (release or reject; quality only: the person who decides the goods are good is quality). Every transition and comment is audited (`hold.open`, `hold.release`, `hold.reject`, `hold.comment`).
- **Quality notifications to the ERP:** opening, releasing and rejecting a hold post a notification (a comment doesn't) in the same transaction as the transition, through `orders.erp_message_log` (ADR-0028), with `Idempotency-Key` `{holdId}~{transition}~{n}` built by `qualityNotificationKey` in `@shopfloor/contracts/erp-api`: subject, reason, user, and the scope counts at that moment (units, cartons, orders), marked provisional (`scopeAsOf`, `scopeFinal: false` while a machine of the scope is not final through the transition), since the scope can still grow. #201 adds a migration that extends the outbox for the kind `quality-notification`: `order_id` and `revision` nullable only for that kind (a `CHECK` per kind), a `subject` column (kind and id), the ERP client posting the new kind, and `Orders.enqueueErpMessage(trx, message)` taking the caller's transaction, so one publisher and one backoff serve every ERP message.

## Review decisions

**Round 1** (review of PR #207, changes requested; probes P1, P2 and P4 run by the reviewer). Every decision of both rounds is adopted in this plan; where round 2 refines round 1, round 2 holds.

**Probe results**

- **P1 (OPC UA arrays):** node-opcua 2.187.3, 3,000 cycle events with `String[]` lot fields: all received, intact and in order; empty arrays arrive as empty `String` arrays, and the fields of another event type as `Null`. Arrays are kept.
- **P2 (trace cost and append-only):** with 22,000 units and 66,000 edges as `mes_app`, the backward trace of a serial runs in 0.02 ms and the forward trace of the largest lot (1,800 units) in 3.6 ms; `UPDATE`, `DELETE`, `TRUNCATE` and `DISABLE TRIGGER` on `quality.control_limit` are refused. **The close race reproduced:** a close guard reading `hold_unit` at READ COMMITTED saw no hold, a hold committed meanwhile, and the order was closed with a unit in an open hold.
- **P4 (drift detection):** `orders-01` has 400 first-pass readings and only 127 in Monday's shift A (27 after a 100-reading baseline); a +0.6 drift is detected within 1–2 readings, +0.4 within 8–13; but in control the draft's default rules signal on 37.4 readings per 1,000, and P(a signal within 20 readings) is 0.35 with no drift at all. With rules 1, 2, 5 on I and X̄ the in-control rate is 16.5 per 1,000 and P(signal in 20 readings) 0.18 without drift, 0.99 with +0.6.
- **P3 (SPC rebuild cost):** open; measured in #200, including the database rewrite of the episodes.

**Decisions**

- **HIGH 1, close guard race:** the guard derives the scope at check time from hold subjects and genealogy links, not from `hold_unit`; hold opening and order close serialize on one transaction-level advisory lock (chosen over `FOR UPDATE` on `production_order`, which needs the affected orders before the scope is derived); #201 adds a two-connection test.
- **HIGH 2, exit criterion 3's counterfactual:** `trace.json` records the counterfactual readings (drift removed from the same draws); the counterfactual must open no episode in the 20-reading window nor in the 40 readings before the injection, and the drifted readings must open one within 20.
- **HIGH 3, SPC semantics:** a signal is an episode (opens at the first triggering point, stays open while the same chart and rule keep firing, acknowledged once); defaults rules 1, 2, 5 on I and X̄ plus rule 1 on MR and R, with the false-alarm run length recorded in ADR-0032; `leak-drift` has an end time (`until`).
- **HIGH 4, live comparison:** the reference is a headless `quality-01` with `end` at the end of shift A, its event log asserted to be a prefix of the full run's; the live truth is compared with it once simulator time reaches the end of shift A.
- **MEDIUM 5:** #201's migration extends `orders.erp_message_log` for `quality-notification` (`order_id` and `revision` nullable only for that kind, a `subject` column, the ERP client's new kind, `Orders.enqueueErpMessage(trx, …)`).

- **MEDIUM 7:** the operator is taken at the cycle's start (the part's first `material-consumed` at ASM-01); the crew join uses the same instant.
