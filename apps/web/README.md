# @shopfloor/web

The MES web app (#98, #122, #145, #146, #170): a login with user administration, a plant overview with every machine's live state, a machine detail with its state timeline and telemetry trends, the OEE dashboard, the downtime coding screen, the alarm list, the alarm KPI page and the shift reports with their handover notes (printable). React 19, Vite 8, TanStack Router and Query, Tailwind 4, uPlot, Apache ECharts (plan section 6; decisions in ADR-0020).

## Develop

Start the MES first (runbook, "Run the MES server"); it listens on `127.0.0.1:4700`. Then:

```bash
pnpm --filter @shopfloor/web dev        # http://127.0.0.1:5173
```

The dev server proxies `/api` (REST and the WebSocket at `/api/v1/ws`) to the MES, so the page and the API share one origin, as they are behind nginx in the `web` container (#99):

- `MES_URL` (default `http://127.0.0.1:4700`) points the proxy elsewhere.
- **Host:** the MES answers only `Host` names in `HTTP_ALLOWED_HOSTS` (default `localhost,127.0.0.1,[::1]`). The proxy sends the target's host (`changeOrigin`), so this works with the defaults. Open the app as `localhost` (the session cookie is per host name, runbook "Cookie scope on localhost"); names outside `HTTP_ALLOWED_HOSTS` are refused.
- **Origin:** the MES accepts a WebSocket only from its own origin or `HTTP_ALLOWED_ORIGINS` (ADR-0019). Because `changeOrigin` already satisfies the MES's Host check and Vite's own host check doesn't run on proxied WebSocket upgrades, the proxy has to keep the MES's protection against DNS rebinding itself (`src/dev-proxy.ts`): it refuses (403) an upgrade whose `Host` is not a loopback name (`localhost`, `127.0.0.1`, `[::1]`), and presents the page's origin as the MES's own only when it equals that loopback `Host`. Any other `Origin` is passed on unchanged and the MES refuses it. The same rule applies to HTTP requests (#121): the MES refuses a write without an `Origin` of its own host (ADR-0023), so writes from `pnpm dev` pass only through this rewrite. No `HTTP_ALLOWED_ORIGINS` is needed for development.

The MES needs a login (`MES_AUTH=on`, the default since #170): create the first admin as the runbook says ("Identity": `MES_BOOTSTRAP_ADMIN_PASSWORD` or `user:create`), open `/login`, and add users in `/admin/users`.

## Build

```bash
pnpm --filter @shopfloor/web build      # static files in apps/web/dist
pnpm --filter @shopfloor/web preview    # serves dist on http://127.0.0.1:4173 with the same proxy
```

`dist/` is plain static files (an `index.html` and hashed assets; uPlot and ECharts are separate chunks loaded with the first chart of their kind; the ECharts chunk is about 170 KB gzipped, so Vite warns that it is over 500 KB unzipped). A server must send every unknown path to `index.html` (client-side routes such as `/equipment/cnc-01`) and proxy `/api` to the MES, including the WebSocket upgrade.

## Container

`apps/web/Dockerfile` builds `dist/` with Vite and serves it with nginx (unprivileged, port 8080); Compose publishes it on `127.0.0.1:8080` (`WEB_PORT`) as service `web` (#99, runbook "Full stack"). The nginx configuration is in `nginx/`:

- unknown paths get `index.html` (client-side routes); hashed `/assets/` are cached for a year (`immutable`), `index.html` is always revalidated (`no-cache`); gzip for text;
- `/api/` passes only GET (with HEAD), POST, PUT and DELETE (`limit_except`, others 403) and bodies up to 16 KiB (ADR-0023);
- `/api/` goes to `mes:4700` with the WebSocket upgrade headers, unbuffered, and a 60 s read timeout (the MES pings every 15 s). Docker's DNS is asked again every 10 s, so a recreated MES is found and nginx starts without it;
- it forwards the browser's `Host` **with the port** (`proxy_set_header Host $http_host`): the MES checks the name against `HTTP_ALLOWED_HOSTS` (default `localhost,127.0.0.1,[::1]`, which covers `http://localhost:8080` and `http://127.0.0.1:8080`), and the page's `Origin` (`http://localhost:8080`) then names the MES's own host, so the WebSocket's Origin check passes without `HTTP_ALLOWED_ORIGINS`. `$host` would drop the port and every WebSocket would be refused;
- security headers on every answer: a Content Security Policy without `unsafe-inline` (Vite's output has no inline scripts or styles; React, uPlot and ECharts set styles through the DOM, which CSP allows; ECharts' HTML tooltip would write markup with `style` attributes, which the policy refuses, so its tooltip is drawn on the canvas, checked in a browser in #122), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy: same-origin`;
- `GET /healthz` for the container healthcheck.

To open the app under another name (for example a LAN host name, which also needs a port published beyond loopback), add that name to `MES_ALLOWED_HOSTS` in `.env`.

## How it works

- **Routes:** code-based (ADR-0020), one file per area in `src/routes/` since #170 (`plant`, `oee`, `alarms`, `shifts`, `orders`, `identity`), joined in `src/router.tsx`. The root route wraps `AuthProvider` and the `Shell` (`src/auth/`).
- **Identity (#170, ADR-0026):** `AuthProvider` reads `GET /session`; the `Shell` shows `/login` alone and every other route only with a session whose password needs no change, deciding by the matched route, not the location (the location moves before the matches during a navigation, ADR-0020 note). `/login` takes `redirect` (only a path of this app, `safeRedirect` in `src/auth/redirect.ts`) and `reason` (`ended`, `idle`, `logout`); a temporary password is changed there before anything else. A 401 from any request, or a WebSocket close 4401, goes to `/login?redirect=…&reason=ended` and back after the login; a 403 `password-change-required` or a close 4403 goes to the forced change. The `LiveClient` stops on 4401 and 4403 (no reconnect) and starts again after the login. **Log out** ends the session at the MES (`DELETE /session`), empties the query cache and stops the live client; a login as another user empties the cache too. `useCan(permission)` reads the session's permissions (`ROLE_PERMISSIONS` of `@shopfloor/contracts/identity`), and screens hide the writes a role lacks; the writes send no name, the MES takes the actor from the session.
- **Drafts and idle timeout (#170):** a form with unsaved input registers it (`useUnsavedDraft`). If the session is lost while one exists, the page stays mounted, inert and covered by a login dialog for the same user (`relogin`), who carries on after logging in; **Log in as someone else** discards the input. A person's input (`pointerdown`, `keydown`, `wheel`, `touchstart`) in any tab of this browser counts as use (shared through `localStorage` key `shopfloor.lastActivity`, `try`/`catch`); pushed messages and background refreshes don't (`src/auth/idle.ts`). Two minutes before the idle limit of the session's kind (`SESSION_IDLE_MS`: desk 60 min, terminal 15 min) a banner offers **Stay logged in**; at the limit the app ends the session (`DELETE /session`) itself and `/login` says why (`idle`). The deadline is the earliest of that, the MES's own `idleExpiresAt` and `expiresAt` (moved onto the browser's clock by the answers' `Date` header, `serverClockOffsetMs`). While someone types (or another tab is used), a `GET /session` at most every 30 s, and one when the warning opens, keeps the MES session alive and its expiry known. The absolute limit (12 h, `SESSION_ABSOLUTE_MS`) is announced too, without **Stay logged in**.
- **API:** `src/api/client.ts` reads `/api/v1` and parses every answer with the zod schemas in `@shopfloor/contracts/mes-api`, the same schemas `mes-server` generates `docs/api/mes.openapi.json` from (ADR-0020). Errors become `ApiError` with the MES's problem details (RFC 9457). Interval reads follow `next` while the MES truncates.
- **Live data:** one `LiveClient` per tab (`src/live/live-client.ts`) holds the WebSocket: reference-counted subscriptions, resubscription (and so fresh snapshots) after every reconnect, exponential backoff with jitter, pacing below the MES's rate limit, retries after `busy`, `rate-limited` and `unavailable`. `connectLiveToCache` writes states, the plant clock and telemetry into the TanStack Query cache (`['live', …]`, without structural sharing; a machine's telemetry is dropped a minute after its detail screen closes); the newer of a REST state and a pushed state wins. After a reconnect the REST queries are refetched; on the detail screen a pushed state change rereads the intervals (at most every 2 s), so the timeline has no hole at its live end.
- **OEE live (#122):** the dashboard subscribes to `oee:<id>` for every work center and machine (8 of the MES's 16 topics) and to `downtime`. `connectLiveToCache` keeps per topic only the hour and shift buckets the plant clock is in, as last pushed (`['live', 'oee', id]`); when a topic's hour or shift key moves on, the old bucket is dropped and the REST reads are fetched again (hourly OEE; with a new shift also the shift's OEE and the shifts), so a bucket the clock has left always shows the REST answer. A pushed bucket replaces the REST one of the same key unless the REST one is final where the push is not, or has a higher revision. Values are the API's: four-decimal strings and exact fractions, never recomputed in floating point; minutes and the waterfall's last step use `@shopfloor/oee-core`'s BigInt fractions. A downtime push rereads the Pareto (at most every 2 s).
- **Downtime live and writes (#122):** `downtime` messages are upserts by record id in `['live', 'downtime']` (a higher `version` wins; at the same version a closed record over an open one, then the longer; `removed` deletes), merged into the REST list and sorted UNCODED first. A coding is `PUT /api/v1/downtime/{id}/coding` with a JSON body (`segments` and the record's `version`; the actor comes from the session), relative and same-origin, so the browser sends the page's `Origin` through the proxy (ADR-0023); the body is checked with the shared `codingRequestSchema` first. The version belongs to the machine's coding set: a write to one record moves it for the machine's other records, which the MES pushes as `updated` (#122); the list is also read again after a save. A draft remembers the version and the codings it started from: a newer record with the same codings only moves the version (adopted); one whose codings changed (someone else coded it mid-edit) makes the draft stale, shown as a conflict with **Reload the draft**, and it is never sent with the newer version. On 409 the list is read again and the form reset to what the MES holds; 403, 405, 415, 422 and 429 (with `Retry-After`) are explained from the problem details.
- **Alarms live (#145):** `/alarms` reads `GET /alarms?view=active|acknowledged|shelved` (up to 500 each; `history` only on its tab, the last 24 hours of plant time) and `GET /alarm-points`, subscribes to `alarms` and to `alarm-kpi:position:<id>` per position (`GET /alarms/scopes`). `alarm` messages are upserts by occurrence id in `['live', 'alarms']`, `alarm-point` messages upserts by `equipment/code`. **Monotonic rule** (`newerOccurrence` in `src/domain/alarms.ts`): an incoming copy (a push, a later REST answer, a write's answer) replaces the known one unless the known one is strictly ahead, that is it has taken a step the incoming one lacks (acknowledged, ended, final, more comments, a later state: closed after anything else) and lacks none the incoming one has. The MES pushes an occurrence's messages in commit order with its whole state, so a later push always wins; the rule only stops a REST answer read before a push, or a write's answer, from taking the screen back. A point's shelf is ordered by its `version` (higher wins), and decides whether an occurrence is shelved. The topic has no snapshot, so pushed copies are only current while it is held: when the list subscribes to `alarms` (`useAlarmsTopic`) the pushed alarms are dropped and the REST lists read again, they are dropped again when it lets go, and after a reconnect (missed pushes may have changed fields no rule can order, such as an end reason). A bulk acknowledgement answers without occurrences, so their pushed copies are dropped and the lists read again. The selection is cleared when the tab changes; the Acknowledged tab has no bulk action. The occurrence panel is keyed by the occurrence, so no draft carries over to another alarm. The screen partitions the merged occurrences as the API does (ADR-0024): `closed` in History; else Shelved when the point is shelved; else Acknowledged when `acked-active`; else Active, also once cleared (a clear does not acknowledge). The flood banner of a position shows while its `alarm-kpi` topic reports an episode still in flood.
- **Alarm writes (#145):** JSON-only, relative and same-origin through `sendJson`, each body checked with the shared request schema first: `POST /alarms/{id}/ack` (with an optional comment), `POST /alarms/ack` (the selected rows, at most 100), `POST /alarms/{id}/comments`, `POST /alarm-points/{equipment}/{code}/shelve` (`reason`, a preset of plant time, and the shelf's `version`) and `…/unshelve` (`version`). A shelve draft keeps the version it started from (its first edit): if the point's shelf moves on meanwhile (pushed), the panel says so, sends nothing, and **Reload the shelf** starts again from the new one. A 409 reads the points and the occurrence again and the next attempt sends the new version. The presets are 15 min, 1 h, 4 h and 8 h capped at `maxShelveMs` from `GET /alarms/config` (#160), plus the limit itself when it is none of them, so no preset is refused; until the configuration has arrived there is none and nothing is sent. 403, 405, 415, 422 and 429 (with `Retry-After`) are explained from the problem details, as on the coding screen.
- **Alarm KPIs live (#145):** `/alarms/kpi` subscribes to `alarm-kpi:plant`, `alarm-kpi:position:<id>` per position and the focus scope (an equipment as well), at most four of the MES's 16 alarm KPI topics. `['live', 'alarm-kpi', scope]` keeps the hour and shift buckets the plant clock is in and the open floods; a pushed bucket replaces the REST one of the same key unless the REST one is final where the push is not, or has a higher revision (`pickBucket`, shared with OEE). When a topic's hour or shift moves on, every read of the page is fetched again. Floods, bad actors and operator measures are read again at most every 2 s after a push (KPI pushes for the first two, `alarms` pushes for the operator measures) while the shift is current. Values are the API's: integers, exact fractions and four-decimal strings; the benchmark band compares the exact fraction with BigInt against the benchmarks of `GET /alarms/config` (#160; the rate per KPI window scaled to 10 minutes, no band until it arrived), the hourly chart's flood threshold line and the flood banner's text (threshold and window) come from the same answer, read once per page load (`useAlarmConfig`), and the mean time to acknowledge is `sumMs / count` as an exact fraction (`n/a` without acknowledgements).
- **Shift reports live (#146, ADR-0025):** `/shifts/$date/$shift` reads `GET /shifts/{date}/{shift}/report` once (with `?epoch` when the URL names one) and holds the `shifts` topic. `shift` messages are upserts by (epoch, shift key) in `['live', 'shifts']`, kept only when newer by the MES's own push rule (status, `revision.inputs` and `revision.content` each at least as high, one higher; `isNewerShift`), and `handover-note` messages upserts by note id (the higher `version` wins). When the pushed instance of the shown report is newer than the report, the report is read again: that is how it turns `ended` and `final`, and how a revision after final shows. While the report is `running`, its live numbers come from `oee:<id>` (every work center and machine) and `alarm-kpi:<scope>` (the plant and every position of the report), not from a paced report topic: a pushed shift bucket of the same key and epoch replaces the report's under `pickBucket` (and is marked **Live**); production per machine then comes from that bucket's totals (the API's counts; the total scrap is the integer sum of the rows once one is live). Downtime, bad actors and operator figures are as of the report's `asOf`; **Read again** reads it now. Once the shift has ended but the report is not final, the page says its values are as of `asOf`, holds `downtime` and reads the report again on its pushes (late closes and re-cuts), at most every 5 s. The page is keyed by the instance (epoch, shift key): no note draft or open editor carries over to another shift, even one read before (the M1 lesson). A shift-list row without a stored instance (404) shows the pushed instance of the highest epoch for its key once one arrives. The `shifts` topic has no snapshot (the lesson of #145): the pushed instances and notes are emptied, and instances, reports and notes read again, when a shift screen takes the topic and when it lets go (`useShiftsTopic`), and after a reconnect. Values are the API's, never recomputed in floating point; **changed after final** counts `revision.inputs` and `revision.content - revision.contentAtFinal`, both stored by the MES (#163; no clock is compared).
- **Handover notes (#146):** `POST /shifts/{date}/{shift}/notes?epoch=` and `PUT …/notes/{id}` with `text` (up to 4,000 characters), `category` and, for an edit, `retracted` and the note's `version`, JSON-only and same-origin through `sendJson`, each body checked with the shared schema first. The notes shown are the report's, `GET …/notes` and the pushes and write answers, the highest version per id. An edit draft keeps the version it started from: once the note moves on (pushed, or read after a 409), the editor says who saved which version, sends nothing (another user's edit is never overwritten) and keeps the draft to copy from until **Reload the note**. Failures are told apart by the problem `type` (#163, `PROBLEM_TYPES` in `@shopfloor/contracts/mes-api`, ADR-0023 note), never by the `detail` prose: `urn:shopfloor:handover-closed` is a closed handover window (it lasts from the shift's start to the end of the following shift, plant time), `…:handover-not-open` a shift not begun yet, `…:note-stale` a stale version, `…:note-limit` the limit of 200 notes per shift (the form is disabled at 200), each with its own message; anything else is explained as any write's failure. A note's history (**History**) is `GET …/notes/{id}/audit`, read again for every new version. Notes are React text (`white-space: pre-wrap`), never markup.
- **Print (#146):** **Print** calls `window.print()`; `@media print` (Tailwind's `print:` variant and `src/index.css`) lays the report out on A4 (`@page` 12 mm): the header, navigation, skip link, shift picker, buttons, live marks and every note form are hidden; status, finality, revision, plant epoch, incidents, `asOf` (plant) and `generatedAt` (wall) stay at the top; wide tables print in full instead of in their scroll box, at a smaller size; sections, cards, rows and notes avoid page breaks. ECharts draws on a canvas, which the browser resizes and redraws while it lays the page out for paper, so `EChartsView` hides the canvas in print and prints a still PNG of the chart (`getDataURL`, a `data:` URL the CSP's `img-src` allows) taken on `beforeprint`; the table beside every chart carries its values in any case. **Download JSON** saves the report as served.
- **Orders live (#176):** `/orders` reads `GET /orders` (with `?status=` for the filter) and `/orders/$id` reads `GET /orders/{id}` (routing, BOM, commands with every delivery and `cmd-res`, confirmations, ERP messages, incidents, history), `GET /orders/{id}/execution`, `GET /scrap-records?orderId=` and `GET /execution-incidents?orderId=`. Both hold the `orders` topic (`useOrdersTopic`). `order` messages are upserts by id in `['live', 'orders']`, kept when the `version` is at least as high; `command` messages upserts by command id, kept when `updatedAt` is at least as late; on screen a pushed copy overlays the read one only when strictly newer (at the same version and `updatedAt` the read wins), and a pushed order or command the read lacks is added. A command push also reads the list again (its `dispatched`), and the confirmed `orders` subscription (`subscribed`) reads every order read again, so a change between the read and the subscription is not lost. A push of an order or one of its commands also reads that order's detail, execution, scrap and incidents again (only an open screen refetches): the push carries neither deliveries, results, confirmations nor execution. Execution has no push yet (#177 may add one), so the execution, scrap and incident reads are also polled every 10 s while an order is open. The topic has no snapshot (the lesson of #145): the pushed set is emptied, and the order reads read again, when a screen takes the topic and when it lets go, and after a lost connection or a stopped client (a 4401 or a logout). The detail is keyed by the order id: no open action, draft or message carries over to another order.
- **Order writes (#176):** `POST /orders/{id}/release|dispatch|cancel|redispatch|close` and `POST /orders/{id}/abandon-command`, JSON-only and same-origin through `sendJson`, each body checked with the shared request schema first. A button opens a form that keeps the order `version` it started from; when the order moves on (a push, or the read after a 409) the form says so, sends nothing with the newer version, and offers **Start again on version n** (what was entered is kept) while the action still applies. Dispatch and re-dispatch offer the OP10 machines of the order's routing (its work center's machines with operation OP10) or the dispatch rule's choice; re-dispatch takes an optional blank count (at most `remaining`) and lists the commands not settled yet (the MES refuses with `commands-unsettled`); cancel takes an optional reason. Abandon is offered per command only when the MES would allow it and it matters: the order dispatched or in progress, the command not abandoned, and its run ended (`epoch-ended`, or a job `lost`). Buttons follow the session's `order:*` permissions (`useCan`); the MES refuses the rest (403). Refusals are told apart by the problem `type` (`urn:shopfloor:order-stale`, `…:order-state`, `…:commands-unsettled`, then as any write), and the type is shown.
- **Times** are simulation time; they are shown in the plant's zone (Europe/Istanbul). The detail's ranges (last hour, 8 h, 24 h) end at the plant clock, not the wall clock.

## Screens

- `/`: machines by area and work center in line order, each with its state as colour and text, cause, time in state (to the plant clock), and markers: **Stale** when the live connection is down or the state is from an earlier simulator run, **Provisional** when only the device's start-up state is known (no state change seen yet). Machines that never reported show **No data**. The header shows the plant clock and the connection (`Live`, `Connecting…`, `Reconnecting…`).
- `/equipment/$id?range=1h|8h|24h`: current state, a state timeline over the range (bands per state, drawn on to the plant clock with the live state), time per state over the range, the intervals as a table, metrics with units and latest values, and a trend per metric (min/max band and average from the decimated series, live samples appended).

- `/oee?shift=<date/shift>&focus=<id>`: the shift picker (current shift by default, the last week's from `GET /shifts`); a card per work center (Cell M1, Line A1) with OEE (percent and the API's four decimals), A, P, Q, availability loss own and external, status (**Final**, **Provisional** with the time that may still change, **Revision n**, **n incidents**, **Anomaly**) and the bottleneck (ASM-01, by design) on its line; a machine table; for the work center or machine in **Details for**: OEE per hour (bars, final and provisional), the loss waterfall (PBT → own → external → APT → micro-stops → speed → quality → fully productive, from the API's totals and losses, an alert if they don't add up) and the downtime Pareto (own and external by reason, micro-stops by cause). Null OEE reads `n/a`, never 0. Every chart has its values as text beside it.
- `/downtime?shift=…&uncoded=true&record=<id>`: the shift's downtime records, UNCODED first, live; **Only uncoded** and a machine filter; a record's panel with its reasons in effect, the coding form (split at a plant time, a reason per segment over the reason tree or the automatic one, a comment, **Save coding**, **Undo changes**, **Remove all codings**) and the history from the audit.
- `/alarms?view=active|acknowledged|shelved|history&alarm=<id>`: a flood banner per position while it is in flood; tabs Active, Acknowledged, Shelved (with counts) and History (the last 24 hours), live, newest raise first; per row the priority (colour, mark and text), machine, code and text, raise time, state as text, **Acknowledge** and **Details**; row checkboxes, **select all** and **Acknowledge selected**. **Details** opens the occurrence's panel: priority and severity, definition (text, consequence, response), state, raise and end with the end reason, acknowledgement, finality; acknowledge with an optional comment; the point's shelf (shelve with a reason and a preset, or unshelve); comments and a new one; the history (device raise and end with `seq`, protocol and receive time, and every audited transition with actor and request id).
- `/alarms/kpi?shift=<date/shift>&focus=plant|position:<id>|equipment:<id>&bucket=hour|shift`: a card per scope (plant and positions) for the shift: raises by priority, average per 10 minutes with its benchmark band (the MES's benchmarks, by default acceptable ≤ 1, manageable ≤ 2), peak per 10 minutes, flood windows, flood episodes and time, chattering raises and points, fleeting (and undecided), standing and active at the end, active time, and **Final**, **Provisional**, **Revision n**, **n incidents**; `n/a` without a bucket, never 0. For **Details for** a scope: the hours of the shift (raises and peaks against the flood threshold line, and a table) or the shifts of the last week, the flood episodes, the top 10 bad actors (share as a percentage of the exact fraction) and the operator measures (MES only: annunciated and shelved raises, acknowledged, mean and longest time to acknowledge, unacknowledged at the end, shelved time per point).
- `/shifts`: the shifts of the last week, current first, each with its status (**Running**, **Ended, not final**, **Final**, or no record when the plant clock did not run it), **Final** or **Provisional** and the revision, live; each links to its report.
- `/shifts/$date/$shift?epoch=<n>`: the shift report. The shift picker (as on `/oee`); status, **Final** or **Provisional**, revision (inputs, content), plant epoch, incidents, `asOf` and `generatedAt`; a banner when the report changed after it became final; **Print**, **Download JSON**, **Read again**. Sections: OEE per work center and machine (OEE, A, P, Q, losses own and external, status flags); production (finished parts, total scrap, produced, good, scrap and rework per machine); downtime (availability loss own and external, records, uncoded time with a link to code it, the Pareto by reason as a chart and a table, micro-stops by cause, the ten longest records with the reasons in effect); alarms per scope (the KPIs, the top 5 bad actors and the MES-only operator figures); handover notes with **New note** (category, text), and per note **Edit** (text, category, **Retracted**), **History**. `n/a` wherever the API has no value, never 0.
- `/orders?status=open|<status>` (#176): the production orders by planned start, live: id (links to the detail), product, quantity, blanks dispatched, status with the flags (**Short**, **Dispatch failed**, **Dispatch lost**), priority, planned start and due date; a filter (all, open, or one status).
- `/orders/$id` (#176): the order (status, flags, version and ERP revision, quantities, times, the import's rejection); **Actions** for the session's role (release, dispatch with a CNC choice, re-dispatch the remainder, cancel with a reason, close; read-only otherwise); **Operations and quantities** per routing operation (in, good, scrap by reason, rework, backflushed material, complete) with **Execution and WIP** (units, WIP by position, blanks in a CNC, packed good, rework passes) and the BOM; **Commands and results** (state with its meaning, CNC, blanks, device run, settled, confirmed, job, acceptance, rejection, `seqAfterExpiry`, every delivery and every result, **Abandon command** where it applies); **Incidents** (the order's and its routing violations, newest first, open or closed); **Confirmations to the ERP** (final and corrections with their message status); **Scrap records** (read-only; coding is on the terminal, #177); **ERP messages**; **History** (the audit).
- `/login?redirect=<path>&reason=ended|idle|logout` (#170): user name and password; why the last session ended; a temporary password (a new user, a reset, the bootstrap `admin`) must be changed here (current, new, repeated; the MES's password rules shown) before any other screen opens. Then back to `redirect` or the overview.
- `/account` (#170): the user, roles, permissions, login time and session limits, the own password change (ends the user's other sessions) and **Log out**.

## Accessibility

Semantic landmarks and headings, a skip link, focus moved to the new screen's heading after navigating, visible focus outlines, time without data hatched on the timeline (no state colour can pass for it), state never by colour alone (text labels, AA-contrast colours), a text table for the timeline, the connection announced as a status, `prefers-reduced-motion` respected (no animation then, charts included), layouts down to phone width without horizontal page scroll (wide tables scroll inside their box). OEE and downtime: status as text (Final, Provisional, Uncoded, Own/External), every chart with an image label and its values in a table, labelled form controls, errors in `role="alert"` and a saved coding in `role="status"`, focus on the record panel's heading when a record opens, Escape or **Close** closes it and returns focus to the row's **Code** button, input lengths limited by `MES_API_LIMITS`. Alarms: priority as colour, a mark and its word (High, Medium, Low), states and the benchmark band as text; the lists are WAI-ARIA tabs (arrow keys, Home and End move between them); every checkbox and button is labelled with the alarm and machine; the flood banner's headline is an alert (the counts beside it are not re-announced); messages in `role="alert"` or `role="status"`; the occurrence panel takes focus when it opens and Escape or **Close** returns it to the row's **Details** button; the panel comes before the list on narrow screens, and the wide tables scroll inside their box. Shift reports: status, finality and **Live** as text, never colour alone; every table has a caption, every chart its values in a table; the banner after final is a `role="status"`; note messages in `role="alert"` (refused) or `role="status"` (saved); the editor takes focus in its text area when it opens, Escape or **Cancel** closes it and focus returns to the note's **Edit** button; **History** is a toggle with `aria-expanded`; the text area announces its character count; down to 375 px without horizontal page scroll (wide tables scroll inside their box on screen and print in full).
