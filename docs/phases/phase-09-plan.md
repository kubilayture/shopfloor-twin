## Goal

The owner can steer the plant the way a test engineer steers a real one, from a browser, and replay what he did; the MES reports OEE per order and per line as well as per machine; and the system is shown to survive infrastructure faults, to keep up at 60× with headroom, and to pass a written security review.

## Scope

- **Order and line OEE** (deferred from Phases 7 and 8): `oee-core` gains an order OEE (the order's job windows on its CNCs, changeover included) and a throughput-based line OEE (good packed output against the bottleneck's ideal rate, ADR-0021 option (c)), with hand-calculated reference cases; the simulator writes their truth in a sidecar `line-oee.json` beside each golden summary; the MES computes, serves and pushes them; the order screens and the OEE dashboard show them.
- **Console actions in the simulator:** block and release a component lot, mark operators absent for a shift, break a CNC's tool; each a new event variant written only when used, so no existing event log changes; read routes for lots and operators.
- **Scenario playback:** YAML timelines in `config/scenarios/` of the console's actions, loaded headless or live, with the same event log both ways; dispatches recorded in a live orders run replay headless (ADR-0030's open point).
- **Simulation console** in the web app (`/console`), reached through an allowlisting nginx proxy with a `sim:control` permission and a control-API token the browser never holds.
- **Derived-work costs:** incremental SPC derivation from the earliest changed point (ADR-0032), and hold scopes rebuilt on change, not every second (ADR-0035).
- **Security:** OPC UA SignAndEncrypt with pinned certificates and named users; MQTT client ids bound to users (dynamic security); HTTPS-only web front with `Secure` cookies; fewer published ports; login throttling per client address; a written security review whose items carry evidence.
- **Resilience suite** (`pnpm test:resilience`): broker, gateway, MES, database and ERP restarts or outages, an OPC UA server offline, the washer silent, during live shifts at 60×, in separate runs with stated fault schedules.
- **Performance:** a Node load tool (`pnpm test:perf`), targets set in this plan with the run that measures each; an optional Prometheus and Grafana Compose profile.
- **Test hygiene:** a host-wide lock so only one heavy suite runs at a time, ephemeral host ports for the gate's stacks, disk checks and cleanup per run, resource limits on every container.

Out of scope here:

- a release step, a demo recording, the documentation pass and the `v1.0.0` tag (Phase 10);
- OpenTelemetry tracing and moving metrics off `prom-client` (decided here: not in v1; ADR-0012 amended);
- order release and dispatch from the console: they stay on the MES order screens (Phase 7), because the console is the physical world and releasing is an MES decision;
- retention and compression policies on the hypertables; the O(hours × occurrences) alarm KPI read (carried, ADR-0024); an inbound ERP lot block; automatic holds from SPC signals (carried from Phase 8);
- manual physical scrap of a part from the console (needs a path for a unit the machines didn't scrap, and every quantity rule of ADR-0031 to follow it; after v1.0);
- a tool breakage as a `Down` with its own failure code (a new code in `failures.yaml` changes `configSha256` and so every golden event log; see "Console actions");
- serials unique across simulator runs (ADR-0034's recorded limit stays);
- an OPC UA history service to replay facts raised while a session was down (ADR-0009's known limit stays; the resilience suite proves the loss is **detected** exactly);
- Sparkplug B (decided in the Phase 10 report), SSO, cloud deployment (master plan non-goals).

## Decisions made in this plan

### What the code does today

- **OEE:** per equipment and work center (time-weighted sums, ADR-0021 (b)), per hour and shift, `scheduledTime: orders` in orders mode (Idle `NO-ORDER` excluded on the CNCs). No order or line OEE anywhere; the ground truth (`sim-summary/4`) has per-order quantities and completion times but no OEE per order. **The bottleneck exists only as a web constant** (`apps/web/src/domain/oee.ts`, `DESIGNED_BOTTLENECK = 'asm-01'`); no configuration key names it. `oee.yaml` is hashed into a summary's `analysisConfigSha256` (`apps/simulator/src/headless/run.ts`, `analysisConfigHash`), and the plant configuration into `configSha256` and from there into every event log, so a new key in either file would change every golden.
- **Control API 1.6:** time (pause, resume, step, speed 0.5–60), infrastructure faults (OPC UA server offline per machine, Modbus silent), failure injection (1.3), `leak-drift` (1.5), ground truth with `?asOf` (1.6). No authentication; published on `127.0.0.1` only. `ProductionLine.blockLot` exists in the model (a blocked lot is skipped as if empty) but no route reaches it. Operator absence is a random draw per operator and shift (`absenceProbabilityPerShift`); every shift has **two** operators qualified for ASM-01 (`config/plant/operators.yaml`), and the first present one takes the station, so one absence changes nothing. No tool breakage injection: a CNC's tool is changed by `#tryStart` when `needsChange` (wear at end of life) before the next cycle starts (`Setup`, `TOOL-CHANGE`, 8 minutes); the defect draw of a cycle reads the wear curve (one `bernoulli` per OP10 cycle on `{cnc}/quality/defect`).
- **Scenarios:** golden `scenario.json` files carry `injections` (failures and drifts, one numbering, scheduled after `line.start` and the dispatches) and `dispatches` (orders mode, given after `line.start` and before the injections), mapped onto `HeadlessOptions`; no `config/scenarios/` folder, no YAML timelines, no live playback; a live run that received dispatches mid-run can't be replayed headless (ADR-0030).
- **Web:** no console route; nginx proxies `/api/` to the MES only, over plain HTTP on `127.0.0.1:8080`.
- **Security:** OPC UA security mode None, anonymous, `LoadOrder` and `LoadProgram` callable by any client; the simulator keeps a PKI volume (`simulator-pki`) with node-opcua's self-signed certificates, and **the gateway accepts any server certificate** (`automaticallyAcceptUnknownCertificate: true`, `apps/edge-gateway/src/main.ts`). Mosquitto with a plain ACL file (`config/mosquitto`, mounted read-only; client-id takeover an accepted risk since Phase 3). `MES_COOKIE_SECURE` off; per-account lockout (a denial of service accepted on loopback "until Phase 9", ADR-0026). The ERP mock's bearer token is one shared secret. Published on `127.0.0.1`: database 5442, broker 1883, control API 4800, OPC UA 4841–4845, Modbus 5020, gateway 4900, MES 4700, ERP 4600, web 8080. Resource limits on the simulator, gateway, MES, ERP mock and web, **none on the database and the broker**.
- **Derived work:** SPC re-derives the whole chart per new reading (p95 13–14 ms idle on `week-01`; a late reading 23–45 ms, over the 20 ms budget; a month of readings would need incremental derivation or a window, ADR-0032; histogram `mes_quality_spc_derive_seconds`); hold scopes rebuilt every second while open or rejected (ADR-0035).
- **Resilience:** proven per component in Phases 3–7 (gateway broker outage with no loss and no duplicates, OPC UA reconnect with gap detection, MES persistent session, outboxes). WSH-01's fact ring holds 64 entries (`RING_CAPACITY`). No whole-system suite.
- **Performance:** measured piecemeal: ingest about 1,000 stored messages/s (runbook), push latency budgets of Phases 4–8, trace performance (p95 2.9 ms backward, 29 ms forward through nginx). No ingest lag metric (only counters such as `mes_ingest_messages_total`), no load tool, no stated targets. The golden feed that turns an event log into UNS messages lives in `mes-server`'s test support (`golden-feed.test-support.ts`, #204).
- **Gate:** `pnpm gate` (verify, golden, e2e, smoke, reconcile with three passes; about 45 minutes at #204). The smoke uses the default host ports, so a dev stack must be stopped. Nothing stops two agents' heavy suites from running at once; the Phase 8 log records flakes and timeouts from exactly that (#212, #216, #218).
- **CI:** GitHub Actions still stopped by the spending limit; every criterion below is proven by local runs.

### Order and line OEE (`oee-core`, ADR-0036)

- **Bottleneck, derived:** `oee-core` derives the bottleneck per product as the operation with the largest **effective cycle**, its ideal cycle (`products.yaml`) divided by the number of machines that run it (`plant.yaml`), ties by routing order. OP10 runs on two CNCs in parallel: VB-100 OP10 240 s ÷ 2 = 120 s against OP30 150 s on ASM-01; VB-200 330 s ÷ 2 = 165 s against 210 s. So ASM-01 for both variants. The line OEE's numerator uses the same effective cycle (ASM-01 is one machine, so 150 s and 210 s). **The designed bottleneck holds even when only one CNC has work** (ADR-0036): the CNC is then the actual constraint, and that shows as a lower line OEE, not as a different bottleneck, so a bucket's ratio never changes what its numerator means. No configuration key is added: `oee.yaml` feeds `analysisConfigSha256` and the plant configuration feeds `configSha256` and every event log. A test asserts that both hashes are unchanged for the four goldens. The web's `DESIGNED_BOTTLENECK` is replaced by the MES's answer (P9-06).
- **When a job is head:** a job is the head of its CNC's queue from `max(its accepted fact, the previous job's completed fact on that CNC)`; both are job facts (ADR-0030) that the ground truth and the MES see alike. The head time is before the job's changeover (`Setup`, cause changeover) and its `started` fact (the first blank taken after the changeover), so the changeover counts against the order that caused it. Idle `NO-ORDER` while a head job waits for its `notBefore` is excluded as today. **When a fact is missing** (a written-off gap; ADR-0036): a lost `accepted` fact is replaced by the command result's `acceptedAt` (`uns.cmd-res/1`, the plant time of the device's `accepted` fact, `docs/contracts/uns.md`); if neither is known, or the previous job's `completed` fact is lost, the order's OEE stays provisional with `headTimeUnknown` and is never final. The ground truth always has the facts; the goldens assert no such flag.
- **Order OEE:** for every accepted job of the order, the window on its CNC from its head time to its `completed` fact (an open window is provisional). Inside the windows, the CNC's states give planned busy time and actual production time by the equipment rules (ADR-0021, `scheduledTime: orders`, micro-stop threshold); produced and good are the order's OP10 cycles (by unit, ADR-0031); ideal time is the product's OP10 ideal cycle. A, P, Q and OEE as exact fractions, summed over the order's jobs (time-weighted, as work centers in ADR-0021 (b)). Beside it, not multiplied in: the order's **first-pass yield across the routing** (units packed good on their first pass / units started), because OP10 quality alone hides OP40's leak scrap.
- **Why job windows:** a job window is the only time the plant attributes to one order without a rule of thumb: the CNC runs one job at a time, and downstream machines interleave both CNCs' orders. Splitting ASM-01's time between two orders by its units would need an allocation key the ground truth would have to invent.
- **Line OEE (throughput):** for Line A1 fed by Cell M1, per hour, shift bucket and order: **good packed units × the bottleneck's effective cycle per product ÷ line planned busy time**. Line planned busy time: shift calendar time minus planned stops (breaks, planned maintenance on the bottleneck); in orders mode, only the time at least one order is **in progress**, from its first job's head time (so its changeover counts) to its completion time (ADR-0031), the line's counterpart of `NO-ORDER`. Per order, the same ratio over the order's in-progress time with its own good units; orders overlap, so per-order line OEE is **not additive** (stated on screen and in the ADR). No A × P × Q split: a throughput OEE has one ratio; the dashboard keeps the per-machine waterfall beside it.
- **Above 1, not capped:** line OEE can exceed 1 in a bucket: an operator faster than ideal (`op-b1`, `speedFactor` 0.95) or WIP drained from the buffers into a short bucket packs more than the bottleneck's ideal rate allows for that bucket's time. The value is reported as computed with a flag `aboveOne`, and the dashboard says why; capping would make the bucket sums disagree with the shift. A reference case pins it.
- **Exactness and finality:** fractions as in `oee-core` today; a bucket is final when every machine it reads is final through its end (ADR-0018); an order's OEE is final when its jobs' facts and its units are final (its completion final, ADR-0031).
- **Reference cases:** `docs/oee-reference-cases.md` gains cases, hand-calculated to four decimals and driving the unit tests: one job; a job with a changeover before its `started`; two jobs on two CNCs; a job across a shift boundary and a break; a job with a micro-stop and a breakdown; a short order; a line bucket with no order in progress; two overlapping orders; a rework that packs in a later bucket; a line bucket above 1 from a fast operator and buffer drain; the bottleneck derivation with parallel machines (two CNCs on OP10, whose raw ideal cycle is the largest but not its effective one) and with a tie; a line bucket with only one CNC working; an order whose `accepted` fact is replaced by `acceptedAt`, and one left provisional. Coverage floors as the other pure packages (95 / 90).

### Order and line OEE truth (simulator)

- **A sidecar, not a summary version:** `line-oee.json` (`sim-line-oee/1`) next to `summary.json` for all four goldens (line OEE for each; order OEE for `orders-01` and `quality-01`, empty `orders` in schedule mode), computed with `oee-core` from the same configuration as the MES; `GET /ground-truth` gains `lineOee` (control API 1.7), cut by `?asOf` like `trace`. **`summary.json`, `events.sha256` and `trace.json` of every golden stay byte-identical**; adding a file to a golden folder is not a regeneration (#208's precedent), recorded in `apps/simulator/golden/README.md`. Once committed, a change to a `line-oee.json` is a golden regeneration (written reason, owner approval).

### MES `oee` module (order and line)

- Order OEE per order and job (P9-04) and line OEE per hour, shift bucket and order (P9-05), from the equipment pieces, execution's units and the orders module's job facts, through their modules' `index.ts`; derived and rebuilt like the existing buckets (a late fact rebuilds the affected windows, never patches). API: `GET /oee/orders/{id}`, `GET /oee/line?from&to&bucket=hour|shift`, the bottleneck per product; push on the existing `oee` topic (`order` and `line` deltas, paced like the buckets). No new table if the reads are within budget (computed from the hourly aggregates and the pieces, as the work-center OEE is); a cache table only if the API misses 100 ms p95, recorded in the issue.
- **Web** (P9-06): the order detail shows the order's OEE (A, P, Q, OEE, provisional marked) and its first-pass yield; the OEE dashboard gains a line card per shift with the bottleneck named, `aboveOne` explained and "not additive across orders" for per-order line OEE.

### Console actions (simulator, ADR-0037)

- **Read routes:** `GET /api/v1/lots` (lot, material, quantity remaining, blocked) and `GET /api/v1/operators` (roster per shift, skills, present or absent in the current shift, forced absences planned), for the console.
- **Lot block and release:** `POST /api/v1/lots/{lot}/block` and `/release` reach `ProductionLine.blockLot`; a blocked lot is skipped (the consuming station starves with cause `MATERIAL:<material>` once no other lot remains), written as a `lot` event variant (`blocked | released`). This is the physical counterpart of an MES hold, never triggered by the MES (ADR-0035 stays: the MES doesn't command the simulator for quality).
- **Operator absence:** `POST /api/v1/operators/absent` with a list of operator ids and a shift (the next shift start at the earliest, so no running shift's staffing changes mid-cycle). Every listed operator is absent at that shift's start whatever the roster draw says; the draw itself still happens, one per operator per shift on its own stream (ADR-0007), so the number of draws and every other shift are unchanged. Marking both of a shift's ASM-01-qualified operators (for shift A, `op-a1` and `op-a2`) leaves ASM-01 unstaffed: the test asserts ASM-01 `Idle` with cause `NO-OPERATOR` at that shift's start. Written as an `absence` event variant.
- **Tool breakage:** `POST /api/v1/faults/tool/{machine}` (CNCs only) at a time `at`. Defined against the existing tool model: at `at` the tool's cycle count is set to its `lifeCycles` (wear 1.0). A cycle in progress at `at` completes normally and draws its defect at wear 1.0 (the end-of-life probability, 5 % by default); `needsChange` is then true, so `#tryStart` changes the tool before the next cycle as it does at end of life (`Setup`, `TOOL-CHANGE`, `changeMinutes`). With no cycle in progress, the change happens at the next start. **Draws:** every OP10 cycle still makes exactly one defect draw on `{cnc}/quality/defect`, only its probability changes; the tool change itself draws nothing (`changeMinutes` is fixed). So the run before `at` is identical, and every other stream draws the same sequence (its timing after `at` may move, as with any injection). Written as a `tool-breakage` variant. A `Down` with a `TOOL-BREAK` failure code is not added (out of scope).
- **Rule for every action:** a new variant of the event union, written only by runs that use it; the run header lists actions under a new key `actions` only when a run has one (existing headers keep `injections` and `dispatches` as they are); same calendar-boundary refusal as failure injections. So `week-01`, `alarms-01`, `orders-01` and `quality-01` keep every byte (asserted).

### Scenario playback (simulator, ADR-0037)

- **Timelines:** `config/scenarios/<name>.yaml`, one Zod schema in `plant-config`. Entries `{ at, action, … }` for `failure`, `leak-drift`, `opcua-offline`, `modbus-silent`, `lot-block`, `lot-release`, `operators-absent`, `tool-breakage`, `dispatch`, `speed`, `pause`. Headless (`pnpm sim:headless --timeline config/scenarios/x.yaml`) and live (`SIM_TIMELINE` at start, or `POST /api/v1/scenario` while idle) read the same file. Infrastructure entries (`opcua-offline`, `modbus-silent`, `speed`, `pause`) don't touch the plant model, so headless ignores them and the event log is the same.
- **The loader maps `scenario.json` onto `HeadlessOptions` unchanged:** dispatches after `line.start` and before the injections, failures and drifts in list order sharing one numbering, header keys `injections` and `dispatches` kept apart, the new actions under `actions`. The golden `scenario.json` files are parsed by the same schema and give byte-identical runs (asserted).
- **`dispatch` entries are headless only.** A live timeline with a `dispatch` entry is refused at load (400, or a start-up error for `SIM_TIMELINE`): in a live orders run the MES dispatches through `LoadOrder`, and two sources of jobs would make neither reproducible. Live schedule-mode runs have no jobs at all.
- **Live recording:** a live run can write its event log (`SIM_EVENT_LOG`), so live and headless are compared byte for byte.
- **Dispatch recording and replay** (P9-09): in live orders mode the simulator records each accepted job with the simulation time and the device sequence of its acceptance (`GET /api/v1/scenario/recorded`), a headless timeline of `dispatch` entries that reproduces the run (ADR-0030's limit closed). Probe Q2 confirms that acceptance at the recorded time and sequence gives the same event order.
- **Example timelines** committed: `monday-breakdown-and-recovery.yaml` (a failure and repair, a lot block and release, a tool breakage, both ASM-01 operators absent for shift B).

### Simulation console (web, ADR-0037)

- **Route `/console`:** run status (sim time, speed, paused, epoch), pause, resume, single step, speed slider (0.5–60); failure injection per machine and code; `leak-drift`; OPC UA offline per machine and Modbus silent; lots with block and release; operators with "absent next shift" (several at once); tool breakage; scenario load from the committed timelines with a progress list; the recorded dispatches as a downloadable timeline. Live through the control API's WebSocket (plant events) and a 1 s status poll.
- **Proxy:** nginx proxies `/sim/` to the control API for an **allowlist** of routes only: `GET status`, `POST pause|resume|step`, `PUT speed`, `faults/*`, `lots`, `operators`, `scenario`, and the plant-events WebSocket. `GET /ground-truth` is not proxied (it is the test oracle, not a console view). Each request first passes `auth_request` to the MES (`GET /api/v1/session/permission/sim:control`, 204, 401 or 403), and nginx adds the control API's token itself, so the browser never holds it. Because `auth_request` is a GET, the MES's `Origin` guard (ADR-0023) never sees a console write: **nginx checks `Origin` on every non-GET `/sim/` request** against the configured public origin and answers 403 otherwise.
- **Session use:** the permission check passes the original method (`X-Original-Method`); only a non-GET console action counts as session use, so the 1 s status poll doesn't keep an unattended console's session alive (ADR-0026's idle expiry), while a user acting on the console stays signed in. The MES trusts `X-Original-Method` only on connections from the `edge` network (see "Login throttling"), as `X-Real-IP`.
- **Control-API token** (moved here from the hardening issues so the console never ships with an open control API): `SIM_CONTROL_TOKEN` required on every control route but `/health/*` and `/metrics` (401 without it), random per stack like the other secrets, added to `.env.example` (without a value) and to the smoke's required-secret check (`scripts/stack-smoke.sh`, the loop that asserts Compose refuses to start without each); the reconcile, smoke, resilience and perf harnesses send it.
- **Permission:** `sim:control`, **held by `admin` only**: the console is the physical world, not a plant role, and an MES user acting on the world under test would blur the two (ADR-0026's separation of duties). The MES never calls the control API (master plan section 5 stays true).

### Derived-work costs (MES)

- **Incremental SPC:** `spc-core` gains a derivation that resumes from the earliest changed point (moving ranges, subgroups, rule windows and episodes from there on), with a property test that it equals the whole derivation on random sequences with late inserts, duplicates and epoch changes; the `quality` module uses it. Targets on `mes_quality_spc_derive_seconds` (label `kind` = `new | late`): on `week-01` a new reading p95 ≤ 10 ms and a late reading p95 ≤ 20 ms; on a synthetic month (about 9,000 first-pass readings; cut line) the same budgets and the default chart read (last 500 readings) p50 ≤ 10 ms on a new histogram `mes_quality_chart_read_seconds`.
- **Hold scopes on change:** `hold_unit` rebuilt on genealogy's `onChange` and on hold transitions, not on a 1 s timer. `Genealogy.onChange` listeners are not claimed to run inside the round (the quality module may defer its rebuild), so the budget is judged as two measurements: a new histogram `mes_genealogy_round_seconds` (the round alone) and a new histogram `mes_quality_hold_scope_seconds` (one scope rebuild); with 200 open holds, **the round's p95 plus the scope rebuild's p95 exceeds the round's p95 with no hold by ≤ 50 ms**.
- **How budgets are read:** every budget's percentile is computed from the raw timings the test collects through the module's timing hook (as #200's probe P3 did), not interpolated from histogram buckets; the histograms (`mes_quality_spc_derive_seconds`, `mes_quality_chart_read_seconds`, `mes_quality_hold_scope_seconds`, `mes_genealogy_round_seconds`) share the bucket edges 1, 2.5, 5, 10, 20, 25, 50, 100, 250 ms, 0.5 s and 1 s, so every budget (10, 20, 50 ms) is an edge when a dashboard shows it.

### OPC UA security (ADR-0038)

- **Endpoints:** every machine server offers **SignAndEncrypt only** with `Basic256Sha256` and `Aes128_Sha256_RsaOaep` (mode None off in Compose; `OPCUA_SECURITY=none` kept for unit tests that don't test security).
- **Trust by pinned leaf certificates, no CA:** a one-shot `pki` service in Compose **generates every OPC UA key and certificate itself**, since node-opcua would otherwise create them on each server's and the gateway's first start (`machine-server.ts`, `plant-servers.ts`), too late for a step that runs before them. For each of the five machine servers and the gateway it creates a key and a self-signed certificate whose SAN carries that component's `applicationUri` (`${SHOPFLOOR_NAMESPACE_URI}:<machineId>` for a server, the gateway's own URI) and its stable host name, writes them into that component's PKI volume (`own/private`, `own/certs`), copies the gateway's certificate into each server's `trusted/certs` and each server's into the gateway's, and exits; it keeps existing material that is valid for more than 30 days. The simulator and the gateway start only after it completed successfully (`depends_on: condition: service_completed_successfully`) and, in Compose, refuse to start without their certificate instead of making one; tests outside Compose either run an explicit exchange step (the same code as the `pki` service, called by the test helper before the servers and clients start) or set `OPCUA_SECURITY=none` when they don't test security. **No automatic acceptance anywhere:** `automaticallyAcceptUnknownCertificate: false` on all five machine servers (today `true` in `machine-server.ts`) and in the gateway (today `true` in `apps/edge-gateway/src/main.ts`); node-opcua's `applicationUri` check stays on. Not "anything signed by a shared CA": the web and MQTT certificates come from the dev CA (below), and a certificate issued for nginx must not open an OPC UA session. Pinning also avoids node-opcua's refusal of CA-issued certificates without a CRL; probe Q1 records that behaviour so the choice is evidenced.
- **Certificate details (P9-12):** files at the paths node-opcua resolves by default (per machine server `pkiFolder/<machineId>/own/certs/certificate.pem` and `own/private/private_key.pem`; the client's own default certificate name in the gateway's folder), or passed explicitly as `certificateFile` and `privateKeyFile` where a default doesn't fit; the issue checks the pinned node-opcua version's defaults and prefers explicit paths. Key usage `digitalSignature, nonRepudiation, keyEncipherment, dataEncipherment` (plus `keyCertSign` on the self-signed certificate) and extended key usage `serverAuth` for servers, `clientAuth` for clients, as OPC UA Part 6 expects. SAN: the `applicationUri` as a URI, and DNS `simulator` and `localhost` for the servers (the gateway reaches them as `simulator`, host tools as `localhost`). The gateway's `applicationUri` is set explicitly (today it is derived from `applicationName`, `shopfloor-twin-edge-gateway`). A third client certificate, for tools and the `opcua-reader` tests, is issued and pinned on the servers like the gateway's. **On renewal** the `pki` service removes the old pinned certificate of a renewed peer from every `trusted/certs` folder before adding the new one, so a superseded certificate is no longer trusted.
- **Users:** the gateway authenticates as `opcua-gateway` (user name and password, `OPCUA_GATEWAY_PASSWORD`); a read-only user `opcua-reader` (`OPCUA_READER_PASSWORD`) can browse and read (development tools, a test); anonymous sessions are refused. `LoadOrder` **and `LoadProgram`** are executable only by `opcua-gateway` (address space 1.3). Both passwords are random per stack, added to `.env.example` without a value and to the smoke's required-secret check.
- **Keys and expiry:** the `pki` service is the only one that mounts every PKI volume, and only while it runs; each component mounts only its own, so a component's private key is readable by that component alone. The dev CA's key lives only in the `pki-ca` volume, which no long-running service mounts. Certificates are made with a fixed validity; **cost per gate project:** every gate project starts from empty volumes, so the `pki` service makes 7 OPC UA keys (five servers, the gateway, the tools client) plus the dev CA's and nginx's (and the broker's, unless cut); P9-12 measures and records that time (RSA 2048, expected a few seconds) and the smoke asserts that the `pki` service exited 0 and that a machine server refuses a session from a client certificate it doesn't pin. The runbook gains a section on expiry (how to see the dates, renewing by rerunning the `pki` service, which replaces material within 30 days of expiry, and resetting all PKI volumes).
- **Probe Q1** (first commit of P9-12): ADR-0009's lossless delivery at 60× with SignAndEncrypt (five servers, two clients each, a scripted shift, gap-free `Sequence`), the CPU cost per message against mode None, an untrusted certificate refused, and the CRL behaviour of a CA-issued certificate. If delivery fails, the issue stops and reports before anything else changes.

### Dev CA, HTTPS and ports (ADR-0039)

- **Dev CA:** one per stack, made by the `pki` step; its key stays only in that step's volume (`pki-ca`), never in a service's. It issues the nginx certificate and, unless cut, the broker's. Separate from OPC UA trust (above).
- **HTTPS only:** nginx serves the web front on HTTPS only (`WEB_HTTPS_PORT`, default 8443); there is no HTTP listener, so no redirect can point at a wrong port when gate projects publish ephemeral ports. **No HSTS:** on `localhost` it would pin every local port to HTTPS. `MES_COOKIE_SECURE=on` by default in Compose, so the cookie is `__Host-sft_session; Secure; HttpOnly; SameSite=Strict` (ADR-0026's plan for TLS).
- **Harness trust:** Node clients (smoke, reconcile, resilience, perf, trace-perf) trust the dev CA through `NODE_EXTRA_CA_CERTS` pointing at the CA certificate the `pki` step exports. Playwright's Chromium doesn't read that variable, and `ignoreHTTPSErrors` would accept any certificate (weakening S4), so Chromium is launched with `--ignore-certificate-errors-spki-list=<SPKI SHA-256 of this stack's nginx certificate>`: it accepts that one key and no other. A test asserts that the browser refuses a different certificate on the same port.
- **Published ports (hardened Compose):** published on `127.0.0.1` only: web HTTPS 8443, broker 1883 (8883 with TLS), control API 4800 (token), OPC UA 4841–4845 (SignAndEncrypt), Modbus 5020, ERP mock 4600 (token). **No longer published by default:** MES 4700, gateway 4900, database 5442. A Compose override (`compose.dev-ports.yml`) publishes them for development and for harnesses that need them (the trace-perf loader already uses an override for the database), on ephemeral ports in gate projects. With 4700 unpublished, nothing but nginx reaches the MES from outside the Compose network. **Dev workflow:** `docker compose up` and `pnpm stack:up` stay the hardened default (master plan success criterion 1, and what S8 reviews); a new `pnpm stack:up:dev` adds `compose.dev-ports.yml` for development; the runbook's "Full stack" section and every place that names 4700, 4900 or 5442 are updated in P9-14.

### MQTT dynamic security (ADR-0039)

- Mosquitto's dynamic-security plugin replaces the plain ACL file. `config/mosquitto` is mounted read-only, so the dynamic-security JSON lives in `/mosquitto/data`, created by `entrypoint.sh` on first start with `mosquitto_ctrl dynsec` from the passwords in the environment (random per stack).
- **Client-id binding:** `gw-01`, `gw-01-cmd` and `mes-server` are bound to their users, so a connection with another user's id is refused; the `dev` and `healthcheck` users connect with arbitrary client ids (`mosquitto_sub` makes its own), so they get no binding and only their read-only ACLs. Every ACL refusal of ADRs 0015 and 0029 is kept and tested (PUBACK 0x87).
- **Alternative recorded in ADR-0039:** `use_username_as_clientid` binds ids without the plugin, but the gateway's two connections share one user and would take each other's session; it would need two users and changes to ADR-0029's ACL.
- **TLS** on the broker listener with the dev CA: on the cut line.

### Login throttling (ADR-0039)

- **Address source:** nginx sets `X-Real-IP` to `$remote_addr`, overwriting whatever the client sent. The web container's address can't be resolved once at the MES's start (the web starts only after the MES is healthy, `docker-compose.yml`, and gets a new address when recreated), so nginx and the MES share a dedicated network `edge` (`internal: true`, only those two services attached). **The subnet is not pinned:** a fixed subnet would make parallel Compose projects (the gate's, a dev stack, the reconcile passes) fail with "Pool overlaps" and could collide with Docker's or Colima's own pools. Instead the MES learns its `edge` subnet at start: it resolves its own alias on that network (`MES_EDGE_ALIAS`, default `mes-edge`, an alias that exists only on `edge`) to its address there, finds the interface holding that address (`os.networkInterfaces()`, which carries the CIDR) and trusts `X-Real-IP` and `X-Original-Method` only on connections whose source lies in that CIDR, after normalising an IPv4-mapped IPv6 source (`::ffff:a.b.c.d`) to its IPv4 address; it refuses to start in Compose if the alias doesn't resolve to a local interface. A per-stack shared-secret header from nginx was the alternative; it was not chosen because the trust then rests on one more secret to generate, check and keep out of logs, while network membership is enforced by Docker and needs none. `internal: true` gives the network no route out, but Docker still puts its gateway address on the bridge in the VM's host namespace, inside the subnet; so the network also sets `com.docker.network.bridge.inhibit_ipv4` (P9-10 security review), which leaves the bridge without an IPv4 address and the network without an IPAM gateway, and only its two attached containers have addresses there.
- **One path from nginx to the MES:** nginx and the MES also share the default network (the MES needs the database and the broker there), so the name `mes` may resolve to the MES's default-network address, and requests over it would arrive from outside the trusted CIDR and lose their trusted headers. So nginx proxies both `/api/` and the `/sim/` `auth_request` to `http://mes-edge:4700` (`$mes_upstream`, still resolved per request through Docker's DNS, as today), never to `mes`. The MES counts proxied requests, those carrying `X-Real-IP` and no others, by whether their source was trusted (`mes_http_proxy_requests_total{trusted}`), and the smoke asserts that requests through nginx arrive trusted and none untrusted.
- **Per (account, address):** five failures lock that pair for 15 minutes (today's per-account lock, keyed by address too).
- **Per account, from all addresses together:** a refusal, never a lock. Let n be the account's **failed judged attempts** within the last 15 minutes from all addresses; **a 429 is not a judged attempt and doesn't count toward n**. Once n ≥ 10, an attempt made less than `min(2^(n − 10) s, 30 s)` after the account's last failure is **refused with 429 and `Retry-After`** (the remaining wait in whole seconds, rounded up) without hashing. The decision is taken in ADR-0026's reserve-before-hash transaction under the user's row lock (`SELECT … FOR UPDATE`), so concurrent attempts serialize and at most one attempt per wait is judged, however many arrive at once (a delay before judging would let parallel guesses through). n falls as failures leave the window and resets on a success. `admin` keeps its existing doubling delay (capped at 5 minutes) and is never locked.
- **What it does and doesn't fix:** it **reduces** ADR-0026's accepted denial of service: an attacker on one address no longer locks the account for users on other addresses. Through Colima's port forwarding every host client appears as one address, so on a developer machine the browser and an attacker on the host still share a key; the global delay is then the only brake. S5 is tested from two containers on the Compose network (two addresses through nginx), and with a deterministic burst: n is driven to 15 or more from two addresses (a 30 s wait), the test waits for that wait to expire, then sends 20 concurrent attempts from a fresh third address (so no (account, address) lock applies); exactly one is judged and 19 are refused with 429, each `Retry-After` equal to the remaining wait rounded up.
- **ERP token:** compared in constant time (checked); rotated by restarting with a new value (runbook). One shared secret stays an accepted risk on loopback.

### Resilience suite (`pnpm test:resilience`)

- **Stacks:** each run is its own disposable Compose project with ephemeral host ports (P9-01), hardened (wave C), on `orders-01` in orders mode at 60× (one simulated hour is one minute of wall time), dispatched through the API as the `orders` reconcile pass does. **Every fault is driven by the test**, infrastructure faults through the control API and process faults through `docker compose`, at the scheduled simulated time read from the control API (polled every 250 ms); no timeline schedules a resilience fault. **Settled before each fault:** at each fault's scheduled time the test asserts the system has settled from the previous one: readiness back, the gateway's buffer empty, `mes_ingest_pending_messages` ≤ 100, and every machine's final-through past the previous fault's end. **If it hasn't, the run fails** and names the fault and the unsettled condition; the times below leave at least 60 simulated minutes (one wall minute) between a fault's end and the next. Times are Monday, Istanbul time; shift A is 06:00–14:00.
- **Run R1, no loss, infrastructure:** broker restart at 07:00; database restart at 08:30; ERP mock stopped 09:45–10:45 (one wall minute); WSH-01 silent 11:45–12:00 (fewer facts than its 64-entry ring, asserted from the washer's fact count in that window); run to 14:00, then drain. Spacing is measured from a fault's **end** (a restart's end is its service's readiness) to the next fault's start, at least 60 simulated minutes each time.
- **Run R2, no loss, MES:** MES stopped with SIGTERM at 07:00 and started at 08:00; killed with SIGKILL at 10:00 and started at 11:00; run to 14:00, then drain.
- **No-loss assertions (R1, R2):** after the drain, states, OEE (equipment, work center, order, line), alarms, shift reports, units, quantities, confirmations and the trace at 14:00 equal the live truth and are final; no duplicate fact stored (dedup counters); no `sequence-gap` incident; the ERP holds each message once.
- **Run R3, detected loss:** CNC-01's OPC UA server offline 07:00–07:30; the gateway killed (SIGKILL) at 10:00 and started again when the simulated time reaches 10:05; run to 14:00, then drain.
- **Detected-loss assertions (R3):** for each machine, the set of sequence numbers in its `sequence-gap` incidents equals **(numbers the simulator raised) − (numbers the MES stored)**, read from the live event log (`SIM_EVENT_LOG`) and from ingest. **The window is judged in simulated time**, never by converting wall clocks: the outage starts at the simulated time the test read from the control API when it took the fault action, and ends at the gateway's resync, taken from the gateway's own record of it (the `sequence-gap` incident it raises on reconnect, with the device's `Sequence` and the plant time of the first fact after the gap, or, after the gateway's restart, its first resync snapshot's `asOfSeq` fact). Every lost number's fact time lies within `[outage start − ε, resync]` with **ε = 2 simulated minutes** (2 s of wall time at 60×), covering facts in flight when the session dropped and the 250 ms polling of the control API. The test records the observed maximum lead (how far before the outage start the earliest lost fact lies), so ε can be tightened from evidence. The state resyncs from the anchors within 10 s of wall time of the session's return; nothing is duplicated; every machine is final once the gaps are written off; and the MES's answers equal the golden harness's answers on the facts the MES stored (recovery is deterministic, not corrupt).
- **Recovery checks (all runs):** readiness returns within 30 s of each restart; the web reconnects its WebSocket and the overview is current within 2 s (Playwright); the metrics show each outage (`mes_ingest_suspensions_total`, gateway buffer depth).

### Performance (`pnpm test:perf`, ADR-0040)

- **Tool, decided here:** a Node script (`e2e/src/perf.ts`), with Node's built-in `fetch` and `WebSocket` and the repo's MQTT.js, no new dependency, as `pnpm test:trace-perf`. k6 was considered: a new binary or image, MQTT only through an extension, and the plant itself is the main load.
- **Golden feed for T6 without crossing module rules:** as #204's trace-perf loader, a `mes-server` Vitest entry gated by `PERF_REPLAY_BROKER_URL` (`perf-replay.e2e.test.ts`, invoked with `pnpm --filter @shopfloor/mes-server`) publishes the golden feed from `golden-feed.test-support.ts` to the run's broker at the paced rate; `e2e/src/perf.ts` only measures and never imports `mes-server` code.
- **New measurements:** a histogram `mes_ingest_lag_seconds` (gateway `receivedAt` to the MES's commit, observed after the commit, labelled by message class), observed **only for live device deliveries stored for the first time**: retained messages, state and alarm anchors, snapshots, duplicates (dedup hits) are not observed, and are counted instead by `mes_ingest_lag_excluded_total{reason}` (`retained`, `anchor`, `snapshot`, `duplicate`). Ingest can't tell a delivery the gateway replays from its store-and-forward buffer from a live one, so there is no `replayed` reason; instead run P1 asserts that the gateway's `gateway_buffer_messages` stays 0 over the whole T1 window, so no replayed delivery can be in it. A gauge `mes_ingest_pending_messages` (messages received from the broker and not yet committed). Mosquitto's `$SYS` tree has no per-client queue figure, so the broker's queue is not a target; T1's lag covers it. CPU and memory from the containers' cgroups (`cpu.stat`, `memory.peak`) and `docker inspect`.
- **Runs and targets** (each target names its run; all on the hardened stack, `orders-01` in orders mode):
  - **Run P1, steady** (Monday shift A at 60×, no fault): **T1** ingest lag p95 ≤ 250 ms, p99 ≤ 1 s, max ≤ 5 s, measured from the MES's catch-up (the first moment after start with `mes_ingest_pending_messages` ≤ 100 and the gateway's buffer empty) to the end of shift A, with the excluded counts recorded beside it, and `mes_ingest_pending_messages` ≤ 100 at every simulated hour boundary; **T3** push latency: overview state ≤ 1 s p95; OEE dashboard, SPC page and terminal ≤ 2 s p95 (the existing budgets, with the latency judge of Phases 4–8); **T4** reads under load: 20 concurrent virtual users (10 desks polling overview, OEE and orders at their screens' rates, 5 terminals over WebSocket, 5 trace searches with backward traces): reads p95 ≤ 200 ms, backward traces p95 ≤ 100 ms, no 5xx, no WebSocket closed but by a session end; **T5** resources over the shift: MES CPU ≤ 0.5 core averaged, the MES's CFS throttling share (`nr_throttled / nr_periods` from `cpu.stat`) ≤ 5 %, every container's peak memory below 80 % of its limit, no OOM kill and `RestartCount` 0 for every container, the gateway's buffer empty at the end.
  - **Run P2, drain** (its own stack): the MES stopped at 07:00 for 5 minutes of wall time (five simulated hours) and started; **T2** the queued messages are stored at ≥ 800 messages/s (from `mes_ingest_messages_total`) and every machine is final again within 3 minutes of wall time of the start.
  - **Run P3, headroom** (its own stack, no simulator): `week-01`'s Monday golden feed published at three times the 60× rate; **T6** lag p95 ≤ 1 s, every machine final within 30 s of the last message, Monday's OEE equal to the truth.
- **Probe Q3** (first commit of P9-18): P1–P3 on `main` as a baseline. **A target the baseline misses gets its own fix issue** (P9-F1, …, opened from the probe's numbers, each one pull request), or is raised to the owner with the numbers; never quietly relaxed.
- **Entry condition for P9-16 and P9-18:** the Docker VM has 4 GiB and 4 CPUs (the owner's item since Phase 7), or the issue restates the targets for 2 GiB / 2 CPUs with the owner's approval before running. The results file records the VM's memory, CPUs and disk, the host's load average and the image digests.

### Local gate

- `pnpm gate` stays the merge gate and runs locally (GitHub Actions unavailable): verify, golden, e2e, smoke, reconcile. `pnpm test:resilience`, `pnpm test:perf` and `pnpm test:trace-perf` are commands of their own, run by the pull requests whose paths the rerun table names, and all three by the closing gate (P9-19).
- **One heavy suite at a time** (disk space and the Phase 8 flakes). P9-01 makes every heavy command take a host-wide lock: `gate`, `verify` (its Testcontainers suites), `test:e2e`, `test:reconcile`, `test:resilience`, `test:perf`, `test:trace-perf` and Playwright. The lock is a directory at a fixed absolute path, `~/.cache/shopfloor-twin/heavy.lock` (not `os.tmpdir()`, which is per session under the sandbox), holding the holder's PID, command and start time. A waiting command prints the holder and waits up to `HEAVY_LOCK_TIMEOUT_MS` (default 3 hours), then fails. The lock is stale **only** when `kill(pid, 0)` fails with `ESRCH` (an `EPERM` means the holder is alive). A holder's children inherit it through `SHOPFLOOR_HEAVY_LOCK` (the gate's `verify` doesn't wait on its own gate). Until P9-01 merges, the coordinator runs heavy suites one at a time by hand. `pnpm verify --concurrency=1` as today.
- **Ephemeral ports:** tests bind runtime ports (`@shopfloor/test-kit/ports`, #212, #216). P9-01 moves the smoke's Compose project to ephemeral host ports (published as `127.0.0.1::<port>`, read back with `docker compose port`), so a dev stack can stay up during the gate; the reconcile, resilience and perf projects do the same. No test may assume a fixed host port.
- **Disk:** the gate and every heavy command refuse to start below **25 GiB free on the host** (the repository's file system) or **15 GiB free in Docker's data root** (inside the VM), saying which. Every project removes its volumes and its `GATE_TAG` images at the end, also on failure, and the BuildKit cache is pruned to at most 10 GiB after each build (`docker builder prune --keep-storage`).
- **Limits:** P9-01 adds resource limits to the database and the broker (S8) before any measurement, measured by one full gate.
- **Process hygiene:** a harness stops what it started by PID or process group, never by name (no unscoped `pkill`).
- **Rerun table** (runbook "Merge gate") gains: `packages/oee-core` → `verify,golden,e2e,smoke,reconcile` (shapes `line-oee.json`); `config/scenarios/` → `verify,golden,e2e`; `config/mosquitto/`, nginx, the `pki` step and `compose.dev-ports.yml` → `verify,e2e,smoke,reconcile` and `pnpm test:resilience`; `e2e/src/resilience*` → `verify` and `pnpm test:resilience`; `e2e/src/perf*`, `apps/mes-server/src/perf-replay*`, `compose.observability.yml` → `verify` and `pnpm test:perf`.

## Exit criteria (plan section 11)

Row 9: "Resilience suite passes; performance at 60× meets the targets set in the phase plan; security review checklist complete", plus its deliverables. Every criterion is proven by local runs on the final commits; the CI jobs exist but don't run.

1. **Order and line OEE, golden:** the new `oee-core` reference cases pass (hand arithmetic to four decimals, the changeover and above-1 cases included); in `orders-01` and `quality-01` every order's OEE (A, P, Q, OEE, exact inputs) and first-pass yield, and in all four goldens the line OEE per hour, shift bucket and order, equal `line-oee.json`, in order, in bounded disorder and shuffled with 10 % duplicates, with the comparison counts asserted; `configSha256` and `analysisConfigSha256` unchanged for the four goldens; the equipment and work-center OEE reconciliations of Phases 5–8 pass unchanged.
2. **Order and line OEE, live:** in the `orders` reconcile pass, **exactly the 5 orders `orders-01` completes in shift A** (the golden run's set) are completed live, each with a final order OEE equal to the live truth's; shift A's line OEE is final and equal; the order detail and the dashboard show them (Playwright, values read from the page).
3. **Scenario playback:** a timeline with every action kind (lot block and release, both ASM-01 operators of a shift absent, tool breakage, failures, a drift, the infrastructure faults, speed changes and pauses) played live at speeds between 1× and 60× gives an event log byte-identical to the headless run of the same timeline; a live orders run's recorded dispatches replayed headless give its event log byte for byte; a live timeline with a `dispatch` entry is refused; `week-01`, `alarms-01`, `orders-01` and `quality-01` keep `events.sha256`, `summary.json` and `trace.json` byte-identical.
4. **Simulation console:** through `/console` as `admin`, each action reaches the simulator and its effect is seen (status, the plant event stream, or the MES: a blocked lot starves OP10 with cause `MATERIAL:`, a failure raises its alarm, both ASM-01 operators absent leave ASM-01 `Idle` `NO-OPERATOR` at the shift start); `/sim/` answers 401 anonymous, 403 to the other five roles and 403 to a cross-origin write, and 404 outside its allowlist; the control API answers 401 without its token.
5. **Resilience:** `pnpm test:resilience` passes twice in a row: runs R1 and R2 end with every listed answer equal to the live truth and final, no duplicate stored, no gap incident and each ERP message once; run R3 ends with each machine's gap set equal to (raised − stored), every lost fact inside its outage window judged in simulated time with ε = 2 simulated minutes (the observed maximum lead recorded), state resynced within 10 s, every machine final after the write-off, and the MES's answers equal to the golden harness's on the stored facts.
6. **Performance at 60×:** `pnpm test:perf` meets T1, T3, T4 and T5 in run P1, T2 in run P2 and T6 in run P3, on the hardened stack with the VM configuration of the entry condition, the figures (p50, p95, max, counts, the VM and the load average) recorded in the results file, the phase log and ADR-0040; `pnpm test:trace-perf` still meets Phase 8's 100 ms p95 through HTTPS.
7. **Security review:** `docs/security-review.md` has the threat model and every item S1–S10 with its evidence; an accepted risk appears only for the sub-findings the checklist names (the ERP mock's shared token, Modbus 5020, plaintext MQTT if TLS is cut, an unfixed dependency finding), each with its reason; the tests behind S1–S5 and S10 are part of `pnpm verify`, `pnpm test:e2e`, the smoke or the console Playwright run.
8. **Derived work:** the incremental SPC derivation equals the whole derivation in the property test and on the three SPC goldens; on `week-01` `mes_quality_spc_derive_seconds` p95 ≤ 10 ms for a new reading and ≤ 20 ms for a late one (on the synthetic month the same, and the default chart read p50 ≤ 10 ms, unless cut); with 200 open holds `mes_genealogy_round_seconds` p95 rises by ≤ 50 ms.
9. **No regression:** the golden reconciliations of Phases 4–8 and the `alarms`, `orders` and `quality` reconcile passes keep their checks; every OPC UA event of a scripted shift keeps its (machine, `seq`, type) under SignAndEncrypt; `pnpm verify` passes uncached three times in a row with random property seeds.
