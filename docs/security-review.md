# Security review

Started in P9-15 ([#242](https://github.com/kubilayture/shopfloor-twin/issues/242)), **completed at the Phase 9 close** (P9-19, [#246](https://github.com/kubilayture/shopfloor-twin/issues/246), 2026-10-20). It holds the threat model per component and the checklist S1–S10 of `docs/phases/phase-09-plan.md` ("Security review checklist"), each item with its evidence: a test, a command's output or a file.

**Accepted risks.** An accepted risk is used in a verdict **only for a sub-finding the checklist names** (round 1 finding 5): the ERP mock's shared token (S7), Modbus 5020 (S8), plaintext MQTT with TLS cut (S2), a dependency finding with no fix released (S9, unused). Each has its reason under its item. The ADRs record further risks of the same components (the dev CA's `localhost` scope, the login ceiling, the OPC UA connection cap and others); they are listed under "Residual risks outside the checklist", each with the item it touches and its reason. **No verdict below rests on them**: each item's checked behaviour holds as stated, and these risks describe what remains around it. They were accepted by the coordinator or the reviewers under the owner's standing instruction, and they await the owner's review (STATUS, owner items).

**Status at the close:** S1–S10 met, by evidence that ran on the closing gate's commit of record (`1cecd17`, `main` with every Phase 9 merge, P9-F3 and P9-F4 included; a first closing run on `86a1757` gave the same results; "Re-verified at the close" below). Every test name quoted in this document was checked to exist in the repository at that commit.

The scope is the hardened Compose stack (`docker compose up`, `pnpm stack:up`) on one developer machine (macOS, Colima), every published port on `127.0.0.1`. The plant network is loopback and the Compose bridge; the attacker considered is a local process or container, a web page in the owner's browser, or a holder of one leaked component secret. Out of scope: an attacker with root on the host or the Docker VM (who can read every volume), physical access, the owner's own browser profile.

Evidence references: test files and test names as they run in `pnpm verify` (V), `pnpm test:e2e` (E), the stack smoke `scripts/stack-smoke.sh` in the gate (S, quoted by its `ok:` line), the Playwright runs `pnpm test:console` and the reconciliation (P), and the security reviews of the pull requests (R).

### S1 – OPC UA

- **SignAndEncrypt only; an untrusted client certificate refused; anonymous refused; `LoadOrder` and `LoadProgram` refused for `opcua-reader` on a session opened with the trusted tools certificate.**
- Evidence (V, `apps/simulator/src/opcua/security.test.ts`): "offers SignAndEncrypt only, with user names and no anonymous token"; "refuses a client certificate it does not pin" (`BadSecurityChecksFailed`); "refuses a pinned certificate presented under another application's URI"; "refuses an anonymous session, also when the client sends the token anyway"; "refuses a wrong password and an unknown user"; "lets opcua-reader read but not call LoadOrder or LoadProgram (address space 1.3)" (`BadUserAccessDenied`, on a session opened with the tools certificate, so the permission is what refuses); "lets neither opcua-reader nor opcua-gateway write any variable"; "refuses a pinned certificate without clientAuth"; "refuses a legacy pin and a certificate minted with a pinned key once the pki step ran"; "passes the smoke's security check (the opcua-tools container's code)".
- Evidence (S): the `opcua-tools` container runs the same checks against the live stack: `ok: OPC UA servers offer SignAndEncrypt only (user names, no anonymous token); opcua-reader reads on all five`; `ok: opcua-reader (pinned tools certificate) refused LoadOrder and LoadProgram with BadUserAccessDenied`; `ok: a client certificate the server does not pin is refused (BadSecurityChecksFailed)`; `ok: anonymous sessions and a wrong password are refused by the server`; `ok: no variable is writable (118 variables on five machines, every Write refused)`; `ok: pki step exited 0 (…)`; `ok: each PKI volume mounted by its own component only (pki-ca by none, web-tls read-only)`.
- Evidence (R): PR #260 security review (approved after two rounds; writable variables, stale trust material, client certificate usage fixed; live check `rev239sec2`). The reconciliation runs under SignAndEncrypt (PR #260 gate: reconcile passed 1,660.3 s).
- Residual risks outside the checklist (listed below; the verdict doesn't rest on them): the CRL-after-pki limit (ADR-0038); OPC UA password guesses not serialised per user (ADR-0039 "Login throttling", also S5); the connection cap (ADR-0039 "Login throttling", S8).
- **The pki pin race (#265, P9-F2, found by the security review of PR #264, F4):** a `pki` rerun dropped unchanged OPC UA pins from a running server's trust index. Fixed in #267: unchanged pins are no longer rewritten and writes are staged outside the watched folders; the smoke checks the rerun and runs the pin-race check. Remaining limits: a renewal, and removing a hand-copied duplicate, both need a restart of the simulator and the gateway (runbook, "OPC UA certificates").
- Observation: one smoke-only run on this branch failed the `opcua-tools` S1 step once (`opcua-reader refused on lkt-01: BadSecurityChecksFailed`; the other machines passed); it did not recur in later runs (phase log, #242 entry).

### S2 – MQTT

- **Client-id takeover of `gw-01`, `gw-01-cmd`, `mes-server` refused; every ACL refusal kept (0x87); passwords random per stack.**
- Evidence (V/E, `apps/edge-gateway/src/broker-security.test.ts`): "refuses every user another user's client id: no session can be taken over" (42 pairs, no session dropped); "refuses every user with any other client id, or with a generated one"; "refuses a wrong password, another user's password and an unknown user"; "refuses an anonymous client, with or without a bound client id"; "refuses $CONTROL/dynamic-security/v1 to every user, createClient included"; "never delivers a will on a topic its user may not publish"; "refuses an empty client id (MQTT 5, broker-assigned) for every user"; ACL parity with the frozen Phase 8 broker: "publishes …", "subscribes …", "delivers …", "unsubscribes …" ("exactly as before").
- Evidence (S): `ok: anonymous MQTT client refused`; `ok: broker client ids bound to every user (no takeover, also by dev or healthcheck); wrong passwords refused`; `ok: broker ACLs (gateway may publish machine data only; dev is read-only)`. The gate generates every `*_PASSWORD` per run (`scripts/gate.ts`, `envFile`), and Compose refuses to start without each MQTT password (`ok: Compose refuses to start without a required secret …`).
- Evidence (R): PR #261 security review (approved; no takeover in 168 attempts over 7×6 user and id pairs, MQTT 3.1.1 and 5; F1–F8 fixed).
- **Accepted risk (named sub-finding "plaintext MQTT on loopback if TLS is cut"):** MQTT TLS was cut (Phase 9 cut line; ADR-0039 MQTT). The listener is plaintext on `127.0.0.1:1883` and the Compose bridge. Reason: the port is published on loopback only, and whoever can read loopback or the bridge on the host can also read the volumes that hold the passwords; the dev CA exists and could serve TLS later (ADR-0039).

### S5 – Login

- **A lock from one address doesn't lock the account from another (two containers); after n ≥ 15 and an expired wait, a burst of 20 from a fresh address has exactly one attempt judged and 19 refused with 429 and the remaining wait rounded up as `Retry-After`; a 429 doesn't count toward n; the account is never locked.** Design: ADR-0039 "Login throttling", ADR-0026 amendment (#242), revised after the security review of PR #264 (F1–F3, F7–F9).
- **What "never locked" means here** (F3): no counter locks the account as a whole, an address with a login within the last 15 minutes is exempt from the global delay, and an admin's password reset clears every failure. It does **not** mean a user can always get in at once: an attacker failing from several addresses keeps n at 15 or more and so holds the account to one judged attempt per 30 s for every address without a recent login (residual risk, below); and behind Colima's port forwarding every host client is one address.
- Evidence (V, `apps/mes-server/src/identity.test.ts`, Testcontainers PostgreSQL, the identity module's clock under the test's control):
  - "locks a user per (account, address): five failures from one address leave every other address open (#242, S5)";
  - "delays a user globally from 10 failures in 15 minutes: min(2^(n-10) s, 30 s) after the last, 429 without a hash, never counted, never a lock (#242, S5)" (waits 1, 2, 4, 8, 16, 30, 30 s; `Retry-After` 20 with 19.5 s left; no hash for a 429, counted by `hashesStarted()`);
  - "reads the time of a decision once it holds the row lock, never before (#242 gate: Retry-After 31)";
  - "applies the global delay to a password change too: 429 before the hash (#242)";
  - "keys a login by X-Real-IP only over the edge network: a lock from one client leaves another open; a spoofed header from elsewhere is ignored" (the forged header from outside `edge` is keyed by the sender's own address and counted in `mes_http_proxy_requests_total{trusted="false"}`);
  - "judges exactly one of a burst of 20 from a fresh third address once the wait of n >= 15 expires; 19 get 429 with the remaining wait rounded up, uncounted (deterministic burst)": n driven to 15 from three addresses through the edge (a and b five each, both pairs lock; c five more, each after its wait), the 30 s wait let expire, 20 concurrent logins from d: one 401 and nineteen 429, every `Retry-After` `30`, exactly one hash, n = 16, d's pair one failure; 10.5 s later `Retry-After` `20`; once the wait is over the right password from d logs in and n resets;
  - "keeps the victim in while an attacker address hammers its name and random names (#264 review, F2)" (the real buckets on a clock held still since #347: of 120 attempts from one address exactly its burst of 10 are judged and 110 get 429, its pair locked; the victim from its own address logs in at once);
  - "exempts an address that logged in within the window from the global delay; others wait (#264 review, F3)";
  - "answers an admin's delay with 429 and its Retry-After, not a plain 401 (#264 review, F3)";
  - "keeps authenticated reads answered while logins hold every connection of the login pool and a flood waits (#264 review, F1)" (the MES's pool shape, two connections for sessions and two for logins; since #347 both login connections are held for certain, waiting on row locks another transaction holds, while 300 logins from 300 addresses arrive: 20 reads all answer 200 with the pool still held, where a shared pool would make them wait; overflowing logins get 429. Until #347 it compared read times with max(25 ms, 3 × their quiet median), which a loaded machine could fail);
  - "keeps a login answered within 10 hash times (at least 1 s) while open-loop attacks from 4 and 8 addresses run, never more hashes in flight than slots, every refusal a 429 (#264 re-review, N1)" (real scrypt hashes, the real buckets, ceiling and hash slots; the victim's p95 at most max(1 s, 10 × the mean hash time measured meanwhile, `hashesDone()`), where it was a fixed 1 s until #347 (1080 ms on a loaded machine); never more hashes in flight than the hash slots; its refusals 429s);
  - "lets a home address with a recent login in on every try while 2 and 4 attacker addresses fill the ceiling (#264 round 3, R1)" (since #347 on a bucket clock the test moves: each round the attackers send their whole bursts, a fresh address is refused by the empty ceiling, and the home address logs in);
  - "remembers the logins of the window across a restart: the exemption holds against memory (#264 re-review, N2)";
  - "forgets a user's remembered delay when its roles change or it is disabled (#264 re-review, N3)";
  - "asks the login buckets only for an attempt the global delay let through";
  - the existing ADR-0026 tests still hold: "evaluates at most five of many parallel wrong attempts, then refuses the right password (H1)", "lets parallel attempts on an admin through one per delay (H1)" (now 429s inside the delay), "delays an admin instead of locking it …".
- Evidence (S, the smoke, real time, through nginx from four probe containers on the Compose network): `ok: login lock per (user, address): locked from probe a (…), b (…) logged in`; `ok: a spoofed X-Real-IP from outside the edge network is ignored (keyed by c, …; 5 untrusted)`; `ok: burst of 20 from a fresh address after n = 15: 1 judged, 19 x 429 (Retry-After 30 s, … ms), n = 16`. Figures of the gate below.
- **OPC UA logins** (#242 comment, from the review of PR #260): the simulator answers a refused password after 250 ms per attempt, not serialised per user; 30 concurrent guesses on one channel took 575 ms (about 50 per second per channel, about 10 channels). Not serialised: a per-user queue would let any holder of a pinned certificate delay the gateway's own login without end. Residual risk, recorded in ADR-0039 "Login throttling" (below; not part of the verdict).
- **Residual risk, not part of the verdict: a sustained multi-address attacker** (ADR-0039 "Login throttling", Consequences): see above. Reason: no counter that an attacker can drive may lock a user out; the exemption keeps a recently used browser working, the wait is at most 30 s per judged attempt, and an admin's reset clears it. On a developer machine the Colima limit (one host address) remains; between containers on the Compose network the addresses are distinct.
